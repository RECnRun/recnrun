# POC: cross-profile control over WebRTC

Branch `poc/cross-profile-webrtc-v2`, from `master` at `44c154d`. Not for merge as is.

**Question.** Can RECnRun control the tabs of several independent Chrome profiles from one dashboard and one PiP window, with no backend and no helper app?

**Answer.** Yes, for two profiles on the same machine, for listing tabs, bringing one to the front, and running a session's lifecycle (record, pause, stop): one WebRTC DataChannel between the two installations' offscreen documents, with no ICE server, paired by copying two codes by hand or through a shared folder. Recording page events and Run cannot be judged yet, because `master` has no capture or replay engine (tests E and F). The link does not survive a browser restart without pairing again, since there is no signaling channel to reconnect through.

## Design

```text
Profile A                                                Profile B
pairing.html ─┐                                          ┌─ pairing.html
dashboard ────┼─► background ◄─► offscreen.html ═══════► offscreen.html ◄─► background
PiP session ──┘   (decides, stores)  (RTCPeerConnection)  DataChannel     (executor: tabs, session)
```

- The **offscreen document** (`chrome.offscreen`, reason `WEB_RTC`) holds the one `RTCPeerConnection`, created with `iceServers: []`, so only host candidates exist: no STUN, no TURN, no server of any kind. It relays frames and states to the background and decides nothing.
- **Pairing** is manual, with ICE fully gathered before a code is shown (no trickle ICE). A code is one line, `RECNRUN-PAIR-1.<base64url JSON>`: `kind`, `pairingId`, `profileId`, `displayName`, `expiresAt` (five minutes), `sdp`. B shows who made A's offer and six digits derived from both DTLS certificate fingerprints; B's user accepts, which answers. A checks that the answer is for its own pending offer and shows the same six digits; A's user confirms.
- **Identity** is `{ profileId: crypto.randomUUID(), displayName }` in `storage.local`, never the extension id (which is the same in every profile that loads the same unpacked folder). Each profile keeps one DTLS certificate in the offscreen document's IndexedDB, so its fingerprint is stable across restarts.
- **Authorization.** The accepted peer is pinned as `{ profileId, displayName, fingerprint }`. When the channel opens, the background checks that the DTLS-proven remote fingerprint is the pinned one, or closes the link. Every frame is parsed with one closed schema (envelope `recnrun-peer`, protocol 1, ≤256 KB) and accepted only if `from` is the pinned peer and `to` is this profile. A malformed frame from the verified peer gets one `ERROR`; anything else gets nothing.
- **Protocol 1.** `HELLO`, `PING`/`PONG`, `GET_TABS`/`TABS_SNAPSHOT`, `TABS_CHANGED`, `ACTIVATE_TAB`, `SESSION_START`, `SESSION_SET_STATUS`, `SESSION_STOP`, `SESSION_STATUS`, `COMMAND_RESULT`, `ERROR`, `BYE` (an intended close). No message runs code, reads a page, or reads storage.
- **Executor and controller.** The profile that owns a tab runs every command on it, refuses tabs it does not list, a second session, and a session another profile controls, and reports its session on every change. The controller's dashboard lists the peer's tabs under "Chrome — Profile B (Connected)" with Show tab and Record; Record opens the existing PiP window, whose session page shows the local session or else the one it controls in B. The session is stored only in B. While a session runs in either profile, neither dashboard offers Record; each list says "Recording in <name>" or "Controlled from <name>".
- **RECnRun folder** (usability phases 2 and 3). A dashboard banner, shown while no folder is chosen or Chrome does not grant `readwrite` on it, opens a small popup window of the pairing page (`pairing.html#folder`): a top-level extension page, since the framed dashboard cannot show a picker (`NotAllowedError: Failed to execute 'showDirectoryPicker' on 'Window': Third party iframes are not allowed to show a file picker.`). Its one button, **Choose folder**, calls `showDirectoryPicker({ id: "recnrun-folder", mode: "readwrite", startIn: "documents" })`, where the user creates or chooses `Documents/RECnRun`. The handle is kept in IndexedDB (`recnrun-p2p` version 2, store `folders`), the folder gets `pairing/` and `recordings/` (reserved for M1), pairing starts, and the window closes. When Chrome asks again after a restart, the banner reads "Allow the RECnRun folder" and the window's **Allow folder** calls `requestPermission` on the kept handle. The dashboard shows "Waiting for <name> in the RECnRun folder…", or the one click pairing may need: **Pair with another profile**, or **Reconnect** after a Disconnect. While the profile pairs through the folder, the offscreen document polls `pairing/` once a second, keeps `pairing/<its profileId>/presence.json` fresh (one minute, renewed at half), and reports the others' presences and the signals addressed to it, so no page has to stay open. The background decides: the partner is the pinned peer, or else the profile that has waited longest; the lower profile id offers and the other answers. A signal counts only when its code's kind, pairing id, and maker match its file, and its SDP fingerprint is the one the partner's presence announced. Choosing the folder is the consent, so nobody compares digits. Each profile writes only into its own subfolder, atomically through `createWritable`. It keeps its presence once paired, and its service worker starts with the browser (a `runtime.onStartup` listener), so the pinned peer reconnects with no click after either side restarts. Disconnect and Forget stop waiting and remove its files. Manual pairing stays, under "Pair by hand instead".
- **Builds.** All of it exists only in `development` and `test` builds. The production build has no `offscreen` permission, no `offscreen.html` or `pairing.html`, and no `createDocument` or `RTCPeerConnection` in `background.js` (`apps/extension/scripts/manifest.checks.mjs`).

## How to try it

1. `vp install`, then `vp run extension#build:test` (builds `apps/extension/.output/chrome-mv3-test`). The `test` build also keeps every frame in the service worker as `globalThis.recnrunPeerFrames`, for inspection.
2. Start the website: `vp run dev:website` (http://localhost:5173).
3. Create two Chrome profiles (or start Chrome twice with `--user-data-dir=<dir>`; never use your own profile). In each, open `chrome://extensions`, turn on Developer mode, and **Load unpacked** `apps/extension/.output/chrome-mv3-test`.
4. In each profile, open http://localhost:5173/. **Manage pairing** in the dashboard opens the pairing page (or open `chrome-extension://<id>/pairing.html`); set a name for each profile and click **Save name**.
5. **Manual pairing.** Under **Pair by hand instead**, in A: **Create offer**, **Copy offer**. In B: paste it into "Code from the other profile", **Import code**, check the name and the six digits, **Accept and create answer**, **Copy answer**. In A: paste, **Import code**, check that both pages show the same six digits, **Confirm and connect**. Both pages show "Connected — <other name>".
6. **Folder pairing.** In A's dashboard: **Choose folder** in the "Choose the RECnRun folder" banner opens a small window. There, **Choose folder**, create `RECnRun` in Documents (or choose it), and **Allow** Chrome's prompt. The window closes and the dashboard says "Waiting for another profile in the RECnRun folder…". Do the same in B, choosing the same folder. Both dashboards list the other profile as "Connected" within seconds, with no other click. Quit either browser and open it again: the profiles reconnect with no click. After the first restart Chrome may ask for the folder again: the banner reads "Allow the RECnRun folder"; **Allow folder** in its window, then **Allow on every visit**.
7. **Tabs.** Open tabs in B: they appear in A's dashboard under "Chrome — B (Connected)", and leave when closed. **Show tab** brings B's tab to the front in B.
8. **Session.** **Record** on one of B's tabs in A's dashboard opens the PiP window in A; Pause, Continue, and Stop act on B's session. B's own dashboard shows the session too.
9. **Logs.** **Show diagnostics** on the pairing page lists the link's states and candidate types (never addresses or payloads). The service worker's console has `[RECnRun peer]` lines: message types and verdicts, never payloads.
10. **Failures and disconnects.** **Disconnect** closes the link on both sides and stops waiting in the folder, so nothing reconnects until **Reconnect** in the dashboard; **Forget the other profile** also removes the pinned peer. A Disconnect shows "Disconnected by <name>" in the other profile. Quitting one browser shows "Disconnected" or "Not reachable" in the other within about 7 s, and its tabs stay listed as last seen, read only, under "Not connected. These tabs are as last seen." After a restart, profiles that chose the folder reconnect on their own; profiles paired only by hand pair again (the digits are the same, and A's page notes "This is the profile already paired."). A session in B keeps running while the link is down; A closes its PiP window, shows "Not connected. Last seen recording.", and offers no Stop until the link is back.

## Architectural assessment

- **Is WebRTC adequate?** For two profiles on one machine, yes: host candidates connect in under half a second with no server, DTLS gives an authenticated, encrypted channel, and the certificate fingerprint is a usable identity. Without STUN or TURN, two machines connect only on the same reachable network, and not across NATs; that is the price of "no server".
- **Is the offscreen document enough?** Yes. It is the only place an MV3 extension can hold an `RTCPeerConnection`; with reason `WEB_RTC` it stayed alive for every test, and the service worker wakes for its messages. The background stays the only decision maker; the offscreen document only relays.
- **The PiP window with a remote tab.** It works unchanged: the session page reads a store, and the remote store's writes are commands to B. Chrome shows one Document PiP window at a time across the profiles of one browser (H5, measured by hand): opening one profile's PiP closes the other's, though the other's session keeps running. Hence one session across the pair.
- **Does the folder simplify pairing?** Since phase 2, yes: once each profile chose the folder (a banner, the picker, Chrome's prompt), nothing else is clicked, because choosing the folder is the consent. The price is trusting whoever can write to the folder (the plan's recorded risk), a poll once a second while a profile waits, and files in a user's folder.
- **Complexity added.** Four folders (`p2p`, `offscreen`, `pairing`, `peers`), seven new storage keys (`local:profileIdentity`, `local:authorizedPeer`, and `session:` `peerLink`, `pendingOffer`, `remoteRecording`, `remoteController`, `peerTabs`), a second message family with its own versioning, one permission, and two pages, about 2,400 added lines of extension source, plus tests. The dashboard and session pages change little, because the remote side reuses the `TabSource` and `RecordingStore` ports.
- **Can it integrate cleanly?** Yes: dependency-cruiser keeps the POC out of the content script, the views, and the tab model; the entrypoints inject it. It hides behind one mode check, and the production build provably leaves it out.
- **Before production.**
  - Reconnection for profiles paired only by hand, which needs some rendezvous: the folder, or a server, which the brief rules out.
  - The pairing code and the signal files carry host IP addresses: in the Docker runs, Chromium gave the offscreen document plain host candidates (`172.17.0.2`), and on macOS Chromium IPv4 and IPv6 ULA host addresses, not mDNS `.local` names. Treat a code as private, or strip addresses and resolve them another way.
  - More than one peer, and a controller shown which profile a PiP session belongs to.
  - Event capture and Run over the link (tests E and F), with flow control for large event streams (`bufferedAmount`).
  - A Chrome Web Store review of the `offscreen` permission; its justification is user facing.
  - Folder permission loss: after the first restart Chrome asked again for the folder (H1), so the banner returned once; its window's **Allow folder** asks Chrome, and its "Allow on every visit" lasted across the next restart. Revoking the permission was not exercised.
  - If the offscreen document cannot load or create its certificate, the rejection stays unhandled until the first command; it should fail the link visibly at start.
