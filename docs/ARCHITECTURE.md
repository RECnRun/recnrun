# Architecture

[PRODUCT_BRIEF.md](PRODUCT_BRIEF.md) describes what the product does. This document fixes how the code is split and which way dependencies point. `.dependency-cruiser.cjs` enforces every boundary below (`vp run deps`); change both together.

```text
apps/website ──► @recnrun/bridge ──► @recnrun/domain ──► valibot
apps/extension ─┘                    ▲
        └────────────────────────────┘

apps/website, apps/extension ──► @recnrun/brand (CSS and fonts)

apps/fixture: imports nothing from the workspace; only tests/ may import it
apps/isolator (POC) ──► isolation-core, worker-bootstrap, @recnrun/brand, valibot; nothing imports it
worker-bootstrap (POC) ──► isolation-core ──► valibot
```

## Packages

| Package                     | Holds                                                                                                                                                                                           | May import                                |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `packages/domain`           | Valibot schemas and inferred types for every concept; `Snapshot`, the versioned document the extension stores                                                                                   | `valibot` only                            |
| `packages/bridge`           | The website ↔ content script protocol, its client, host, and `window` transport                                                                                                                 | `@recnrun/domain`, `valibot`              |
| `packages/isolation-core`   | Browser-agnostic logic of the namespaced-sessions POC (see [PLAN.md](poc/namespace-sessions/PLAN.md) section 5), and `vendor/splitsession/`, MIT-licensed SplitSession modules pinned by commit | `valibot` only (`src/`)                   |
| `packages/worker-bootstrap` | `isolation-core` built into `BOOTSTRAP_SOURCE`, one classic script the isolator evaluates in a worker before its first statement, with its SHA-256 and version                                  | `isolation-core`, Node built-ins (`src/`) |
| `packages/brand`            | Brand assets both apps style themselves with: Mona Sans and the stylesheet that loads it                                                                                                        | nothing                                   |
| `apps/website`              | The Preact SPA                                                                                                                                                                                  | all packages; never the extension         |
| `apps/extension`            | The WXT extension                                                                                                                                                                               | all packages; never the website           |
| `apps/fixture`              | Development-only application under test for the namespaced-sessions POC; see its [README](../apps/fixture/README.md)                                                                            | Node built-ins only                       |
| `apps/isolator`             | The namespaced-sessions POC extension (WXT, MV3); see [Isolator](#isolator-poc)                                                                                                                 | POC packages, brand, and `valibot`        |

- Packages never import apps. Apps never import each other: they meet only at the bridge protocol.
- Packages export their TypeScript sources (`exports` → `./src/index.ts`); apps bundle them. A package `build` only type checks, except `@recnrun/worker-bootstrap`'s (below).
- `@recnrun/brand` holds no code: it exports `mona-sans.css`, which each app's entry imports, so the font and its license exist once instead of once per app. It imports nothing (`brand-is-leaf`).
- `@recnrun/isolation-core` exists so the isolation logic (jar, DNR rules, namespace contract, and P1's bootstrap: `installMarker`, which tags a global's requests, databases, and caches with a marker, and `installOriginalFilter`, which keeps the original session from listing, reading, clearing, or creating any name with the reserved `__rec:` prefix in IndexedDB, Cache Storage, and `localStorage`) stays free of extension APIs and testable on Node; this is why it is a package and not a folder of the extension (`isolation-core-pure`). `vendor/splitsession/` holds unmodified upstream files with `LICENSE`, `NOTICE`, and `vendor-manifest.json` (SHA-256 per file, checked by `tests/vendor.test.ts`); `src/` does not import `vendor/`, and Knip (as entries, until P2 imports them) and jscpd still scan the vendored files. Format and lint ignore `vendor/` because the files stay byte-identical, and `not-to-unresolvable` skips it because the files import siblings that are not vendored.
- `@recnrun/worker-bootstrap` has a real build because a debugger can only evaluate a string in a worker: `vp build` bundles `src/entrypoints/bootstrap.ts` (isolation-core's `installBootstrap`, which dispatches to either installer) as an IIFE, and a plugin in `vite.config.ts` wraps it into `BOOTSTRAP_SOURCE`, `(function (options) { … })`, and writes `dist/bootstrap.js` with the source, its SHA-256, and the package version. `src/index.ts` re-exports them with `withMarker(marker)` and `withOriginal()`, the expressions to evaluate in a namespaced session and in the original session. `dist/` is not committed: the root `prepare` and `clean` scripts and `Dockerfile.tests` build it, and the isolator's builds build it first. `src/` may import only its own files, `isolation-core`, and Node built-ins (`worker-bootstrap-only-core`); `artifact.ts` uses `node:crypto` at build time and is not part of the bundle.
- `@recnrun/domain/testing` exports fixtures for tests; no `src/` file imports a test file.
- `apps/fixture` is the application the namespaced-sessions POC tests against ([PLAN.md §5](poc/namespace-sessions/PLAN.md#5-target-layout)). It must not share code with RECnRun, so it imports no workspace package (`fixture-isolated`), and only `tests/` may import it to start it (`only-tests-start-the-fixture`). Its served files and server modules are frozen by hash (`apps/fixture/freeze.json`). The browser layer runs it as a separate process through Playwright's `webServer` in `playwright.browser.config.ts`, on its default ports.
- Every module is reachable from an entrypoint, a test, or a config (`no-orphans`), and there are no import cycles (`no-circular`).

## Website

```text
src/main.tsx ─► src/app ─► src/features/<name> ─► src/services ─► @recnrun/bridge
                   │              │
                   └──────────────┴──► src/ui
```

- `src/ui`: presentational components and pure helpers. It imports nothing from `features`, `services`, or `app`.
- `src/services/extension.ts`: the extension gateway, `createExtensionGateway()`, and the only module that imports `@recnrun/bridge`.
- `src/features/<name>`: state and views for one capability (`extension-status`, `explorer`). Features never import each other.
- `src/app`: composition. It picks the banner, the empty state, or the explorer from the extension state.
- `src/main.tsx`: mounts `App` with the real gateway. Nothing imports it.

Components take the gateway or data as props, so component tests use a fake gateway.

## Extension

| Folder            | Runs in                | Role                                                                                       |
| ----------------- | ---------------------- | ------------------------------------------------------------------------------------------ |
| `src/entrypoints` | (WXT)                  | Thin wiring: each file calls one `start*` function. Nothing imports an entrypoint.         |
| `src/content`     | The RECnRun website    | Bridge host. Relays known requests to the background and returns its reply.                |
| `src/background`  | The service worker     | Validates requests and senders, answers them from storage.                                 |
| `src/storage`     | The service worker     | Repositories over WXT `storage`; validates what it reads with the domain schemas.          |
| `src/popup`       | The toolbar popup      | Preact UI. Reads through a function it is given, never through content or background code. |

| `src/messaging`   | Content and background | The internal content ↔ background message schema.                                          |

`content` never imports `storage`, and `popup` never imports `content` or `background`.

## Isolator (POC)

`apps/isolator` is the runtime of the namespaced-sessions proof of concept on branch `poc-namespace-sessions` ([PLAN.md §5](poc/namespace-sessions/PLAN.md#5-target-layout)). It is separate from the recording product: it may import only `packages/isolation-core`, `packages/worker-bootstrap`, and `@recnrun/brand` (`isolator-only-poc-packages`) among the workspace packages, plus `valibot`, which Route B and the stop mechanisms use to validate their requests and the CDP events they read, never `apps/extension` or `apps/website` (`isolator-not-to-recording-apps`), and nothing imports it (`nothing-to-isolator`): tests load its build output, `apps/isolator/.output/chrome-mv3-test` (`vp run @recnrun/isolator#build:test`, which builds `@recnrun/worker-bootstrap` first, run by `test:browser:local` and `test:experiments:local`). Its entrypoints are thin like the extension's; `src/background` records a `chrome.storage.session` marker on install and startup and answers its own `getSelf` message with `chrome.management.getSelf()`. `src/background/probes` holds E1's probes (the `recnrunProbes` global). `src/background/route-a` is Route A (P1.1, the `recnrunRouteA` global): `arm({ tabId })` attaches to the tab and sets `Target.setAutoAttach` with `waitForDebuggerOnStart` and `flatten`; on each `Target.attachedToTarget` it sends `Runtime.evaluate` of `withMarker(marker)` to a worker, sets the same auto-attach on the new session so nested workers pause too, and then sends `Runtime.runIfWaitingForDebugger` without waiting for the bootstrap's reply, which a paused service worker gives only once released. Its journal records every target, the time from the event to the bootstrap's result, Chrome's exact errors, and the worker targets on the tab's origin it never attached. R11 holds although `debugger` needs no host permission: `arm`, `attachTarget`, and `closeTarget` refuse a tab or target outside the loopback before they attach, and a child auto-attached from outside it (once the armed tab navigated away) gets only `Runtime.runIfWaitingForDebugger` and the journal error `refused: not on the loopback`. `clearOrigin({ tabId })` sends `Storage.clearDataForOrigin` for the tab's origin, refused outside the loopback, so experiments reset registrations and storage through the isolator rather than the harness. P1.2 (E3) adds three calls. `arm({ tabId, pauseBeforeScript: true })` sends `Debugger.enable` and `Debugger.setInstrumentationBreakpoint` (`beforeScriptExecution`) on a waiting worker's session before the release, and at the first `instrumentation` pause records `typeof caches`, evaluates the bootstrap, removes the breakpoint, and resumes. `watch({ origin, marker })` polls `chrome.debugger.getTargets()` (every 10 ms unless `intervalMs` says otherwise) and attaches by id each new worker target of a loopback origin, skipping those listed when it started, then evaluates the bootstrap; `unwatch()` detaches them and returns what it saw. `closeTarget({ targetId })` attaches by id and sends `Target.closeTarget` on the target's own session, so experiments stop a worker without the harness, then sends `Target.detachFromTarget` for each armed tab's auto-attached child session on that target: Chrome keeps that session across the stop and holds the restarted worker for it without reporting it (E8), so the restart comes back as a new `Target.attachedToTarget`, waiting, that Route A bootstraps and releases. The journal keeps every `Target.*` event and `onDetach` it received (`events`). `src/background/route-b` is Route B (P1.4, the `recnrunRouteB` global): `arm({ tabId, marker })` attaches to the tab, sends `Fetch.enable` with the service-worker script pattern at the response stage, and sets the same auto-attach; on a worker's `Target.attachedToTarget` it also sends `Fetch.enable` on the worker's session, where Chrome pauses a service worker's main script and its imports, before `Runtime.runIfWaitingForDebugger`. A paused script response is read with `Fetch.getResponseBody` and fulfilled with the original status and headers, less `Content-Length` and `Content-Encoding`, and a body that starts with `withMarker(marker)` (a classic script) or with a static `import` of the web-accessible `route-b/bootstrap.js?marker=<marker>` (a module script); every other request continues. The journal records `declared: "transformed"`, the sizes, and the wait of every fulfilled script. `update({ tabId })` runs `registration.update()` in the tab and `stopWorker({ targetId })` closes a worker target. The `build:publicAssets` hook in `wxt.config.ts` writes `route-b/bootstrap.js` from `@recnrun/worker-bootstrap`'s `BOOTSTRAP_SOURCE`; it reads the marker from its own URL. `src/background/route-c` is Route C (P1.6, the `recnrunRouteC` global): `install({ marker, matches?, workers? })` registers, with `chrome.scripting.registerContentScripts`, a MAIN-world script at `document_start` on every frame with `matchOriginAsFallback`, whose files are a slot (`public/ns/slot-<k>.js`, which sets `globalThis.__recnrunMarker`), an optional worker strategy file, and `route-c.js` (`src/entrypoints/route-c.ts` over `src/content/route-c`), which installs the marker with `installBootstrap` and wraps `Worker` and `SharedWorker`; `setMarker({ marker })` moves the registration to the next slot and returns that slot's marker, and `setOriginal()` points it at `public/ns/original.js` (which sets `globalThis.__recnrunOriginal`), so later loads and their workers get the original session's filter instead (P1.7). The wrapped constructors throw a `SecurityError` by default, since a `blob:` or `data:` wrapper changes the worker's `self.location`; E7 measures those wrappers as opt-in strategies. `src/background/original` is P1.7's probe (the `recnrunOriginal` global): `seed({ tabId, key, value })` sets a `localStorage` item from the ISOLATED world, and `probe({ tabId, step, name? })` runs, with `chrome.scripting.executeScript` in the page's MAIN world, the enumerations, reserved-name calls, and clearing a page could make, since the fixture app makes none. `src/background/stop` holds E4's stop mechanisms (P1.3, the `recnrunStop` global), which check each request with a `valibot` schema (the only npm import, as in the other apps) and refuse a target, tab, or origin outside the loopback before any command: `closeTarget`, `terminateExecution`, `pauseHold`/`release` (`Debugger.pause` held on a forced statement), `blockScope`/`unblock` (a `declarativeNetRequest` session rule that blocks the origin's `/sw-*.js` scripts, then eviction of the worker's window clients through `clients.matchAll()` and `client.navigate()` evaluated in the worker, and `chrome.tabs.remove` for the tabs left), `unregister` and `client` (fixed expressions evaluated on a tab session: registration status, a `postMessage` with a bounded reply, `registration.update()`, a Background Sync tag), and `watch` (records `Inspector.targetCrashed` and `Inspector.targetReloadedAfterCrash` on the sessions the isolator holds and, with a marker, bootstraps and releases a worker that restarts under one). Each returns a journal of every `chrome.*` call with its result or Chrome's exact error and `performance.now()` timestamps. `src/background/lab` is E8's strict lab channel, the isolator's only input when no CDP client exists: when a managed policy sets `3rdparty.extensions.<id>.lab` (Chrome passes it to `chrome.storage.managed` only through the manifest's `storage.managed_schema`, `public/lab-schema.json`; `lab/schema.ts` validates it), the background arms each tab that loads the configured origin on Route A or B, applies the `selection`, `stop` (Route A's `closeTarget` on the origin's workers), and `clear` (`clearOrigin`) commands once per id, reads each armed page's `#report` and IndexedDB names in the ISOLATED world and its Cache Storage names on the tab session, and posts a `loaded` beacon and a journal to the value's `journalUrl` on `lab.localhost`. Without that policy value it does nothing. Permissions are `storage`, `management`, and `debugger` (P0.4), `scripting` with loopback host permissions for Route C (P1.6), and `declarativeNetRequest` with host permissions for the fixture apps `http://app.localhost:4600/*` and `http://app.localhost:4603/*` (P1.3), so `chrome.tabs.query` sees their tabs; `route-c.js` and `ns/*.js` are web-accessible to the app origins, so a wrapped worker can import them. `vp run deps` cruises the isolator's modules, not `public/`, whose files Chrome loads by URL. R11 keeps the whole runtime in the extension: `apps/isolator/tests/egress.test.ts` runs the background with `fetch`, `WebSocket`, `EventSource`, and `XMLHttpRequest` shims that fail on any host other than the loopback (`127.0.0.1`, `localhost`, `*.localhost`, `[::1]`) or `chrome-extension://`, and checks that `wxt.config.ts` and, when it is built, the test manifest have no `update_url`, `externally_connectable`, or `nativeMessaging`. `vp run dev:isolator` builds it in watch mode; without `web-ext` WXT opens no browser, so load it by hand (MANUAL_VALIDATION.md M-P0.a).

## Bridge protocol v1

The website and the content script share a window, so they talk through `window.postMessage`. Every message is an envelope `{ channel: "recnrun", protocol: 1, kind, ... }`:

| Kind       | Sender         | Fields                                              |
| ---------- | -------------- | --------------------------------------------------- |
| `announce` | content script | `extensionVersion`; sent once on start              |
| `request`  | website        | `id`, `type`                                        |
| `response` | content script | `id`, then `ok: true, result` or `ok: false, error` |

Request types and their result schemas live in `RESULT_SCHEMAS` (`packages/bridge/src/protocol.ts`):

| Type          | Result                 |
| ------------- | ---------------------- |
| `ping`        | `{ extensionVersion }` |
| `getSnapshot` | `Snapshot`             |

- **Detection.** `client.detect()` resolves `installed` on the first `announce` or `ping` reply, and `missing` after the timeout (1.5 s by default). Either signal is enough, so the order in which the page and the content script load does not matter.
- **Validation.** The host answers only valid requests of a known type. The client validates every result against its schema and rejects with `BridgeError` on a timeout, an error reply, or a malformed result.
- **Versioning.** `protocol` changes only for an incompatible envelope or message change; adding a request type does not change it.

Inside the extension, the content script forwards `{ type }` with `browser.runtime.sendMessage`; the background replies `{ ok: true, result }` or `{ ok: false, error }`.

## Security model

The extension holds the user's data; the website only displays it.

- **Where the content script runs.** Production builds match only `https://recnrun.com/*`, where the website lives. The project also owns recnrun.app, recnrun.io, and recn.run; they only redirect to recnrun.com at the Cloudflare edge and never serve a page, so the extension does not match them. `development` and `test` builds add `http://localhost/*` and `http://127.0.0.1/*` (any port) for the dev server and end-to-end tests. `vp run test:extension-manifest` fails the build if a production manifest matches anything else.
- **Permissions.** Only `storage`: no host permissions, no `externally_connectable`, no access to other sites. The same check enforces it.
- **Who may ask.** The `window` transport accepts only messages whose `source` is the page's own window and whose `origin` is the page's own origin, and replies only to that origin. Pages on other origins, other windows, and frames get no answer (`tests/e2e/origin-guard.spec.ts`).
- **What they can get.** The bridge is read-only. The content script cannot read storage itself; it can only relay known request types to the background, which checks that the sender is its own extension.
- **What the website trusts.** Stored data is validated when the extension reads it and again when the website receives it. Data is rendered as text.
- **Script injection on recnrun.com** would let an attacker read the user's data through the bridge, so the website ships a strict CSP (`default-src 'self'`, no inline scripts or styles; `apps/website/build/content-security-policy.ts`). GitHub Pages sends no headers, so the CSP is a `<meta>` tag added to production builds only. Third-party scripts are not allowed on the website.
- Adding a write request widens this model; the `adding-a-bridge-message` skill requires documenting it here first.

### Recording (not built)

Recording in the user's own applications needs more than `storage`. Whatever M1 settles on follows these limits:

- **Per-origin access, granted at run time** (optional host permissions and `permissions.request`), or `activeTab` for a one-off page. No install-time host permissions, and never `<all_urls>`.
- Recording scripts in the user's applications never answer the bridge; they only report events to the background.
- `apps/extension/scripts/manifest.checks.mjs` changes in the same commit, so the production manifest allows exactly the new permissions.

Findings from the bootstrap spike, kept here because they explain the configuration:

- **WXT on Vite+.** The workspace overrides `vite` with `@voidzero-dev/vite-plus-core`; WXT 0.21 builds on it unchanged. `import.meta.env.MODE` is available in `defineContentScript` options, which is how `origins.ts` varies matches per build mode.
- **WXT tests.** `vitest.config.ts` passes its own `root` to `WxtVitest`; without it, Vitest projects started from the repo root cannot resolve the `@/` alias. `.wxt/` is generated by `wxt prepare` (the root `prepare` script, and explicitly in `Dockerfile.tests`, because pnpm skips `prepare` when `node_modules` is current).
- **dependency-cruiser and TypeScript 7.** dependency-cruiser 18 supports TypeScript below 7, so it parses with SWC (`parser: "swc"`, `@swc/core`); type-only imports are still detected. Its tsconfig-paths plugin resolves `paths` from the working directory, so each app has a `tsconfig.deps.json` repeating its `@/` alias from the repo root, and `vp run deps` cruises each app with its own. npm packages are not followed but stay in the graph as leaves, so rules can name them (`not-to-dev-dep`, `extension-content-not-to-storage`); the `exclude` names only the workspaces' build output, since a pattern on `dist/` would also drop every package's own `dist/`.
- **WXT dev browser.** WXT 0.21 opens a browser only when its optional peer `web-ext` is installed; without it, `wxt` builds and asks you to load the extension by hand. `apps/extension` depends on `web-ext` for that reason. `wxt.config.ts` opens `http://localhost:5173/` (the website's fixed dev port) in a persistent profile under `.wxt/chrome-data`, which `vp run clean` deletes.
- **Knip and WXT.** Knip's WXT plugin expects `entrypoints/` at the package root; `knip.jsonc` lists `src/entrypoints` explicitly.
- **Extensions need a headed Chromium.** Playwright and Vitest Browser Mode run headed; Docker provides the display, so no window opens on the host.
- **Google Chrome in Docker.** `Dockerfile.tests` installs `google-chrome-stable` from Google's apt repository in its `runtime` stage, with xdotool and scrot for `tests/browser/fixtures/x-display.ts` (Chrome's infobar and DevTools windows), and writes `/opt/recnrun/versions.json`, which `scripts/test-container.mjs` copies with the image id into each run's `.artifacts/docker/<run-id>/versions.json`. `tests/container/runner.checks.mjs` builds that stage alone (cached) and checks `google-chrome --version` reports 144 or later. Chrome runs as root in the container, where its sandbox cannot start, so `tests/browser/fixtures/chrome.ts` adds `--no-sandbox` there and only there.
- **Experiment evidence.** Experiments write `.artifacts/evidence/<RECNRUN_RUN_ID>/` (`verdicts.json`, `capabilities.json`); `scripts/test-container.mjs` passes its run id as `RECNRUN_RUN_ID` and exports the container's `.artifacts/evidence` to `.artifacts/docker/<run-id>/evidence/`. For `verify` it also sets `RECNRUN_EXPERIMENT_SAMPLES=smoke`, so experiments take one sample per hypothesis (`tests/experiments/samples.ts`) and stamp their verdicts `mode: "smoke"`; evidence for the reports comes from `vp run test:experiments` at full counts.
- **Stress runs.** [POC PLAN.md decision 8](poc/namespace-sessions/PLAN.md#2-decisions) keeps stress out of `verify`. `vp run test:stress` builds the isolator and runs `scripts/test-stress.mjs` in the same Docker runner; it lists the tests tagged `@order-critical` in the browser and experiment configs (none is an error), runs them serially for 100 iterations (`RECNRUN_STRESS_ITERATIONS`, which the Docker runner forwards, or `--iterations N`), and gives each iteration its own `RECNRUN_RUN_ID` (`<run>/stress/<iteration>-<condition>`) and a `RECNRUN_STRESS_CONDITION` from a fixed cycle (`baseline`, `net-delay`, `cpu-load`, `cold`, `warm`, `switch-early`, `switch-late`). During `cpu-load` it runs one busy worker thread per core next to Chrome. It then aggregates every iteration's `verdicts.json` into `.artifacts/evidence/<run>/stress.json` and exits 0 only when every iteration ran and no hypothesis recorded a `fail`. `scripts/test-stress.checks.mjs` proves this with a throwaway tagged spec that only writes verdicts.
- **Observer and evidence set.** Browser tests inspect Chrome through `tests/browser/observer/` ([POC PLAN.md decisions 5 and 7](poc/namespace-sessions/PLAN.md#2-decisions)): a CDP observer that only enables event domains and reads storage. Each test that uses it writes `.artifacts/evidence/<RECNRUN_RUN_ID>/<spec>/<test>/`: `trace.jsonl` (network, target, navigation, and console events, one per line), `ledger.json` (the fixture's `GET /__ledger`), `storage.json` (IndexedDB databases, caches, usage, and Web Storage keys per origin, and every cookie), and `counters.json` (bytes copied, rules installed, switch timings, Chrome version, run id, labels). `redact.ts` replaces cookie values, `Authorization`/`Cookie`/`Set-Cookie` header values, `idp_sid`/`api_sid` values, and strings shaped like the fixture's session ids with `sha256:<hex>` before anything is kept; `tests/redaction.test.ts` covers it, and `tests/browser/fixture.spec.ts` checks that the browser's raw session cookies never appear in its evidence while their hashes do. Chrome answers IndexedDB, Cache Storage, and Web Storage reads only for origins that have a frame in the observed page; for other origins `storage.json` records Chrome's error.
- **Observer allowlist.** `tests/observer-allowlist.test.ts` parses every file under `tests/browser` and `tests/experiments` (Vite+'s `parseAst`, through `tests/harness-scan.ts`) and fails on a CDP command at a `send` call site outside its allowlist, on the commands decision 5 forbids, on raw `Runtime.evaluate` outside the extension loaders, on `Browser.setPermission` unless its params literal says `setting: "denied"`, on Playwright calls that send capability-providing commands or inject into the page (`route`, `addInitScript`, `addScriptTag`, `addStyleTag`, `setContent`, `evaluate`, and others), and on launch flags outside decision 5; `--load-extension` is accepted only in the diagnostic `loadInChromium` loader, which must hand `launchChrome` Playwright's Chromium. `tests/e2e` is the recording product's suite on Playwright's Chromium and is not scanned.
- **Extensions in Google Chrome.** Chrome 137 removed `--load-extension` from branded builds. The browser layer loads `apps/isolator` with CDP `Extensions.loadUnpacked` (`tests/browser/fixtures/extension.ts`); the methods and their measured outcomes are in [E0.md](poc/namespace-sessions/experiments/E0.md).
