# Architecture

[PRODUCT_BRIEF.md](PRODUCT_BRIEF.md) describes what the product does. This document fixes how the code is split and which way dependencies point. `.dependency-cruiser.cjs` enforces every boundary below (`vp run deps`); change both together.

```text
apps/website ──► @recnrun/bridge ──► valibot
     │            ▲                     ▲
     │      apps/extension ──► @recnrun/domain
     │            │
     └────────────┴──► @recnrun/brand (CSS and fonts)
```

## Packages

| Package           | Holds                                                                                                                                                                                                                                                                          | May import                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| `packages/domain` | Valibot schemas and inferred types for every concept; `Snapshot`, the versioned document the extension stores; `RecordingSession`, the recording in progress, and its pure helpers (`elapsedSeconds`, `toggled`, `formatElapsed`); `errorMessage`, the text for a caught value | `valibot` only                   |
| `packages/bridge` | The website ↔ content script protocol, its client, host, and `window` transport                                                                                                                                                                                                | `valibot` only                   |
| `packages/brand`  | Mona Sans, and `base.css`: the palette, semantic tokens, and base layout both apps import first                                                                                                                                                                                | nothing                          |
| `apps/website`    | The Preact SPA                                                                                                                                                                                                                                                                 | bridge, brand; never extension   |
| `apps/extension`  | The WXT extension                                                                                                                                                                                                                                                              | every package; never the website |

- Packages never import apps. Apps never import each other: they meet only at the bridge protocol.
- Packages export their TypeScript sources (`exports` → `./src/index.ts`); apps bundle them. A package `build` only type checks.
- `@recnrun/brand` holds no code: it exports `base.css` (tokens and base layout) and `mona-sans.css`, which each app's entry imports before its own stylesheet, so the palette, the font, and its license exist once instead of once per app. It imports nothing (`brand-is-leaf`).
- `@recnrun/domain/testing` exports fixtures for tests; no `src/` file imports a test file. The root workspace lists `@recnrun/domain` as a devDependency so `tests/e2e`, which belongs to no workspace, imports it by name; lint rejects relative paths into `packages/*` or `apps/*` sources from `tests/**`.
- Every module is reachable from an entrypoint, a test, or a config (`no-orphans`), and there are no import cycles (`no-circular`).

## Website

```text
src/main.tsx ─► src/app ─► src/features/<name> ─► src/services ─► @recnrun/bridge
                   │              │
                   └──────────────┴──► src/ui
```

- `src/ui`: presentational components and pure helpers. It imports nothing from `features`, `services`, or `app`.
- `src/services/extension.ts`: the extension gateway, `createExtensionGateway()`, and the only module that imports `@recnrun/bridge`.
- `src/features/<name>`: state and views for one capability (`extension-status`). Features never import each other.
- `src/app`: composition. It picks the install banner or a short status from the extension state; when the extension is installed, its dashboard frame covers the site.
- `src/main.tsx`: mounts `App` with the real gateway. Nothing imports it.
- `privacy/index.html`: the privacy policy, a second build entry with no script. As its own file it gets status 200 on GitHub Pages at `/privacy/`, where a route served by `404.html` would get 404, and the Chrome Web Store listing links to it.

Components take the gateway or data as props, so component tests use a fake gateway.

`content` never imports `storage` or WXT's `storage` helper, and never touches `browser.storage`. `dashboard` and `session` never import each other, `content`, or `background`: the dashboard asks the background to start a session, and the site's content script frames the session in its PiP window. `views` imports none of those, nor `storage`. `tabs` imports none of those, nor `views`, so it stays the one tab model. Every folder may import `ports`, type-only (`extension-ports-type-only`); `ports` imports only the domain (`extension-ports-are-contracts`), so a port never pulls an implementation along.

### Dashboard and session

The **dashboard** renders only framed over the site; opened on its own, `dashboard.html` (like `session.html`) only points to recnrun.com. Any number of site tabs can show it. It lists the recordings and every browser tab, normal and incognito (`tabs/open-tabs.ts`, kept current by the `tabs` and `windows.onFocusChanged` events). With no session, each tab offers Record. While a dashboard controls the session, the recorded tab shows its status and "The session floats in its own window" in every dashboard; without a controller, it offers Continue and Stop. Once the recorded tab closes, a "Closed tab" item takes its place, with the status and Stop only. Other tabs offer nothing until the session ends.

**Incognito.** The manifest sets `incognito: "spanning"`, so with "Allow in Incognito" on, one service worker and the dashboard in a normal window see incognito windows too (`windows.getAll` lists them, each tab with `incognito: true`); a tab is identified by `id`, `windowId`, and `incognito`. The dashboard asks `extension.isAllowedIncognitoAccess()`: without access it lists normal tabs, with an "Enable Incognito Mode" banner below them whose **Open Extension Config** opens RECnRun's details (`tabs.create` on `chrome://extensions/?id=` + `runtime.id`, so dev and store builds alike), where the user turns the toggle on; Chrome offers no API to flip, scroll to, or highlight it. A failed read shows neither the banner nor the button, since it says nothing about the toggle; with access it offers "New incognito window" (`windows.create({ incognito: true })`), which starts no session. Record works on an incognito tab as on any other, and RECnRun never closes an incognito window. In spanning mode the dashboard frame renders blank on an incognito recnrun.com tab, so the content script there covers the site with a notice to open recnrun.com from a normal window instead (`content/notice.ts`). Incognito tabs show no favicon unless it is a `data:` image: loading its URL from the extension's normal context would send that context's cookies.

**Reload or turn off.** When Chrome reloads RECnRun (an update, a reload in `chrome://extensions`, or a toggle such as "Allow in Incognito") or turns it off, it blanks the dashboard frame in every open site tab and leaves the content script there orphaned, with no event on the site. So once the frame loads, the content script opens a `recnrun-site` port (`messaging/site-port.ts`) that every dashboard frame holds (`dashboard/site-ports.ts`); the frame, unlike the service worker, does not sleep, so the port drops only when RECnRun unloads. Then the content script closes the PiP window it opened, if one is open, removes the frame, and asks for a reload (`content/site-session.ts` owns all three; `content/orphan-watch.ts` holds the port), so no stale dashboard or session page stays on screen, and none opens a PiP window the extension can no longer fill, and makes that reload itself once the tab is visible or focused again: back from `chrome://extensions`, each site tab shows a fresh dashboard that reads the new incognito access, or, with RECnRun off, the install prompt. No polling and no new channel: the reload is the reconnection.

**Current tab.** The PiP window shows the current tab (the active tab of the focused browser window) apart from the recorded one (`session/SessionTabs.tsx`): favicon, title (its URL, or "Untitled tab", when it has none), the URL truncated with the full one as a tooltip, Incognito, and Recorded. When the focus is not on a browser window, as when the user clicks the PiP window or another app, it keeps the last tab shown, marked "Not in focus", until that tab closes. Chrome lists the Document PiP window as an always-on-top normal window, so the tab model leaves `alwaysOnTop` windows out. Switching tabs only changes what the window shows; the recorded `tabId` changes only by Record. The dashboard and the PiP read the same `TabSource` through `views/use-browser-tabs.ts`, which reads again once per burst of events and renders only when what it shows changed. Nothing about tabs is stored: titles and URLs, incognito ones included, live only in the pages' memory.

The **session** is one per profile, stored as `RecordingSession` (with the recorded `tabId`) in `storage.session`, which every view reads and watches; it is the shared state. It is rendered by `session.html` only inside the PiP window, framed by the site. Only Stop, in a dashboard or the PiP window, ends it; the framed session then posts `close-panel`, so the window closes. Closing a tab, the recorded one included, never ends it. The extension has no toolbar popup, commands, or context menu items: the site is the only way in.

**Control.** One dashboard at a time controls the session: the one holding the `recnrun-control` Web Lock (`views/view-locks.ts`), shared by the pages of one extension origin. Record and Continue take it with `ifAvailable`, so of two dashboards starting at once only one gets it; the other shows "Another RECnRun tab controls the session." The holder announces itself on a `BroadcastChannel` of the same name, and watchers queue a shared request to learn when it frees, since exclusive waiters would take it from each other. Chrome frees the lock when the holder's page goes, so closing or reloading the controlling site tab gives up the control without a message; nothing else stores the controller, so no late message can bring it back.

With the lock, the dashboard frame posts `open-panel` to the site (a frame cannot open a Document PiP window), and the content script opens the window from the site's page, which the click in the frame activated, and frames `session.html` in it (`content/panel-window.ts`, `pip/document-pip.ts`). The dashboard then sends `start-session` with the tab id to the background, which creates the session unless one is stored (Continue keeps it), focuses the recorded tab and its window, and replies `{ ok: true }` (`background/session-requests.ts`). A session starts only on a tab that is still open: the background checks `tabs.get` before it writes, since a session whose tab is gone could only be stopped, and a stored session for a tab that closed while the click was in flight would otherwise show a "Closed tab" item with a running timer. When the tab is gone, the stored session is unreadable, or the write fails, it replies `{ ok: false, error }` and changes nothing: the dashboard awaits the reply, releases the lock on an error, and shows the error in the tab list, so no dashboard holds the control of a session that does not exist. When the window closes, by Stop or by the user, or cannot open, the content script posts `panel-closed` to the dashboard frame; the frame releases the lock and sends `return-to-dashboard`, and the background focuses the sender's own tab. Closing the window never ends the session.

The background accepts session requests (`messaging/session-protocol.ts`) only from its own extension pages: the route table (`background/routes.ts`) names `ownPage` as their only sender, which the listener grants when `sender.id` is its own and `sender.url` starts with its own origin, ruling out content scripts on recnrun.com. Every accepted request gets a `BackgroundReplySchema` answer, which the dashboard validates before trusting it.

A workspace is the origin a recording starts on, derived when the dashboard renders; nothing stores it. On recnrun.com the content script covers the site with a full-viewport `<iframe>` of `dashboard.html` (`content/dashboard-frame.ts`), so the dashboard keeps the site's address. They sync the route over `postMessage` on the `recnrun-frame` channel (`messaging/frame-protocol.ts` defines the six messages; `messaging/frame-channel.ts` validates them once per page with a `variant` on `type` and hands each to its subscriber, so the content script and the dashboard page each register one `message` listener): the frame starts at `?route=<site path>`, the content script sends a `route` message on Back and Forward, and the dashboard sends a `navigate` message when the user opens one of its links, which the content script applies with `history.pushState`, and a `location` message (`path`, `title`) for the route it shows, which sets `document.title` only while that path is still in the address bar. Only `navigate` adds history entries, so the dashboard's answer to a Back never pushes a route the address bar has moved past. Inside the frame, the dashboard's links point at the site's own URLs. Every view shares the recording through `storage.session` (POC 6E), not through frame messages. GitHub Pages answers unknown paths with `404.html`, so the website build copies `index.html` there (`apps/website/build/not-found-page.ts`) and deep links like `/recordings/<id>` load the site.

## Bridge protocol v1

The website and the content script share a window, so they talk through `window.postMessage`. Every message is an envelope `{ channel: "recnrun", protocol: 1, kind, ... }`:

| Kind       | Sender         | Fields                                              |
| ---------- | -------------- | --------------------------------------------------- |
| `announce` | content script | `extensionVersion`; sent once on start              |
| `request`  | website        | `id`, `type`                                        |
| `response` | content script | `id`, then `ok: true, result` or `ok: false, error` |

Request types and their result schemas live in `RESULT_SCHEMAS` (`packages/bridge/src/protocol.ts`):

| Type   | Result                 |
| ------ | ---------------------- |
| `ping` | `{ extensionVersion }` |

- **Detection.** `client.detect()` resolves `installed` on the first `announce` or `ping` reply, and `missing` after the timeout (1.5 s by default). Either signal is enough, so the order in which the page and the content script load does not matter.
- **Validation.** The host answers only valid requests of a known type. The client validates every result against its schema and rejects with `BridgeError` on a timeout, an error reply, or a malformed result.
- **Versioning.** `protocol` changes only for an incompatible envelope or message change; adding a request type does not change it. `getSnapshot` was removed while still at protocol 1, because no version had been released.

Inside the extension, the content script forwards `{ type }` with `browser.runtime.sendMessage`; the background validates the type with the bridge's `RequestTypeSchema` and replies `{ ok: true, result }` or `{ ok: false, error }`.

## Security model

The extension holds the user's data and is the only code that reads or shows it; the website only detects the extension.

- **Where the content script runs.** Production builds match only `https://recnrun.com/*`, where the website lives. The project also owns recnrun.app, recnrun.io, and recn.run; they only redirect to recnrun.com at the Cloudflare edge and never serve a page, so the extension does not match them. `development` and `test` builds add `http://localhost/*` and `http://127.0.0.1/*` (any port) for the dev server and end-to-end tests. Every build excludes `/privacy/*` on those origins (`exclude_matches`), so the dashboard frame never covers the privacy policy. `vp run test:extension-manifest` fails the build if a production manifest matches or excludes anything else.
- **Permissions.** Only `storage` and `tabs`, and `incognito: "spanning"`, which grants nothing until the user turns on "Allow in Incognito"; then the dashboard and the PiP window also show incognito tabs' titles and URLs, kept in memory only. `tabs` lets the dashboard list every tab's title and URL, and the background focus the recorded tab; Chrome warns "Read your browsing history" at install. It runs no script in those tabs and grants no access to their pages. No host permissions, no `externally_connectable`, no access to other sites. The same check (`apps/extension/scripts/manifest.checks.mjs`) asserts exactly this on the production manifest: `permissions` is `["storage", "tabs"]`; `host_permissions`, `optional_permissions`, `optional_host_permissions`, `externally_connectable`, `content_security_policy`, and `commands` are absent; `action` has no `default_popup`; `incognito` is `spanning`; and no content script sets `all_frames`, `match_about_blank`, or `match_origin_as_fallback`, so it runs only in the top frame of a real document on the matched origins.
- **Who may frame the dashboard and the session.** `dashboard.html` and `session.html` are the only web-accessible resources, and only for the content script's own matches (`use_dynamic_url: false`, since the matches already scope them); any other page that frames them gets `ERR_BLOCKED_BY_CLIENT`. Pages may frame them regardless of their CSP. If any `location.ancestorOrigins` entry is not an allowed site, for example a page framing recnrun.com to clickjack it, either page renders only a refusal (`tests/e2e/dashboard-embedding.spec.ts`); with no ancestor, either page only points to recnrun.com.
- **What the site sees of the frame.** The site cannot read the frame's document (`contentDocument` is `null`); it sees the frame's `src`, extension id included. Each side accepts frame messages only from the other's window and origin, validates them through `messaging/frame-channel.ts`, and accepts only paths that start with `/` but not with `//` (a protocol-relative URL to another host, which `history.pushState` would reject), so script on the site can navigate the dashboard but never read it. The content script opens a PiP window only for an `open-panel` from the dashboard frame, and closes it only for a `close-panel` from the session frame inside it. Script on the site could post a forged `panel-closed` to the dashboard frame, as the content script does; that only gives up the control and refocuses the site tab, never ends or changes the session.
- **Who may ask.** The `window` transport accepts only messages whose `source` is the page's own window and whose `origin` is the page's own origin, and replies only to that origin. Pages on other origins, other windows, and frames get no answer (`tests/e2e/origin-guard.spec.ts`).
- **What they can get.** Only the extension version: `ping` is the only request type, and no bridge message carries the user's data. The content script is forbidden to touch storage, and the gates enforce it: with the `storage` permission a content script could read it, so `vp run deps` rejects an import of `src/storage` or of `wxt/utils/storage` from `src/content` (`extension-content-not-to-storage`), and `vp lint` rejects `browser.storage` there (`no-restricted-properties`). It can only relay known request types to the background, which checks that the sender is its own extension.
- **What the dashboard trusts.** Stored data is validated when the extension reads it and rendered as text.
- **Script injection on recnrun.com** could navigate the dashboard frame or fake its content, so the website ships a strict CSP (`default-src 'self'`, no inline scripts or styles; `apps/website/build/content-security-policy.ts`). GitHub Pages sends no headers, so the CSP is a `<meta>` tag added to production builds only. Third-party scripts are not allowed on the website.
- Adding a write request widens this model; the `adding-a-bridge-message` skill requires documenting it here first.

### Recording (not built)

Recording in the user's own applications needs more than `storage`. Whatever M1 settles on follows these limits:

- **Per-origin access, granted at run time** (optional host permissions and `permissions.request`), or `activeTab` for a one-off page; `tabs` reveals URLs, not page access. No install-time host permissions, and never `<all_urls>`.
- Recording scripts in the user's applications never answer the bridge; they only report events to the background.
- `apps/extension/scripts/manifest.checks.mjs` changes in the same commit, so the production manifest allows exactly the new permissions.

| Concern                  | Tool                                                                       |
| ------------------------ | -------------------------------------------------------------------------- |
| Package manager, tasks   | Vite+ (`vp`) with pnpm workspaces and a version catalog                    |
| Format, lint, type check | `vp check`: Oxfmt, Oxlint (type aware, with `eslint-plugin-sonarjs`), tsgo |
| Architecture boundaries  | dependency-cruiser (`.dependency-cruiser.cjs`)                             |

| Unit and component tests | Vitest with V8 coverage; Vitest Browser Mode with Playwright Chromium      |

| Extension build          | WXT with `@preact/preset-vite`                                             |

Findings from the bootstrap spike, kept here because they explain the configuration:

- **WXT on Vite+.** The workspace overrides `vite` with `@voidzero-dev/vite-plus-core`; WXT 0.21 builds on it unchanged. `import.meta.env.MODE` is available in `defineContentScript` options, which is how `origins.ts` varies matches per build mode.
- **WXT tests.** `vitest.config.ts` passes its own `root` to `WxtVitest`; without it, Vitest projects started from the repo root cannot resolve the `@/` alias. `.wxt/` is generated by `wxt prepare` (the root `prepare` script, and explicitly in `Dockerfile.tests`, because pnpm skips `prepare` when `node_modules` is current).
- **One TypeScript base.** `tsconfig.base.json` holds the compiler options every workspace shares (`strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `noFallthroughCasesInSwitch`, `erasableSyntaxOnly`, `noUnusedLocals`, `noUnusedParameters`, and the common module settings); the root, both packages, and the website extend it and declare only what differs. The extension extends WXT's generated `.wxt/tsconfig.json`, which already sets most of them, and adds the rest.
- **dependency-cruiser and TypeScript 7.** dependency-cruiser 18 supports TypeScript below 7, so it parses with SWC (`parser: "swc"`, `@swc/core`); type-only imports are still detected. Its tsconfig-paths plugin resolves `paths` from the working directory, so each app has a `tsconfig.deps.json` repeating its `@/` alias from the repo root, and `vp run deps` cruises each app with its own. npm packages are not followed but stay in the graph as leaves, so rules can name them (`not-to-dev-dep`, `extension-content-not-to-storage`); the `exclude` names only the workspaces' build output, since a pattern on `dist/` would also drop every package's own `dist/`.
- **WXT dev browser.** WXT 0.21 opens a browser only when its optional peer `web-ext` is installed; without it, `wxt` builds and asks you to load the extension by hand. `apps/extension` depends on `web-ext` for that reason. `wxt.config.ts` opens `http://localhost:5173/` (the website's fixed dev port) in a persistent profile under `.wxt/chrome-data`, which `vp run clean` deletes. It uses an absolute `chromiumProfile` with `keepProfileChanges` so Chrome and `web-ext` use the same profile. On macOS and Windows, Chrome protects the Developer mode preference and can discard values written directly to `Preferences`; Linux does not enforce this protection. Before WXT opens Chrome, the `server:started` hook calls `apps/extension/scripts/dev-chrome.ts`, which opens the same profile in headless Google Chrome, enables Developer mode through `chrome://extensions`, and closes it to save the protected preference. This also creates the profile after a clean and preserves its existing data. The preparation uses Playwright from the extension's own development dependencies (`@playwright/test`) and the installed Google Chrome, without downloading a browser; `tests/e2e/dev-chrome.spec.ts` covers it.
- **Knip and WXT.** Knip's WXT plugin expects `entrypoints/` at the package root; `knip.jsonc` lists `src/entrypoints` explicitly.
- **Docker is the reference Node.** `Dockerfile.tests` pins the Node that every public test command and `vp run verify` run on (`VP_NODE_VERSION`, 24.x); `engines.node` requires the same major (`>=24.0.0`), `@types/node` stays on 24, and `tests/container/runner.checks.mjs` fails when the two majors drift. On the host, `vp` installs a matching Node from `engines.node`; `vp env doctor` shows which.
- **Extensions need a headed Chromium.** Playwright and Vitest Browser Mode run headed; Docker provides the display, so no window opens on the host.
