# Architecture

[PRODUCT_BRIEF.md](PRODUCT_BRIEF.md) describes what the product does. This document fixes how the code is split and which way dependencies point. `.dependency-cruiser.cjs` enforces every boundary below (`vp run deps`); change both together.

```text
apps/website ──► @recnrun/bridge ──► valibot
     │            ▲                     ▲
     │      apps/extension ──► @recnrun/domain
     │            │
     └────────────┴──► @recnrun/brand (CSS and fonts)
```

- Packages never import apps. Apps never import each other: they meet only at the bridge protocol.
- Packages export their TypeScript sources (`exports` → `./src/index.ts`); apps bundle them. A package `build` only type checks.
- `@recnrun/brand` holds no code: it exports `base.css` (tokens and base layout) and `mona-sans.css`, which each app's entry imports before its own stylesheet, so the palette, the font, and its license exist once instead of once per app. It imports nothing (`brand-is-leaf`).
- `@recnrun/domain/testing` exports fixtures for tests; no `src/` file imports a test file. The root workspace lists `@recnrun/domain` as a devDependency so `tests/e2e`, which belongs to no workspace, imports it by name; lint rejects relative paths into `packages/*` or `apps/*` sources from `tests/**`.
- Every module is reachable from an entrypoint, a test, or a config (`no-orphans`), and there are no import cycles (`no-circular`).

## Website

```text
src/main.tsx ─► src/app ─► src/features/<name> ─► src/services ─► @recnrun/bridge
                   │              │
                   └──────────────┴──► src/ui
```

- `src/ui`: presentational components and pure helpers. It imports nothing from `features`, `services`, or `app`.
- `src/services/extension.ts`: the extension gateway, `createExtensionGateway()`, and the only module that imports `@recnrun/bridge`.
- `src/features/<name>`: state and views for one capability (`extension-status`). Features never import each other.
- `src/app`: composition. It picks the install banner or a short status from the extension state; when the extension is installed, its dashboard frame covers the site.
- `src/main.tsx`: mounts `App` with the real gateway. Nothing imports it.
- `privacy/index.html`: the privacy policy, a second build entry with no script. As its own file it gets status 200 on GitHub Pages at `/privacy/`, where a route served by `404.html` would get 404, and the Chrome Web Store listing links to it.

Components take the gateway or data as props, so component tests use a fake gateway.

for a capture it restarts the bound at each message. The capture (`capture.ts`, POC) reads the managed tab's top frame (`webNavigation.getFrame`), refuses a page that is not `http:` or `https:` and a tab with no Incognito cookie store of its own, before anything is injected, injects the agent with `scripting.executeScript` into that document only (no barrier, nothing registered), and takes only that document's port; it begins an in-progress capture, keeps the tab's Web Storage (`localStorage`, and `sessionStorage` of the managed tab only: another tab's `sessionStorage` is out of scope) for the header, writes each chunk of a store's records, and each cache, as one part, in order (`capture-collector.ts`; after a failed write, no later part), first replacing every Blob in it with a copy of its own (`own-blobs.ts`: a Blob that arrives from an Incognito page reads fine, but the extension's IndexedDB refuses it with `DataError` "Failed to write blobs (InvalidBlob)"; the other direction, extension to page, needs no copy), and publishes the complete capture (every adapter `captured`: `localStorage`, `sessionStorage`, IndexedDB, cookies, and Cache Storage, and the value types it met, `value-types.ts`) only when the agent's counts (Web Storage entries, databases, records, caches, cache entries) match what arrived, so an entry lost on the way fails the capture with `CaptureIncomplete`. The cache entries the agent could not keep join the cookies' in `unsupported`. A restored cache entry reads back with its status, status text, the headers the page could read, its body, and its Vary matching, but as type `default` with an empty `url` and `redirected` false: a constructed `Response` has no URL list, and no API sets one. Its cookies (`cookie-capture.ts`) are every cookie of the tab's store, partitioned ones included (`cookies.getAll` with an empty `partitionKey`), whose host is the target's or one the capabilities declare (a domain cookie when one of those hosts is in its domain); every other cookie goes to `unsupported` by name, domain, and path, never its value, and a failed listing fails the capture with `CookiesNotCaptured`. A restore skips a cookie that expired since its capture, as Chrome would not store it. A `failed` reply, a disconnect, a failed write, unlisted cookies, or a bound of silence discards the capture, so the identity's previous one stays readable. The barrier's CSP binds only the page's scripts, so the injected reload runs, and no page script ran in that document. Each step is journaled before it runs, and the window as soon as it exists, so a worker that stops mid-start leaves enough for `recover` to undo. ### Dashboard and session

The **dashboard** renders only framed over the site; opened on its own, `dashboard.html` (like `session.html`) only points to recnrun.com. Any number of site tabs can show it. It lists the recordings and every browser tab, normal and incognito (`tabs/open-tabs.ts`, kept current by the `tabs` and `windows.onFocusChanged` events). With no session, each tab offers Record. While a dashboard controls the session, the recorded tab shows its status and "The session floats in its own window" in every dashboard; without a controller, it offers Continue and Stop. Once the recorded tab closes, a "Closed tab" item takes its place, with the status and Stop only. Other tabs offer nothing until the session ends.

**Incognito.** The manifest sets `incognito: "spanning"`, so with "Allow in Incognito" on, one service worker and the dashboard in a normal window see incognito windows too (`windows.getAll` lists them, each tab with `incognito: true`); a tab is identified by `id`, `windowId`, and `incognito`. The dashboard asks `extension.isAllowedIncognitoAccess()`: without access it lists normal tabs under an "Enable Incognito Mode" banner (the list waits for the answer, so the banner never moves a Record button) whose **Open Extension Config** opens RECnRun's details (`tabs.create` on `chrome://extensions/?id=` + `runtime.id`, so dev and store builds alike), where the user turns the toggle on; Chrome offers no API to flip, scroll to, or highlight it. A failed read shows neither the banner nor the button, since it says nothing about the toggle; with access it shows the Incognito workspace panel (see below) in place of a plain new-window button. Record works only on the managed Incognito tab (POC branch; see below). RECnRun closes an incognito window only for a `workspace-close-and-start` that names exactly the foreign windows open at that moment, or for a `workspace-restart` of its managed window (see below). In spanning mode the dashboard frame renders blank on an incognito recnrun.com tab, so the content script there covers the site with a notice to open recnrun.com from a normal window instead (`content/notice.ts`). Incognito tabs show no favicon unless it is a `data:` image: loading its URL from the extension's normal context would send that context's cookies.

**Reload or turn off.** When Chrome reloads RECnRun (an update, a reload in `chrome://extensions`, or a toggle such as "Allow in Incognito") or turns it off, it blanks the dashboard frame in every open site tab and leaves the content script there orphaned, with no event on the site. So once the frame loads, the content script opens a `recnrun-site` port (`messaging/site-port.ts`) that every dashboard frame holds (`dashboard/site-ports.ts`); the frame, unlike the service worker, does not sleep, so the port drops only when RECnRun unloads. Then the content script closes the PiP window it opened, if one is open, removes the frame, and asks for a reload (`content/site-session.ts` owns all three; `content/orphan-watch.ts` holds the port), so no stale dashboard or session page stays on screen, and none opens a PiP window the extension can no longer fill, and makes that reload itself once the tab is visible or focused again: back from `chrome://extensions`, each site tab shows a fresh dashboard that reads the new incognito access, or, with RECnRun off, the install prompt. No polling and no new channel: the reload is the reconnection.

**Current tab.** The PiP window shows the current tab (the active tab of the focused browser window) apart from the recorded one (`session/SessionTabs.tsx`): favicon, title (its URL, or "Untitled tab", when it has none), the URL truncated with the full one as a tooltip, Incognito, and Recorded. When the focus is not on a browser window, as when the user clicks the PiP window or another app, it keeps the last tab shown, marked "Not in focus", until that tab closes. Chrome lists the Document PiP window as an always-on-top normal window, so the tab model leaves `alwaysOnTop` windows out. When the focus moves between a normal and an Incognito window, Chrome can report both focused while it sends the one `onFocusChanged`, so the tab model takes the focused window that `windows.getLastFocused` names (`tabs/open-tabs.ts`). Switching tabs only changes what the window shows; the recorded `tabId` changes only by Record. The dashboard and the PiP read the same `TabSource` through `views/use-browser-tabs.ts`, which reads again once per burst of events and renders only when what it shows changed. Nothing about tabs is stored: titles and URLs, incognito ones included, live only in the pages' memory.

The **session** is one per profile, stored as `RecordingSession` (with the recorded `tabId`) in `storage.session`, which every view reads and watches; it is the shared state. It is rendered by `session.html` only inside the PiP window, framed by the site. Only Stop, in a dashboard or the PiP window, ends it; the framed session then posts `close-panel`, so the window closes. Closing a tab, the recorded one included, never ends it. The extension has no toolbar popup, commands, or context menu items: the site is the only way in.

**Control.** One dashboard at a time controls the session: the one holding the `recnrun-control` Web Lock (`views/view-locks.ts`), shared by the pages of one extension origin. Record and Continue take it with `ifAvailable`, so of two dashboards starting at once only one gets it; the other shows "Another RECnRun tab controls the session." The holder announces itself on a `BroadcastChannel` of the same name, and watchers queue a shared request to learn when it frees, since exclusive waiters would take it from each other. Chrome frees the lock when the holder's page goes, so closing or reloading the controlling site tab gives up the control without a message; nothing else stores the controller, so no late message can bring it back.

With the lock, the dashboard frame posts `open-panel` to the site (a frame cannot open a Document PiP window), and the content script opens the window from the site's page, which the click in the frame activated, and frames `session.html` in it (`content/panel-window.ts`, `pip/document-pip.ts`). The dashboard then sends `start-session` with the tab id to the background, which creates the session unless one is stored (Continue keeps it; a new one starts only on the active managed window's tab, `local:managed-window`, and any other tab gets `{ ok: false, error }` with nothing written), focuses the recorded tab and its window, and replies `{ ok: true }` (`background/session-requests.ts`). A session starts only on a tab that is still open: the background checks `tabs.get` before it writes, since a session whose tab is gone could only be stopped, and a stored session for a tab that closed while the click was in flight would otherwise show a "Closed tab" item with a running timer. When the tab is gone, the stored session is unreadable, or the write fails, it replies `{ ok: false, error }` and changes nothing: the dashboard awaits the reply, releases the lock on an error, and shows the error in the tab list, so no dashboard holds the control of a session that does not exist. When the window closes, by Stop or by the user, or cannot open, the content script posts `panel-closed` to the dashboard frame; the frame releases the lock and sends `return-to-dashboard`, and the background focuses the sender's own tab. Closing the window never ends the session.

The background accepts session and workspace requests (`messaging/session-protocol.ts`, `messaging/workspace-protocol.ts`) only from its own extension pages: the route table (`background/routes.ts`) names `ownPage` as their only sender, which the listener grants when `sender.id` is its own and `sender.url` starts with its own origin, ruling out content scripts on recnrun.com. Every accepted request gets a `BackgroundReplySchema` answer, which the dashboard validates before trusting it.

**Incognito workspace (POC).** The workspace commands (`background/workspace/commands.ts`) keep one managed Incognito window (`ManagedWindowState` in `local:managed-window`). `workspace-status` answers `{ access, managed, foreign, busy, identities }` (`WorkspaceStatusSchema`): the stored managed window (with the identity it holds, if any), the saved identities, and every other Incognito window by id and tab count, never a title or URL. Every Incognito window but a DevTools one counts, a Document PiP opened from an Incognito page included, since any of them keeps the Incognito session alive; RECnRun's own PiP opens from a normal tab and is never Incognito. `workspace-start { url }` accepts only an `http:` or `https:` target (`isAllowedTarget`), requires "Allow in Incognito" (without it Chrome hides Incognito windows, so the inventory could prove nothing), opens the managed window on `about:blank` only while no Incognito window exists and Chrome has destroyed the previous Incognito profile (below), and then navigates its tab to the target. Every window RECnRun opens, in these commands and in the bootstrap alike, goes through that wait (`fresh-window.ts`): Chrome unlists an Incognito cookie store with its last tab (`cookies_api.cc:895-904`) but destroys the profile only once its renderers have gone (`browser_manager_service.cc:145-161`, `profile_destroyer.cc:335-343, 395-411`, at most 1 s later), and until then `windows.create({ incognito: true })` reuses that profile with its data (`tabs_api.cc:1044-1047`, `profile_impl.cc:1063-1066`). So RECnRun remembers every store id it sees listed with only Incognito tabs (`local:incognito-store-ids`): after it opens a window, when it resolves the managed tab's store, and before every close, failure cleanup and recovery included. Before opening a window it waits until no store but the normal one is listed and `cookies.getAll` with each remembered id rejects with "Invalid cookie store id" (the store lookup only finds an existing profile, `cookies_helpers.cc:81-98`, `chrome_extensions_browser_client.cc:322-325`), asking again after each answer within 10 s (`IncognitoNotGone` otherwise). A store that was listed only while RECnRun never looked, for example a window the user opened and closed between two commands, is not remembered; the store list check still catches it while it has a tab. These calls need the `cookies` permission, which production builds lack (OD-1), so there every workspace command that opens a window fails with `CookiesUnavailable` and the workspace is unavailable. `workspace-close-and-start { url, windowIds }` refuses unless `windowIds` is exactly the current foreign set, so a window that appeared after the user looked needs a fresh decision; it closes those windows, waits until Chrome reported each removal and a fresh inventory no longer lists them, and then starts. One operation runs at a time (an in-memory lock): a second one gets `{ ok: false, error }` saying RECnRun is busy. An open managed window blocks both commands; `workspace-close-and-start` refuses then before closing anything ("Close and start empty replaces the open workspace; close the other Incognito windows first."), since starting would still find the managed window open. `workspace-restart { url }` replaces it: with access, an allowed target, no foreign Incognito window, and an active managed window that is still open, it closes that window (waiting as above), opens a fresh one on `about:blank`, and navigates its tab to the target; otherwise it refuses and closes nothing. Restarting discards the managed window's Incognito data, since nothing captures it yet; the switch operations will save it first. While a recording session exists, `workspace-close-and-start` and `workspace-restart` refuse ("Stop the recording first.") and close nothing (OD-2), since closing a window could end the recorded tab.

**Identity lifecycle (POC).** `lifecycle.ts` runs five commands from the dashboard (own pages only): `workspace-switch { identityId }`, `workspace-suspend`, `workspace-resume { identityId }`, `workspace-new-identity { label, url, capabilities?, closeWindowIds? }`, and `workspace-delete-identity { identityId }`. Under the workspace lock it reads the saved identities, the managed window (counted only while Chrome still lists it), the other Incognito windows, and whether a recording exists, and `planLifecycle` decides:

| Command      | Refused when                                                                                                                                                | Steps                                                                                                                       |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Switch to    | recording; another Incognito window; unknown or already open identity; the open window holds no identity                                                    | capture, persist, close (when a window is open), then start from capture, or start empty when the target was never captured |
| Suspend      | recording; another Incognito window; no managed window; the open window holds no identity                                                                   | capture, persist, close                                                                                                     |
| Resume       | recording; another Incognito window; unknown identity; any managed window open; the identity has no capture                                                 | start from capture                                                                                                          |
| New identity | an invalid label or address; recording; another Incognito window unless `closeWindowIds` is exactly that set (closed without saving: they hold no identity) | capture, persist, close (when a window is open), start empty; the identity is saved just before its start                   |
| Delete       | unknown identity; the identity is open (allowed while recording or beside other windows)                                                                    | remove its captures, then the identity                                                                                      |

`capture` publishes the open identity's capture (`capture.ts`), `persist` records its id, time, and size on the identity, and only then does `close` read the windows again and close the managed one; a window that appeared during the capture stops it (`IncognitoWindowsOpen`, the capture kept). So a capture or persistence failure keeps the workspace open and nothing is lost. A start runs the bootstrap with a window that holds the identity (`identityId` on `ManagedWindowState`) and journals its steps under the command's kind and operation id; a start from a capture RECnRun cannot read (missing, or a stored row that does not validate) fails with no window opened and never becomes an empty session. Each step is journaled before it runs; a failure is recorded at its step, or at the bootstrap step that failed, and a command that ends without a start is recorded `done`. A failed start after the close leaves the previous identity's capture saved and no window open. Messages from an older capture or restore are already dropped by the agent link (generation, document, operation id).

The dashboard's Incognito workspace panel (`dashboard/IncognitoWorkspace.tsx`, POC branch) reads `workspace-status` on mount and again whenever an Incognito window opens or closes (`IncognitoAccess.watchWindows`), a tab changes, or a command ends, refused or not. It holds one Address field (an `http:`/`https:` URL) that **Use this tab's address** on a normal tab in the list fills; that copies the address only, never the tab's cookies or storage. The tab list offers Record only on the managed tab while its window is active (`managedTabId`), from the same status read. It offers one action per state: without access, the requirement and no action; with an active managed window and foreign windows, their list and no command, with a hint to close them by hand (both commands would refuse); with an active managed window alone, **Close and start empty** (`workspace-restart`), warning that its Incognito data is discarded; with foreign windows, their count and tab counts (titles come from the live tab model, never from storage) and **Close these windows and start** (`workspace-close-and-start` with exactly the ids shown), or the user closes them and the list follows; otherwise **Start** (`workspace-start`). Buttons wait while a command is in flight or the status reports `busy`, and look disabled; a refusal shows as an alert in the panel, once even when the journaled failure already names it.

Below it, **Saved identities** (`dashboard/Identities.tsx`) lists `status.identities` with each one's last capture time and approximate size ("Not saved yet" before its first), and says they are kept on this computer after Incognito closes. Each row offers one command from the status: with no managed window, **Resume** for a captured identity and **Switch to** for one never captured (it opens empty); with a managed window that holds an identity, **Suspend** on its row (marked Open) and **Switch to** on the others; with an anonymous managed window, none (Close and start empty replaces it). While the window holds an identity, the panel names it instead of offering Close and start empty. **Delete** asks again ("Delete <label>" or Keep) and is absent on the open row. **New identity** takes a Label and the Address field and sends no extra cookie hosts. A conflict, any foreign Incognito window or a second tab in the managed window (from the live tab model; the backend refuses only the first), shows a banner and disables every row command and New identity, but not Delete. Missing access disables the row commands too and hides New identity; a command in flight disables every button, Delete included.

A workspace is the origin a recording starts on, derived when the dashboard renders; nothing stores it. On recnrun.com the content script covers the site with a full-viewport `<iframe>` of `dashboard.html` (`content/dashboard-frame.ts`), so the dashboard keeps the site's address. They sync the route over `postMessage` on the `recnrun-frame` channel (`messaging/frame-protocol.ts` defines the six messages; `messaging/frame-channel.ts` validates them once per page with a `variant` on `type` and hands each to its subscriber, so the content script and the dashboard page each register one `message` listener): the frame starts at `?route=<site path>`, the content script sends a `route` message on Back and Forward, and the dashboard sends a `navigate` message when the user opens one of its links, which the content script applies with `history.pushState`, and a `location` message (`path`, `title`) for the route it shows, which sets `document.title` only while that path is still in the address bar. Only `navigate` adds history entries, so the dashboard's answer to a Back never pushes a route the address bar has moved past. Inside the frame, the dashboard's links point at the site's own URLs. Every view shares the recording through `storage.session` (POC 6E), not through frame messages. GitHub Pages answers unknown paths with `404.html`, so the website build copies `index.html` there (`apps/website/build/not-found-page.ts`) and deep links like `/recordings/<id>` load the site.

## Bridge protocol v1

The website and the content script share a window, so they talk through `window.postMessage`. Every message is an envelope `{ channel: "recnrun", protocol: 1, kind, ... }`:

| Kind       | Sender         | Fields                                              |
| ---------- | -------------- | --------------------------------------------------- |
| `announce` | content script | `extensionVersion`; sent once on start              |
| `request`  | website        | `id`, `type`                                        |
| `response` | content script | `id`, then `ok: true, result` or `ok: false, error` |

Request types and their result schemas live in `RESULT_SCHEMAS` (`packages/bridge/src/protocol.ts`):

| Type   | Result                 |
| ------ | ---------------------- |
| `ping` | `{ extensionVersion }` |

- **Detection.** `client.detect()` resolves `installed` on the first `announce` or `ping` reply, and `missing` after the timeout (1.5 s by default). Either signal is enough, so the order in which the page and the content script load does not matter.
- **Validation.** The host answers only valid requests of a known type. The client validates every result against its schema and rejects with `BridgeError` on a timeout, an error reply, or a malformed result.
- **Versioning.** `protocol` changes only for an incompatible envelope or message change; adding a request type does not change it. `getSnapshot` was removed while still at protocol 1, because no version had been released.

Inside the extension, the content script forwards `{ type }` with `browser.runtime.sendMessage`; the background validates the type with the bridge's `RequestTypeSchema` and replies `{ ok: true, result }` or `{ ok: false, error }`.

## Security model

The extension holds the user's data and is the only code that reads or shows it; the website only detects the extension.

- **Where the content script runs.** Production builds match only `https://recnrun.com/*`, where the website lives. The project also owns recnrun.app, recnrun.io, and recn.run; they only redirect to recnrun.com at the Cloudflare edge and never serve a page, so the extension does not match them. `development` and `test` builds add `http://localhost/*` and `http://127.0.0.1/*` (any port) for the dev server and end-to-end tests. Every build excludes `/privacy/*` on those origins (`exclude_matches`), so the dashboard frame never covers the privacy policy. `vp run test:extension-manifest` fails the build if a production manifest matches or excludes anything else.
- **Permissions.** Only `storage` and `tabs`, and `incognito: "spanning"`, which grants nothing until the user turns on "Allow in Incognito"; then the dashboard and the PiP window also show incognito tabs' titles and URLs, kept in memory only. `tabs` lets the dashboard list every tab's title and URL, and the background focus the recorded tab; Chrome warns "Read your browsing history" at install. It runs no script in those tabs and grants no access to their pages. No host permissions, no `externally_connectable`, no access to other sites. The same check (`apps/extension/scripts/manifest.checks.mjs`) asserts exactly this on the production manifest: `permissions` is `["storage", "tabs"]`; `host_permissions`, `optional_permissions`, `optional_host_permissions`, `externally_connectable`, `content_security_policy`, and `commands` are absent; `action` has no `default_popup`; `incognito` is `spanning`; and no content script sets `all_frames`, `match_about_blank`, or `match_origin_as_fallback`, so it runs only in the top frame of a real document on the matched origins.
- **Incognito workspace POC: test and development builds only.** `src/config/permissions.ts` adds `declarativeNetRequest` (tab-scoped session rules for the bootstrap barrier), `scripting` (registering the page-origin agent only during an operation, injecting it for a capture, and reloading the barrier's document to release the app), `cookies` (resolving the managed tab's Incognito cookie store, then capturing its cookies and restoring them with its explicit `storeId`), `webNavigation` (the commit and `documentId` of each bootstrap navigation), `unlimitedStorage` (identity captures in the extension's IndexedDB can exceed the default quota), host access to the fixture origins only (`http://*.localhost/*` and `https://*.localhost/*`, because Chrome lists and sets a Secure cookie only with access to its `https` URL, even on `http` localhost, where Secure cookies are allowed; plus each origin in `RECNRUN_POC_HOSTS` for a manual run against a real app; anything but an `http(s)` origin fails the build), and `"message_serialization": "structured_clone"`, so `Date`, `Blob`, and `ArrayBuffer` values cross between the agent and the service worker intact. Production builds get none of them, whatever `RECNRUN_POC_HOSTS` holds (decision OD-1 of the POC plan): the production check above is unchanged and also asserts the default JSON messaging, and a second check asserts that the test manifest asks for exactly `storage`, `tabs`, and these five, the two fixture host patterns, and structured clone. With these, a test build can read and write cookies, block and rewrite requests, and run a script on the fixture origins of any tab, Incognito tabs included once "Allow in Incognito" is on. The script it runs there is the origin agent (`src/origin`), and only while an operation holds the barrier, or once in the managed tab's document for a capture: Chrome runs it in every page of the target origin, in any tab, for that time, so the agent does nothing until the background sends a valid `restore` or `capture`, and the background sends one only to the expected document (`isExpectedAgent`). The background writes cookies only into the store Chrome lists for the managed tab, never the normal profile's. A test build also exposes `recnrunPoc` on its service worker so end-to-end tests can start with an identity, capture one and start from its capture, delay the restore, and fail a step; capture and restore are reachable through nothing else, never `@recnrun/bridge` or the website; a build check asserts the production `background.js` does not contain it. The agent writes the page's storage and never the extension's: dependency-cruiser rejects its imports of `src/storage`, WXT's `storage` helper, and the other extension folders, and lint rejects `browser.storage` there as in `src/content`.
- **Who may frame the dashboard and the session.** `dashboard.html` and `session.html` are the only web-accessible resources, and only for the content script's own matches (`use_dynamic_url: false`, since the matches already scope them); any other page that frames them gets `ERR_BLOCKED_BY_CLIENT`. Pages may frame them regardless of their CSP. If any `location.ancestorOrigins` entry is not an allowed site, for example a page framing recnrun.com to clickjack it, either page renders only a refusal (`tests/e2e/dashboard-embedding.spec.ts`); with no ancestor, either page only points to recnrun.com.
- **What the site sees of the frame.** The site cannot read the frame's document (`contentDocument` is `null`); it sees the frame's `src`, extension id included. Each side accepts frame messages only from the other's window and origin, validates them through `messaging/frame-channel.ts`, and accepts only paths that start with `/` but not with `//` (a protocol-relative URL to another host, which `history.pushState` would reject), so script on the site can navigate the dashboard but never read it. The content script opens a PiP window only for an `open-panel` from the dashboard frame, and closes it only for a `close-panel` from the session frame inside it. Script on the site could post a forged `panel-closed` to the dashboard frame, as the content script does; that only gives up the control and refocuses the site tab, never ends or changes the session.
- **Who may ask.** The `window` transport accepts only messages whose `source` is the page's own window and whose `origin` is the page's own origin, and replies only to that origin. Pages on other origins, other windows, and frames get no answer (`tests/e2e/origin-guard.spec.ts`).
- **What they can get.** Only the extension version: `ping` is the only request type, and no bridge message carries the user's data. The content script is forbidden to touch storage, and the gates enforce it: with the `storage` permission a content script could read it, so `vp run deps` rejects an import of `src/storage` or of `wxt/utils/storage` from `src/content` (`extension-content-not-to-storage`), and `vp lint` rejects `browser.storage` there (`no-restricted-properties`). It can only relay known request types to the background, which checks that the sender is its own extension.
- **What the dashboard trusts.** Stored data is validated when the extension reads it and rendered as text.
- **Script injection on recnrun.com** could navigate the dashboard frame or fake its content, so the website ships a strict CSP (`default-src 'self'`, no inline scripts or styles; `apps/website/build/content-security-policy.ts`). GitHub Pages sends no headers, so the CSP is a `<meta>` tag added to production builds only. Third-party scripts are not allowed on the website.
- Adding a write request widens this model; the `adding-a-bridge-message` skill requires documenting it here first.

### Recording (not built)

Recording in the user's own applications needs more than `storage`. Whatever M1 settles on follows these limits:

- **Per-origin access, granted at run time** (optional host permissions and `permissions.request`), or `activeTab` for a one-off page; `tabs` reveals URLs, not page access. No install-time host permissions, and never `<all_urls>`.
- Recording scripts in the user's applications never answer the bridge; they only report events to the background.
- `apps/extension/scripts/manifest.checks.mjs` changes in the same commit, so the production manifest allows exactly the new permissions.

Findings from the bootstrap spike, kept here because they explain the configuration:

- **WXT on Vite+.** The workspace overrides `vite` with `@voidzero-dev/vite-plus-core`; WXT 0.21 builds on it unchanged. `import.meta.env.MODE` is available in `defineContentScript` options, which is how `origins.ts` varies matches per build mode.
- **WXT tests.** `vitest.config.ts` passes its own `root` to `WxtVitest`; without it, Vitest projects started from the repo root cannot resolve the `@/` alias. `.wxt/` is generated by `wxt prepare` (the root `prepare` script, and explicitly in `Dockerfile.tests`, because pnpm skips `prepare` when `node_modules` is current).
- **One TypeScript base.** `tsconfig.base.json` holds the compiler options every workspace shares (`strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `noFallthroughCasesInSwitch`, `erasableSyntaxOnly`, `noUnusedLocals`, `noUnusedParameters`, and the common module settings); the root, both packages, and the website extend it and declare only what differs. The root config includes only the root-level files (`*.ts`, `scripts`, `tests`), so `tsc -p tsconfig.json` checks them without swallowing the apps; the `node --test` check files await every top-level `test()` so the type-aware lint sees no floating promise. The extension extends WXT's generated `.wxt/tsconfig.json`, which already sets most of them, and adds the rest.
- **dependency-cruiser and TypeScript 7.** dependency-cruiser 18 supports TypeScript below 7, so it parses with SWC (`parser: "swc"`, `@swc/core`); type-only imports are still detected. Its tsconfig-paths plugin resolves `paths` from the working directory, so each app has a `tsconfig.deps.json` repeating its `@/` alias from the repo root, and `vp run deps` cruises each app with its own. npm packages are not followed but stay in the graph as leaves, so rules can name them (`not-to-dev-dep`, `extension-content-not-to-storage`); the `exclude` names only the workspaces' build output, since a pattern on `dist/` would also drop every package's own `dist/`.
- **WXT dev browser.** WXT 0.21 opens a browser only when its optional peer `web-ext` is installed; without it, `wxt` builds and asks you to load the extension by hand. `apps/extension` depends on `web-ext` for that reason. `wxt.config.ts` opens `http://localhost:5173/` (the website's fixed dev port) in a persistent profile under `.wxt/chrome-data`, which `vp run clean` deletes. It uses an absolute `chromiumProfile` with `keepProfileChanges` so Chrome and `web-ext` use the same profile. On macOS and Windows, Chrome protects the Developer mode preference and can discard values written directly to `Preferences`; Linux does not enforce this protection. Before WXT opens Chrome, the `server:started` hook calls `apps/extension/scripts/dev-chrome.ts`, which opens the same profile in headless Google Chrome, enables Developer mode through `chrome://extensions`, and closes it to save the protected preference. This also creates the profile after a clean and preserves its existing data. The preparation uses Playwright from the extension's own development dependencies (`@playwright/test`) and the installed Google Chrome, without downloading a browser; `tests/e2e/dev-chrome.spec.ts` covers it.
- **Knip and WXT.** Knip's WXT plugin expects `entrypoints/` at the package root; `knip.jsonc` lists `src/entrypoints` explicitly.
- **Docker is the reference Node.** `Dockerfile.tests` pins the Node that every public test command and `vp run verify` run on (`VP_NODE_VERSION`, 24.x); `engines.node` requires the same major (`>=24.0.0`), `@types/node` stays on 24, and `tests/container/runner.checks.mjs` fails when the two majors drift. On the host, `vp` installs a matching Node from `engines.node`; `vp env doctor` shows which.
- **Extensions need a headed Chromium.** Playwright and Vitest Browser Mode run headed; Docker provides the display, so no window opens on the host.
- **Coverage has a denominator.** `coverage.include` is a glob, so a narrowed include or a renamed folder would measure fewer files and still pass the thresholds. `scripts/coverage.checks.mjs` runs after Vitest in `test:coverage:local` and fails unless the files in `coverage/coverage-summary.json` (the `json-summary` reporter) are exactly the `.ts` and `.tsx` files under `apps/*/src` and `packages/*/src` minus the configured excludes: tests, `.d.ts`, and the entrypoints and `main.tsx`, which only call a `start*` function and run in the end-to-end suite. It globs the tree instead of `git ls-files` because the Docker build context carries no `.git`. The same script enforces a per-file floor (80% lines, statements, and functions; 75% branches, the former global thresholds) on every file with executable code, so the global averages cannot hide an untested module; files with no executable code (type-only `ports/*.ts`, the packages' `index.ts`, `bridge/transport.ts`) report `total: 0` and are skipped, which is why Vitest's own `thresholds.perFile` is not used.
