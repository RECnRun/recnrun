# Architecture

[PRODUCT_BRIEF.md](PRODUCT_BRIEF.md) describes what the product does. This document fixes how the code is split and which way dependencies point. `.dependency-cruiser.cjs` enforces every boundary below (`vp run deps`); change both together.

```text
apps/website ──► @recnrun/bridge ──► valibot
     │            ▲                     ▲
     │      apps/extension ──► @recnrun/domain
     │            │
     └────────────┴──► @recnrun/brand (CSS and fonts)
```

## Packages

| Package           | Holds                                                                                                                                                                                                                                                                          | May import                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| `packages/domain` | Valibot schemas and inferred types for every concept; `Snapshot`, the versioned document the extension stores; `RecordingSession`, the recording in progress, and its pure helpers (`elapsedSeconds`, `toggled`, `formatElapsed`); `errorMessage`, the text for a caught value | `valibot` only                   |
| `packages/bridge` | The website ↔ content script protocol, its client, host, and `window` transport; it keeps its own one-line error text rather than depend on the domain's `errorMessage`                                                                                                        | `valibot` only                   |
| `packages/brand`  | Mona Sans, and `base.css`: the palette, semantic tokens, and base layout both apps import first                                                                                                                                                                                | nothing                          |
| `apps/website`    | The Preact SPA                                                                                                                                                                                                                                                                 | bridge, brand; never extension   |
| `apps/extension`  | The WXT extension                                                                                                                                                                                                                                                              | every package; never the website |

- Packages never import apps. Apps never import each other: they meet only at the bridge protocol.
- Packages export their TypeScript sources (`exports` → `./src/index.ts`); apps bundle them. A package `build` only type checks.
- `@recnrun/brand` holds no code: it exports `base.css` (tokens and base layout) and `mona-sans.css`, which each app's entry imports before its own stylesheet, so the palette, the font, and its license exist once instead of once per app. It imports nothing (`brand-is-leaf`).
- `@recnrun/domain/testing` exports fixtures for tests; no `src/` file imports a test file. The root workspace lists `@recnrun/domain` as a devDependency so `tests/e2e`, which belongs to no workspace, imports it by name; lint rejects relative paths into `packages/*` or `apps/*` sources from `tests/**`.
- Every module is reachable from an entrypoint, a test, or a config (`no-orphans`), and there are no import cycles (`no-circular`).

## Website

```text
src/main.tsx ─► src/app ─► src/features/<name> ─► src/services ─► @recnrun/bridge
                   │              │
                   └──────────────┴──► src/ui
```

- `src/ui`: presentational components and pure helpers. It imports nothing from `features`, `services`, or `app`.
- `src/services/extension.ts`: the extension gateway, `createExtensionGateway()`, and the only module that imports `@recnrun/bridge`.
- `src/features/<name>`: state and views for one capability (`extension-status`). Features never import each other.
- `src/app`: composition. It picks the install banner or a short status from the extension state; when the extension is installed, the root page brings the dashboard tab forward and shows an **Open dashboard** button above the docs.
- `src/main.tsx`: mounts `App` with the real gateway. Nothing imports it.
- `privacy/index.html`: the privacy policy, a second build entry with no script. As its own file it gets status 200 on GitHub Pages at `/privacy/`, and the Chrome Web Store listing links to it. The site has no other routes: the dashboard keeps its own in its hash, so the build ships no `404.html` copy and an unknown path gets GitHub Pages' 404.

Components take the gateway or data as props, so component tests use a fake gateway.

`content` never imports `storage` or WXT's `storage` helper, and never touches `browser.storage`. `dashboard` never imports `content` or `background`: it asks the background to start a session, and renders the session into its own PiP window. `views` imports none of those, nor `storage`. `tabs` imports none of those, nor `views`, so it stays the one tab model. Every folder may import `ports`, type-only (`extension-ports-type-only`); `ports` imports only the domain (`extension-ports-are-contracts`), so a port never pulls an implementation along. There is no session page and no `src/session`: the session renders straight into the dashboard's PiP window, so the rule that isolated it went with the frame. The POC keeps to itself: `p2p` imports no other app folder (`extension-p2p-is-protocol`); `offscreen` imports neither `storage` nor WXT's `storage` helper, nor any page or `background` (`extension-offscreen-holds-only-the-link`), so the background alone decides and stores; `pairing` reaches the link only through the background (`extension-pairing-page-isolated`); `content`, `dashboard`, `tabs`, and `ports` never import `offscreen`, `pairing`, or `peers`, nor do `views` (`extension-poc-stays-out-of-the-main-flow`, `extension-views-shared`), so only the dashboard entrypoint injects the POC's `PeerServices`.

### Dashboard and session

The **dashboard** is the extension's own tab, never framed, with its route in the hash, `dashboard.html#/recordings/<id>` (`dashboard/hash-router.ts`): the extension serves files by path, so only the hash survives a reload. Back, Forward, and reload work through `hashchange`, and the dashboard titles its tab itself. Any number of tabs can show the dashboard. It lists the recordings and every browser tab, normal and incognito, but the extension's own pages, which are nothing to record (`tabs/open-tabs.ts`, kept current by the `tabs` and `windows.onFocusChanged` events). With no session, each tab offers Record. While a dashboard controls the session, the recorded tab shows its status and "The session floats in its own window" in every dashboard; without a controller, it offers Continue and Stop. Once the recorded tab closes, a "Closed tab" item takes its place, with the status and Stop only. Other tabs offer nothing until the session ends.

**Incognito.** The manifest sets `incognito: "spanning"`, so with "Allow in Incognito" on, one service worker and the dashboard in a normal window see incognito windows too (`windows.getAll` lists them, each tab with `incognito: true`); a tab is identified by `id`, `windowId`, and `incognito`. The dashboard asks `extension.isAllowedIncognitoAccess()`: without access it lists normal tabs under an "Enable Incognito Mode" banner (the list waits for the answer, so the banner never moves a Record button) whose **Open Extension Config** opens RECnRun's details (`tabs.create` on `chrome://extensions/?id=` + `runtime.id`, so dev and store builds alike), where the user turns the toggle on; Chrome offers no API to flip, scroll to, or highlight it. A failed read shows neither the banner nor the button, since it says nothing about the toggle; with access it offers "New incognito window" (`windows.create({ incognito: true })`), which starts no session. Record works on an incognito tab as on any other, and RECnRun never closes an incognito window. In spanning mode extension pages do not open in incognito windows, so recnrun.com in an incognito tab, like the toolbar icon there, opens the dashboard in a normal window. Incognito tabs show no favicon unless it is a `data:` image: loading its URL from the extension's normal context would send that context's cookies.

**Reload or turn off.** When Chrome reloads RECnRun (an update, a reload in `chrome://extensions`, or a toggle such as "Allow in Incognito") or turns it off, it closes every open dashboard tab, and its PiP window goes with it ([POC 7](POCS.md#poc-7-spike-on-the-top-level-dashboard)). After a reload `runtime.onInstalled` opens a fresh dashboard, which reads the new incognito access. No other tab changes: the content script adds nothing to the site, so an orphaned one leaves nothing stale on screen.

**Current tab.** The PiP window shows the current tab (the active tab of the focused browser window) apart from the recorded one (`views/SessionTabs.tsx`): favicon, title (its URL, or "Untitled tab", when it has none), the URL truncated with the full one as a tooltip, Incognito, and Recorded. When the focus is not on a browser window, as when the user clicks the PiP window or another app, it keeps the last tab shown, marked "Not in focus", until that tab closes. Chrome lists the Document PiP window as an always-on-top normal window, so the tab model leaves `alwaysOnTop` windows out. Switching tabs only changes what the window shows; the recorded `tabId` changes only by Record. The dashboard and the PiP read the same `TabSource` through `views/use-browser-tabs.ts`, which reads again once per burst of events and renders only when what it shows changed. Nothing about tabs is stored: titles and URLs, incognito ones included, live only in the pages' memory.

The **session** is one per profile, stored as `RecordingSession` (with the recorded `tabId`) in `storage.session`, which every view reads and watches; it is the shared state. The dashboard renders it straight into its own PiP window. Only Stop, in a dashboard or the PiP window, ends it, and the window then closes. Closing a tab, the recorded one included, never ends it. The extension has no toolbar popup, commands, or context menu items.

**Opening the dashboard.** The background keeps a dashboard tab in front of the user (`background/dashboard-opener.ts`, with Chrome behind `background/chrome-dashboard-browser.ts`). A dashboard tab is a non-incognito tab whose address, before its hash, is `dashboard.html`, found with `tabs.query`, which also sees a tab still loading through `pendingUrl`; the first is the lowest window id, then the lowest index. The toolbar icon (`action.onClicked`) focuses the first one, or opens one in the clicked window; from an incognito window, in the last focused normal window, or a new one, since extension pages do not open in incognito windows in spanning mode. `runtime.onInstalled`, at any reason, and `runtime.onStartup` put the dashboard first in the last focused normal window and focus it, moving a restored one to index 0 instead of opening another: Chrome restores a profile's windows before the worker starts, and `windows.onCreated` does not fire for them (POC 7). `windows.onCreated` gives a normal window the dashboard only when the profile has no other normal window, so Ctrl+N gets none. The opener runs one request at a time, so a second click finds the tab the first one opened. No API pins the icon to the toolbar (only the enterprise policy `toolbar_pin` can), so the dashboard reads `action.getUserSettings().isOnToolbar` through the `ToolbarPin` port (`dashboard/toolbar-pin.ts`) and, while it is false, shows a hint to pin RECnRun from the Extensions menu (`dashboard/PinHint.tsx`); `action.onUserSettingsChanged` hides it once pinned, and a failed read shows nothing.

**Control.** One dashboard at a time controls the session: the one holding the `recnrun-control` Web Lock (`views/view-locks.ts`), shared by the pages of one extension origin. Record and Continue take it with `ifAvailable`, so of two dashboards starting at once only one gets it; the other shows "Another RECnRun tab controls the session." The holder announces itself on a `BroadcastChannel` of the same name, and watchers queue a shared request to learn when it frees, since exclusive waiters would take it from each other. Chrome frees the lock when the holder's page goes, so closing or reloading the controlling dashboard tab gives up the control without a message; nothing else stores the controller, so no late message can bring it back.

With the lock, the dashboard opens the window itself, still within the click's user activation, copies its stylesheets into it, and renders the session there (`dashboard/control.ts`, `dashboard/start.tsx`): the window has the extension's origin, so it needs no frame. It then sends `start-session` with the tab id to the background, which creates the session unless one is stored (Continue keeps it), focuses the recorded tab and its window, and replies `{ ok: true }` (`background/session-requests.ts`). A session starts only on a tab that is still open: the background checks `tabs.get` before it writes, since a session whose tab is gone could only be stopped, and a stored session for a tab that closed while the click was in flight would otherwise show a "Closed tab" item with a running timer. When the tab is gone, the stored session is unreadable, or the write fails, it replies `{ ok: false, error }` and changes nothing: the dashboard awaits the reply, releases the lock on an error, and shows the error in the tab list, so no dashboard holds the control of a session that does not exist. When the window closes (its `pagehide`), by Stop or by the user, or cannot open, the dashboard releases the lock and sends `return-to-dashboard`, which focuses the dashboard's own tab. Closing the dashboard tab closes its window too. Closing the window never ends the session. Chrome drops a `BroadcastChannel` message still on its way to the opener when the window opens, so the dashboard announces the lock again once the window is up ([POC 7](POCS.md#poc-7-spike-on-the-top-level-dashboard)).

The background accepts session requests (`messaging/session-protocol.ts`) only from its own extension pages: the route table (`background/routes.ts`) names `ownPage` as their only sender, which the listener grants when `sender.id` is its own and `sender.url` starts with its own origin, ruling out content scripts on recnrun.com. Every accepted request gets a `BackgroundReplySchema` answer, which the dashboard validates before trusting it.

A workspace is the origin a recording starts on, derived when the dashboard renders; nothing stores it. Every view shares the recording through `storage.session` (POC 6E).

### Cross-profile POC (development and test builds only)

A proof of concept ([POCS.md](POCS.md#cross-profile-control-over-webrtc-october-2026), `POC-CROSS-PROFILE-WEBRTC.md` on branch `poc/cross-profile-webrtc-v2`) lets one profile's dashboard and PiP window list and control another Chrome profile's tabs and session, with no server: one WebRTC DataChannel between the two installations, paired by hand. Production builds leave all of it out (`peersEnabled(mode)` in `config/origins.ts`): the `entrypoints:resolved` hook in `wxt.config.ts` drops `offscreen.html` and `pairing.html`, the `offscreen` permission is added only for `development` and `test`, `background/start.ts` starts the peers only in those modes, and `manifest.checks.mjs` asserts the production output has neither page nor `createDocument` or `RTCPeerConnection`.

```text
pairing.html ─┐                     ┌─► offscreen.html (RTCPeerConnection, DataChannel)
dashboard ────┼─ runtime message ──► background ◄── link events ──┘        ▲
PiP session ──┘   { type: "peer" }   (peer-channel, pairing,               │ DTLS, host candidates
                                       executor, peers)           other profile's offscreen
```

- **Identity.** Each installation creates `{ profileId: crypto.randomUUID(), displayName }` once (`local:profileIdentity`); the extension id is the same in every profile and identifies nothing. The offscreen document keeps one DTLS certificate in the `recnrun-p2p` IndexedDB database (`p2p/certificate-store.ts`; version 2 adds the `folders` store beside `certificates`), so its fingerprint stays the profile's across restarts.
- **Pairing.** The pairing page asks the background, which asks the offscreen document, for a complete offer SDP (ICE gathering finished, no trickle, `iceServers: []`). It becomes a one-line code: `{ kind, pairingId, profileId, displayName, expiresAt, sdp }`, valid for five minutes. The other profile imports it and shows who made it and six digits derived from both certificate fingerprints; its user accepts, which stores the peer and answers. The first profile imports the answer, checks that it answers its own pending offer, shows the same six digits, and its user confirms. Accepting a new peer replaces the old one: one peer at a time.
- **The RECnRun folder.** One folder per machine, `Documents/RECnRun` by default, chosen in a popup window of the pairing page (`pairing.html#folder`, a top-level extension page; the framed dashboard cannot show the picker), which a dashboard banner opens while Chrome does not grant `readwrite` on it; after a restart the window asks Chrome again (`requestPermission`). The grant is a session grant that ends with the extension's last top-level page (the frame on the site does not count), so the window stays open, says so, and closes itself once the profiles pair (H2 in `docs/poc-cross-profile-usability-plan.md`). Its handle is kept in IndexedDB; it holds `pairing/` and `recordings/`, the latter reserved for M1. Choosing it is the consent to pair: `local:folderPairing` marks the profile as pairing through the folder and stays once paired, so the service worker, started with the browser by a `runtime.onStartup` listener, resumes and the pinned peer reconnects with no click. The dashboard shows the wait, or **Pair with another profile** or **Reconnect** when the profile stopped waiting. The offscreen document polls `pairing/` once a second, keeps `pairing/<profileId>/presence.json` (`profileId`, `displayName`, certificate fingerprint, one-minute expiry) fresh, and reports the others' presences and the signals addressed to this profile. The background (`background/folder-pairing.ts`) decides: the partner is the pinned peer, or else the profile that has waited longest; the lower profile id offers and the other answers, each through `<kind>-<pairingId>.json` holding the same code as manual pairing. A signal counts only when its code's kind, pairing id, and maker match its file, and its SDP fingerprint is the partner's. Each profile writes only into its own subfolder, atomically (`createWritable`), ignores files that expired, that exceed 128 KB, or whose `profileId` is not their folder's, and removes its files when the user disconnects or forgets the peer.
- **Authorization.** `local:authorizedPeer` pins `{ profileId, displayName, fingerprint }`. When the link connects, the background compares the DTLS-proven remote fingerprint with the pinned one and closes the link on a mismatch; until it matches, `session:peerLink.verified` is false and nothing is sent or accepted. Every frame is parsed with the closed `PeerMessageSchema` (envelope `recnrun-peer`, protocol 1, at most 256 KB) and accepted only when `from` is the authorized peer and `to` is this profile (`background/peer-channel.ts`). "Forget the other profile" removes the pinned peer and closes the link.
- **Messages.** `HELLO`, `PING`/`PONG`, `GET_TABS`/`TABS_SNAPSHOT`, `TABS_CHANGED` (one per burst of tab events, 150 ms), `ACTIVATE_TAB`, `SESSION_START`, `SESSION_SET_STATUS`, `SESSION_STOP`, `SESSION_STATUS`, `COMMAND_RESULT`, `ERROR`, and `BYE`, which Disconnect and Forget send before closing so that the peer shows "Disconnected by <name>", not a failure (`session:peerLink.reason`); "Error" is left for a certificate mismatch. Commands carry tab ids and statuses only; there is no message that runs code, reads a page, or reads storage.
- **Executor.** The profile that owns a tab runs every command on it (`background/executor.ts`): it shares only normal tabs, without favicons, and refuses a tab it does not list, a second session, and a session another controller started. It records which peer started its session (`session:remoteController`) and reports `SESSION_STATUS` on every change. The session is stored only there, as any local session.
- **Controller.** The other profile keeps the peer's tabs as last reported in `session:peerTabs`, so they outlive a sleeping worker, and its last `SESSION_STATUS` in `session:remoteRecording`, marked disconnected when the link drops; only the executor may say a session ended. Without a verified link, the peer's list stays as last seen, read only ("Not connected. Last seen recording."), and the PiP window of a session in the peer closes. With no peer paired, the dashboard is the local one plus a "Pair another profile" button; once paired, it lists this profile's tabs under "Chrome — <name> (Local)" and the peer's under "Chrome — <name> (<state>)", with Show tab and Record. Record opens the PiP window as for a local tab; the session page shows this profile's own session, or else the one it controls in the peer (`views/remote-peer.ts`).
- **One session across the pair.** Chrome shows one Document PiP window at a time across a browser's profiles, so opening one profile's PiP closes the other's. While a session runs in either profile, no list in either dashboard offers Record (`dashboard/peer-blocks.ts`): the status says whether the peer runs one (`peerSession`) and whether the peer controls the one that runs here (`controlledByPeer`, only while the link holds, so this profile's user can stop it once the peer is gone). Each blocked list says why: "Recording in <name>" or "Controlled from <name>". The controller still sees Continue and Stop for the session it runs in the peer. The rule is in the pages; a Record that races the peer's is refused by the executor only when it targets the peer.

## Bridge protocol v1

The website and the content script share a window, so they talk through `window.postMessage`. Every message is an envelope `{ channel: "recnrun", protocol: 1, kind, ... }`:

| Kind       | Sender         | Fields                                              |
| ---------- | -------------- | --------------------------------------------------- |
| `announce` | content script | `extensionVersion`; sent once on start              |
| `request`  | website        | `id`, `type`                                        |
| `response` | content script | `id`, then `ok: true, result` or `ok: false, error` |

Request types and their result schemas live in `RESULT_SCHEMAS` (`packages/bridge/src/protocol.ts`):

| Type             | Result                 |
| ---------------- | ---------------------- |
| `ping`           | `{ extensionVersion }` |
| `open-dashboard` | `{}`                   |

- **Detection.** `client.detect()` resolves `installed` on the first `announce` or `ping` reply, and `missing` after the timeout (1.5 s by default). Either signal is enough, so the order in which the page and the content script load does not matter.
- **Opening the dashboard.** `open-dashboard` goes to the same opener as the toolbar icon: it focuses the first dashboard tab, or opens one in the site tab's window. The website's root sends it once on load and again from its **Open dashboard** button; the privacy policy never does.
- **Validation.** The host answers only valid requests of a known type. The client validates every result against its schema and rejects with `BridgeError` on a timeout, an error reply, or a malformed result.
- **Versioning.** `protocol` changes only for an incompatible envelope or message change; adding a request type does not change it. `getSnapshot` was removed while still at protocol 1, because no version had been released.

Inside the extension, the content script forwards `{ type }` with `browser.runtime.sendMessage`; the background validates the type with the bridge's `RequestTypeSchema` and replies `{ ok: true, result }` or `{ ok: false, error }`.

## Security model

The extension holds the user's data and is the only code that reads or shows it; the website only detects the extension.

- **Where the content script runs.** Production builds match only `https://recnrun.com/*`, where the website lives. The project also owns recnrun.app, recnrun.io, and recn.run; they only redirect to recnrun.com at the Cloudflare edge and never serve a page, so the extension does not match them. `development` and `test` builds add `http://localhost/*` and `http://127.0.0.1/*` (any port) for the dev server and end-to-end tests. Every build excludes `/privacy/*` on those origins (`exclude_matches`): the policy needs no bridge, so RECnRun runs nothing there. `vp run test:extension-manifest` fails the build if a production manifest matches or excludes anything else.
- **Permissions.** Only `storage` and `tabs`, and `incognito: "spanning"`, which grants nothing until the user turns on "Allow in Incognito"; then the dashboard and the PiP window also show incognito tabs' titles and URLs, kept in memory only. `tabs` lets the dashboard list every tab's title and URL, and the background focus the recorded tab; Chrome warns "Read your browsing history" at install. It runs no script in those tabs and grants no access to their pages. No host permissions, no `externally_connectable`, no access to other sites. The same check (`apps/extension/scripts/manifest.checks.mjs`) asserts exactly this on the production manifest: `permissions` is `["storage", "tabs"]`; `host_permissions`, `optional_permissions`, `optional_host_permissions`, `externally_connectable`, `content_security_policy`, and `commands` are absent; `action` has no `default_popup`; `incognito` is `spanning`; `web_accessible_resources` is absent; and no content script sets `all_frames`, `match_about_blank`, or `match_origin_as_fallback`, so it runs only in the top frame of a real document on the matched origins.
- **No page can load an extension page.** The manifest has no `web_accessible_resources`, so Chrome blocks any web page, recnrun.com included, that frames or loads `dashboard.html`, and nothing can clickjack it (`tests/e2e/dashboard-embedding.spec.ts`). The dashboard opens only as its own tab.
- **Who may ask.** The `window` transport accepts only messages whose `source` is the page's own window and whose `origin` is the page's own origin, and replies only to that origin. Pages on other origins, other windows, and frames get no answer (`tests/e2e/origin-guard.spec.ts`).
- **What they can get.** Only the extension version: `ping` and `open-dashboard` are the only request types, and no bridge message carries the user's data. `open-dashboard` lets any script on recnrun.com bring the dashboard tab forward or open one; that moves the focus only, and the reply is empty. The content script is forbidden to touch storage, and the gates enforce it: with the `storage` permission a content script could read it, so `vp run deps` rejects an import of `src/storage` or of `wxt/utils/storage` from `src/content` (`extension-content-not-to-storage`), and `vp lint` rejects `browser.storage` there (`no-restricted-properties`). It can only relay known request types to the background, which checks that the sender is its own extension.
- **What the dashboard trusts.** Stored data is validated when the extension reads it and rendered as text.
- **Script injection on recnrun.com** could fake the site's content or send `open-dashboard`, so the website ships a strict CSP (`default-src 'self'`, no inline scripts or styles; `apps/website/build/content-security-policy.ts`). GitHub Pages sends no headers, so the CSP is a `<meta>` tag added to production builds only. Third-party scripts are not allowed on the website.
- **The cross-profile POC** (development and test builds only) adds the `offscreen` permission and the `offscreen.html` and `pairing.html` pages, neither web accessible. The background accepts `link` messages only from its own `offscreen.html` (`Sender` `offscreen`) and `peer` requests only from its own pages. Nothing crosses the link but the messages above: no cookies, storage, page content, or incognito tab; `tests/e2e/cross-profile-isolation.spec.ts` signs two users in to one site in the two profiles and finds neither token in the dashboards or in extension storage. The pairing codes and signal files hold SDP, the profile id, and the display name, no secret: the six digits and the pinned fingerprint authorize the peer.
- Adding a write request widens this model; the `adding-a-bridge-message` skill requires documenting it here first.

### Recording (not built)

Recording in the user's own applications needs more than `storage`. Whatever M1 settles on follows these limits:

- **Per-origin access, granted at run time** (optional host permissions and `permissions.request`), or `activeTab` for a one-off page; `tabs` reveals URLs, not page access. No install-time host permissions, and never `<all_urls>`.
- Recording scripts in the user's applications never answer the bridge; they only report events to the background.
- `apps/extension/scripts/manifest.checks.mjs` changes in the same commit, so the production manifest allows exactly the new permissions.

Findings from the bootstrap spike, kept here because they explain the configuration:

- **WXT on Vite+.** The workspace overrides `vite` with `@voidzero-dev/vite-plus-core`; WXT 0.21 builds on it unchanged. `import.meta.env.MODE` is available in `defineContentScript` options, which is how `origins.ts` varies matches per build mode.
- **WXT tests.** `vitest.config.ts` passes its own `root` to `WxtVitest`; without it, Vitest projects started from the repo root cannot resolve the `@/` alias. `.wxt/` is generated by `wxt prepare` (the root `prepare` script, and explicitly in `Dockerfile.tests`, because pnpm skips `prepare` when `node_modules` is current).
- **One TypeScript base.** `tsconfig.base.json` holds the compiler options every workspace shares (`strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `noFallthroughCasesInSwitch`, `erasableSyntaxOnly`, `noUnusedLocals`, `noUnusedParameters`, and the common module settings); the root, both packages, and the website extend it and declare only what differs. The root config includes only the root-level files (`*.ts`, `scripts`, `tests`), so `tsc -p tsconfig.json` checks them without swallowing the apps; the `node --test` check files await every top-level `test()` so the type-aware lint sees no floating promise. The extension extends WXT's generated `.wxt/tsconfig.json`, which already sets most of them, and adds the rest.
- **dependency-cruiser and TypeScript 7.** dependency-cruiser 18 supports TypeScript below 7, so it parses with SWC (`parser: "swc"`, `@swc/core`); type-only imports are still detected. Its tsconfig-paths plugin resolves `paths` from the working directory, so each app has a `tsconfig.deps.json` repeating its `@/` alias from the repo root, and `vp run deps` cruises each app with its own. npm packages are not followed but stay in the graph as leaves, so rules can name them (`not-to-dev-dep`, `extension-content-not-to-storage`); the `exclude` names only the workspaces' build output, since a pattern on `dist/` would also drop every package's own `dist/`.
- **WXT dev browser.** WXT 0.21 opens a browser only when its optional peer `web-ext` is installed; without it, `wxt` builds and asks you to load the extension by hand. `apps/extension` depends on `web-ext` for that reason. `wxt.config.ts` opens `http://localhost:5173/` (the website's fixed dev port) in a persistent profile under `.wxt/chrome-data`, which `vp run clean` deletes. It uses an absolute `chromiumProfile` with `keepProfileChanges` so Chrome and `web-ext` use the same profile. On macOS and Windows, Chrome protects the Developer mode preference and can discard values written directly to `Preferences`; Linux does not enforce this protection. Before WXT opens Chrome, the `server:started` hook calls `apps/extension/scripts/dev-chrome.ts`, which opens the same profile in headless Google Chrome, enables Developer mode through `chrome://extensions`, and closes it to save the protected preference. This also creates the profile after a clean and preserves its existing data. The preparation uses Playwright from the extension's own development dependencies (`@playwright/test`) and the installed Google Chrome, without downloading a browser; `tests/e2e/dev-chrome.spec.ts` covers it.
- **Knip and WXT.** Knip's WXT plugin expects `entrypoints/` at the package root; `knip.jsonc` lists `src/entrypoints` explicitly.
- **Docker is the reference Node.** `Dockerfile.tests` pins the Node that every public test command and `vp run verify` run on (`VP_NODE_VERSION`, 24.x); `engines.node` requires the same major (`>=24.0.0`), `@types/node` stays on 24, and `tests/container/runner.checks.mjs` fails when the two majors drift. On the host, `vp` installs a matching Node from `engines.node`; `vp env doctor` shows which.
- **Extensions need a headed Chromium.** Playwright and Vitest Browser Mode run headed; Docker provides the display, so no window opens on the host.
- **Coverage has a denominator.** `coverage.include` is a glob, so a narrowed include or a renamed folder would measure fewer files and still pass the thresholds. `scripts/coverage.checks.mjs` runs after Vitest in `test:coverage:local` and fails unless the files in `coverage/coverage-summary.json` (the `json-summary` reporter) are exactly the `.ts` and `.tsx` files under `apps/*/src` and `packages/*/src` minus the configured excludes: tests, `.d.ts`, and the entrypoints and `main.tsx`, which only call a `start*` function and run in the end-to-end suite. It globs the tree instead of `git ls-files` because the Docker build context carries no `.git`. The same script enforces a per-file floor (80% lines, statements, and functions; 75% branches, the former global thresholds) on every file with executable code, so the global averages cannot hide an untested module; files with no executable code (type-only `ports/*.ts`, the packages' `index.ts`, `bridge/transport.ts`) report `total: 0` and are skipped, which is why Vitest's own `thresholds.perFile` is not used.
