# Architecture

[PRODUCT_BRIEF.md](PRODUCT_BRIEF.md) describes what the product does. This document fixes how the code is split and which way dependencies point. `.dependency-cruiser.cjs` enforces every boundary below (`vp run deps`); change both together. The decisions behind it are [ADR 0001](adr/0001-local-service-over-cdp.md) and [ADR 0002](adr/0002-retire-extension-and-bridge.md).

## Target layout

The layout of [PLAN.md §4](plan/PLAN.md#4-target-layout). Workspaces stay `apps/*` and `packages/*`; arrows are allowed imports.

```text
apps/cli ──► apps/service ──► packages/engine ──► packages/protocol ──► valibot
   │              │              │    ▲
   │              │              ▼    │
   │              ├──► packages/adapter ──► playwright-core, CDP
   │              └──► packages/persistence ──► node:sqlite, node:fs, yaml
apps/ui ──► packages/protocol (types and schemas only), @recnrun/brand
apps/website ──► @recnrun/brand (landing and install guide; no engine code)
apps/fixture: the controllable test application; nothing imports it
```

| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- | ----- |
| `packages/protocol`    | Versioned schemas: flow DSL, locator lists, event envelope, run manifest, summary and coverage, capability matrix, service API, MCP shapes | `valibot`                                                                                                             | F0.2  |
| `packages/engine`      | Sessions, leases, steps, locator resolution, recorder normalization, function registry, macro runtime                                      | `protocol`                                                                                                            | F0.2  |

| `packages/persistence` | Flow folders, revisions, the JSONL journal, blobs by hash, the SQLite index, export and import, [bindings](#profile-bindings)              | `protocol`, `yaml`, `node:` builtins                                                                                  | F0.2  |
| `packages/brand`       | The Mona Sans font and the stylesheet every app imports                                                                                    | nothing                                                                                                               | M0    |
| `apps/service`         | The loopback HTTP and WebSocket API, locks, lifecycle, logs, the MCP stdio adapter; serves the built UI                                    | `engine`, `adapter`, `persistence`, `protocol`                                                                        | F0.2  |
| `apps/ui`              | The Preact SPA on localhost: catalog, recorder, editor, run, diagnostics                                                                   | `protocol`, `brand`, `preact`                                                                                         | F0.2  |

| `apps/website`         | The public landing at recnrun.com and the install guide                                                                                    | `brand`                                                                                                               | M0    |

- The engine never imports Playwright or CDP types. It defines the adapter interface (`BrowserAdapter`); `packages/adapter` imports that interface from `engine` and implements it, and `engine` never imports the adapter. The service wires the two together, so unit tests use a fake adapter and browser tests use the real one.
- Packages never import apps. Apps meet through `packages/protocol` and the service API; the only app that imports another is `apps/cli`, which starts `apps/service`.
- Packages export their TypeScript sources (`exports` → `./src/index.ts`); apps bundle them. A package `build` only type checks, and so do the Node apps (`service`, `cli`, `fixture`) until F7 bundles the CLI; `apps/ui` builds with Vite.
- `@recnrun/brand` holds no code: it exports `mona-sans.css`, which each app's entry imports, so the font and its license exist once. It imports nothing (`brand-is-leaf`).
- Every module is reachable from an entrypoint, a test, or a config (`no-orphans`), and there are no import cycles (`no-circular`).

Each workspace has one dependency-cruiser rule that lists what its `src` may import; anything else is a violation:

| `adapter-boundaries`         | `packages/adapter`     | itself, `engine`, `protocol`, `playwright-core`, `valibot`, `node:fs/promises`, `node:net`, `node:os`, `node:path`                                                   |

| `service-boundaries`         | `apps/service`         | itself, `engine`, `adapter`, `persistence`, `protocol`, `valibot`, `node:crypto`, `node:fs/promises`, `node:http`, `node:net`, `node:os`, `node:path`, `node:stream` |

## Protocol

`packages/protocol/src` holds one module per concept; `index.ts` re-exports them.

| Module                                             | Shapes                                                                                                                                                                                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `flow.ts`, `steps.ts`, `actions.ts`, `locators.ts` | The flow DSL: actors, inputs, requirements, preconditions, action, assertion, and builtin steps, targets                                                                                                                  |
| `interpolation.ts`                                 | `${env.*}`, `${inputs.*}`, `${vars.*}`, `${locals.*}`, and `${secrets.*}`; any other namespace is rejected                                                                                                                |
| `validate.ts`                                      | `validateFlow(input)`: the schema plus the cross-step checks, as `{ ok: true, flow }` or `{ ok: false, issues }`                                                                                                          |
| `discovery.ts`                                     | `DiscoveryResultSchema`: the endpoint found in `DevToolsActivePort`, or a failure code with its remedy; Chrome channels                                                                                                   |
| `events.ts`                                        | The event envelope of the journal (source plan §11), the gap record, and the adapter events (`connection.lost`, `control.contested`)                                                                                      |
| `connection.ts`                                    | The browser handshake (`Browser.getVersion` and the domain probe), CDP targets, the connection source, and the reconnect result                                                                                           |
| `instrumentation.ts`                               | The observer binding name, the hook version, observer messages (`document.hook-installed`), instrumentation events, and the report                                                                                        |
| `run.ts`                                           | `manifest.json`, `steps.json`, `coverage.json`, and `summary.json` of a run, with the exit code of each status                                                                                                            |
| `states.ts`                                        | Session, control, step, and pause states and their legal transitions (source plan §6); the three pause modes                                                                                                              |
| `lease.ts`                                         | A target's lease (holder, kind, fencing token, `acquiredAt`, `expiresAt` in epoch ms) and the fence a controlled request carries                                                                                          |
| `capabilities.ts`                                  | Capture surfaces, statuses, and the capability matrix                                                                                                                                                                     |
| `api.ts`, `api-commands.ts`                        | The request and response envelopes, error codes, and the params and result of every command (`SERVICE_COMMANDS`)                                                                                                          |
| `bindings.ts`                                      | Profile bindings, `bindings.json`, a binding's status (`fresh`, `stale-restarted`, `stale-missing`), and `parseBindingsFile`                                                                                              |
| `capture.ts`                                       | `CapturedEventSchema`: the raw DOM, network, console, error, navigation, and target events of F1.5                                                                                                                        |
| `network.ts`                                       | The network events (F3.1): headers with sensitive values `redacted`, timing, cache state, bodies inline or as blob references (`BodyRefSchema`, `isSha256`), and WebSocket frames flagged `truncated` with their encoding |
| `journal.ts`                                       | `events.jsonl` and `parseJournalEvent`, which validates one journal line for persistence                                                                                                                                  |
| `flow-folder.ts`                                   | A flow folder's `manifest.json` (current revision, status, history), `datasets/<name>.json`, and the revision hash                                                                                                        |
| `stored-files.ts`                                  | The catalog rows of the SQLite index, the flow store's error codes, `parseStored` for persistence, and `isId` for safe folder names                                                                                       |

The `if` block names its branches `steps` and `otherwise`, never `then`/`else`: an object with a `then` property is a thenable, so `await` or `return` in async code would treat a parsed step as a promise. The source plan's §9.3 example is adapted that way, with a comment in its fixture.

Each issue of `validateFlow` has a `code` (`unknown-action`, `unknown-namespace`, `duplicate-step-id`, `missing-input`, `cyclic-variable`, `nth-without-index`, and others in `FLOW_ISSUE_CODES`) and the `path` of the offending key from the flow's root.

The capability matrix lives in code (`capability-matrix.ts`, fed by `capability-surfaces.ts`, `capability-features.ts`, and `capability-roadmap.ts`). `vp run capabilities:generate` renders it to [CAPABILITIES.md](CAPABILITIES.md), and `vp run docs:check` fails when that file is stale. A capability status moves only with a test that shows the new behavior.

`vp run schema:generate` writes JSON Schema for the flow, the event, the adapter events, the discovery result, the browser handshake, the bindings file, the instrumentation event, report, and observer message, the captured event, the run files, the flow manifest and dataset, the capability matrix, the service envelopes, the lease, and the session status to `packages/protocol/schema/*.json` through `@valibot/to-json-schema`, and the files are committed. `tests/schema-drift.test.ts` fails when a schema changes without regenerating them. JSON Schema describes structure only: rules written as `v.check` (known interpolation namespaces, `nth` needs an index, the exit code matches the status) and the cross-step checks of `validateFlow` are enforced by the protocol code, not by the exported files. Only `src` must stay pure; `scripts/` and `tests/` use Node APIs to write and read those files.

## Engine

`packages/engine` holds the rules that need no browser: it imports only `protocol` and drives Chrome through the `BrowserAdapter` interface it defines, so its unit tests use a fake adapter.

- **Replay executor** (`src/replay/`, F2.5; F1.6 was its spike). `replayFlow(driver, flow, { env, inputs, secrets, defaultTimeoutMs, run, control, observe })` runs a flow's top-level steps in order through `ReplayDriver`, the part of `BrowserAdapter` replay needs: `inspect` (count, visibility, enabled, editable, text, and value of a target), `readAttribute`, `tabs` (the replay's tabs in opening order and the current one), and `act`, which dispatches one `DriverCommand` and answers `done`, `not-dispatched`, `failed`, or `unknown`. It covers the actions `navigate`, `reload`, `click`, `fill`, `type`, `select`, `check`, `uncheck`, `keyPress`, `scroll`, `openTab`, `selectTab` (a tab index, or the one tab whose URL or title equals or contains the text), `closeTab`, and `waitFor` (a target's `visible`, `hidden`, `attached`, or `detached` state, a URL, or both); the assertions `visible`, `hidden`, `textEquals`, `textContains`, `value`, `enabled`, `disabled`, `count`, and `url` (`*` matches any characters); and `extractText` and `extractAttribute`, which save `vars.<saveAs>`. `${env|inputs|vars|secrets.<name>}` resolves in URLs, values, targets, and expected text; an unknown name fails the step with `unresolved-variable`. Secret inputs and `secrets` come only from the caller for that run, and every secret value is replaced by `[redacted]` in results, evidence, events, and returned `vars`. A flow whose required input has no value, whose steps name more than one actor or an undeclared one (`multi-actor-unsupported`, until F4.3), or that has a builtin step ends `error` before any step runs, with every step `blocked`.
- **Wait policy and writes.** Each step has one deadline, its `timeoutMs` or `defaultTimeoutMs` (10 s). Reads (locating, assertions, `waitFor`, extraction) poll every `POLL_INTERVAL_MS` (100 ms) until their condition holds or the deadline passes; there is no `networkidle` and no recorded delay, and the result keeps the number of `attempts`. Every driver call, the tab list included, gets the time left and is bounded by the deadline; the list gives each title read half of that time and reads it as empty after it, so the URL it carries still answers before the deadline. A read that answers after the deadline is not believed, so a late match never passes a step, and a step whose reads never answered fails with `timeout`. A write first polls until its target is unique and actionable (or editable), then is dispatched exactly once with the time left: `not-dispatched` and `failed` fail the step with the driver's code, and `unknown` (dispatched, effect unknown, such as a click whose navigation timed out or a lost page) makes it `indeterminate`. A write that does not answer by the deadline, or answers after it, is `indeterminate` with `timeout`; the adapter also ends tab opening, switching, and closing and page key presses, which take no Playwright timeout, as `unknown` once their time is up. The executor never sends a write again. A step that does not pass stops the run; it moves through the F2.2 step machine (`pass`, `fail`, `outcomeUnknown`, `block`, `cancel`).
- **Run results.** Every result is a `StepResultSchema` entry with timestamps and `attempts`; a failed assertion carries `error.code` `assertion-failed` and the evidence `expected:` and `observed:`. The run is `passed` (exit 0); `failed` (exit 1) when the first failure blames the application (`assertion-failed`, `timeout`, `ambiguous`, `navigation-failed`, `not-actionable`); `error` (exit 2) for any other code or an `indeterminate` step; `interrupted` (exit 2) when the session stops. Given `run: { store, manifest }` (a F2.4 flow store's `createRun` and `finishRun`), it writes the manifest first, a `step.started` and `step.finished` journal event per step (`observe` sees each), and `steps.json`, `coverage.json` (no surfaces until F3.5), and `summary.json` at the end. Given `control`, it reads the session before each step and waits while `pauseReplay` holds it (`mayStartNextStep`), never mid-step; a session that stops or is no longer live cancels the remaining steps (`packages/engine/tests/replay-*.test.ts`, `tests/browser/replay.spec.ts`).
- **Sessions, control, leases** (`src/machine.ts`, `src/machines.ts`, `src/session.ts`, `src/lease.ts`, F2.2). The session (`start`, `pause`, `resume`, `stop`, `complete`, `interrupt`), control (`acquireManual`, `acquireAgent`, `acquireReplay`, `release`, `expire`, `takeControl`), step (`start`, `block`, `cancel`, `pass`, `fail`, `outcomeUnknown`), and pause (`pause`, `resume`) machines are transition tables; `sessionTransition(state, event)` and its siblings return `{ ok: true, state }` or `{ ok: false, error }` with an `illegal-transition` error, and every table reaches exactly the targets of the protocol's `*_TRANSITIONS`. A session holds its state and one pause machine per mode: `pauseSession`/`resumeSession(session, mode, now)` change only that mode, the session is `paused` while any mode is paused and `recording` again when the last resumes, and `createsSuggestedSteps`, `mayStartNextStep`, and `isCapturing` each read only their own mode (`pauseStepCreation` keeps capturing, `pauseReplay` is checked before each step, never mid-step). Resuming `suspendCapture` returns the gap (`capture-suspended`, `startedAt`, `endedAt`) for the journal. `createLeaseRegistry({ now, ttlMs })` grants exclusive control per target: a lease (`LeaseSchema`) has a fencing token that only grows for that target, `heartbeat` moves `expiresAt` to `now() + ttlMs`, `release` frees the target at once, and a lease past `expiresAt` authorizes nothing even before `tick(now)` sweeps it and reports it once. Another holder acquires only a free target (`lease-held` otherwise); `takeControl` is the explicit operation for a person and takes the target at once from an agent or a replay, never from another person. `authorize(targetId, fence)` checks the `leaseId` and `fencingToken` a request carries (`RequestEnvelopeSchema.lease`) and answers `stale-lease` for any other lease. The modules hold no timer; the service calls `tick` (`packages/engine/tests/{session,lease,pause}.test.ts`).
- **Normalization** (`src/normalization/`, F2.3). `normalize(events, options)` is a pure function from raw `CapturedEvent`s to `{ steps, excluded }` (`NormalizationResultSchema`): each `SuggestedStep` carries the refs (`id`, `producer`, `seq`) of the raw events it came from, and every event a rule set aside is listed in `excluded` with its reason. Events are ordered by timestamp, then producer and sequence. The rules, one golden pair each in `tests/normalization/*.json`:
  - **Exclusions.** Events with a replay `commandId` (all of them, or only `replayCommandIds`) are `replay-caused` and marked `replayCaused: true`; events on the recorder overlay (test id or id starting with `RECORDER_OVERLAY_PREFIX`) are `recorder-overlay`; untrusted DOM events come from page scripts and are `untrusted`. None of them is suggested; all stay in the journal as evidence.
  - **Actor.** A step's `actor` is the name `options.actors` gives the producer (its session), else the event's `profileBinding`; never `isTrusted` or the envelope's `actor`.
  - **Fill.** A run of key, input, and composition events on one text field, ended by blur, change, submit, navigation, or an interaction elsewhere, becomes one `fill` with the final value (`select` for a `<select>`); a late `change` joins it and a checkbox's `input`/`change` join its click. A redacted field becomes `fill` with `${secrets.<name>}` and `redacted: true`, never the value.
  - **Type.** When a special key (Enter, Tab, Escape, arrows, Home, End, PageUp, PageDown) or a shortcut comes before the run's last input, or the value is not what the typed data alone produces (autocomplete, masks), the run becomes `type` and `keyPress` steps in order. In such a run, Backspace and Delete are `keyPress` steps too, so a deletion after a cursor move is replayed where it happened (`type-deletion.json`); in a run that stays one `fill`, the value already holds them. A special key after the last input is its own `keyPress`.
  - **Shortcuts and keys.** A key held with Control, Alt, or Meta becomes `keyPress` with the combo (`Control+k`); outside a text field every non-modifier key is a `keyPress`, on no target when it reached the page body. The click with `detail: 0` that Enter or Space fires joins that `keyPress`.
  - **Composition.** `compositionstart` to `compositionend` adds only the committed text to the run, so IME input collapses into the resulting `fill` or `type`.
  - **Clicks.** A click joins the `pointerdown` and `pointerup` on its target. A second click on the same target within `dblclickWindowMs` (500) that the browser counted (`detail` ≥ 2 when reported) turns the step into `dblclick`, and the `dblclick` event joins it. A `pointerdown` and a `pointerup` on different targets become `drag`, with the click fired on their common ancestor.
  - **Navigation.** A main-frame navigation within `navigationWindowMs` (2000) of a click on a link or submit control, an Enter `keyPress`, a `submit`, or a previous navigate (a redirect) is `navigation-caused`; any other becomes `navigate`. Subframe navigations are ignored.
  - **Scroll.** Consecutive scrolls of one node merge into one `scroll` at the last position. A scroll is kept only when a network request starts before the next step (lazy loading) or a container (not the page) scrolls before an interaction (virtual lists); otherwise it is `scroll-dropped`, since replay scrolls targets into view. `keepScrolls` keeps them all.
  - **Locators.** `suggestLocators(target)` returns an `orderedFallback` list: `testId`, then `role` with its accessible name (only when the caller knows the name; the hook does not capture it yet), then `#id`, then `tag[name="…"]`, and a CSS selector of tag, type, and role only when none of those exists.

  `dblclick` and `drag` are suggestions without a flow action yet; the editor converts or rejects them.

  `toFlowSteps(suggestions)` turns suggestions into flow steps for `flow.finalize`: `navigate`, `click`, `fill`, `type`, `select`, and `keyPress` keep their id, actor, and value, and each locator list becomes its first candidate in the one-key form F2.5 replay resolves (`testId`, `css`, or `role` with `name` and `exact`); `dblclick`, `drag`, and `scroll` are left out, since replay has no step for them yet (`tests/flow-steps.test.ts`). `replayableAssertion(step)` narrows a drafted assertion's locator list, such as the one the picker answers, the same way, and leaves any other target as written.

## Adapter

`packages/adapter` is the only package that imports `playwright-core` or speaks CDP. `createCdpAdapter()` (`src/adapter.ts`) implements the engine's `BrowserAdapter` interface: `discover`, `connect`, `listTargets`, `reconnect`, `disconnect`, `onEvent`, and `describeProfile`, over one connection at a time: `connect()` while a connection is held (even a lost one) rejects with `AlreadyConnectedError` (`code: "already-connected"`) until `disconnect()`, and `connect`, `reconnect`, and `disconnect` run one after another through a single promise chain, so they never interleave. The [F1 spike report](spikes/2026-11-f1-cdp-connection.md) lists the versions, proofs, and observed limits behind this section.

- **Discovery** (`src/discovery.ts`, F1.1). `discover({ userDataDir?, channel? })` reads `<userDataDir>/DevToolsActivePort`, which Chrome writes when remote debugging is on: line 1 is the port (1 to 65535), line 2 the browser path (`/devtools/browser/<id>`). It answers `{ ok: true, wsEndpoint: "ws://127.0.0.1:<port><path>", userDataDir, source: "active-port-file", port, path }`, or `{ ok: false, code, remedy, userDataDir }` with `missing-file`, `malformed-file`, or `stale-file` (the port does not accept a TCP connection on 127.0.0.1 within 500 ms, as after Chrome crashed). Every remedy says to enable remote debugging at `chrome://inspect/#remote-debugging` and keep Chrome open. `DiscoveryResultSchema` in `packages/protocol` is the shape, so the service and `doctor` reuse it.
- **Default user-data dirs.** Without `userDataDir`, the channel (`stable`, `beta`, `dev`, `canary`) picks the folder Chromium uses: macOS `~/Library/Application Support/Google/Chrome` (`Chrome Beta`, `Chrome Dev`, `Chrome Canary`); Windows `%LOCALAPPDATA%\Google\Chrome\User Data` (`Chrome Beta`, `Chrome Dev`, `Chrome SxS`); Linux `$CHROME_CONFIG_HOME`, else `$XDG_CONFIG_HOME`, else `~/.config`, then `google-chrome` (`google-chrome-beta`, `google-chrome-unstable`, `google-chrome-canary`). The platform, environment, file reader, and port probe are options, so unit tests run on temporary directories.
- **Connection** (`src/connection.ts`, F1.2). `connect(endpoint, { source, onEvent })` first sends `Target.getTargets` on a raw browser-level WebSocket of its own (`src/raw-cdp.ts`, Node's global `WebSocket`, no import), then opens Playwright `connectOverCDP` and a browser CDP session (`src/playwright-transport.ts`). The handshake (`src/handshake.ts`) reads `Browser.getVersion` and probes each domain of `CDP_PROBE_DOMAINS` with a side-effect-free command: `Target` on the browser session, the others on a CDP session of ours on the first page, detached afterwards. A domain is `unavailable` only when Chrome answers that the method `wasn't found`; any other answer means the domain exists and is recorded as the `reason`. Every CDP entry point (`connect`, the preflight, the Playwright transport, `instrument`, and the instrumentation socket that function locators reuse) first checks `isLoopbackEndpoint` (`src/loopback.ts`): only `ws:` on `127.0.0.1`, `[::1]`, or `localhost` passes, and anything else is rejected with `NonLoopbackEndpointError` (`code: "non-loopback-endpoint"`) before a socket exists.
- **Loss and reconnection.** When the socket drops without `disconnect()`, the adapter emits one `connection.lost` event whose `gap` is a journal gap payload (`reason: "connection-lost"`, `startedAt`, the last `seq` seen); writing it to a run's `coverage.json` comes with runs (F3.5). `reconnect()` runs discovery again on the same `source` (`userDataDir` or `activePortFile`) and connects only when that `DevToolsActivePort` answers again; otherwise it returns `endpoint-gone` with discovery's remedy. Adapter events carry one producer `seq` across reconnections.
- **Contested control.** CDP marks a target `attached` while any client holds a session, and fires `targetInfoChanged` only for the first one. Before Playwright attaches, the preflight `Target.getTargets` therefore shows exactly the pages another debugger holds; each yields `control.contested` (`signal: "attached-before-connect"`) at connect and at each reconnect, and RECnRun never detaches the other client. A debugger that attaches after RECnRun (DevTools opened later) changes neither the flag nor any event, so it goes unreported: the capability is `partial` (M-F1.d).
- **Instrumentation** (`src/instrumentation.ts`, F1.4). `instrument(endpoint, { onEvent })` opens a browser-level CDP socket of its own (`src/cdp-socket.ts`, flatten mode, so child sessions are reached by `sessionId`; a socket that errors, closes, or has not opened within 5 s rejects with `CdpOpenError`, `code` `refused`, `closed-before-open`, or `open-timeout`) and sends `Target.setAutoAttach` with `autoAttach`, `flatten`, and `waitForDebuggerOnStart`, which attaches every existing target and holds every new one before its first script. For each attached `page` or `iframe` it sends, in order, nested `Target.setAutoAttach`, `Page.enable`, `Page.addScriptToEvaluateOnNewDocument` with the hook (`src/hook-source.ts`), `Runtime.enable`, `Runtime.addBinding` (`__recnrunObserver`), and then `Runtime.runIfWaitingForDebugger` only when Chrome held the target (`before-first-script`); a dedicated worker gets nested auto-attach, `Runtime.enable`, and the binding, a service worker `Runtime.enable` and the binding, and every other target type is only resumed (`ignored`). The commands go out in one burst without awaiting replies: a session runs them in order, and a held worker answers nothing until it is resumed. A target already running at connect is `late`, and no resume is sent. `runImmediately` hooks any document that already has a script context: a late target's current document, or a popup's `about:blank`, whose context exists as soon as `window.open` returns and may predate the hook when another client (Playwright, DevTools) resumed the popup first, since Chrome releases a held popup on the first client's resume.
- **The hook.** It runs in the page's main world before the application's first script, defines a frozen `window.__recnrunHook` (`version`, `installedAt`, `documentId`, 32 random hex digits per document), and posts `document.hook-installed` with its URL through the binding, numbered by a per-document `seq`. When the binding is not there yet (a late target), an accessor queues messages until `Runtime.addBinding` assigns it, since V8 installs a binding with an ordinary set. Chrome gives a popup opened with `window.open` the script context of its initial `about:blank` document again for its first same-origin document, without running new-document scripts: the hook is therefore already in place there, and it starts the new document's `documentId` and posts its install the first time `__recnrunHook` is read in it. The collector reads it in every context of a frame on each `Page.frameNavigated`, and holds that context's console and error events until the install or the read answers (at most 2 s), so a log the new document writes before anything else reads the hook never carries the `about:blank` document.
- **Validation and drops.** A binding payload longer than 64 KiB, not JSON, or not an `ObserverMessageSchema` message increments `droppedInvalid`; one from an execution context CDP never announced on that session, or claiming another target id, increments `droppedUnknownFrame`. An accepted message becomes an `InstrumentationEvent` with `targetId`, `sessionId`, `frameId` (from the context's `auxData`, `null` in a worker), `documentId`, the install mode, and a `seq` per source (one attached session). `report()` lists every attached session with its install mode, `hookInstalled`, `hookInstalls`, both drop counters, `detached`, and the first failed install command, and says whether dedicated and service workers were observed as targets. Chrome can attach one target more than once (a service worker through the browser and through its page), so the report is per session. Nothing is captured inside workers yet (F6.2); the journal is written by capture, below.
- **Raw capture** (`src/capture.ts`, F1.5). `instrument(endpoint, { capture: { runId, onEvent, bodyTimeoutMs?, maxBodyLength?, blobs?, redactHeaders? } })` extends the same install, never a second one: each `page` and `iframe` also gets `Network.enable` and `Log.enable` before it resumes. Every observation becomes a `CapturedEvent` with the journal envelope (source plan §11): a `producer` per CDP session (`cdp:<sessionId>`, with that session as `source`) or `cdp:browser` for target lifecycle, a `seq` per producer, `id` `<producer>#<seq>`, and the `targetId`, `frameId`, and `documentId` it came from; the document is learned from the hook's messages per execution context. A draft that fails `CapturedEventSchema` is dropped, counted in `report().capture.dropped`, and leaves a hole in its producer's `seq`. Categories: `dom` (hook messages, `Page.javascriptDialogOpening`/`Closed`), `network`, `console` (`Runtime.consoleAPICalled`, `Log.entryAdded`), `error` (`Runtime.exceptionThrown`), `navigation` (`Page.frameNavigated`, `navigatedWithinDocument`), and `target` (`attached` with its install mode and opener, `detached`, `hook-installed`). Lines and columns are 1-based, and console arguments are serialized as text at capture time, at most 32 of them, each clipped to 1,024 characters. The adapter writes no file: the caller passes events to persistence.
- **Network** (`src/capture-network.ts`, F1.5 and F3.1). `request` (with the cumulative `redirectChain` of every hop's URL, method, and status), `response`, `finished`, `failed`, and one `body` per response with a condition: `captured` or `truncated` (over `maxBodyLength`, 64 KiB by default and clamped to `MAX_INLINE_BODY_LENGTH`, the 64 KiB the journal schema allows inline, with the full size), read with `Network.getResponseBody` after `loadingFinished` only for `Document`, `XHR`, and `Fetch`; `not-requested` for other resource types; `unavailable` with a reason when Chrome has no body, loading failed, the response was still loading after `bodyTimeoutMs` (10 s by default), Chrome did not answer `Network.getResponseBody` within another `bodyTimeoutMs`, the target went away, or capture stopped. Whichever settles a body first wins: a reply that arrives later is ignored, and `settled()` never waits for it. With a `blobs` sink (a `BodySink`, such as persistence's blob store), the adapter hands it the body's bytes (UTF-8 text, or decoded base64 as `binary`) once Chrome answers, and the `body` event carries the returned `BodyRef` and its condition instead of the text; a sink that fails leaves the body `unavailable` with the reason. `request`, `response`, and the WebSocket handshake carry their headers after redaction (`src/capture-network-evidence.ts`): `SENSITIVE_HEADERS` and the session's `redactHeaders` are replaced with `redacted` before the event exists, so no original value reaches the journal, a log, or a blob, and other values are clipped to `MAX_HEADER_VALUE_LENGTH` with `headersTruncated`. A response also has its `cache` (`network`, `memory` from `Network.requestServedFromCache`, `disk`, `service-worker`, or `prefetch`, with `fromCache` when not `network`) and the resource `timing` fields the schema knows. WebSockets (`src/capture-websocket.ts`) record `websocket-created`, `websocket-handshake`, one `websocket-frame` per frame each way with its opcode, `encoding` (`utf8` for text, `base64` otherwise), full `size`, and a payload clipped to `MAX_FRAME_PAYLOAD_LENGTH` with `truncated`, then `websocket-error` and `websocket-closed`.
- **DOM capture in the hook** (`src/hook-dom.ts`). The hook listens on `window` in the capture phase, passively, for `DOM_EVENT_TYPES` (pointer, click, keyboard, input, change, composition, selection, focus, scroll, and submit) and posts each as an observer message of kind `dom` with its target (tag, `id`, `data-testid`, `name`, `role`, `type`) and details. A password field never reports keys, data, or values (`redacted: true`); scroll is debounced per scrolled node to one event with the final position after 100 ms of quiet; a failure inside a listener is swallowed so the page never sees it.
- **Session scope** (`src/recording.ts`, `src/instrumentation-scope.ts`, F2.6). `startRecording(endpoint, { capture })` opens a CDP socket, creates the session's own `about:blank` page with `Target.createTarget` before it auto-attaches, and instruments with a `TargetScope`: a top-level `page` is admitted when it is that page or its `openerId` is an admitted page (popups, recursively), and a frame or worker when it was attached through an admitted target's session. Every other target, the person's other tabs and browser-level service workers included, gets no hook, no binding, and no capture event: a held one is resumed, then each is detached with `Target.detachFromTarget` (`tests/recording.test.ts`; `tests/browser/scope.spec.ts`: tabs opened before and after the session produce no events while the session's page and its popup do). The returned `Recording` adds the page's `targetId` to the instrumentation handle.
- **Picker** (`src/picker.ts`, F2.6). `startPicker(endpoint, targetId, { onPicked })` opens a socket of its own (so its `Target.attachToTarget` never reaches the recording's instrumentation), attaches a flat session to the page, and turns on Chrome's own inspect mode there (`DOM.enable`, `Overlay.enable`, `Overlay.setInspectMode` with `searchForNode`), which outlines the element under the pointer in the brand's blue. The renderer takes mouse input before dispatching it, so no application listener runs, window and document capture listeners included, and the recording's hook sees no DOM event (`tests/browser/picker.spec.ts`). The inspect overlay covers the whole viewport, so a click over a cross-site frame reaches none of that frame's listeners either; Chrome then picks in the top document, not inside the frame. Chrome picks on any mouse button. Each `Overlay.inspectNodeRequested` on the picker's own session is described with `DOM.describeNode` and reported as a `DomTarget` (tag, id, test id, name, role, type) validated with `DomTargetSchema`; Chrome reports the node, so the page cannot forge a pick. `stop()` ends inspect mode and closes the socket, which also ends it.
- **Valibot.** The adapter validates every CDP reply it reads (`Target.getTargets`, `Browser.getVersion`, raw socket messages), every CDP event the instrumentation handles, and every binding message with the protocol schemas, which is why `adapter-boundaries` allows `valibot`.
- **Node built-ins.** Discovery is why `adapter-boundaries` allows `node:fs/promises` (read the file), `node:net` (probe the port), `node:os` (the home folder), and `node:path` (Windows and POSIX joins); no other built-in. The adapter only reads Chrome's file; persistence still owns RECnRun's own files.
- **Profile description** (`src/profile.ts`, F1.3). `describeProfile()` answers `{ userDataDir, browserContextIds, chrome }` for the current connection: the folder comes from the connection's `source` (a `userDataDir`, or the folder of an `activePortFile`), the contexts from `Target.getBrowserContexts` (its `browserContextIds` and `defaultBrowserContextId`) plus the `browserContextId` of every target, and `chrome` is the handshake's `Browser.getVersion` product. It is what a binding is created and refreshed from.
- **Replay** (`src/replay.ts`, `src/replay-act.ts`, `src/replay-tabs.ts`, `src/replay-page.ts`, F1.6, F2.5). The adapter implements the engine's `ReplayDriver` over Playwright. Replay owns its tabs per connection: the first write opens one in the default browser context (`CdpLink.openPage`), `openTab` opens another, popups they open join the list, and closing the current tab makes the last open one current; reads never open a tab, and a new connection starts with none. A target is a CSS string or a one-key shorthand (`testId`, `role` with `name` and `exact`, `text`, `label`, `css`, `xpath`) mapped to a Playwright locator, which fails on more than one match (`ambiguous`); locator lists, explicit strategies, and functions are rejected as unsupported until F4A. `inspect` and `readAttribute` read with the timeout the executor passes. `click`, `check`, and `uncheck` run a Playwright trial first, so a failure before dispatch is `not-dispatched`, then dispatch once; `fill`, `type` (`pressSequentially`), `select` (by option value or label, refused as `not-actionable` when the select has no such option), `keyPress`, and `scroll` (`scrollBy` on the page or element, or `scrollIntoViewIfNeeded`) use Playwright's own actions, so Chrome dispatches trusted input events and nothing assigns `.value`. `navigate`, `reload`, and `openTab` wait for `load`, never `networkidle`. After dispatch, a `net::ERR_` error is `failed` (`navigation-failed`) and any other error, a timeout included, is `unknown`; messages keep only the first line of Playwright's error.
- **Function locators** (`src/function-locator.ts`, F1.7). `resolveFunctionLocator(target, request)` runs a JavaScript locator function on a page target, reached through a CDP session already attached to it (`{ session, targetId }`) or a browser endpoint (`{ endpoint, targetId }`, which attaches a flat session of its own and closes it on `release()`). The request (`FunctionLocatorRequestSchema` in `packages/protocol`) has the function's `source`, a `cardinality` (`index` for `nth`), `timeoutMs`, and optional `frameId` (the main frame by default) and `args`. The function runs in the isolated world `__recnrun_locator` of that frame (`Page.createIsolatedWorld`), so it shares the DOM but not the page's globals, and is called as `fn({ root: document }, args)` with `Runtime.callFunctionOn`, `returnByValue: false`, `awaitPromise: true`, and an object group per resolution. It may return an element, an array, NodeList, or HTMLCollection of elements, or `null`/`undefined` (no element); anything else, or an item that is not an element connected to the frame's document, is `unsupported`, and a throw is `error` with the exception's first line. Each element becomes a reference (`ElementReferenceSchema`): `targetId`, `frameId`, the frame's `loaderId` (CDP's document id), the remote `objectId`, and `backendNodeId` from `DOM.describeNode`, which outlives the session; an element returned twice counts once. Cardinality then answers `matched`, `not-found`, or `ambiguous`: `one` needs exactly one, `optional` zero or one, `many` at least one, `nth` the element at `index`. Every handle a result does not hand out is released at once (`Runtime.releaseObject`, or `Runtime.releaseObjectGroup` when nothing matched), and `release()` frees the matched ones. One `timeoutMs` covers every step that can run code the locator controls: the call, the conversion of what it returned (an array's own iterator or a proxy's getters run there), and the description of each element; once it passes, the resolution sends nothing more on its own, so a late result is never converted, and its object group is released again when it arrives, even after `release()`. Past it the adapter probes the renderer with `Runtime.evaluate("1+1")`; when it does not answer within the probe timeout (1 s), synchronous code is blocking it, so `Runtime.terminateExecution` goes out on the same session and the probe runs again. The result is `error` with `deadline: { timeoutMs, blocked, terminated, tabResponsive }`; Google Chrome 156 terminated `while (true) {}`, an array whose iterator loops, and a proxy whose `length` getter loops, and the tab answered again without being closed (`tests/browser/function-locator.spec.ts`). A promise that never settles leaves the renderer idle, so nothing is terminated. Releases wait at most one probe timeout, since a renderer still blocked answers nothing. The request and `FunctionLocatorResultSchema` are exported to JSON Schema (`function-locator-request`, `function-locator-result`). Engine integration (locator lists, shared deadlines, registered functions) is F4A.1 and F4A.3.

## Profile bindings

A flow names portable actors (`a`, `solicitante`); a profile binding ties a friendly name the user chose to one Chrome profile on this machine (PLAN.md F1.3, source plan §7). Bindings are local configuration: they live in `~/.recnrun/bindings.json` and never in a flow folder or an export.

- **Shape** (`packages/protocol/src/bindings.ts`). `ProfileBindingSchema` has `name`, `userDataDir`, `wsEndpoint` (last seen), `browserContextIds` (observed), `chrome` (the `Browser.getVersion` product), `createdAt`, and `lastSeenAt`. `BindingsFileSchema` is `{ schemaVersion: 1, bindings }` with unique names. The service command `profiles.list` returns these bindings.
- **Store** (`packages/persistence/src/bindings-store.ts`). `openBindingsStore({ home })` reads `<home>/.recnrun/bindings.json` (absent means no bindings) and validates it with `parseBindingsFile`, so persistence needs no Valibot. `save` adds a binding or replaces the one with its name; `remove` drops one. Every write goes to a temporary file in the same folder and is renamed over the target, with the file at mode 0600 and the folder at 0700. A file that is not JSON or not a bindings file is reported as a `BindingsFileError` naming its path, and no write replaces it. Each store instance runs its saves and removes one at a time through a single promise chain, so concurrent calls never lose a binding. One store instance per process owns the file; ownership across processes is the service's single-instance lock (F2.1).
- **Rules** (`packages/engine/src/bindings.ts`, pure). `detectDuplicateBinding` finds another name that already holds the candidate's `wsEndpoint` or `userDataDir`. `classifyBinding(binding, discovered, handshake?)` answers `fresh`, `stale-restarted` (the discovered `/devtools/browser/<id>` path or the Chrome version differs from what the binding recorded, with the new endpoint), or `stale-missing` (discovery failed, with its remedy). A stale binding is reported for the user to reconfirm; nothing remaps it to whatever Chrome answers now. `resolveActorBindings(flow, bindingByActor)` maps every actor the flow declares or uses, nested steps included, to a binding name, or fails with the first actor that has none.
- **Isolation.** The profile is the isolation boundary: two Chrome instances on two user-data dirs share no cookies or storage (`tests/browser/profiles.spec.ts`). The same test shows that a restarted Chrome gives the default browser context a new id, so `browserContextIds` are recorded as observed and never used to recognize a profile; the user-data dir and the reconfirmed name do that. Two profiles inside one Chrome instance are not automated (M-F1.c in [MANUAL_VALIDATION.md](plan/MANUAL_VALIDATION.md)).

## Persistence

`packages/persistence` is the only package that writes RECnRun's files. Besides the profile bindings above:

- **Journal** (`src/journal.ts`, F1.5). `openJournal(path)` creates the folder and appends one JSON line per event, validated with `parseJournalEvent` and written in call order; `close()` waits for pending lines, syncs, and closes. Reopening a journal whose last line was cut off (a crash mid-write) drops that partial tail before appending. `readJournal(path)` returns the events, and a partial last line as a `journal-truncated` gap with the last `seq` read and the bytes dropped; a complete line that is not an event fails with `JournalFileError` naming its line, and an absent file reads as empty. `events.jsonl` lives in the run folder below.
- **Blobs** (`src/blobs.ts`, F3.1). `openBlobStore({ folder, maxBytes? })` keeps response bodies content-addressed: `put(bytes, { mime, encoding })` cuts the bytes to `maxBytes` (`DEFAULT_MAX_BLOB_BYTES`, 1 MiB) before hashing or writing anything, writes them once to `<folder>/<sha256>` (a temporary file hard-linked into place, mode 0600 in a 0700 folder, so the same body stored twice is one file), and returns a `BodyRef` whose `size` is the whole body and whose `condition` is `truncated` when the cap cut it. `read(sha256)` refuses a name that is not a lowercase sha256 (`invalid-name`), reports a missing file as `not-found`, and checks the bytes against their name (`corrupt`), each a `BlobStoreError` naming the path, never the content.
- **Flow folders** (`src/flow-store.ts`, F2.4). `openFlowStore({ home })` keeps each flow in `<home>/.recnrun/flows/<flowId>/` (source plan §12): `flow.yaml` (the current flow), `manifest.json` (`FlowManifestSchema`: id, name, current `revision`, `status` of `draft`, `recorded`, `validated`, `incompatible`, or `needs-review`, `createdAt`, `updatedAt`, and the `revisions` history, oldest first), `requirements.md` (written from the flow's requirements on every save; edit the flow, not this file), `datasets/<name>.json` (`DatasetSchema`: input values, never secrets), `revisions/<hash>.json`, and `runs/<runId>/` with `manifest.json`, `events.jsonl`, `steps.json`, `coverage.json`, and `summary.json`. Flow ids, run ids, and dataset names are slugs (`IdSchema`), so none can name a path outside its folder. The store's methods are `list`, `get`, `saveFlow`, `listRevisions`, `getRevision`, `saveDataset`, `getDataset`, `createRun`, `finishRun`, `getRun`, `listRuns`, `rebuildIndex`, and `close`; its writes and `get` run one at a time per store instance.
- **Canonical form and revisions.** A flow's canonical JSON is the validated flow (defaults filled in) with object keys sorted by code unit at every depth, arrays in their order, no `undefined`, and no whitespace; its revision is the sha256 hex digest of that text. `flow.yaml` holds the same flow in the schema's field order, with no folded lines and no anchors, so writing, reading, and writing again gives the same bytes. `saveFlow` validates the flow (`validateFlow`), writes `revisions/<hash>.json` with exactly the canonical bytes, then `flow.yaml` and `requirements.md`, and last `manifest.json`, which makes the revision current; a save that changes neither the flow nor the status writes nothing. `get` answers the revision `manifest.json` names, read from `revisions/`, never `flow.yaml`, and refuses a manifest of another flow (`invalid`). A save cut short before its manifest leaves `flow.yaml` at a stored revision the manifest does not commit, or missing: `get`, and a save that changes nothing, write `flow.yaml` and `requirements.md` back from the committed revision. A `flow.yaml` whose content no stored revision holds is a person's edit and is left alone. A revision is written with `link()`, which never replaces a file: a hash whose file holds other bytes throws `revision-conflict`, and `getRevision` checks that the bytes still hash to the name (`revision-mismatch`). A run's `manifest.json` names its `flowRevision`, and `createRun` refuses a revision the folder does not hold.
- **Atomic writes and errors.** Every file but the journal, the revisions, and the blobs is written to a temporary file beside it and renamed over it, so a crash leaves the old file or the new one and no temporary file stays behind. Everything read back is validated with the protocol (`parseStored`, `validateFlow`, `parseJournalEvent`); a file that is missing, unreadable, not JSON or YAML, or not the expected shape is a `FlowStoreError` with a `code` (`FLOW_STORE_ERROR_CODES`) and the `path`. `createRun` writes the run manifest and opens the run's journal; `finishRun` writes `steps.json`, `coverage.json`, and last `summary.json`; `getRun` reads them back with the journal, whose truncated last line comes back as a `journal-truncated` gap.
- **SQLite index.** `<home>/.recnrun/index.sqlite` lists flows (id, name, status, revision, updatedAt) and runs (id, flowId, revision, status, startedAt, finishedAt; a run without `summary.json` is `running`), plus the files the last rebuild skipped. It is a cache: `rebuildIndex()` scans the folders and replaces every row in one transaction, `openFlowStore` rebuilds an index that is missing or of another version (`PRAGMA user_version`), and each store write updates its rows after the files. A flow whose `manifest.json` is corrupt, or a run whose files are, is skipped and reported in `list().problems`; the other flows still list. The index uses `node:sqlite` (`DatabaseSync`), built into Node.js since 22.13 without a flag, and the runtime matrix requires 22.18 or later, so there is no JSON fallback (Node.js 22.22 still prints an `ExperimentalWarning` when the module first loads).
- **Crash recovery** (`src/recovery.ts`, `src/interrupted-run.ts`, F3.6). `recoverRuns(store, now)` closes every run the index lists as `running`: it appends to its journal, as producer `service:recovery`, a `journal-truncated` gap when the last line was cut off and a `producer-restarted` gap with the last `seq` read, then writes `steps.json`, `coverage.json` (no surfaces), and an `interrupted` summary (exit 2) ending at the last journal event. Each top-level step keeps its journaled `step.finished` result; one with a `step.started` and no `step.finished` is `indeterminate` (`run-interrupted`) unless it only reads the page (`isReadOnlyStep`: an assertion, `waitFor`, `extractText`, or `extractAttribute`), which is `cancelled` like every step that never started. Nothing is re-executed. A run it cannot read stays `running` and is reported in `problems`.
- **Service state** (`src/service-state-store.ts`, F2.1). `openServiceStateStore({ home })` reads and writes `<home>/.recnrun/service.json` (atomic rename, mode 0600, folder 0700; validated with `parseServiceState`, and a file that is not a service state reads as absent) and owns the single-instance lock `service.lock`: `createLock` stages the lock and hard-links it into place, so it fails when one exists; `readLock` answers `absent`, `invalid`, or `held`; `removeLock(nonce)` removes it only while it still carries that nonce: the remover first creates an exclusive claim file for that nonce (a claim older than 10 s belongs to a dead remover and is superseded by the next attempt), then renames the lock aside and checks the moved file's nonce, linking it back when a remover that outlived its claim moved a newer owner's lock, so two starters that saw the same stale lock never delete the lock that replaced it. `removeState(pid)` likewise removes `service.json` only while it names that pid.
- **Rotating log** (`src/rotating-log.ts`, F2.1). `openRotatingLog({ folder, name, maxBytes, keep })` appends lines in call order to a 0600 file and, when the next line would pass `maxBytes`, shifts `name` to `name.1` up to `name.<keep>`, dropping the oldest.

## UI

`apps/ui` (`@recnrun/ui`) is the Preact SPA the service serves on localhost (F2.6). It mirrors the website's layers, with one more for the service client:

```text
src/main.tsx ─► src/app ─► src/features/<screen> ─► src/ui
                                     │
                                     └─────────► src/api
```

- `src/ui`: presentational primitives (button, badge, card, field, loading, empty and error states); props in, markup out (`ui-presentational`).
- `src/api`: the service client; it renders no screen (`ui-api-headless`). `api.ts` reads the bearer token from `<meta name="recnrun-token">`, which the service injects into the page it serves, and builds an `Api` of `call`, `on`, and `onOpen`. `http.ts` sends each command as a `POST /api` request envelope with `Authorization: Bearer <token>` and validates params before sending and the response envelope and result after; a failure is an `ApiError` with the service's error code, or `unreachable` (no answer, or an answer with no JSON body, such as a 404 from a server that is not the service) or `invalid-response`. `events.ts` listens on `/ws?token=<token>`, sends `events.subscribe` on open, validates each message with the protocol's `ServiceMessageSchema`, delivers `session.event`, `session.status`, `picker.picked`, `run.step`, and `run.finished` whole to the handlers of their `type`, drops anything else, and reconnects with backoff; `onOpen` handlers run after each (re)subscription, since pushes sent while the socket was down are lost. `context.tsx` provides the `Api` to screens (`ApiProvider`, `useApi`, `useLoad`), so component tests pass a fake.
- Validation uses the protocol's schemas through [Standard Schema](https://standardschema.dev) (`schema["~standard"].validate`), so the UI never imports Valibot (`ui-only-protocol`). `commands.ts` types `call` and `on` from the protocol's `SERVICE_COMMANDS` and `ServiceMessage`, so the UI sends exactly the params the service validates.
- `src/features/<screen>`: one screen each; screens never import each other (`ui-features-isolated`) and navigate through callbacks the app passes.
- `src/app`: routing and composition (`ui-app-is-top`). The route lives in `location.hash` (`#/flows`, `#/setup`, …), so the service serves one page and needs no router.
- `src/main.tsx`: imports the brand font and `app.css`, then calls `mount`. Without the token meta tag, the page tells the user to open the UI with `npx @recnrun/cli open`.

Screens:

- **Setup** (`#/setup`): `health`, `profiles.list`, and `capabilities.get`; whether Chrome is reachable, with the remedy and the guidance to enable remote debugging at `chrome://inspect/#remote-debugging`; each binding, stale when its endpoint differs from the Chrome found now; the service, protocol, and UI versions.
- **Catalog** (`#/flows`, the default): `flow.list` rows (name, status, revision, update time); opens a flow in the editor or starts a new recording.
- **Recorder** (`#/record`): `session.start`, optionally binding an actor to a profile; suggested steps from `session.suggestions` every second and again after each `session.event` push of the session (one request at a time), with `dblclick` and `drag` marked not replayable yet; the status follows `session.status` pushes; the three pauses as separate toggles (`session.pause`/`session.resume`); "Take control" (`session.handoff` to `manual`); the capture's scope (the page and the popups it opens), or a note while capture is suspended (collector gaps reach the UI with F3.5); assertions added to the session's draft (`flow.addAssertion`) on an element picked in Chrome (`picker.start` with the lease fence, the `picker.picked` push of that session, `picker.stop`) or described by one locator, through a slot the app fills with the editor's `DraftAssertions`, since screens never import each other; "Stop and save" runs `session.stop` then `flow.finalize` and opens the editor. Commands that act on the session carry the lease fence of its last status. The app keeps the running session's id above screen routing and in the tab's `sessionStorage` (`recnrun.session`, `src/features/recorder/activeSession.ts`), so leaving Record or reloading the page does not lose a recording the service still captures: returning reads `session.status` and restores its controls, and a session that is `completed` or answers `not-found` is forgotten and the start form shows again; finalizing forgets it too.
- **Editor** (`#/flows/<id>`): `flow.get`, then one card per step with its action, target locators, value (an input or secret reference such as `${secrets.password}` as written, never its value), and its own timeout; deletes steps; adds a `visible`, `textEquals`, `textContains`, `value`, or `count` assertion on an element described by one locator, written in the one-key form replay resolves (the picker needs a live session, so it is offered only while recording); edits stay local until "Save" sends `flow.save { flow }` and shows the new revision; "Run" opens the run screen.
- **Run** (`#/flows/<id>/run`): a form built from the flow's declared inputs (text, number, a checkbox for booleans, JSON for arrays and objects; a required input without a default must be filled); secret inputs, and one required field per recorded `${secrets.<name>}` reference no secret input provides, are password fields, emptied once the run starts and never rendered. "Start run" sends `flow.replay` with the non-secret values in `inputs` and the secret ones only in `secrets`; the `step.started` and `step.finished` journal events in `run.step` pushes of that run show each step's status, attempts, and error, and its `run.finished` push carries the summary (status, exit code, counts, failures). Until a summary or a failure is known, the screen also asks `run.summary` at once, after each event socket reconnect, and by polling while it answers `conflict` (0.5 s, doubling to at most 5 s), so a missed push never leaves it running; any other answer, such as `internal` for a replay that failed before writing a summary, is shown as the run's error. The started `runId` is kept per flow in `sessionStorage`, so returning to the screen or reloading the page recovers that run's summary. "Stop" is disabled with a note: `flow.replay` returns no session to stop, and the service has no command to cancel a run yet.

## Fixture application

`apps/fixture` (`@recnrun/fixture`) is the web application the browser tests drive. It stands in for any application under test, so it shares no workspace code (`fixture-isolated`). `src/` is a Node HTTP server on built-ins only: `createFixtureServer({ port, secondPort })` returns `start()`, `stop()`, and `urls`, and `src/bin.ts` runs it. `public/` holds the pages and their plain ES module scripts.

- **Two origins.** It listens on `127.0.0.1` only, on port 4600 (`http://127.0.0.1:4600`) and port 4601, which pages address as `http://localhost:4601`. The other host name makes the second origin cross-site, so Chrome renders the `iframe` route's second child out of process. `RECNRUN_FIXTURE_PORT` and `RECNRUN_FIXTURE_SECOND_PORT` change the ports. `vp run dev:fixture` starts it by hand; `playwright.browser.config.ts` starts it for `vp run test:browser`.
- **Routes.** `/` lists every page as a link with `data-testid="route-<name>"`. Each page is `/routes/<name>`: `form`, `debounce`, `spa`, `submit-redirect` (lands on `submit-result`), `iframe` (embeds `iframe-child`), `popup` (opens `popup-child` and `popup-child-quiet`), `virtual-list`, `ime`, `indexeddb`, `service-worker` (registers `/sw.js`), `worker` (starts the dedicated module worker `/worker.js` and pings it), `network`, `console`, `download`, `dialogs`, `storage`, and `replay` (a control for every replay action and assertion, a button that appears after 1.5 s, a popup, and an order form posting to `/api/orders`; `?order=<key>&delay=<ms>` sets the order's key and how late the server answers). `src/routes.ts` is the list.
- **API.** `/api/json`, `/api/binary` (a PNG), `/api/error` (500), `/api/redirect/<n>` (a 302 chain down to `/api/json`), `/api/stream` (10 chunks over 3 s), `/api/download` (an attachment), `/api/submit` (form POST answered 303), `/api/cacheable` (what the service worker caches), `/api/large?bytes=<n>` (a deterministic text body of up to 4 MiB, for size caps), `/api/secret` (a `Set-Cookie` and an `X-Fixture-Token` header, and whether an `Authorization` header arrived, for redaction), `/api/cached` (`max-age=60`, for Chrome's own cache), `/api/abort` (drops the connection unanswered), `/api/config` (both origins), `/api/orders` (a POST counts an order per `key` at once and answers 303 to `/routes/replay?order=<key>&placed=<key>` only after `delay` ms, so the page it lands on posts the same key, up to 10 s; a GET answers `{ key, count }`, so a test proves a write reached the server exactly once), and the WebSocket echo `/ws/echo`.
- **Page contract.** Every control has a stable `data-testid` and an accessible name; `public/fixture.js` checks both, runs the page's own self-test, and only then sets `window.__fixture = { route, ready: true, counters, fail, loadId }`. `counters` counts handler runs (a button's clicks, the debounced handler, IndexedDB commits), so a test can prove an action ran exactly once; `loadId` changes only on a real reload. Each page's first script, right after `<meta charset>`, is a classic inline head check that records whether RECnRun's hook was already installed; `window.__fixture.hookSeenAtHead` reports it. `popup-child-quiet` is the exception: its first script logs before anything reads the hook, to prove a reused popup window logs under its own document.
- **`?fail=<case>`.** Injects a defect on demand: `status` changes the form's status text, `api-500` makes `/api/json` answer 500, `slow` spaces the stream's chunks 1.5 s apart, and `throw` raises an uncaught error after the self-test.
- **Safety.** Files are served from `public/` only: a path that decodes to a `..` segment, a backslash, or a NUL byte gets 400. Every answer sends `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. There is no Content Security Policy, because the fixture is a test target.
- **Trusted input counters.** The `form` route counts the name field's `input` and `change` events and the submit button's `click` as `inputs`, `changes`, and `clicks` only when `isTrusted`, and any untrusted one as `untrusted`, so a test can prove an action went through Chrome's input pipeline: assigning `.value` fires nothing, and a dispatched event is untrusted.

## Service

`apps/service` (`@recnrun/service`) is the one process per user that owns RECnRun's data (F2.1). `startService({ home, port?, discover?, adapter?, uiRoot?, env?, log? })` returns `{ reused: false, service }` with `port`, `token`, `url`, `journals`, and `stop()`, or `{ reused: true, state }` when an instance already answers for `home`; `src/bin.ts` runs it with `home` set to the user's home, prints `{ reused, port, pid }` (never the token), and stops on `SIGTERM` or `SIGINT`. Nothing is global: `home`, Chrome discovery, Chrome itself (`adapter`, a `BrowserPort` from `src/browser.ts`: `discover`, `record`, `pick`, and `replayDriver`, over `@recnrun/adapter` by default), the UI folder, and the environment are injected, so tests run it on a temporary home with a discovery stub or a fake Chrome.

- **Listening.** It binds `127.0.0.1` only, on a random free port unless `port` is given, and writes `<home>/.recnrun/service.json` (`ServiceStateSchema`: `schemaVersion`, `pid`, `port`, `token`, `startedAt`, `serviceVersion`) through persistence: a temporary file renamed over the target, mode 0600 in a 0700 folder. The token is 32 random bytes in base64url, new on every start, and never logged or printed.
- **HTTP.** `POST /api` with a JSON request envelope, and `GET` of the UI (below): `Host` must be `127.0.0.1:<port>` or `localhost:<port>` and `Origin`, when sent, `http://127.0.0.1:<port>` or `http://localhost:<port>`, or the answer is 403 `forbidden`; then `Authorization: Bearer <token>` must match (compared in constant time), or the answer is 401 `unauthorized` with `WWW-Authenticate: Bearer`. Those checks run before anything else, so an unauthorized caller learns nothing more. Then another path is 404, another method 405, a body over 1 MiB 413, and a body that is not JSON 400. Envelopes failing before a request id is known carry `requestId: "none"`.
- **WebSocket.** `GET /ws` upgrades (RFC 6455, text frames only, 1 MiB per message, no fragments). `Host` and `Origin` are checked as above and refused with HTTP 403 before the handshake; the token comes from the `Authorization` header or, because browsers cannot set headers on a WebSocket, from `?token=` on this path only. A missing or wrong token completes the handshake and closes with 4401. Each text message is one request envelope, answered with one response envelope; after `events.subscribe`, the socket also receives pushed `ServiceMessage` objects, which carry a `type` and no `requestId`.
- **Dispatch** (`src/dispatch.ts`). The envelope, the command name, and its params are validated with the protocol's Valibot schemas (`invalid-request`, HTTP 400), the handler runs, and its result is validated again before it is sent; a handler that throws or returns a result outside the schema answers `internal` (HTTP 500, retryable). A protocol command with no handler yet answers `capability-unavailable`. F2.1 implements `capabilities.get` (the capability matrix) and `health` (`status`, `serviceVersion`, `protocolVersion`, `pid`, `uptimeMs`, and `chrome`: the adapter's discovery result for the default profile); F2.6 adds the commands below (`src/commands.ts`). A handler receives the envelope's `lease` fence and, over a WebSocket, the push channel.
- **Sessions** (`src/sessions.ts`, `src/control.ts`, F2.6). `session.start` finds Chrome (the default profile, or the one profile its `actors` are bound to: actors bound to two profiles are `capability-unavailable` until F6.1, an unknown binding `not-found`), opens the session's own page with the adapter's scoped recording, journals every captured event to `<home>/.recnrun/sessions/<sessionId>/events.jsonl` with response bodies in the blob store `blobs/` beside it (F3.1, so the journal holds only their `BodyRef`), pushes it as `session.event`, and gives the person control: a `manual` lease held by `person` on the page (10 min, renewed by each captured event). `session.pause` and `session.resume` apply the engine's three pause modes: under `pauseStepCreation` events are still journaled but suggest no step, under `suspendCapture` they are dropped and the resume journals a `gap` event (`capture-suspended`). `session.handoff` to `manual` takes control back at once; to `agent`, `replay`, or `unassigned` it needs the current holder's fence (`stale-lease` otherwise) and acquires a lease for the new holder. Every other command that changes the session (`session.pause`, `session.resume`, `session.stop`, `picker.start`, `picker.stop`, `flow.addAssertion`, `flow.finalize`) passes the same check in `controlled`: while a lease is live, only its current fence acts, and a fence that matches no live lease (passed on, released, or expired) is `stale-lease` even when no one holds the page, so a delayed former holder changes nothing; after expiry the person takes control again. `session.stop` ends capture and leaves the session `finalizing`: capture already under way (response bodies still being read, the results the recording delivers as it stops) still lands as the session was at stop, a drain that fails is journaled as a `capture-stopped` gap and a suspension still open as its `capture-suspended` gap, then the journal closes; every state change is pushed as `session.status`, and an illegal transition is `conflict`. `session.suggestions` normalizes the captured events into suggested steps.
- **Picker** (F2.6). `picker.start` needs the current holder's fence, starts the adapter's picker on the session's page, and pushes each pick as `picker.picked` with the element's `DomTarget` and `suggestLocators` for it; the click never reaches the page. `picker.stop` ends inspect mode; it needs the fence too. Starts and stops of one session take turns, including the stop inside `session.stop`, so concurrent starts open one picker, and a picker whose session stopped or whose control changed while it opened is closed and its start refused.
- **Flows** (`src/drafts.ts`, F2.6). `flow.addAssertion` adds an assertion step to a live session's draft. `flow.finalize`, once the session is `finalizing`, turns the suggested steps into flow steps (`toFlowSteps`), appends the assertions (`replayableAssertion`), validates the flow, and saves it `recorded` in the flow store (id `flow-<8 hex>`, named `Recording of <time>`); the session becomes `completed`. `flow.validate` answers the engine's issues; `flow.save` and `flow.import` validate and save a whole flow (`invalid-request` on issues) and answer its revision; `flow.list` and `flow.get` read the store. Store failures map to `not-found`, `invalid-request`, `conflict`, or `internal`.
- **Runs** (`src/runs.ts`, F2.6). `flow.replay` reads the stored flow and its optional dataset (request `inputs` override the dataset's; request `secrets`, at most 64 strings, are forwarded only to the executor's `secrets` and never stored, logged, or returned), finds the default profile's Chrome, creates the run (its manifest names the service, protocol, and Node versions), and answers the `runId` at once; the replay runs in the background over a fresh CDP adapter, pushing `run.step` and then `run.finished`. The run's journal is tracked by the journal registry and closed when the replay ends, even when it failed. A replay that fails outside its steps (Chrome unreachable, a journal error, an executor exception) still pushes `run.finished`, with an `error` summary (exit code 2) whose one failure, on the first step as the engine reports a run that could not start, carries the error, and whose steps that never finished count as `pending`. `run.summary` is `conflict` while the run is going, the summary afterwards, and `internal` when the replay itself failed.
- **Run queries** (`src/run-queries.ts`, F3.8; behavior in `@recnrun/persistence` `run-events.ts` and `run-compare.ts`). Both read stored runs, the ones a running replay is still writing included, and answer `not-found` for an unknown run. `run.queryEvents` pages the run's journal: every filter given must match (`category`, `stepId`, `types` (any of up to 64 event types), `origin` of the payload's `url`, `profile` binding, and `from` inclusive to `to` exclusive on the event timestamp); `limit` is 100 by default and at most 1000, and `nextCursor` is the journal position of the next match, so it stays valid while the journal grows; a cursor the service did not return is `invalid-request`. `run.compare { baselineRunId, runId }` (`RunComparisonSchema`) aligns two runs of one flow step by step (`invalid-request` for runs of different flows; `sameRevision` says whether they replayed the same revision) and names the first observable divergence, scanning each step's events before its status: an unmatched `gap` event is kind `collector-gap`, never `application`; a response whose HTTP status differs from the baseline's for the same URL is `network-status`; then a step that ended differently is `assertion-failed`, or `step-status` blamed on the `application` for an application failure code (`APPLICATION_FAILURE_CODES`) and on the `replay` otherwise. Steps still `pending` or `running` are not compared, and a step one run never reached counts only once both ended (`tests/contract/runs-api.test.ts`).
- **Events** (`src/hub.ts`, F2.6). `events.subscribe` works over the WebSocket only (`invalid-request` over HTTP); a filter with `sessionId` or `runId` selects that session's or run's messages, an empty one receives all of them, and the subscription ends with the socket.
- **The UI** (`src/static.ts`, F2.6). `GET /`, `/index.html`, and `/assets/<file>` serve the built `apps/ui/dist` (`uiRoot`), after the same `Host` and `Origin` checks as `/api` but without a token. `index.html` gets `<meta name="recnrun-token" content="<token>">` before `</head>`, so the UI calls `POST /api` with `Authorization: Bearer <token>` and opens `/ws?token=<token>`. Every UI response sends `Content-Security-Policy: default-src 'self'; connect-src 'self' ws://127.0.0.1:* ws://localhost:*; img-src 'self' data:; frame-ancestors 'none'; base-uri 'none'`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and `Cache-Control: no-store`. A missing build is 503 with the command that builds it; a missing asset is 404.
- **Handlers, client, flow files.** `startService({ handlers })` merges extra `CommandHandlers` over the built-in ones, which is how tests replace a command. `createServiceClient({ port, token })` (`src/client.ts`) sends one command to `127.0.0.1` and validates the envelope and the result; a failure is a `ServiceCallError` whose `code` is the service's error code or `unreachable`. `loadFlowFile(path)` (`src/flow-file.ts`) reads a flow folder's `flow.yaml` or a `.flow.json` file and validates it. The CLI uses all three.
- **One instance per user** (`src/instance.ts`). `<home>/.recnrun/service.lock` (`ServiceLockSchema`: `schemaVersion`, `pid`, `nonce`, `createdAt`) is created exclusively (staged, then hard-linked into place). A start that finds the lock reuses the instance when the lock's process is alive, `service.json` names that pid, and its API answers `capabilities.get` with the token within 1 s; it binds no port of its own. The lock is stale, and is removed and retaken, when its process is dead, when that instance no longer answers, when it is not a lock file, or when a live process has held it for more than 10 s without writing `service.json`. A start that keeps finding an instance starting gives up after 15 s with `InstanceStartingError`. Removal names the lock's nonce, so a process never deletes a lock another one took.
- **Logs.** Structured JSON lines (`time`, `level`, `event`, `pid`, then the event's fields) in `<home>/.recnrun/logs/service.log`, rotated at 1 MiB into `service.log.1` to `.3`, mode 0600. Requests are logged by path, never with a query string or a header. A failed log write never fails a request.
- **Stopping.** `stop()` (and `SIGTERM` or `SIGINT` in `bin.ts`) closes the server and every WebSocket, stops every recording session, cancels every running replay (the step under way finishes, the remaining steps are `cancelled`, and the run is stored as `interrupted`) and gives it 5 s to do so (`service.replay-unsettled` is logged if it does not), drains the journal registry (new journals are refused and every open journal, a replay's included, waits for its queued lines, syncs, and closes), then closes the flow store. Only then are `service.json` and the lock removed and the process exits 0, so a run interrupted by `SIGTERM` leaves a complete, readable journal.
- **Recovery on start** (F3.6). Before binding its port, the service calls `recoverRuns` on its flow store, so a run a killed service (`kill -9`, a crash, a power loss) left without a summary is stored as `interrupted` with its in-flight write step `indeterminate`, and `run.summary` and `run.queryEvents` answer for it; nothing is replayed. Each closed run is logged as `run.recovered`, each unreadable one as `run.recovery-skipped`, and a failed scan as `run.recovery-failed`; none of them stops the service from starting (`tests/contract/recovery.test.ts`).
- **No egress.** With `RECNRUN_FORBID_EGRESS=1`, `startService` patches `net.Socket` for the whole process so a connection to any host other than `localhost`, `127.0.0.0/8`, or `::1` throws `EgressForbiddenError`; `fetch`, `http`, `tls`, and WebSocket clients all connect through it. The contract layer runs with it set.
- **Imports.** Service source imports its own modules with `./` paths, never `@/`: `apps/cli` and `tests/contract` compile it with their own `@/` alias, which would resolve to their `src`. Lint enforces both bans on `apps/service/src/**`; the service's own tests still import through `@/`.

## CLI

`apps/cli` (`@recnrun/cli`, bin `recnrun`; `src/bin.ts` runs `main` from `src/main.ts`, F2.7) is a client of the service and carries no engine. It parses its arguments by hand (`src/args.ts`), imports only `@recnrun/service` (`startService`, `createServiceClient`, `loadFlowFile`, `stopOnSignals`) and protocol shapes, and uses `./` imports so Node runs the TypeScript source directly. It stays `private` until F7 bundles and publishes it. Whenever a command starts the service in its own process (`src/connect.ts`), `src/signals.ts` holds `SIGINT` and `SIGTERM` until the command's normal cleanup: a signal stops (drains) that service and exits 130 for `SIGINT` or 143 for `SIGTERM`, since default signal termination skips the cleanup and would leave `service.json` and the lock behind. A reused service is never stopped.

- **Finding the service.** Every command that needs the service calls `startService({ home })`: if an instance already answers for that home (`service.json`, lock, token) the CLI talks to it and leaves it running; otherwise it starts one in its own process. `--home <dir>` (default: the user's home) chooses where `.recnrun` lives; Chrome discovery still resolves the profile from `HOME`, `CHROME_CONFIG_HOME`, and `LOCALAPPDATA`. All traffic is `http://127.0.0.1:<port>/api` with the bearer token; `RECNRUN_FORBID_EGRESS=1` is honored by `startService`.
- **`recnrun open [--no-browser]`.** Prints `http://127.0.0.1:<port>/` on stdout. A service this process started keeps running until `SIGTERM` or `SIGINT` (which drain it and exit 0, replacing the temporary hold); a reused one is left alone and the command exits 0. Unless `--no-browser`, it opens the URL with `open`, `cmd /c start`, or `xdg-open`; a launch failure is a warning on stderr.
- **`recnrun doctor [--json]`.** Asks the service's `health` for Chrome (so it reuses a running service, or starts one for the duration of the command and stops it), and reads `bindings.json` (count, and the names whose endpoint differs from the default profile's current one), the free space of the home volume (`fs.statfs`), and the versions of the CLI, the service, and the protocol. Human output is aligned `Label: value` lines with the remedy; `--json` prints one `DoctorReport` ([`doctor-report.schema.json`](../packages/protocol/schema/doctor-report.schema.json)) line. `remoteDebugging.state` is `found`, `not-found`, `malformed`, or `stale`, from the discovery result. Exit 0 when Chrome is found, 1 when it is not, 2 on error.
- **`recnrun run --flow <dir|file> [--dataset <name>] [--timeout <s>]`.** Loads `<dir>/flow.yaml` or a `.flow.json` file and validates it, sends it with `flow.import` (so the store holds that content), then sends `flow.replay` with the flow's `id` and, with `--dataset`, the `inputs` of `datasets/<name>.json` in that same folder (validated with `DatasetSchema`; inputs the flow declares secret are dropped with a warning, since a dataset never carries secrets), and polls `run.summary` every 250 ms while it answers `conflict` or `not-found`, up to `--timeout` (default 600 s). stdout is exactly one line: the `RunSummary` JSON; progress and errors go to stderr. Exit 0 `passed`, 1 `failed`, 2 `error` or `interrupted`, and 2 for an invalid flow, a missing or invalid dataset, an unreachable or erroring service, or the timeout. `--json` is accepted and changes nothing.
- **Exit codes.** 0 ok, 1 not ok (a failed run, no Chrome), 2 error (bad command line, service error, invalid input).

## Security model

RECnRun reads the user's real Chrome profile, including request bodies and storage, so these are product requirements ([PLAN.md §6](plan/PLAN.md#6-security-tests-cross-cutting-source-17-and-19) lists the test for each, in the phase that introduces the surface):

- **No egress** (decision 8 of [ADR 0001](adr/0001-local-service-over-cdp.md#decision)). The service, the CLI, and the MCP server connect only to loopback. Tests run with `RECNRUN_FORBID_EGRESS=1`, which makes any other connection throw. Evidence is never sent to an AI, telemetry, or any external service.
- **The local API.** The service binds to loopback only. Every HTTP request and WebSocket carries the per-user bearer token from `~/.recnrun/service.json` (mode 0600), and the service checks `Origin` and `Host`, so a page the user visits cannot drive it. The UI's `index.html` carries the token in a `<meta>` tag: only a page served from the service's own origin can read it, it is never cached (`Cache-Control: no-store`), and its CSP (`default-src 'self'`, `connect-src` limited to the service, `frame-ancestors 'none'`) keeps other scripts and framing out.
- **Chrome connections.** The service connects only to a Chrome the user enabled remote debugging on, found through its `DevToolsActivePort`. Messages from page instrumentation are untrusted: they are validated with the protocol schemas and dropped when they come from an unknown target, frame, or document. Capture events never act as engine commands.
- **Capture scope.** A session captures only the page it opened and the popups that page opens; the person's other tabs get no hook and produce no events ([Adapter](#adapter), session scope). Control of the page is a lease, and every command that changes the session needs the current holder's fence; only a person taking control back needs none. The picker uses Chrome's inspect mode, which takes the click before the page dispatches it, so picking an element never triggers it or any page listener.
- **Captured content.** Viewers render captured HTML and bodies in a sandboxed frame where no script runs. Secrets are `${secrets.<name>}` references resolved from a local store and never written to a flow or an export; redaction runs before persistence.
- **Imports.** Importing a flow or a function never executes it; archives are checked for path traversal and decompression bombs.
- **Replay.** Write actions are never retried blindly; an unknown outcome is `indeterminate`.
- **The website.** recnrun.com holds no user data. It still ships a strict CSP (`default-src 'self'`, no inline scripts or styles; `apps/website/build/content-security-policy.ts`) as a `<meta>` tag, because GitHub Pages sends no headers. Third-party scripts are not allowed.

Findings from the bootstrap spike, kept here because they explain the configuration:

- **dependency-cruiser and TypeScript 7.** dependency-cruiser 18 supports TypeScript below 7, so it parses with SWC (`parser: "swc"`, `@swc/core`); type-only imports are still detected. Its tsconfig-paths plugin resolves `paths` from the working directory, so each app has a `tsconfig.deps.json` repeating its `@/` alias from the repo root, and `vp run deps` cruises each app with its own. npm packages are not followed but stay in the graph as leaves, so rules can name them (`not-to-dev-dep`); the `exclude` names only the workspaces' build output, since a pattern on `dist/` would also drop every package's own `dist/`.
- **Docker display.** Vitest Browser Mode runs headed; the test container provides Xvfb, so no window opens on the host. Google Chrome in the browser layer uses the same display.
- **Google Chrome in Docker.** `Dockerfile.tests` installs `google-chrome-stable` from Google's apt repository (amd64 and arm64) and writes `/opt/recnrun/versions.json`, which `scripts/test-container.mjs` copies with the image id into each run's `.artifacts/docker/<run-id>/versions.json`. Chrome runs as root in the container, where its sandbox cannot start, so the browser fixture adds `--no-sandbox` there and only there.
