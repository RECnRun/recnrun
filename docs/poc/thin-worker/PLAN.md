# POC: thin worker extension driven by a Store master

Plan date: 2026-11-06. Branch `poc-thin-worker`, from `18c4ec12` (the stopped [downloads-launcher POC](../downloads-launcher/PLAN.md), tag `archive/downloads-launcher-2026-11-06`). Progress is in [CHECKLIST.md](CHECKLIST.md), owner checks in [MANUAL_VALIDATION.md](MANUAL_VALIDATION.md), answers in [RESULTS.md](RESULTS.md). The repository rules of [AGENTS.md](../../../AGENTS.md) apply to every task: red/green, one commit per task, exercise each change, `vp run verify` exits 0 at a phase gate.

`[unsure]` marks a claim that neither the repository nor Chromium's source settles; each names the task or cell that resolves it.

## 1. The question

Can the owner install one extension from the Chrome Web Store in the personal Default profile, run one onboarding script, and from then on work only in Chrome, while a separate thin worker extension, loaded into bases and clones at provisioning, executes a closed vocabulary of browser operations for that master, with no code from the master, no repeated mutation after a restart, and no Node service running?

Minimum friction in install and use is the top criterion. Every gesture is counted ([RESULTS.md](RESULTS.md), H12).

**Website master first.** Before Phase 0, a spike (§4, Phase W) asks whether a recnrun.com page, in a tab or an installed app window, can replace the Store master. If it passes and the owner accepts it, the extension master becomes the fallback; if it fails, this plan continues unchanged.

**Direction.** The main line's `docs/adr/0001-local-service-over-cdp.md` and `0002-retire-extension-and-bridge.md` (a local Node service drives Chrome; the extension is retired) are superseded by this direction if this POC passes. The ADR change happens when the result merges into the main line, not in this POC.

## 2. Decisions

1. **Two extensions.** The **master** is `apps/extension` in a new WXT mode `poc-master`: Store-shaped, dashboard, no `debugger`, no `downloads`, no `file:///*`. The **worker** is a new WXT app `apps/worker` with its own pinned `key` (so its own id), unpacked, with `debugger`, `downloads`, `offscreen`, `storage`, `alarms`, and `file:///*`; no content script, no dashboard, one bootstrap page and one offscreen document. The worker ships in the versioned package the one-line installer fetches (decision 12) and is loaded into bases (and so clones) over `--remote-debugging-pipe` at provisioning, by the existing installer procedure (`scripts/poc-cross-profile/install.sh`: `Extensions.loadUnpacked`, Developer mode, reload, verify, `Browser.close`). No Node service runs.
2. **Packages.** Two new packages, because their purity differs:
   - `packages/worker-protocol`: closed Valibot schemas of HELLO, the command envelope, the five operations, results, limits, the error vocabulary, and the fixed CDP method table. It imports only `valibot`, runs in Node unit tests, and is what the static CDP check reads. The master and the worker both import it.
   - `packages/link`: identity keys, identity statements, pins, the rendezvous layout and its two adapters (File System Access for the master, Downloads plus `file://` for the worker), and the WebRTC peer link. It uses WebCrypto, WebRTC, and extension APIs. Moving it out of `apps/extension` is what keeps jscpd under its 1% threshold (`package.json` `duplication`) without copying.
   - One package would be simpler to wire, but the static check and the dependency rule "the protocol imports nothing" are easier to state on a package of its own.
   - `packages/bridge` stays the website ↔ master protocol; worker commands never enter it.
   - Every package or allowed dependency is added with `docs/ARCHITECTURE.md` and `.dependency-cruiser.cjs` in the same task (P1.1).
3. **Master rendezvous through one File System Access folder.** Onboarding has the owner choose `~/RECnRun/rendezvous` with `showDirectoryPicker({ mode: "readwrite" })` in the dashboard tab; the handle is stored in IndexedDB. The master reads **and** writes there: presence, offers, answers, acks, provisioning requests, and clone-control requests. So the master needs no file-access toggle, makes no `chrome.downloads` item in the Default, and never meets "Ask where to save".
   - Never `~/RECnRun` itself, which holds the bases with their cookies; never Documents, Downloads, home, or `~/Library` (the picker blocks them or iCloud syncs them).
   - The onboarding script writes the marker `.recnrun-rendezvous` (a fresh token) into the folder; the dashboard reads it after the pick and refuses any other folder.
   - Persistent consent ("Allow on every visit") is obtained during onboarding when possible: the offscreen document releases its handles, the dashboard reloads the handle from IndexedDB, and Chrome offers the restore prompt ([TROUBLESHOOTING](../../TROUBLESHOOTING.md#chrome-shows-its-write-prompt-instead-of-allow-on-every-visit-solved)). `[unsure]` that this works in the same session: cell `P1.master-fsa`.
   - A lost, revoked, or embargoed grant makes the dashboard show one recovery action; the offscreen document cannot prompt.
   - **Fallback**, only if `P1.master-fsa` fails: Gate P1 stops and the owner decides. The prepared branch is a `poc-master-downloads` build that adds `downloads` and `file:///*`, uses the Downloads adapter of `packages/link` for both directions, and reruns the cell's round trips with its own pass condition: Downloads items allowed, the file-access toggle counted as gestures, "Ask where to save" detected and warned about (P6.3).
4. **Workers keep their own Downloads; the launcher moves their files** (owner default, option B, 2026-11-06; the owner may still overturn it). A worker writes with `chrome.downloads` into its root's own download directory `<root>/downloads`, which `base.sh` seeds before the base's first launch and `clone.sh` and `base-update.sh` point at the copy's own folder (today's tested behavior, CL01–CL17). It reads the rendezvous folder with `file://` (unpacked: file access with no toggle, E1). The launcher moves each finished file from `<root>/downloads/RECnRun/<namespace>/` to the same relative path under `<rendezvous>/<namespace>/`, by a rename inside `~/RECnRun` (one file system), and skips `*.crdownload`, links, and anything that is not a regular file. No base needs a Chrome settings gesture. Cell `P1.rendezvous-move`.
   - Cost: a worker-to-master file waits for the launcher's move. W.2 runs the move on its own short timer `[unsure]` of the interval (the loop's is `RECNRUN_LAUNCHER_INTERVAL_S`, 10 s); W.rtc and P1.13 record the pairing latency.
   - Rejected for friction: the base's download directory set to the rendezvous folder with the **Change** button of `chrome://settings/downloads`, whose `DownloadsHandler::FileSelected` persists the folder picked in the native chooser, one chooser per base. (`settingsPrivate.setPref` cannot set it: `prefs_util.cc` `IsSettingReadOnly` marks `download.default_directory` read-only.)
   - Considered and not chosen: `~/Downloads/RECnRun/rendezvous`, which needs no preference. Workers would write `RECnRun/rendezvous/...` under the default Downloads folder, and the picker allows it (`GenerateBlockPaths` blocks `DIR_DEFAULT_DOWNLOADS` with `kDontBlockChildren`). But on macOS the launcher, a launchd `sh` agent, would then read and write `~/Downloads`, which TCC protects: either a privacy prompt for `sh` or a silent denial. That is where the old runbook's Full Disk Access step and the old POC's "no TCC reads" task came from. `[unsure]` which of the two happens; M-TW.10 probes it, and a launcher read with no prompt reopens this option. On Linux it would work.
   - The installer still writes only under `~/RECnRun`; Chrome writes the rendezvous files, not the installer.
5. **One shared folder layout.** `<rendezvous>/<namespace>/` holds `peers/<id>/` (presence, offers, answers), `acks/<id>/`, `ops/<operationId>/` (provisioning), `control/<id>/` (clone control), `jobs/<id>/<jobId>.json` (a worker's job outcomes, §6), `cancel/<jobId>.json` (a master's signed cancellation), and `registry.json`; it replaces both the folder build's `pairing/` and Downloads' `RECnRun/poc/<ns>/`. Readers ignore `*.crswap` and `*.crdownload`. A frozen base or an unpublished copy is excluded by the launcher's instance registry and the role check (a template announces nothing), never by per-root folders.
6. **Trust.** The worker accepts only the master key pinned at onboarding: the onboarding script, holding the marker token, accepts the master's signed identity statement written for that token, verifies it, and stores the key in the launcher record (`~/RECnRun/state/`, outside the rendezvous folder; today `~/.recnrun`, moved so decision 13's write rule holds). `clone-open.sh` takes the master key from that record only, never from a presence file (today it reads the presence). The origin allowlist lives in the same record, written by the onboarding script and handed to each worker at provisioning; changing it is a terminal step, never a master action, so neither master can widen it (W.trust). A new clone regenerates its identity key and certificate. The same-user threat model of the old [decision 13](../downloads-launcher/PLAN.md#2-decisions) holds; a program of the owner's user that reads profile files is out of scope.
7. **Closed command vocabulary.** `strictObject` envelopes; five operations (§6) mapped to a fixed CDP method table; no operation takes a function, expression, script, CDP method, or params. A static check fails on any other CDP method name in `apps/worker/src`, on `Runtime.evaluate`, and on `Runtime.callFunctionOn` whose declaration is not a constant of the table. `.claude/rules/extension.md` changes where it forbids page content in peer messages: bounded `read` results of the closed protocol are allowed, nothing else.
8. **Headless clones by default; headed clones start with `--silent-debugger-extension-api`** (no infobar). This is not a remote-debugging flag; clones never get `--remote-debugging-*` or an external CDP client (P5).
9. **Asserting tests.** Phase 1 and later specs assert; a failed hypothesis fails the test. Experiment recorders that write a `fail` verdict inside a passing run are not used for this POC's gates.
10. **Verify stays the gate, and gets shorter.** Phase 0 moves the downloads-launcher experiments to an on-demand lab and deletes what the abandoned design alone needs (§5). Thresholds never drop; jscpd stays at 1%; source and its tests go together.
11. **Process.** Copied into the [resume protocol](CHECKLIST.md#resume-protocol): Sonnet `plan-implementer` agents by default, Opus only for Chrome or WebRTC internals; red/green and one commit per task; Codex review (`gpt-6.1-sol`, high, read-only, stdin closed) before each gate; `vp run verify` exit 0 and push at gates only, except that Phase 0 runs a timed verify after every task (pushes stay at gates); agents never open host Chrome; only the orchestrator touches host Chrome and the personal Default; the pull request of `poc-thin-worker` targets `poc-downloads-launcher`.
12. **One-line install, like mise.** On macOS and Linux the owner runs `curl -fsSL https://recnrun.com/install.sh | sh` and nothing else in a terminal; Windows (`irm https://recnrun.com/install.ps1 | iex`) waits for its own phase (§14).
    - `install.sh` is a static file of `apps/website` (GitHub Pages). It downloads one versioned package (`recnrun-<version>.tar.gz`: worker bundle, launcher and provisioning scripts, `SHA256SUMS`) from recnrun.com over HTTPS, checks it against the SHA-256 pinned in the script, extracts to a temporary folder, and renames it into `~/RECnRun/app/<version>/`. No sudo or admin.
    - Idempotent: a re-run with nothing to change exits 0. An upgrade or a repair installs a new immutable generation `~/RECnRun/app/<version>-<generation>/` and moves the `current` link; it never writes into an existing generation, so running clones keep their files until P3.2 moves them.
    - It prints each step and ends by opening `https://recnrun.com/start` in Chrome (or printing it), which leads to the master's Store listing when the master is missing, then to its onboarding.
    - Ownership: it records every path it creates, and the autostart entry, in `~/RECnRun/app/INSTALLED`. It refuses a symlinked `~/RECnRun` or `app/`; archive entries that are absolute, contain `..`, or are links or devices; and a second concurrent run (a lock directory). An interrupted install or uninstall leaves the previous `current` runnable.
    - POSIX `sh` (runs under `sh` and `dash`), safe when piped: no reliance on `$0` or on stdin being a terminal. Target zero prompts; an unavoidable prompt reads `/dev/tty`.
    - Uninstall is one command, `curl -fsSL https://recnrun.com/install.sh | sh -s -- --uninstall` (or `~/RECnRun/app/current/bin/uninstall`). It removes only the paths in `INSTALLED` and keeps the owner's data (`bases/`, clones, `rendezvous/`, `state/`), printing where they are.
    - Phase 1 provisioning already reads this package layout (P1.2), so P6 adds only the download step.
    - Tests serve the script and package from a loopback server standing in for recnrun.com, as the Store is simulated; the egress rule stays. The real recnrun.com path and the gesture count are owner checks.
    - Gestures are counted from Chrome installed with no master and no RECnRun files; the Store install is counted separately and in the total.
13. **The installer is reviewable.** A user who pastes the URL or the file into ChatGPT or Claude and asks "is this safe to run?" should hear "yes, it does only X, Y, Z". So `install.sh`:
    - is one short file of plain POSIX `sh` with small named functions and a header comment listing exactly what it does, where it writes, what it downloads (URLs and checksums), and how to undo it;
    - has no obfuscation, `eval`, base64 decode, `sh -c` of downloaded text, nested `curl | sh`, sudo, shell rc edits, or telemetry;
    - writes only under `~/RECnRun` and the autostart entry named in its header; connects only to `recnrun.com` over HTTPS (and GitHub release assets, if used);
    - wraps everything in `main`, called on the last line, so a truncated download runs nothing;
    - never touches the personal Chrome profile or its data, and never kills Chrome by name;
    - verifies the package's pinned SHA-256 before extracting, refuses on mismatch, and installs atomically;
    - has `--dry-run`, which prints every action and does none, and `--uninstall`, which removes exactly what it installed;
    - is published with its own SHA-256 and a link to its source in the repository, so the served file can be compared with the reviewed one.

    A script check enforces the forbidden-construct list on `install.sh` and on every script in the package (P6.7). The installer trust review (P6.10) asks two AI models whether `install.sh` is safe, and separately reviews the package's scripts. `install.ps1` follows the same rules.

14. **Website-master spike first** (owner, 2026-11-06). Phase W (§4) runs before Phase 0, with its own gate; Phase 0 onward waits for its result. The owner accepts a recnrun.com tab or installed app window open while scripts run, and gives up background operation of the master.
15. **Workers run whole jobs** (owner, 2026-11-06). A master sends a job, an ordered, bounded list of the closed operations, signed by the master key; once the worker accepts it, the job runs to completion even if the master goes away, and its outcomes persist in the worker's ledger and the rendezvous folder (§6). This holds for either master.

**Question.** Can a recnrun.com page, in a tab or an installed app window, be the master? It must hold the rendezvous folder through File System Access with no prompt after onboarding, link to separate-root workers over WebRTC with no flag, hand them whole jobs (§6) that finish after the page closes, reconcile on reopen without repeating a mutation, and need fewer gestures than the Store path.

**Why it might not** (Opus and Codex opinions of 2026-11-06, from Chromium `main`; P1.1 pins the files in `CHROMIUM.md`):

- **WebRTC.** A web page offers mDNS `.local` host candidates, while a worker's offscreen document offers plain IPs. `ChromeContentRendererClient::ShouldEnforceWebRTCRoutingPreferences` is true outside extension processes, and `PeerConnectionDependencyFactory::CreatePortAllocator` then turns on obfuscation. Same-machine connectivity with `iceServers: []` is plausible, through peer-reflexive candidates, but unproved. `LocalNetworkAccessPermission::ShouldRequestPermission` may gate WebRTC from a public origin, and macOS Local Network privacy may prompt for Chrome's mDNS `[unsure]`.
- **No background.** `RTCPeerConnection` is `[Exposed=Window]`, a service worker stops when idle, and Periodic Background Sync cannot hold a link. Accepted by the owner; whole jobs make it tolerable.
- **Folder grant.** A tab needs "Allow on every visit" once. An installed app gets the extended grant with no restore prompt (`OriginHasExtendedPermission`, `OnWebAppInstalled` → `UpgradeToExtendedPermission`).
- **Key storage.** The master key in the origin's IndexedDB survives a deploy and a cache-only clear, but not a site-data clear or eviction without `persist()`.
- **Trust.** Any code the origin serves can use a non-extractable key (`extractable: false` stops export, not `sign()`). The workers' limits are then the only bound.

**Lab origin.** The master page comes from a loopback HTTPS server that stands in for recnrun.com at `https://recnrun.test:<port>`. A test CA sits in the container's NSS database, so Chrome needs no certificate flag, and the container's `/etc/hosts` maps `recnrun.test` to loopback.

- **Why HTTPS on a hostname.** `http://localhost` is also a secure context, but the real site is HTTPS on a hostname, and Chrome treats `localhost` specially in places `[unsure]` which ones touch permissions and app install. A hostname keeps the folder grant, the install path, and the storage origin closest to production.
- **Local Network Access.** A loopback server is in the loopback address space, so it cannot show a Local Network Access prompt that the public recnrun.com might get. W.rtc therefore runs a second variant whose master Chrome treats the server as public (`--ip-address-space-overrides` `[unsure]` that the switch exists on the tested revision). This is a lab emulation, never a product flag.
- **Nothing real.** Nothing is deployed to recnrun.com and nothing is pushed to `master`. The real origin is M-TW.12, run only with the owner's explicit authorization. The macOS repeats of W.rtc and W.fsa are M-TW.13 and M-TW.14.

**Minimum code.** Most of it is Phase 1 work pulled forward, kept whichever master wins, because the workers are the same.

## 6. Protocol v2

**HELLO** `{ protocol: { min, max }, capabilities: string[], epoch, identity }`. Each side takes the highest version in both ranges; with no overlap it answers `INCOMPATIBLE { min, max }` and closes. A worker answers HELLO only from the pinned master key (`UNPINNED_MASTER` otherwise, and no link).

**Job** (decision 15; `v.strictObject`, at most 64 KiB): `{ jobId (uuid), epoch (uint), issuedAt, deadlineAt, origins, tabRef, ops, signature }`.

- `ops`: 1 to 32 entries, each `v.strictObject({ op, args, timeoutMs ≤ 30000 })` of the table below; an entry's index is its id, so an outcome is named `(jobId, index)`.
- `deadlineAt` is at most 10 minutes after `issuedAt`: the job's total deadline. A job that arrives after it (worker clock, 5 s skew) is refused with `EXPIRED`.
- `origins`: 1 to 8 origins, each inside the allowlist pinned at provisioning. A job narrows the allowlist, never widens it; any other origin answers `FORBIDDEN_ORIGIN` before the job is accepted.
- `signature`: the master key's ECDSA P-256 signature over the canonical JSON of the other fields. The link already authenticates the master; the signature lets the worker keep the job and show, after any restart, that the pinned master authorized all of it when it was accepted.
- **Acceptance.** The worker checks schema, signature, epoch, origins, deadline, and its limits, records `accepted(digest)` in the ledger, answers `ACCEPTED { jobId }`, and only then runs the first op. One job at a time per worker; another answers `BUSY { jobId }`.
- **Run.** Ops run in order. A mutating op (`navigate`, `type`, `click`) records `applying` before its first CDP call and `done(result)` or `failed(code)` after. The first failure stops the job and the remaining ops are `SKIPPED`. At `deadlineAt` the running op ends with `TIMEOUT`, the rest are `SKIPPED`, and the job is `EXPIRED`. Each outcome goes to the master as `OP_RESULT` while a link is up, and is persisted either way. Bounded `read` results count toward a per-job total of 64 KiB.
- **Master disconnect.** The job keeps running; the worker accepts no new job until a pinned master is linked again. When the job ends, the worker writes `jobs/<workerId>/<jobId>.json` (job state and every op's outcome) to the rendezvous folder (decision 4: through its Downloads and the launcher's move) and keeps the ledger entry, so a reopened master can read outcomes before any link is up.
- **Cancellation.** `CANCEL { jobId, signature }` over the link, or a signed `cancel/<jobId>.json` that the master writes into the rendezvous folder and the worker reads between ops. The running op is never cut inside its CDP sequence: it ends, and the remaining ops are `CANCELLED`.
- **Reconcile.** The master journals each job `submitted` in its own storage before sending it. After every HELLO it sends `JOB_STATUS { jobIds }` for each job its journal holds as not terminal, and the worker answers the stored outcomes. The master never resubmits a job by itself. A repeated `jobId` with the same digest returns the stored status and runs nothing; with another digest it answers `PAYLOAD_MISMATCH`.
- **Worker restart.** A job with an op in `applying` reports that op `OUTCOME_UNKNOWN`; a job stopped between ops reports nothing new for its finished ops. Either way the remaining ops are `SKIPPED` and the job is `INTERRUPTED`: a worker never resumes a job after a restart, since the page state the job built is gone.
- **Documents.** The master sends no `documentId`: the worker carries the document from op to op, checks the main frame's origin before each op, and repeats the document check inside an op before any input.
- Compared with the draft of one request per op: `requestId` becomes `(jobId, index)`, the ledger and its retention are per job, and `BUSY`, `EXPIRED`, `CANCELLED`, `SKIPPED`, and `INTERRUPTED` are new.

| op         | args                                                                                | CDP (worker table, fixed)                                                                                       |
| ---------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `navigate` | `url`: `http`/`https`, ≤ 2048, origin allowed                                       | `Page.navigate`; the main frame's `loaderId` becomes the new `documentId`                                       |
| `wait`     | `selector` (CSS, ≤ 512), `state: attached \| visible \| text`, `text?`, `timeoutMs` | `DOM.getDocument`, `DOM.querySelector`, `DOM.getBoxModel`, bounded polling                                      |
| `type`     | `selector`, `text` ≤ 4096 (inert data, never code)                                  | `DOM.focus`, `Input.insertText`                                                                                 |
| `click`    | `selector`                                                                          | `DOM.scrollIntoViewIfNeeded`, `DOM.getContentQuads`, `Input.dispatchMouseEvent` ×3                              |
| `read`     | `selector`, `what: text \| value`, `maxBytes` ≤ 16 KiB                              | `DOM.resolveNode`, `Runtime.callFunctionOn` with a constant declaration from the table, `Runtime.releaseObject` |
| every op   | (shared checks)                                                                     | `Page.getFrameTree`, `DOM.describeNode`, `Fetch.enable`, `Fetch.continueRequest`, `Fetch.failRequest`           |

- The table is the whole allowlist the static check enforces. If H-CSP fails, adding `DOM.getOuterHTML` for `read` is a reviewed change of the table.
- **Origins.** The allowlist reaches the worker at provisioning, from the onboarding script's launcher record (decision 6), never from the master, so a master cannot widen it.
  - Before every operation the worker reads the main frame's URL and `loaderId` (`Page.getFrameTree`). An origin outside the list answers `FORBIDDEN_ORIGIN` (this catches redirects and in-page navigation, not only the `navigate` target). A main-frame `loaderId` that changed between an op's check and its input or read answers `STALE_DOCUMENT`.
  - Before `click`, the worker reads the target's effective destination (`DOM.describeNode`: the closest `a[href]`, `form[action]`, or `formaction`) and refuses a forbidden one with `FORBIDDEN_ORIGIN`. It repeats the document check just before `Input.dispatchMouseEvent`.
  - Network guard, for what a check cannot see (a document change between check and input, a meta refresh): on attach the worker enables `Fetch` for the tab and fails every request to an origin outside the list (`Fetch.failRequest`), so the forbidden POST never leaves Chrome. `[unsure]` that `chrome.debugger` may use `Fetch` on the tab and that pausing every request costs little: P1.6, P1.14.
  - The allowlist is no network isolation for other programs; the container's egress filter stays separate.
- **No code.** Unknown `op`, extra keys, `script`, `expression`, `method`, `params`, and `javascript:`/`data:` URLs fail the schema with `INVALID_COMMAND` before any debugger call.
- **Ledger.** Keyed by master key, clone identity, durable `epoch`, and `jobId`, with the job's SHA-256 digest, its state, and every op's outcome, in the worker's `storage.local`. An epoch below the highest seen answers `OBSOLETE_EPOCH`.
- **Retention.** Every job of the current epoch is kept until the epoch closes; the cap (64 jobs `[unsure]`) never evicts inside an epoch, and at the cap the worker refuses new jobs with `EPOCH_FULL`. The master opens a new epoch at HELLO only after every job of the old one is terminal and its outcomes are in the master's journal; entries of closed epochs are then dropped, and their jobs answer `OBSOLETE_EPOCH`. So a dropped job can never look new. Claim: an accepted mutation is never repeated; not exactly-once.
- `DETACHED` and `TIMEOUT` are typed and never retried silently.
- **H-CSP** `[unsure]`: `DOM`, `Input`, and `Runtime.callFunctionOn` work under `script-src 'none'; require-trusted-types-for 'script'`. If `callFunctionOn` is blocked, `read` uses `DOM.describeNode`/`DOM.getOuterHTML` with text extracted in the worker. Resolved by P1.13.
