# POC: thin worker extension driven by a Store master

Plan date: 2026-11-06. Branch `poc-thin-worker`, from `18c4ec12` (the stopped [downloads-launcher POC](../downloads-launcher/PLAN.md), tag `archive/downloads-launcher-2026-11-06`). Progress is in [CHECKLIST.md](CHECKLIST.md), owner checks in [MANUAL_VALIDATION.md](MANUAL_VALIDATION.md), answers in [RESULTS.md](RESULTS.md). The repository rules of [AGENTS.md](../../../AGENTS.md) apply to every task: red/green, one commit per task, exercise each change, `vp run verify` exits 0 at a phase gate.

`[unsure]` marks a claim that neither the repository nor Chromium's source settles; each names the task or cell that resolves it.

## 1. The question

Can the owner install one extension from the Chrome Web Store in the personal Default profile, run one onboarding script, and from then on work only in Chrome, while a separate thin worker extension, loaded into bases and clones at provisioning, executes a closed vocabulary of browser operations for that master, with no code from the master, no repeated mutation after a restart, and no Node service running?

Minimum friction in install and use is the top criterion. Every gesture is counted ([RESULTS.md](RESULTS.md), H12).

**Direction.** The main line's `docs/adr/0001-local-service-over-cdp.md` and `0002-retire-extension-and-bridge.md` (a local Node service drives Chrome; the extension is retired) are superseded by this direction if this POC passes. The ADR change happens when the result merges into the main line, not in this POC.

## 2. Decisions

1. **Two extensions.** The **master** is `apps/extension` in a new WXT mode `poc-master`: Store-shaped, dashboard, no `debugger`, no `downloads`, no `file:///*`. The **worker** is a new WXT app `apps/worker` with its own pinned `key` (so its own id), unpacked, with `debugger`, `downloads`, `offscreen`, `storage`, `alarms`, and `file:///*`; no content script, no dashboard, one bootstrap page and one offscreen document. The worker ships in the versioned package the one-line installer fetches (decision 12) and is loaded into bases (and so clones) over `--remote-debugging-pipe` at provisioning, by the existing installer procedure (`scripts/poc-cross-profile/install.sh`: `Extensions.loadUnpacked`, Developer mode, reload, verify, `Browser.close`). No Node service runs.
2. **Packages.** Two new packages, because their purity differs:
   - `packages/worker-protocol`: closed Valibot schemas of HELLO, the command envelope, the five operations, results, limits, the error vocabulary, and the fixed CDP method table. It imports only `valibot`, runs in Node unit tests, and is what the static CDP check reads. The master and the worker both import it.
   - `packages/link`: identity keys, identity statements, pins, the rendezvous layout and its two adapters (File System Access for the master, Downloads plus `file://` for the worker), and the WebRTC peer link. It uses WebCrypto, WebRTC, and extension APIs. Moving it out of `apps/extension` is what keeps jscpd under its 1% threshold (`package.json` `duplication`) without copying.
   - One package would be simpler to wire, but the static check and the dependency rule "the protocol imports nothing" are easier to state on a package of its own.
   - `packages/bridge` stays the website ↔ master protocol; worker commands never enter it.
   - Every package or allowed dependency is added with `docs/ARCHITECTURE.md` and `.dependency-cruiser.cjs` in the same task (P1.1).
3. **Master rendezvous through one File System Access folder.** Onboarding has the owner choose `~/RECnRun/rendezvous` with `showDirectoryPicker({ mode: "readwrite" })` in the dashboard tab; the handle is stored in IndexedDB. The master reads **and** writes there: presence, offers, answers, acks, provisioning requests, and clone-control requests. So the master needs no file-access toggle, makes no `chrome.downloads` item in the Default, and never meets "Ask where to save".
   - Never `~/RECnRun` itself, which holds the bases with their cookies; never Documents, Downloads, home, or `~/Library` (the picker blocks them or iCloud syncs them).
   - The onboarding script writes the marker `.recnrun-rendezvous` (a fresh token) into the folder; the dashboard reads it after the pick and refuses any other folder.
   - Persistent consent ("Allow on every visit") is obtained during onboarding when possible: the offscreen document releases its handles, the dashboard reloads the handle from IndexedDB, and Chrome offers the restore prompt ([TROUBLESHOOTING](../../TROUBLESHOOTING.md#chrome-shows-its-write-prompt-instead-of-allow-on-every-visit-solved)). `[unsure]` that this works in the same session: cell `P1.master-fsa`.
   - A lost, revoked, or embargoed grant makes the dashboard show one recovery action; the offscreen document cannot prompt.
   - **Fallback**, only if `P1.master-fsa` fails: Gate P1 stops and the owner decides. The prepared branch is a `poc-master-downloads` build that adds `downloads` and `file:///*`, uses the Downloads adapter of `packages/link` for both directions, and reruns the cell's round trips with its own pass condition: Downloads items allowed, the file-access toggle counted as gestures, "Ask where to save" detected and warned about (P6.3).
4. **Workers keep Downloads and `file://`.** A worker writes with `chrome.downloads` and reads with `file://` (unpacked: file access with no toggle, E1). `chrome.downloads` filenames are relative and cannot climb with `..`, so the base's default download directory must be the rendezvous folder itself. It is a persisted preference set through Chrome (R4: no hand edit of `Preferences`; `Browser.setDownloadBehavior` is only a temporary override). Clones inherit it; `clone.sh` and `base-update.sh` stop rewriting it.
   - `settingsPrivate.setPref` cannot set it: Chromium's `prefs_util.cc` `IsSettingReadOnly` marks `download.default_directory` read-only. The Chrome-owned route is the **Change** button of `chrome://settings/downloads`, whose `DownloadsHandler::FileSelected` persists the folder picked in the native chooser. Provisioning opens that page in the base, and the owner picks the folder once per base (counted in H12; driven with `xdotool` in the lab). Cell `P1.base-download-dir`.
   - Considered and not chosen: `~/Downloads/RECnRun/rendezvous`, which needs no preference. Workers would write `RECnRun/rendezvous/...` under the default Downloads folder, and the picker allows it (`GenerateBlockPaths` blocks `DIR_DEFAULT_DOWNLOADS` with `kDontBlockChildren`). But on macOS the launcher, a launchd `sh` agent, would then read and write `~/Downloads`, which TCC protects: either a privacy prompt for `sh` or a silent denial. That is where the old runbook's Full Disk Access step and the old POC's "no TCC reads" task came from. `[unsure]` which of the two happens; M-TW.10 probes it, and a launcher read with no prompt reopens this option. On Linux it would work.
   - The installer still writes only under `~/RECnRun`; Chrome writes the rendezvous files, not the installer.
5. **One shared folder layout.** `<rendezvous>/<namespace>/` holds `peers/<id>/` (presence, offers, answers), `acks/<id>/`, `ops/<operationId>/` (provisioning), `control/<id>/` (clone control), and `registry.json`; it replaces both the folder build's `pairing/` and Downloads' `RECnRun/poc/<ns>/`. Readers ignore `*.crswap` and `*.crdownload`. A frozen base or an unpublished copy is excluded by the launcher's instance registry and the role check (a template announces nothing), never by per-root folders.
6. **Trust.** The worker accepts only the master key pinned at onboarding: the onboarding script, holding the marker token, accepts the master's signed identity statement written for that token, verifies it, and stores the key in the launcher record (`~/RECnRun/state/`, outside the rendezvous folder; today `~/.recnrun`, moved so decision 13's write rule holds). `clone-open.sh` takes the master key from that record only, never from a presence file (today it reads the presence). A new clone regenerates its identity key and certificate. The same-user threat model of the old [decision 13](../downloads-launcher/PLAN.md#2-decisions) holds; a program of the owner's user that reads profile files is out of scope.
7. **Closed command vocabulary.** `strictObject` envelopes; five operations (§5) mapped to a fixed CDP method table; no operation takes a function, expression, script, CDP method, or params. A static check fails on any other CDP method name in `apps/worker/src`, on `Runtime.evaluate`, and on `Runtime.callFunctionOn` whose declaration is not a constant of the table. `.claude/rules/extension.md` changes where it forbids page content in peer messages: bounded `read` results of the closed protocol are allowed, nothing else.
8. **Headless clones by default; headed clones start with `--silent-debugger-extension-api`** (no infobar). This is not a remote-debugging flag; clones never get `--remote-debugging-*` or an external CDP client (P5).
9. **Asserting tests.** Phase 1 and later specs assert; a failed hypothesis fails the test. Experiment recorders that write a `fail` verdict inside a passing run are not used for this POC's gates.
10. **Verify stays the gate, and gets shorter.** Phase 0 moves the downloads-launcher experiments to an on-demand lab and deletes what the abandoned design alone needs (§4). Thresholds never drop; jscpd stays at 1%; source and its tests go together.
11. **Process.** Copied into the [resume protocol](CHECKLIST.md#resume-protocol): Sonnet `plan-implementer` agents by default, Opus only for Chrome or WebRTC internals; red/green and one commit per task; Codex review (`gpt-6.1-sol`, high, read-only, stdin closed) before each gate; `vp run verify` exit 0 and push at gates only, except that Phase 0 runs a timed verify after every task (pushes stay at gates); agents never open host Chrome; only the orchestrator touches host Chrome and the personal Default; the pull request of `poc-thin-worker` targets `poc-downloads-launcher`.
12. **One-line install, like mise.** On macOS and Linux the owner runs `curl -fsSL https://recnrun.com/install.sh | sh` and nothing else in a terminal; Windows (`irm https://recnrun.com/install.ps1 | iex`) waits for its own phase (§13).
    - `install.sh` is a static file of `apps/website` (GitHub Pages). It downloads one versioned package (`recnrun-<version>.tar.gz`: worker bundle, launcher and provisioning scripts, `SHA256SUMS`) from recnrun.com over HTTPS, checks it against the SHA-256 pinned in the script, extracts to a temporary folder, and renames it into `~/RECnRun/app/<version>/`. No sudo or admin.
    - Idempotent: a re-run with nothing to change exits 0. An upgrade or a repair installs a new immutable generation `~/RECnRun/app/<version>-<generation>/` and moves the `current` link; it never writes into an existing generation, so running clones keep their files until P3.2 moves them.
    - It prints each step and ends by opening `https://recnrun.com/start` in Chrome (or printing it), which leads to the master's Store listing when the master is missing, then to its onboarding.
    - Ownership: it records every path it creates, and the autostart entry, in `~/RECnRun/app/INSTALLED`. It refuses a symlinked `~/RECnRun` or `app/`; archive entries that are absolute, contain `..`, or are links or devices; and a second concurrent run (a lock directory). An interrupted install or uninstall leaves the previous `current` runnable.
    - POSIX `sh` (runs under `sh` and `dash`), safe when piped: no reliance on `$0` or on stdin being a terminal. Target zero prompts; an unavoidable prompt reads `/dev/tty`.
    - Uninstall is one command, `curl -fsSL https://recnrun.com/install.sh | sh -s -- --uninstall` (or `~/RECnRun/app/current/bin/uninstall`). It removes only the paths in `INSTALLED` and keeps the owner's data (`bases/`, clones, `rendezvous/`, `state/`), printing where they are.
    - Phase 1 provisioning already reads this package layout (P1.2), so P6 adds only the download step.
    - Tests serve the script and package from a loopback server standing in for recnrun.com, as the Store is simulated; the egress rule stays. The real recnrun.com path and the gesture count are owner checks.
    - Gestures are counted from Chrome installed with no master and no RECnRun files; the Store install is counted separately and in the total.
13. **The installer is reviewable.** A user who pastes the URL or the file into ChatGPT or Claude and asks "is this safe to run?" should hear "yes, it does only X, Y, Z". So `install.sh`:
    - is one short file of plain POSIX `sh` with small named functions and a header comment listing exactly what it does, where it writes, what it downloads (URLs and checksums), and how to undo it;
    - has no obfuscation, `eval`, base64 decode, `sh -c` of downloaded text, nested `curl | sh`, sudo, shell rc edits, or telemetry;
    - writes only under `~/RECnRun` and the autostart entry named in its header; connects only to `recnrun.com` over HTTPS (and GitHub release assets, if used);
    - wraps everything in `main`, called on the last line, so a truncated download runs nothing;
    - never touches the personal Chrome profile or its data, and never kills Chrome by name;
    - verifies the package's pinned SHA-256 before extracting, refuses on mismatch, and installs atomically;
    - has `--dry-run`, which prints every action and does none, and `--uninstall`, which removes exactly what it installed;
    - is published with its own SHA-256 and a link to its source in the repository, so the served file can be compared with the reviewed one.

    A script check enforces the forbidden-construct list on `install.sh` and on every script in the package (P6.7). The installer trust review (P6.10) asks two AI models whether `install.sh` is safe, and separately reviews the package's scripts. `install.ps1` follows the same rules.

## 5. Protocol v2

**HELLO** `{ protocol: { min, max }, capabilities: string[], epoch, identity }`. Each side takes the highest version in both ranges; with no overlap it answers `INCOMPATIBLE { min, max }` and closes. A worker answers HELLO only from the pinned master key (`UNPINNED_MASTER` otherwise, and no link).

**Envelope** (`v.strictObject`): `{ requestId (uuid), epoch (uint), op, tabRef, documentId?, deadlineMs ≤ 30000, args }`, at most 64 KiB.

| op         | args                                                                                | CDP (worker table, fixed)                                                                                       |
| ---------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `navigate` | `url`: `http`/`https`, ≤ 2048, origin allowed                                       | `Page.navigate`; the main frame's `loaderId` becomes the new `documentId`                                       |
| `wait`     | `selector` (CSS, ≤ 512), `state: attached \| visible \| text`, `text?`, `timeoutMs` | `DOM.getDocument`, `DOM.querySelector`, `DOM.getBoxModel`, bounded polling                                      |
| `type`     | `selector`, `text` ≤ 4096 (inert data, never code)                                  | `DOM.focus`, `Input.insertText`                                                                                 |
| `click`    | `selector`                                                                          | `DOM.scrollIntoViewIfNeeded`, `DOM.getContentQuads`, `Input.dispatchMouseEvent` ×3                              |
| `read`     | `selector`, `what: text \| value`, `maxBytes` ≤ 16 KiB                              | `DOM.resolveNode`, `Runtime.callFunctionOn` with a constant declaration from the table, `Runtime.releaseObject` |
| every op   | (shared checks)                                                                     | `Page.getFrameTree`, `DOM.describeNode`, `Fetch.enable`, `Fetch.continueRequest`, `Fetch.failRequest`           |

- The table is the whole allowlist the static check enforces. If H-CSP fails, adding `DOM.getOuterHTML` for `read` is a reviewed change of the table.
- **Origins.** The allowlist reaches the worker signed by the pinned master at pairing.
  - Before every operation the worker reads the main frame's URL and `loaderId` (`Page.getFrameTree`). An origin outside the list answers `FORBIDDEN_ORIGIN` (this catches redirects and in-page navigation, not only the `navigate` target). A `documentId` other than the current `loaderId` answers `STALE_DOCUMENT`, before any input or read.
  - Before `click`, the worker reads the target's effective destination (`DOM.describeNode`: the closest `a[href]`, `form[action]`, or `formaction`) and refuses a forbidden one with `FORBIDDEN_ORIGIN`. It repeats the document check just before `Input.dispatchMouseEvent`.
  - Network guard, for what a check cannot see (a document change between check and input, a meta refresh): on attach the worker enables `Fetch` for the tab and fails every request to an origin outside the list (`Fetch.failRequest`), so the forbidden POST never leaves Chrome. `[unsure]` that `chrome.debugger` may use `Fetch` on the tab and that pausing every request costs little: P1.6, P1.14.
  - The allowlist is no network isolation for other programs; the container's egress filter stays separate.
- **No code.** Unknown `op`, extra keys, `script`, `expression`, `method`, `params`, and `javascript:`/`data:` URLs fail the schema with `INVALID_COMMAND` before any debugger call.
- **Ledger.** Keyed by master key, clone identity, durable `epoch`, and `requestId`, with a SHA-256 payload digest, in the worker's `storage.local`. A mutating op (`navigate`, `type`, `click`) records `applying` before its first CDP call and `done(result)` before the answer. A repeated `requestId`: `done` with the same digest returns the stored result; another digest returns `PAYLOAD_MISMATCH`; `applying` after a crash returns `OUTCOME_UNKNOWN` and never runs again. An epoch below the highest seen returns `OBSOLETE_EPOCH`. The master journals each request `pending` and re-sends the same `requestId` after reconnecting.
- **Retention.** Every `requestId` of the current epoch is kept until the epoch closes; the cap never evicts inside an epoch. At the cap the worker refuses new requests with `EPOCH_FULL`. The master opens a new epoch at HELLO only after each pending request of the old one has an answer (stored result, `PAYLOAD_MISMATCH`, or `OUTCOME_UNKNOWN`); entries of closed epochs are then dropped, and their requests get `OBSOLETE_EPOCH`. So a dropped request can never look new. Claim: acknowledged mutations are not repeated; not exactly-once.
- One mutating operation at a time per worker; `DETACHED` and `TIMEOUT` are typed and never retried silently.
- **H-CSP** `[unsure]`: `DOM`, `Input`, and `Runtime.callFunctionOn` work under `script-src 'none'; require-trusted-types-for 'script'`. If `callFunctionOn` is blocked, `read` uses `DOM.describeNode`/`DOM.getOuterHTML` with text extracted in the worker. Resolved by P1.13.

> Is the script install.sh in this directory safe to run? What exactly does it do, what does it download, where does it write, and is anything in it dangerous or suspicious?

- ChatGPT side: `codex exec --ephemeral -s read-only -m gpt-6.1-sol -c model_reasoning_effort=high "<prompt>" </dev/null`.
- Claude side: `claude -p "<prompt>"` in a fresh session with read-only tools.
