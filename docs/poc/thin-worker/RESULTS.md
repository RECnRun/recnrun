## W1 lab run (`W.rtc`)

Google Chrome 157.0.8103.38 on Linux (Docker image `sha256:ab532ec9e844`), run `2026-11-06T22-18-09.019Z-886ddf42-a879-4c38-b371-798de8a1d80f`, `vp run lab:web-master` (`tests/lab/web-master/w-rtc.spec.ts`), both variants passed. Fast track: the harness relays the SDP, so the folder signalling and its latency belong to W.fsa.

- **Setup.** The master is a normal root with no extension, opened at `https://recnrun.test:<port>` (secure context, valid chain, no certificate flag; master flags: `--user-data-dir`, `--remote-debugging-port=0` to drive it, `--no-first-run`, `--no-sandbox` for root in the container). Two workers on roots of their own, one headed and one `--headless`, each an unpacked MV3 extension whose offscreen document (`WEB_RTC`) answers with `iceServers: []`.
- **Deviation.** The test CA is trusted through the managed `CACertificates` policy, not Chrome's NSS store: the image has no `certutil`, and the policy is the documented trust path that needs no flag. `recnrun.test` maps to `127.0.0.1` through the runner's `--add-host`.
- **Pass.** For each worker: the offer's only host candidate is an mDNS `.local` name, kept in the SDP; the data channel opened; the page verified the worker's ECDSA P-256 signature, under the key pinned before the offer, over a nonce and both DTLS fingerprints; 100 ping round trips.
- **Selected pairs** (`getStats`): every link is `host` (the page's `.local`, address hidden in stats) to `host` `172.21.0.2` (the worker's plain IP), UDP. The worker offscreen documents offer plain IPs, as the plan expected.
- **Timings** (default / public): answer applied to channel open 3.2 / 2.8 ms (headed) and 7.9 / 6.3 ms (headless); 100 pings 27.9 / 29.2 ms and 36.5 / 35.1 ms; two links from the first offer 586 / 548 ms.
- **Variant `public`.** `--ip-address-space-overrides=127.0.0.1:<stand-in port>=public` scoped to the stand-in's endpoint: CDP reports the document and subresource as `Public` and the page's `initiatorIPAddressSpace` as `Public` (`Loopback` in the default variant), with `localNetworkAccessRequestPolicy: PermissionBlock` in both. The link to the worker's private address still came up with no prompt; `navigator.permissions.query({ name: "local-network-access" })` read `prompt` before and after, so WebRTC did not consult it on this revision `[unsure]` whether a later revision gates WebRTC. The restart repeat is moot with no prompt.
- **Prompts.** None on the display in either variant (`display-default.png`, `display-public.png`).
- **Negative control.** The same spec with the answer's DTLS fingerprint changed by one byte before the page applied it failed: `Error: channel headed did not open` after 20 s (scratch worktree, not committed).
- **Not covered.** macOS (M-TW.13), the real origin (M-TW.12), and the folder signalling (W.fsa).

## W2 lab run (`W.fsa`)

Google Chrome 157.0.8103.38 on Linux (Docker image `sha256:6bdb27d0f509`), run `2026-11-06T22-53-07.297Z-205f196a-f0cb-405e-8495-e345250763df`, `vp run lab:web-master -- tests/lab/web-master/w-fsa.spec.ts`, 2 passed. Evidence: `.artifacts/docker/<run>/evidence/<run>/w-fsa/` (`w-fsa-tab.json`, `w-fsa-app.json`, one display screenshot per step and per prompt).

- **Setup.** The W1 master page at `https://recnrun.test:<port>` picks `~/RECnRun/rendezvous` with `showDirectoryPicker({ id, mode: "readwrite" })` and keeps the handle in IndexedDB. Chrome's picker and prompts are driven with xdotool and scrot (`tests/e2e/fixtures/native-dialogs.ts`). Each restart is an orderly quit (SIGTERM) and a new launch on the same root; the pids in the evidence differ at each restart. Master flags: `--user-data-dir`, `--remote-debugging-port=0` (tab) or `--remote-debugging-pipe` (app), `--no-first-run`, `--no-sandbox`.
- **Pass, both variants.** At every visit the same stored handle reports `queryPermission({ mode: "readwrite" })` `granted`, reads the marker file, and writes a new file the harness reads back. The identity thumbprint (RFC 7638 over the page's master key) is unchanged.
- **Tab (decides): PASS, 5 gestures, all in the onboarding session.** Gestures:
  - click "Choose the rendezvous folder";
  - the picker: type the path, then Open;
  - write prompt: Allow (`tab-onboarding-write-prompt.png`);
  - after the page closes and reopens in the same session, `queryPermission` reads `prompt`: click "Restore folder access";
  - restore prompt "View and edit files from the last time you visited this site": "Allow on every visit" (`tab-onboarding-reopen-prompt.png`).

  The grant then held with no gesture across a page reload, a further page close and reopen, and two restarts (`tab-reopen-open.png`, `tab-restart-1-open.png`, `tab-restart-2-open.png`).

- **Reading applied: the strict one.** Chrome offered "Allow on every visit" before any restart, at the first reopen of the onboarding session. Answering it there counts as onboarding. The later reading (an offer that first appears after a restart) did not arise: no prompt or gesture followed the onboarding reopen.
- **App (recorded): 4 gestures, no restore prompt.** Gestures:
  - install (the omnibox install button for a person; `PWA.install` here);
  - the 3 onboarding gestures of the tab variant, in a tab of the installed origin (`app-onboarding-write-prompt.png`).

  The tab closed, and the app then launched with `PWA.launch` as a standalone window (`display-mode: standalone` true, `app-restart-2-open.png`). That launch and two restarts each read `granted` with no prompt.

- **App records.**
  - Install state: `chrome://web-app-internals` lists `install_state` 1, which is `INSTALLED_WITH_OS_INTEGRATION`. The same state appears after both restarts.
  - `navigator.storage.persist()`: `true`, `persisted()` `true`, both in the tab and in the app.
  - `chrome://discards`, after its internal pages are enabled at `chrome://chrome-urls`: the app tab is not discardable. Its reasons are "Tab is recently visible, Tab is a web application, Tab is currently active, Tab is currently using DevTools".
  - After `PWA.uninstall`, the stored handle opened in a tab reads `prompt`. The extended grant went with the install.
- **Deviation.** CDP registers the `PWA` domain only for a client that allows unsafe operations, which the pipe does and the port does not (`chrome_devtools_session.cc`). So the app variant runs over `--remote-debugging-pipe`. A DevTools install opens in a tab, so `PWA.changeAppUserSettings` sets the display mode to standalone, as the omnibox install would.
- **Negative control.** A scratch worktree answered the restore prompt with "Allow this time" instead of "Allow on every visit". The spec failed with `Expected: "granted"`, `Received: "prompt"`: the page close after onboarding, and both restarts, read `prompt` (not committed).
- **[unsure] Pinned tab.** The tab is a plain tab, not a pinned one. Whether pinning changes the grant was not exercised.
- **[unsure] Gesture count.** The count assumes a person who reopens the page once during onboarding. A person who closes the page and comes back only after a restart meets the same restore prompt then, and answers it once. This run did not exercise that order.
- **Not covered.** macOS and the real origin (M-TW.14), the default profile, a session-restore launch, and the master's folder signalling to workers (later cells).

## W3 lab run (`W.lifecycle`)

Google Chrome 157.0.8103.38 on Linux (Docker image `sha256:852eea83a082`), run `2026-11-06T22-35-09.757Z-08c38dd4-83af-44a9-85af-adfdb29769f7`, `vp run lab:web-master -- tests/lab/web-master/w-lifecycle.spec.ts`, 3 passed. Evidence: `.artifacts/docker/<run>/evidence/<run>/w-lifecycle.json`. Fast track: the harness relays the SDP, as in W1.

- **Setup.** The master page of W1 signs a strict job (ECDSA P-256, key pinned in the worker before the first job) of five ops against a script-free loopback form: navigate, wait, type, click (the POST), read. The worker runs it whole in its MV3 service worker over `chrome.debugger`, keeps a per-op ledger in `storage.local`, writes one result file to `~/Downloads/RECnRun/jobs/<jobId>.json`, and answers `JOB_STATUS`. A lab-only knob stops the runner at a named point (`between`, `applying`, `afterEffect`).
- **1. Page closed between ops.** Stopped before op 2 (type) with no POST yet; the only master page closed (0 master targets), the worker saw its link close 6.1 s later (`closedAt` 1794004515098, `linkClosedAt` 1794004521212), then the runner was released. All five ops DONE; the POST reached the target at 1794004521735, 0.5 s after the link closed, with no master page open. Result file state DONE.
- **2. Reopen.** A new master page linked and got `JOB_STATUS` 237 ms after opening (budget 60 s): one job, DONE, every op outcome, the read result `received <jobId>`, rendered in the page journal. The page sent nothing (`sent` 0); the target saw exactly one POST.
- **3. Kill between effect and ledger.** Stopped after the click's effect (POST count 1) and before its ledger write, with the page closed; worker root killed by pid (561) and restarted on the same root. Restart recovery: job INTERRUPTED, ops DONE, DONE, OUTCOME_UNKNOWN (click), SKIPPED, SKIPPED. The reopened page (217 ms) shows `click unknown`; 3 s later the POST count is still 1 and the page sent nothing: no replay. Result file state INTERRUPTED.
- **Negative control.** A scratch-worktree runner that stops once the link closes failed test 1 at the wait for DONE: the job ended FAILED (`sabotage: master gone`) and the POST never ran (not committed).
- **[unsure] Link-close detection.** A closed page sent no prompt SCTP close; the worker noticed through ICE consent loss (`iceConnectionState` disconnected), about 6 s. The runner does not depend on it; only the test uses it to prove ordering.
- **[unsure] Lab flags.** The worker root runs with `--remote-debugging-port=0` and `--enable-unsafe-extension-debugging` so the harness can drive it, and is installed as `install.sh` does (pipe install, Developer mode, reload). A root without them is not exercised here.
- **Not covered.** PWA master and sleep or suspend (not cheap in Docker), cancel, replay of a resubmitted job, macOS, and M-TW.15.

## W4 lab run (`W.trust`)

Google Chrome 157.0.8103.38 on Linux (Docker image `sha256:783e3f2d39de`), run `2026-11-06T23-05-22.232Z-3c627f27-b75e-4a94-97e2-5e683becead4`, `vp run lab:web-master` (all cells), 11 passed, the four W.trust tests among them. Evidence: `.artifacts/docker/<run>/evidence/<run>/w-trust.json` and `w-trust/` (prompt screenshots). Fast track: the harness relays the SDP and stands in for the onboarding script, which alone pins the master key and the allowlist in the worker (`lab.provision`).

- **1. Site update.** The stand-in served a rebuilt site, every script renamed (`/master-v2.js`). The reopened page kept the key thumbprint and linked with no new pairing; a job before and a job after both ran DONE with one POST each.
- **2. Cache-only clear.** `Network.clearBrowserCache` and `Storage.clearDataForOrigin` with `cache_storage`: same thumbprint, a job ran DONE.
- **3. Changed same-origin code.** A variant page adds `hostile.js`, which opens the origin's IndexedDB, takes the non-extractable master key, and signs whatever it likes, with no owner action. A job inside the allowlist ran DONE with one POST: the risk is measured, not assumed. Refused before acceptance, with no ledger entry and no POST: origin outside the allowlist and `navigate` outside the job's origins (`FORBIDDEN_ORIGIN`); a job carrying its own `allowlist`, an `evaluate` op, a `script` argument, a `javascript:` URL, 33 ops, a deadline 10 min + 1 ms after issue, an op timeout of 30 001 ms, `text` of 4 097, a selector of 513, `maxBytes` of 16 385, and a job over 64 KiB (`INVALID_COMMAND`). `provision`- and `allowlist`-typed messages over the link changed nothing: the worker's pinned record read back equal. The origin outside the allowlist (a second loopback form server) received 0 POSTs.
- **4. Site-data clear.** `Storage.clearDataForOrigin` with `all` dropped the key and the folder handle (`handle: false`). The reopened page showed "Pair again", held no key 2 s later, and refused to sign (`PAIR_AGAIN`): it made no key by itself. After the owner's "Pair again" (a new thumbprint), the worker answered `UNPINNED_MASTER` to that key's job, with no ledger entry and no POST. The folder had to be chosen again (3 gestures, as at onboarding: click, picker, write prompt), so recovery cost 4 gestures plus the onboarding script. Once the script pinned the new key, a job ran DONE.
- **Defects fixed in this cell** (plan §4: a fail-closed failure is the spike's defect). The worker's job check had no argument caps: `text` over 4 096 and `maxBytes` over 16 KiB were ACCEPTED and ran (red run `2026-11-06T23-00-34.692Z-26231483-e8f4-48ca-a9f6-ff28e2661210`); it now caps `selector`, `text`, `maxBytes`, `state`, and `what`. A job from another key answered `BAD_SIGNATURE`; it now answers `UNPINNED_MASTER`. The page made a key on first use; it now makes one only on the owner's explicit pairing (`lab.pair`, the "Pair again" button).
- **Negative control.** A scratch-worktree worker whose signature check accepts any key failed test 4: the new key's job was ACCEPTED instead of `UNPINNED_MASTER` (not committed).
- **Storage persistence.** `navigator.storage.persist()` answered `false` (`persisted()` `false`) in the tab of this run. `[unsure]` why W2 recorded `true` for the same page; site engagement or the folder grant may count. The app variant was not asked here; W2 has its answer.
- **Residual risk.** Any code the origin serves, a compromised deploy or a supply-chain change of recnrun.com included, can use the stored key with no owner action and no visible sign: `extractable: false` stops export, not `sign()`. It can do whatever the five ops can do on the allowlisted origins, in the workers' logged-in sessions, within the caps: navigate, type, click, wait, and read up to 16 KiB per read and 64 KiB per job, up to 32 ops, one job at a time, and it can read the outcomes of earlier jobs through `JOB_STATUS`. What bounds it: the closed op set and its argument caps, the allowlist that only the onboarding script writes (no page message changes it), the per-job caps, the ledger (no replay of an accepted mutation), and the pin, which fails closed when the key is lost. A key the owner revokes is replaced only through the onboarding script. Compared with the Store master, the trusted code base grows from a reviewed extension package to whatever the origin serves at each visit.
- **Not covered (Phase 1 after a GO, PW-plan dispositions).** No `HELLO` handshake in the lab: the pin is enforced on each job's signature, so an unpinned page can still link and ask `JOB_STATUS`. No destination check or network guard (finding 2): an allowlisted page whose form posts elsewhere is not exercised. A future `issuedAt` passes the 10-minute span check, and the runner does not enforce `deadlineAt` (finding 6). The app variant, macOS, and the real recnrun.com origin.
