# E2: probe write and real path

Task P1.3 of [PLAN.md](../PLAN.md). The `poc-d0` build, installed unpacked over CDP (`diagnostic`), writes a probe through `chrome.downloads.download` from its service worker and its diagnostics page reads it back through `file://`. Environments: Google Chrome 157.0.8103.38 on Linux (Ubuntu noble) in Docker (lab, full run `2026-11-03T23-36-54.382Z-9c60631f`, smoke run `2026-11-03T23-44-32.508Z-db206fa7`) and the installed Google Chrome 156.0.8078.80 on macOS 27.0.1 (26A434) arm64 (host run `host-2026-11-03T23-38-29.899Z`). The lab image moved from 156 (Gate P0) to 157 between gates; CHROMIUM.md stays pinned at 156. Verdict files: [lab full](verdicts/E2-lab-full.json), [lab smoke](verdicts/E2-lab-smoke.json), [lab versions](verdicts/E2-lab-versions.json), [host](verdicts/E2-host.json).

## Question

Can an extension with no folder picker and no write grant write a file under its own Downloads root, learn that file's absolute path, and read the same bytes back through `file://`?

## Hypotheses

Every cell runs on a throwaway profile root whose `Default/Preferences` sets `download.default_directory` to `<root>/downloads` before launch, except `E2.location.default` (no directory set: the lab container's `~/Downloads`, and on the host only `~/Downloads/RECnRun/poc-downloads-launcher/<run>/`, files deleted by their reported path). Samples are 3 in the full run and on the host, 1 in smoke; `E2.overwrite.100` writes 100 times per sample (5 in smoke).

## Observation

- Write and path: every write completed, on both environments, and `DownloadItem.filename` was the absolute path under the configured root (`<root>/downloads/RECnRun/poc/<ns>/probe.json`). The `file://` URL built from it read the same bytes from the extension page; the fresh unpacked install had file access on and needed the POC `file:///*` host permission (P1.1 follow-up).
- Overwrite: 100 writes per sample, 3 samples on each environment, always one `probe.json` and the last content; never a `(1)` name. About 3 to 4 ms per write in the lab and 73 to 97 ms on the host.
- Names Chrome produced: `probe.json` (empty content), `probe with spaces.json`, `próbé 日本.json`, `probe#1.json` unchanged; `probe%20x%.json` became `probe_20x_.json`; `probe?x=1.json` was refused with `Invalid filename`. The `?` refusal is the failure of `E2.content.roundTrip`, identical on both environments.
- Interrupted (Codex P1 finding 6 split the cell in two; lab run `2026-11-04T00-21-10.223Z-9d433758-dbe3-48d7-852c-ae04e326fdc9`, host run `host-2026-11-04T00-20-53.258Z`, 3 samples each): while the stalled download ran, the target folder held only the previous `probe.json` and `Unconfirmed <n>.crdownload`, and the tolerant reader answered `fresh` with the exact previous publication. A cancel settled as `interrupted` / `USER_CANCELED` (1 request). With the source down after the drop, Chrome restarted the request once by itself (2 requests, none with `Range`), the restart failed, and Chrome settled the item `interrupted` / `NETWORK_FAILED` with no cancel from the harness; the item then reported `<root>/downloads/stall.json`, the URL's name, not the suggested `RECnRun/poc/<ns>/probe.json`. In both cases `probe.json` kept its bytes, the reader still answered the exact publication, and neither a `.crdownload` nor a file under the URL's name remained (`bytesReceived` 0 on the settled item). The verdict requires each of these: a run with no partial seen, or a download already `complete`, fails (`tests/experiments/downloads-interrupted.test.ts`). An earlier round, whose source came back stalled after the drop, saw the restart keep running past 15 s until the cell cancelled it, so that round proved no automatic cleanup. A `data:` URL, the probe's source, has no connection to drop.
- Save As (lab): a GTK window titled "Save File" opened for a `saveAs: false` call; one Escape closed it, the call answered `interrupted` / `USER_CANCELED` with an empty `filename`, and nothing was written. Screenshots under `.artifacts/screens/P1.3/`.
- Location: the custom root and the default root were both learned from `filename`. The default cell wrote to the container's `~/Downloads` in the lab and to the run folder under the owner's `~/Downloads` on the host; each reported file was deleted, and on the host `left` was empty and `~/Downloads/RECnRun` no longer existed afterwards.
- Traces: no new X window in the lab; the screenshot shows the toolbar download bubble ("probe.json 145 B • Done"); the one write left one entry in `chrome.downloads.search` on a fresh profile; D0 declares no notifications permission, so only Chrome's own download UI appears. Windows are not observable on the host.
- Harness: Playwright's `connectOverCDP` sends `Browser.setDownloadBehavior` with `allowAndName` and its own folder, so every download got a GUID name under `/tmp/playwright-artifacts` until each cell reset it to `default` (now in the observer allowlist).

## Prediction check

[CHROMIUM.md group 4](../CHROMIUM.md#4-downloads-destination-filename-conflictaction-saveas) predicted that a relative portable path is accepted, an absolute or `..` path is refused, `%` becomes `_`, `overwrite` replaces in place, and "Ask where to save each file" prompts even with `saveAs: false`. Lab and host agree with each of these. They go beyond it in two places: `?` is refused rather than rewritten, so `%` is not the only URL-encoding character a name must avoid; and an automatically restarted network download loses the creator's suggested name, a case group 4 does not cover.

## What it means for the plan

- §14 question 1, "write and read back": yes for D0 installed unpacked, on both environments, with no picker and no write grant, as long as "Ask where to save each file" is off; with it on, every write is a counted gesture.
- Names under `RECnRun/poc/` stay inside `[a-z0-9-]`, as `probePath` already enforces: no `%`, no `?`, nothing URL-shaped.
- Publications are written from `data:` URLs only; a network source could restart under another name, outside the rendezvous layout.
- A write shows the download bubble and adds a download history entry; whether 100 overwrites keep one entry or 100 was not measured, and P3.6 has to count it against the presence rate.
