# E2: probe write and real path

Task P1.3 of [PLAN.md](../PLAN.md). The `poc-d0` build, installed unpacked over CDP (`diagnostic`), writes a probe through `chrome.downloads.download` from its service worker and its diagnostics page reads it back through `file://`. Environments: Google Chrome 157.0.8103.38 on Linux (Ubuntu noble) in Docker (lab, full run `2026-11-04T00-23-27.338Z-efaba3ab-2547-40a6-b883-c3fd4f6dec0e`, smoke run `2026-11-04T00-24-26.752Z-82231c17-1aff-42ac-a408-278c1a143080`) and the installed Google Chrome 156.0.8078.80 on macOS 27.0.1 (26A434) arm64 (host run `host-2026-11-04T00-24-46.606Z`). The lab image moved from 156 (Gate P0) to 157 between gates; CHROMIUM.md stays pinned at 156. These runs follow the Codex P1 review fixes 2, 3, 5, 6, 8, and 9 (every verdict now carries `gestures` and `steps`; a harness error fails the test instead of becoming a sample). Verdict files: [lab full](verdicts/E2-lab-full.json), [lab smoke](verdicts/E2-lab-smoke.json), [lab versions](verdicts/E2-lab-versions.json), [host](verdicts/E2-host.json).

## Question

Can an extension with no folder picker and no write grant write a file under its own Downloads root, learn that file's absolute path, and read the same bytes back through `file://`?

## Hypotheses

Every cell runs on a throwaway profile root whose `Default/Preferences` sets `download.default_directory` to `<root>/downloads` before launch, except `E2.location.default` (no directory set: the lab container's `~/Downloads`, and on the host only `~/Downloads/RECnRun/poc-downloads-launcher/<run>/`, files deleted by their reported path). Samples are 3 in the full run and on the host, 1 in smoke; `E2.overwrite.100` writes 100 times per sample (5 in smoke).

## Observation

- Write and path: every write completed, on both environments, and `DownloadItem.filename` was the absolute path under the configured root (`<root>/downloads/RECnRun/poc/<ns>/probe.json`). The `file://` URL built from it read the same bytes from the extension page; the fresh unpacked install had file access on and needed the POC `file:///*` host permission (P1.1 follow-up).
- Overwrite: 100 writes per sample, 3 samples on each environment, always one `probe.json` and the last content; never a `(1)` name. About 4 ms per write in the lab and 77 to 92 ms on the host.
- Names Chrome produced: `probe.json` (empty content), `probe with spaces.json`, `próbé 日本.json`, `probe#1.json` unchanged; `probe%20x%.json` became `probe_20x_.json`; `probe?x=1.json` was refused with `Invalid filename`. The `?` refusal is the failure of `E2.content.roundTrip`, identical on both environments.
- Interrupted (Codex P1 finding 6 split the cell in two; 3 samples each in the full lab and host runs): while the stalled download ran, the target folder held only the previous `probe.json` and `Unconfirmed <n>.crdownload`, and the tolerant reader answered `fresh` with the exact previous publication. A cancel settled as `interrupted` / `USER_CANCELED` (1 request). With the source down after the drop, Chrome restarted the request once by itself (2 requests, none with `Range`), the restart failed, and Chrome settled the item `interrupted` / `NETWORK_FAILED` with no cancel from the harness; the item then reported `<root>/downloads/stall.json`, the URL's name, not the suggested `RECnRun/poc/<ns>/probe.json`. In both cases `probe.json` kept its bytes, the reader still answered the exact publication, and neither a `.crdownload` nor a file under the URL's name remained (`bytesReceived` 0 on the settled item). The verdict requires each of these: a run with no partial seen, or a download already `complete`, fails (`tests/experiments/downloads-interrupted.test.ts`). An earlier round, whose source came back stalled after the drop, saw the restart keep running past 15 s until the cell cancelled it, so that round proved no automatic cleanup. A `data:` URL, the probe's source, has no connection to drop.
- Save As (lab): a GTK window titled "Save File" opened for a `saveAs: false` call; one Escape closed it, the call answered `interrupted` / `USER_CANCELED` with an empty `filename`, and nothing was written. Screenshots under `.artifacts/screens/P1.3/`.
- Location: the custom root and the default root were both learned from `filename`. The default cell wrote to the container's `~/Downloads` in the lab and to the run folder under the owner's `~/Downloads` on the host; each reported file was deleted, and on the host `left` was empty and `~/Downloads/RECnRun` no longer existed afterwards.
- Traces, history (lab and host): one write on a fresh profile left exactly one `chrome.downloads.search` entry, the probe's path; after 100 more overwrites of one name the history held 101 entries, on both environments: every overwrite is a history entry of its own, though the folder keeps one file. Traces, UI (lab only): xdotool listed `RECnRun diagnostics - Google Chrome`, `google-chrome`, and `Chromium clipboard` before and after the write and no new window; the screenshot shows the toolbar download bubble ("probe.json 145 B • Done") inside Chrome's own window (`.artifacts/screens/P1.3/E2-traces-ui.png`). D0 declares no notifications permission, so only Chrome's own download UI appears. On the host neither the windows nor the bubble were observed: that cell is `unavailable`, not a pass.
- Harness: Playwright's `connectOverCDP` sends `Browser.setDownloadBehavior` with `allowAndName` and its own folder, so every download got a GUID name under `/tmp/playwright-artifacts` until each cell reset it to `default` (now in the observer allowlist).

## Prediction check

[CHROMIUM.md group 4](../CHROMIUM.md#4-downloads-destination-filename-conflictaction-saveas) predicted that a relative portable path is accepted, an absolute or `..` path is refused, `%` becomes `_`, `overwrite` replaces in place, and "Ask where to save each file" prompts even with `saveAs: false`. The lab agrees with each of these; the host agrees with each except the prompt, which it could not observe (`E2.saveAs.prompt` is `unavailable` there). They go beyond it in two places: `?` is refused rather than rewritten, so `%` is not the only URL-encoding character a name must avoid; and an automatically restarted network download loses the creator's suggested name, a case group 4 does not cover.

## What it means for the plan

- §14 question 1, "write and read back": yes for D0 installed unpacked, on both environments, with no picker and no write grant, as long as "Ask where to save each file" is off; with it on, every write is a counted gesture.
- Names under `RECnRun/poc/` stay inside `[a-z0-9-]`, as `probePath` already enforces: no `%`, no `?`, nothing URL-shaped.
- Publications are written from `data:` URLs only; a network source could restart under another name, outside the rendezvous layout.
- A write shows the download bubble (lab) and adds a download history entry (lab and host), and 100 overwrites leave 101 entries: P3.6 has to count the history growth against the presence rate, and a publisher that overwrites often may need to erase its own entries (`chrome.downloads.erase`), to be measured there.
