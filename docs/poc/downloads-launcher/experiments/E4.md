## Question

§14 question 3: "Como as raízes reais de Downloads e os perfis são descobertos sem configuração manual?" How does the launcher learn, with nothing typed by a person, which Downloads folder each profile really writes to, and which profile is which?

## Method

The extension (`poc-d0`) gains one page and one message. `chrome-extension://<id>/bootstrap.html#token=<uuid>` accepts only a fragment that is exactly `#token=` and a lowercase v4 uuid (Valibot, `src/diagnostics/bootstrap.ts`), stores the token as the session's boot (`session:pocBoot`), and asks its own worker, with `POC_PUBLISH_PRESENCE`, to publish its presence at once instead of waiting for the next 30 s period; the worker answers only its own extension pages. Each extension makes three calls and no other, all on its own profile:

- `chrome.downloads.download` of its own `RECnRun/poc/lab/peers/<profileId>/presence.json`, a relative path that Chrome resolves against the profile's own download folder (P2.2);
- `chrome.downloads.search({ id })` of the item that download just created, to learn its own root from the absolute filename (kept in `session:pocDownloadsRoot`); it never searches without an id and never looks at another profile's downloads;
- `fetch(file://<own root>/RECnRun/poc/lab/registry.json)` from its diagnostics page, through `window.__poc.readRegistry()`, which validates the file with `readRegistry` (`RegistrySchema`). No extension writes `registry.json`.

The launcher is a Node stand-in (`tests/experiments/fixtures/e4-launcher.ts`) until P4.2 writes it in `sh`. For each profile it runs `<Google Chrome> --user-data-dir=<root> chrome-extension://<id>/bootstrap.html#token=<uuid>` with a fresh `crypto.randomUUID()` token (plus `--no-sandbox` in the container, and the off-screen and mock-keychain flags on the host), so that process hands the URL to the Chrome already running on the root and exits. It then scans each candidate Downloads folder for `RECnRun/poc/lab/peers/*/presence.json` whose `boot` is the token, every 100 ms for up to 15 s. The candidates are the OS default Downloads folder and every `downloadsRoot` of its record. Once it finds the token, it takes the `profileId` from the presence that carries it and writes that id and the presence's folder, as `downloadsRoot`, into the profile's record block; the identity the harness knows serves only to check it: a token found in no candidate or outside the profile's own folder, a token carried by more than one presence, or a presence naming another profile fails the sample (`bindingOf` in `tests/experiments/fixtures/e4-run.ts`). It then runs `scripts/poc-cross-profile/catalog.sh <record> lab <root>/RECnRun/poc/lab` once per distinct root, one after the other; `catalog.sh` is the only writer of `registry.json`.

In the lab, a session starts only inside the test container (`RECNRUN_TEST_CONTAINER=1` and `/.dockerenv`, the policy install's guard) with `$HOME` equal to the container user's home and no symbolic link on the way to `Downloads/RECnRun/poc`, before it clears that namespace folder of the default (Codex P2 finding 1). A harness failure (a scanned folder or file that cannot be read, a presence that exists but is not JSON, a process that cannot start or ends on a signal, a native reader that cannot run) fails the test and writes no verdict; only a missing folder or file is absence, and only `UnavailableError` marks a method unavailable (finding 5).

The harness launches each profile with `Extensions.loadUnpacked` after `Browser.setDownloadBehavior { behavior: "default" }` (the silent-start pattern of P2.2), so Chrome's own download setting takes the first presence. A profile's folder is set by writing `download.default_directory` into its `Preferences` before the first launch. In the lab, a profile "on the OS default" has no such key; on the host it gets a stand-in folder, because E4 does not write to `~/Downloads`. Only the harness knows which folder each Chrome downloads to, and it checks the launcher's findings against that; it never hands this to the launcher. Observations name folders by label (`<default Downloads>`, `<launcher folder>`, `<custom folder>`) and profiles by name (A, B, P, Q), never by path or id.

Samples: 3 full and 1 smoke (lab), 3 (host); the smoke run gave the same verdicts. In every sample of E4.a and E4.b.differentRoots the scan found exactly one presence carrying each token (`foundIn` lists every match), and that presence named the profile the harness had opened; in E4.b.customRoot, B's token matched none. Gestures: 0 everywhere. Every cell starts two fresh roots (one for E4.c on the host).

## Observation

- Opening: every opening, lab and host, exited 0 within the 15 s limit and never had to be stopped, and Chrome then listed exactly one bootstrap tab on the profile. The page received the fragment: the next presence carried the token as its `boot`.
- Learned roots: in every sample, each profile's `session:pocDownloadsRoot` was the folder its Chrome downloads to (`ownRoot` in the observations), the default, the launcher folder, the custom folder, and the typed folders alike.
- E4.a: one root id, `r1`; `registry.json` listed A and B on `r1`; both profiles read it `fresh` with A and B.
- E4.b.differentRoots: the scan found A's token in the default and B's in the launcher folder; `catalog.sh` numbered them `r1` and `r2` and wrote both into the record; each of the two registries listed A on `r1` and B on `r2`; A read the default's copy and B the launcher folder's, both `fresh` with A and B.
- E4.b.customRoot: A's token was found in the default; B's never appeared there during the 15 s scan, though the harness found it in the custom folder (`tokenInCustom: true`), and B's worker had learned that folder as its root. Verdict `fail`, the expected limit, in every sample, lab and host.
- E4.b.closedProfile: right after B's Chrome quit, `catalog.sh` exited 0 and still listed A and B; its presence was still valid. The sample requires this run, and fails on any other exit code or listing (finding 9). The sample then rewrote B's presence with `createdAt` 62 s and `expiresAt` 2 s in the past, in the exact bytes the extension writes. The next run exited 0, logged `catalog.sh: skipped r1/<B>: expired`, and wrote A alone, and A read `fresh` with A alone; the sample requires all three. Each observation says `expiry: "forced"`. The sample did not wait out `PRESENCE_TTL_MS` (60 s), so the time a quit profile stays listed is that TTL after its last write, by construction; it was not timed.
- E4.c: after each Chrome quit, a JSON read of `Default/Preferences` gave P's own folder (lab and host). In the lab, Q, left on the default, had no `download.default_directory` at all. On the host, `plutil -extract download.default_directory raw -o - <root>/Default/Preferences` returned P's folder in 3 of 3 samples. When the key is missing, `plutil` exits 1 with `No value at that key path or invalid key path` (a scratch file); the reader returns no folder for that exit and message only, so the sample records a fail, and any other `plutil` failure is a harness error.
- E4.d: typed folders `r1` and `r2`; both registries listed both profiles; both read them `fresh`.

The opening still exited 0 and left a tab, but no presence carried the token.
- Unit tests and manifest checks, against stubs and the builds before the page existed: see the P2.1 `red:` line in [CHECKLIST.md](../CHECKLIST.md).
- `plutil` on a `Preferences` with no `download.default_directory`: exit 1, as above.

## Prediction check

1. The command-line URL opened one tab on the bootstrap page with its fragment, forwarded to the Chrome already running on the root. Neither process carried `--enable-automation`, and the build declares no `web_accessible_resources`. Holds in the lab and on the host.
2. A profile whose `Preferences` names a folder wrote its presence there, and `chrome.downloads.search` reported a filename under it. Holds in both environments.

4. `Preferences` held `download.default_directory` only when it had been set. Holds in the lab (Q had no key); not measured on the host.

## Answer to §14 question 3

> The launcher already knows each profile's user-data-dir, because it creates or registers the profiles. It learns each profile's identity and real Downloads root with no manual configuration by opening the profile once on `chrome-extension://<id>/bootstrap.html#token=<uuid>`. The extension adopts the token as its boot and writes its presence through `chrome.downloads` into whatever folder its Chrome downloads to. The launcher finds the presence that carries the token by scanning the OS default Downloads folder and the roots its record already names, writes the `profileId` that presence carries and its folder into the profile's record block, and runs `catalog.sh`, the single writer of `registry.json`, once per root. Each extension then reads the registry from the root it learned from its own download. In E4 this held for two profiles sharing one root and for two profiles on two roots (one created by the launcher), on Google Chrome 157 in the Linux lab and 156 on the macOS host, 3 of 3 samples each: every token led to exactly one presence, whose `profileId` the record took and which was the profile the launcher opened. There are two limits. First, a profile whose owner pointed its Downloads folder somewhere that is neither the OS default nor a root the launcher knows is not found by the scan (E4.b.customRoot fails in both environments). On macOS, `plutil` reads that folder from the profile's `Preferences` (E4.c passes on the host), so it can become a candidate, but the scan and the read were not combined in one measurement. On Linux no native reader exists (`unavailable`). Second, a profile that was closed stays in the registry until its last presence expires, at most `PRESENCE_TTL_MS` (60 s) after its last write. `catalog.sh` then drops it, but only on its next run. On the host the "OS default" candidate was a stand-in folder, since E4 neither writes nor scans `~/Downloads`. The real macOS default is predicted by the Chromium source, not measured.

## Limits of this measurement

- Host default: the OS default Downloads candidate on the host was a throwaway folder written into each root's `Preferences`, not `~/Downloads`; the lab measured Chrome's real Linux default, `$HOME/Downloads`.
- The launcher is a Node stand-in; P4.2 has to reproduce the scan, the token, and the record update in POSIX `sh`, and the opening of a Chrome the owner started (not launched by the harness with remote debugging) is measured there.
- Installs are diagnostic (`Extensions.loadUnpacked` over CDP); the owner's `Load unpacked` gesture is M-P1.a.
- E4.b.closedProfile wrote an already expired presence instead of waiting 60 s, and runs `catalog.sh` by hand; when the launcher reruns it is P4's choice.
- E4.c on Linux records what a JSON read sees, not a launcher reader. Owner decision 2026-11-04: P4.2 reads the key in POSIX `sh` (`plutil` where present, `sed` over Chrome's compact JSON otherwise) and uses it only as a scan candidate, with the OS default, the record's roots, and a bounded `find` as fallbacks (PLAN.md P4.2); `catalog.sh` still parses no JSON (decision 11).
- One namespace (`lab`), at most two profiles per cell, and no concurrent `catalog.sh` runs (their lock is covered by the P2.3 checks). Windows: not executed.

## What it means for the plan

- P2.3's layout holds as written: E4 needed no change to `presence.json`, `registry.json`, the record, or `catalog.sh`; decision 11 now names the bootstrap page and its token. P3.3 later added the identity statement `{ key, signedAt, signature }` to `presence.json`, after `fingerprint`; `catalog.sh` checks its form and does not copy it into `registry.json`, and the smoke cell of this spec reran with it on 2026-11-04 with the same verdicts (lab run `2026-11-04T09-56-02.090Z-0d26bda2`).
- P4.2: the launcher's candidates are the OS default, the record's roots, and on macOS the `plutil` value of each profile's `Preferences`. On Linux, a custom folder needs the manual path of E4.d, or a launcher that sets `download.default_directory` itself when it creates the profile, as E4.b.differentRoots does with its own folder.
- Closed profiles: the launcher reruns `catalog.sh` after a profile quits and again once that profile's presence can have expired. Each peer entry carries the presence's `expiresAt`, so readers could also drop expired peers; that is not measured.
