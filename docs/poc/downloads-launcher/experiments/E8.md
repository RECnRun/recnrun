# E8: the launcher finds a profile's Downloads root

Task P4.2 of [PLAN.md](../PLAN.md), build variant `poc-d0`, installed unpacked over CDP (`diagnostic`, external client true), no debugger, namespace `lab`. This report covers the five root cells (run C of P4.2) and the eight discovery cells (run D). Lab: Google Chrome 157.0.8103.38 on Linux (Ubuntu noble) in Docker on Xvfb (image `sha256:f0ef04a4…`), full run `2026-11-04T22-58-06.135Z-e9146103-bb60-4f18-b435-ce288aa2e0d1`, 14 tests passed. Host: Google Chrome 156.0.8078.80 on macOS 27.0.1 (arm64), run `host-2026-11-04T22-35-29.327Z`, the five root cells only, **smoke mode** (one sample each, 0 gestures; the owner's decision for host cells from P4). Verdict files: [lab](verdicts/E8-lab.json), [lab versions](verdicts/E8-lab-versions.json), [host](verdicts/E8-host.json), [host versions](verdicts/E8-host-versions.json). The chain under test is `scripts/poc-cross-profile/discovery.sh` (run A of P4.2) and the discovery commands of `scripts/poc-cross-profile/profiles.sh` (run B); the source read before measuring is [CHROMIUM.md group 11](../CHROMIUM.md#11-opening-a-profiles-extension-page-and-its-downloads-folder).

## Question

Given a profile's user-data directory and a token the launcher opened it with, does the launcher's one shell chain find the Downloads root that the profile's extension really writes to, at the step the topology says, verifying each candidate only by the presence that carries the token, and does it report every candidate tried when no presence does?

## Method

`tests/experiments/E8-launcher-discovery.spec.ts` reuses the E4 session fixtures (`fixtures/e4-profiles.ts`, `e4-run.ts`, `e4-lab.ts`): each sample starts a real profile with `poc-d0`, opens its bootstrap page with a fresh token (the extension adopts it as its `boot`), and waits until the presence carrying the token is in the profile's Downloads folder. It then runs the chain itself, `discovery.sh profile_downloads_root <root> <profileDirectory> <record> lab <token>`, with `execFile` (fixed arguments, no shell string; `tests/experiments/fixtures/e8-discovery.ts`) and an environment of its own: `HOME` is a throwaway folder (the lab's own home for `osDefault`, so Chrome's real default is under it), so the bounded find stays inside it. The sample also runs `downloads_root_candidates`, `pref_download_dir`, `record_roots`, and `find_presences` on the same inputs, to show which step supplies which candidate. The lab has no `plutil`, so step 1 is the `sed` reader.

A sample holds when the chain exits 0 and prints the expected root (or exits 66 with empty stdout and every candidate on stderr), and the candidate list and the output of steps 1, 3, and 4 equal what the topology predicts (`tests/experiments/e8-chain.ts`, unit-tested in `e8-chain.test.ts`). Folders are labelled in the observations; no path is stored. Where a cell must leave step 1 empty, it reads a profile directory the root does not have (`Profile 9`), which is the same output as a key absent; `osDefault` in the lab reads the real `Default`. Samples: 3, gestures 0 in the lab; the host ran one sample per cell (smoke).

## Observation

- E8.root.preferences: in 3 of 3 samples the candidates were the custom folder then the OS default, step 1 printed the custom folder, and the chain exited 0 printing it (`chainMs` 9, 9, 9).
- E8.root.osDefault: in 3 of 3 samples the key was absent from the real `Default/Preferences` (step 1 printed nothing), the only candidate was the OS default, and the chain printed it (5 ms). The bounded find also saw that presence under `HOME`.
- E8.root.record: in 3 of 3 samples the candidates were the OS default then the record's folder, step 3 printed it, step 4 found nothing (the folder is outside `HOME`), and the chain printed it (4 ms).
- E8.root.find: in 3 of 3 samples the record was empty of roots, step 1 printed nothing, and `find_presences` found the folder two levels under `HOME`; the chain printed it (4 ms).
- E8.root.notFound: in 3 of 3 samples the chain exited 66 with nothing on stdout, and stderr listed the custom folder, the OS default, and the record's folder, in that order (8 to 10 ms). The profile's presence was there, carrying the extension's own boot, so a path that holds some presence is still not accepted without the token.

Discovery cells, 3 of 3 samples each:

- E8.discovery.chromeClosed: `profiles_in_root` printed `Default` then `Profile 2`, and `bind_profiles` printed both `distinct` from the presences left in their own Downloads folders (13 to 16 ms after the profiles quit).
- E8.discovery.defaultOpen: with `Default` open, `bind_profiles` listed it only after Chrome had flushed its `Preferences` (`visibleMs` 10116 to 10153: before the flush `extension_in_profile` finds no entry and the profile is not listed), then both `distinct`.
- E8.discovery.secondaryOpen: `Profile 2` open and `Default` quit, both bound after about 10 s. Chrome's display name for `Profile 2` in `Local State` was "Person 1"; after the harness quit it and renamed it "Work display name", the bindings were identical, each named by `Default` and `Profile 2`.
- E8.discovery.severalRoots: `chrome_roots` printed the default root (`$XDG_CONFIG_HOME/google-chrome`) then the record's `userDataDir`; one profile in each bound `distinct` (`visibleMs` 9625 to 9643, one profile open).
- E8.discovery.fixedId: `extension_in_profile` printed `unpacked` (exit 0) for `Default` of both roots and printed nothing (exit 1) for `Profile 3`, a real Chrome profile without the extension; both extensions answered with `omllgeochjfpkjbkpcgjmnnbncdpiedd`.
- E8.discovery.unpackedPaths: the build copied to two folders (three paths with the original) loaded under the same id in two roots; both bound.
- E8.discovery.extensionUpdated: the worker reported `0.1.0` before and `0.1.1` after `Extensions.loadUnpacked` of a copy with the bumped version, under the same id; once quit, the profile read `unpacked` and bound.
- E8.discovery.extensionRemoved: the extension called `chrome.management.uninstallSelf({ showConfirmDialog: false })` in its own worker, which never replied (it was gone; the harness waits 30 s); after the quit `extension_in_profile` exited 1 with nothing and `bind_profiles` listed only the other profile, while the removed profile's presence file was still in its Downloads folder.

### What the measurement changed

The first lab run of `E8.discovery.extensionRemoved` (smoke, then run again alone) recorded `fail`: `extension_in_profile` printed `unpacked` for the removed extension, and `bind_profiles` still listed it. Chrome 157 leaves `"extensions":{"settings":{"<id>":{}}}` in `Preferences` after an uninstall, an empty entry, which `profiles.sh` read as installed. `profiles.sh` now requires the entry to have content (`"<id>":{` followed by anything but `}`), and `profiles.checks.mjs` has an `Uninstalled` fixture for it; the cell then passed in 3 of 3.

## Limits of this measurement

- The lab ran the `sed` reader only; the `plutil` reader is the host's, and is exercised there and by `discovery.checks.mjs`.
- One namespace (`lab`). The discovery cells give each profile a Downloads folder of its own, so `shared` and `unbound` bindings are exercised by `profiles.checks.mjs`, not here.
- The discovery cells run on Linux (`$XDG_CONFIG_HOME/google-chrome` is the OS default root); the macOS default root is covered by `profiles.checks.mjs` fixtures. A secondary profile is started with `--profile-directory`, which a person's Chrome also gets from its profile picker.
- The extension is removed by its own `chrome.management.uninstallSelf`, not from `chrome://extensions` with a click; the preferences effect is Chrome's uninstall either way, but the owner's gesture is not measured.
- Chrome flushes a running profile's `Preferences` after about 10 s, so a scan of an open profile within that time does not list it; the launcher must scan after that, or ask the profile (P4.3).
- The lab's `HOME` for `osDefault` is the container user's home, with `~/Downloads/RECnRun/poc` cleared before each sample; the other cells use a throwaway `HOME`.
- The host cannot use `~/Downloads` and cannot leave the key absent (its Preferences name a stand-in), so its `osDefault` cell reads a profile directory the root lacks, with `HOME` a throwaway folder whose `Downloads` the profile writes to.
- Installs are diagnostic (`Extensions.loadUnpacked` over CDP); the owner's `Load unpacked` gesture is M-P1.a.

## Host

Run `host-2026-11-04T22-35-29.327Z` on this Mac, Google Chrome 156.0.8078.80 (macOS 27.0.1, arm64), the five root cells, `mode: "smoke"` (one sample each, 0 gestures): all five `pass` (`chainMs` 23, 23, 19, 19, 23). The chain read `Preferences` with `plutil`; the cells and their expected steps are the lab's. A smoke verdict is not evidence for a full count; it shows the chain and `plutil` work on the real Chrome on macOS. The eight discovery cells are lab only.

## Conclusion

In the lab, the chain found the Downloads root at the step each topology predicts for the preferences, OS default, record, and find cells, printed nothing and exited 66 with every candidate when the only presence carried another boot, and failed the find cell when step 4 was disabled. The same five cells passed on the host in smoke mode with `plutil`. All eight discovery hypotheses held in the lab in 3 of 3 samples, with directory names (never display names) in every binding, after one fix the cells found: `extension_in_profile` read the empty entry Chrome leaves after an uninstall as installed.
