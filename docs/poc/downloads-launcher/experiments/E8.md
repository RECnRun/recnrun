# E8: the launcher finds a profile's Downloads root

Task P4.2 of [PLAN.md](../PLAN.md), build variant `poc-d0`, installed unpacked over CDP (`diagnostic`, external client true), no debugger, namespace `lab`. This report covers the five root cells, run C of P4.2. Lab: Google Chrome 157.0.8103.38 on Linux (Ubuntu noble) in Docker on Xvfb (image `sha256:bab6fc51…`), full run `2026-11-04T22-33-34.171Z-5340b198-5728-46e7-90b9-62fded01104a`. Host: pending the host run. Verdict files: [lab](verdicts/E8-lab.json), [lab versions](verdicts/E8-lab-versions.json). The chain under test is `scripts/poc-cross-profile/discovery.sh` (run A of P4.2); the source read before measuring is [CHROMIUM.md group 11](../CHROMIUM.md#11-opening-a-profiles-extension-page-and-its-downloads-folder).

## Question

Given a profile's user-data directory and a token the launcher opened it with, does the launcher's one shell chain find the Downloads root that the profile's extension really writes to, at the step the topology says, verifying each candidate only by the presence that carries the token, and does it report every candidate tried when no presence does?

## Method

`tests/experiments/E8-launcher-discovery.spec.ts` reuses the E4 session fixtures (`fixtures/e4-profiles.ts`, `e4-run.ts`, `e4-lab.ts`): each sample starts a real profile with `poc-d0`, opens its bootstrap page with a fresh token (the extension adopts it as its `boot`), and waits until the presence carrying the token is in the profile's Downloads folder. It then runs the chain itself, `discovery.sh profile_downloads_root <root> <profileDirectory> <record> lab <token>`, with `execFile` (fixed arguments, no shell string; `tests/experiments/fixtures/e8-discovery.ts`) and an environment of its own: `HOME` is a throwaway folder (the lab's own home for `osDefault`, so Chrome's real default is under it), so the bounded find stays inside it. The sample also runs `downloads_root_candidates`, `pref_download_dir`, `record_roots`, and `find_presences` on the same inputs, to show which step supplies which candidate. The lab has no `plutil`, so step 1 is the `sed` reader.

A sample holds when the chain exits 0 and prints the expected root (or exits 66 with empty stdout and every candidate on stderr), and the candidate list and the output of steps 1, 3, and 4 equal what the topology predicts (`tests/experiments/e8-chain.ts`, unit-tested in `e8-chain.test.ts`). Folders are labelled in the observations; no path is stored. Where a cell must leave step 1 empty, it reads a profile directory the root does not have (`Profile 9`), which is the same output as a key absent; `osDefault` in the lab reads the real `Default`. Samples: 3, gestures 0.

## Observation

- E8.root.preferences: in 3 of 3 samples the candidates were the custom folder then the OS default, step 1 printed the custom folder, and the chain exited 0 printing it (`chainMs` 8, 8, 10).
- E8.root.osDefault: in 3 of 3 samples the key was absent from the real `Default/Preferences` (step 1 printed nothing), the only candidate was the OS default, and the chain printed it (4 to 5 ms). The bounded find also saw that presence under `HOME`.
- E8.root.record: in 3 of 3 samples the candidates were the OS default then the record's folder, step 3 printed it, step 4 found nothing (the folder is outside `HOME`), and the chain printed it (4 ms).
- E8.root.find: in 3 of 3 samples the record was empty of roots, step 1 printed nothing, and `find_presences` found the folder two levels under `HOME`; the chain printed it (4 ms).
- E8.root.notFound: in 3 of 3 samples the chain exited 66 with nothing on stdout, and stderr listed the custom folder, the OS default, and the record's folder, in that order (8 to 9 ms). The profile's presence was there, carrying the extension's own boot, so a path that holds some presence is still not accepted without the token.

## Negative controls

- Step 4 disabled: in a scratch worktree of the parent commit with `return 0` as the first line of `find_presences`, `vp run test:experiments -- tests/experiments/E8-launcher-discovery.spec.ts -g "E8.root.find"` (run `2026-11-04T22-33-17.291Z-208c01b4-4d83-4991-a444-1356a7d1d1db`) recorded `E8.root.find` `fail` in 3 of 3 samples: "exit code was 66, expected 0; printed root was null, expected \"<folder under home>\"; tried candidates was [\"<OS default>\"], expected []; candidates was [\"<OS default>\"], expected [\"<OS default>\",\"<folder under home>\"]; find step was [], expected [\"<folder under home>\"]".
- Unit tests of the output reader and the judgement (`tests/experiments/e8-chain.test.ts`) against a stub that returned empty values: 4 of 6 failed before the implementation.

## Limits of this measurement

- The lab ran the `sed` reader only; the `plutil` reader is the host's, and is exercised there and by `discovery.checks.mjs`.
- One profile per cell and one namespace (`lab`); several roots, a profile opened with other profiles, and the extension being absent or updated are the eight discovery hypotheses of P4.2 and are not measured here.
- The lab's `HOME` for `osDefault` is the container user's home, with `~/Downloads/RECnRun/poc` cleared before each sample; the other cells use a throwaway `HOME`.
- The host cannot use `~/Downloads` and cannot leave the key absent (its Preferences name a stand-in), so its `osDefault` cell reads a profile directory the root lacks, with `HOME` a throwaway folder whose `Downloads` the profile writes to.
- Installs are diagnostic (`Extensions.loadUnpacked` over CDP); the owner's `Load unpacked` gesture is M-P1.a.

## Conclusion

In the lab, the chain found the Downloads root at the step each topology predicts for the preferences, OS default, record, and find cells, printed nothing and exited 66 with every candidate when the only presence carried another boot, and failed the find cell when step 4 was disabled.
