# E1: clean install and the file-scheme state

Task P1.2 of [PLAN.md](../PLAN.md), build variant `poc-d0` with `host_permissions: ["file:///*"]` (added after the first E1 round, see below), no debugger. Lab: Google Chrome 156.0.8078.79 on Linux (Ubuntu noble) in Docker on Xvfb, toggles clicked with xdotool. Host: Google Chrome 156.0.8078.80 on macOS 27.0.1 (arm64), on throwaway roots under `~/Documents/RECnRun/poc-downloads-launcher/roots/`, toggles clicked with CDP mouse input (`cdp-click`, there is no xdotool on macOS); the personal Default was not touched. Verdict files: [lab full](verdicts/E1-lab-full.json), [lab smoke](verdicts/E1-lab-smoke.json), [lab versions](verdicts/E1-lab-versions.json), [host](verdicts/E1-host.json) (run `host-2026-11-03T23-24-49.000Z`). The smoke file was regenerated after Codex P1 finding 5 (a harness error now fails the test instead of becoming a sample) on Google Chrome 157.0.8103.38, run `2026-11-04T00-14-55.662Z-a93bed85-be9d-407a-a77a-939d90a7a4e0`: the same verdicts and gestures.

## Question

Right after an install with no gesture, can the extension read a `file://` URL? What does the "Allow access to file URLs" toggle change, and does a revoke survive a relaunch and a reinstall?

## Hypotheses

Every unpacked cell installs with `Extensions.loadUnpacked` (diagnostic, external client) on a fresh root, writes `e1-probe.txt` into the root from Node, opens `chrome-extension://<id>/diagnostics.html` with `Target.createTarget`, and evaluates `chrome.extension.isAllowedFileSchemeAccess()` and `fetch("file://…/e1-probe.txt")` there. Gestures count the switches clicked at `chrome://extensions`, one per sample (the verdict keeps the most). Samples: 3 full, 1 smoke; the smoke run gave the same verdicts.

| Hypothesis                   | What it claims                                                                                                      | Label      | Gestures | Lab         | Host        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- | ---------- | -------- | ----------- | ----------- |
| E1.unpacked.default          | No file access after the install with no gesture, and the fetch fails                                               | diagnostic | 0        | fail        | fail        |
| E1.unpacked.toggleOff        | Developer mode on, then the toggle off: the API says false and the fetch fails                                      | diagnostic | 2        | pass        | pass        |
| E1.unpacked.toggleOn         | Off first, then on: the API says true and the fetch reads the probe                                                 | diagnostic | 3        | pass        | pass        |
| E1.unpacked.reinstall        | After a revoke, a quit, a relaunch, and a reinstall of the same path, access is back to the install default         | diagnostic | 2        | fail        | fail        |
| E1.unpacked.noHostPermission | Control: the same build with `host_permissions` removed; access is on from the install, yet the fetch fails         | diagnostic | 0        | pass        | pass        |
| E1.unpacked.noDeveloperMode  | With Developer mode off, as a fresh root starts, the toggle disables the build (`unsupportedDeveloperExtension`)    | diagnostic | 1        | pass        | pass        |

Reasons recorded for `unavailable`: packed distribution not executed in this round (decision 4, M-P9.c); on macOS a managed policy needs a root-owned plist in `/Library/Managed Preferences`, which the host runner never writes; the personal Default install is manual item M-P1.a.

## Observation

- Default: every unpacked sample, lab and host, reports `isAllowedFileSchemeAccess()` true, the diagnostics page renders `fileSchemeAccess: true`, the root's `Preferences` hold `newAllowFileAccess: true` with `creation_flags` 32806, and the fetch reads the probe's exact bytes (status 200). The hypothesis "no access after the install" therefore fails.
- Host permission: the first E1 round ran the P1.1 build, whose manifest had `storage`, `tabs`, `offscreen`, `downloads` and no `file:` host permission. There every fetch failed with `TypeError: Failed to fetch` although the API said true, and a copy with `host_permissions: ["file:///*"]` read the probe (that round's verdict files are in commit `223b800`). P1.1 then gave the POC variants that permission, and this round reruns E1 on it. `E1.unpacked.noHostPermission` keeps the old build's condition as a control (the same build with `host_permissions` removed from a copy of its manifest): access on, fetch `TypeError: Failed to fetch`, in every sample on both environments.
- Toggle: the switch is `#allow-on-file-urls` in the detail view. Every lab click went through xdotool on the first try, every host click through `cdp-click`; no fallback was needed. Off makes the API false, the pref `newAllowFileAccess: false`, and the fetch fail; on makes them true again and the fetch reads the probe.
- Developer mode: a fresh root has it off. The toggle reloads the unpacked build, and with Developer mode off Chrome then disables it (`state: DISABLED`, `unsupportedDeveloperExtension`). Every toggle cell therefore turns Developer mode on first, which is one of the counted gestures.
- Reinstall: the revoke survives everything. After the quit the pref is `false`; a relaunch of the same root with the same flags still runs the build (its worker answers, nothing reinstalled); a reinstall of the same path keeps access false and the fetch failing. `creation_flags` go from 32806 at the CDP install to 38 after the toggle's reload and back to 32806 after the reinstall: the reload drops the 32768 bit (consistent with `INSTALLED_VIA_CDP`, whose value was not read), so the toggled install is no longer purged at the next profile load.
- Policy (lab): the force-installed CRX (its own id, signed with the policy key) runs at install location 7 with no `newAllowFileAccess` entry, so no file access.

## Prediction check

- [CHROMIUM.md group 1](../CHROMIUM.md#1-initial-file-access-packed-and-unpacked) predicted that `Extensions.loadUnpacked` starts **with** file access (`DefaultUnpackedFileAccess`), so the plan's "false after an unpacked install" fails. The lab and the host agree. The same group's `UnpackedInstaller::GetFlags` line predicted that a revoked toggle survives a reload of the same path; the reinstall cell agrees. The policy install starts with no access setting, as predicted; packed stays unmeasured.
- [CHROMIUM.md group 7](../CHROMIUM.md#7-file-loading-from-extension-contexts) predicted that `fetch(file:)` works from an extension page iff `AllowFileAccess`. Contradicted: with access allowed, the fetch also needs a `file:` host permission in the manifest (`E1.unpacked.noHostPermission`). With both, the read follows the toggle, as predicted. The check that refuses a read without the permission was not inventoried.
- [CHROMIUM.md group 9](../CHROMIUM.md#9-extensionsloadunpacked-and-the---load-extension-removal) predicted that a CDP install lives only for its process. That holds for an untouched install (E0), but an install whose toggle was flipped survived a relaunch here, because the reload rewrote its creation flags.

## What it means for the plan

- §14 question 2, unpacked: yes. Right after the install, with no gesture, the extension reads `file://`, provided the build declares `host_permissions: ["file:///*"]`, which the POC variants now do. Packed: not executed (decision 4).
- V1's "install only" criterion: the file read adds no gesture to a `Load unpacked` in the Default. Turning the toggle off and back on costs Developer mode, which a `Load unpacked` already requires. M-P1.a still has to confirm that the UI's `Load unpacked` takes the same path as `Extensions.loadUnpacked` on the personal Default.
- A revoke is sticky: once the owner turns access off, neither a relaunch nor a reinstall of the same path restores it, so the diagnostic for a failed read must point at the toggle.
- E10 and CL17: a toggle's reload clears the CDP install's purge bit, so the CDP install may persist after one gesture. E10 has to measure that on purpose instead of inheriting E0's verdict.
