# E3: `file://` reads in the page and in the offscreen document

Task P1.4 of [PLAN.md](../PLAN.md), build variant `poc-d0` (with `host_permissions: ["file:///*"]`, see [E1](E1.md)), no debugger, one root. Lab: Google Chrome 157.0.8103.38 on Linux (Ubuntu noble) in Docker on Xvfb (the image now installs this stable; E1 ran on 156.0.8078.79). Host: Google Chrome 156.0.8078.80 on macOS 27.0.1 (arm64), on throwaway roots under `~/Documents/RECnRun/poc-downloads-launcher/roots/`; the personal Default was not touched. Verdict files: [lab full](verdicts/E3-lab-full.json), [lab smoke](verdicts/E3-lab-smoke.json), [lab versions](verdicts/E3-lab-versions.json), [host](verdicts/E3-host.json). After Codex E3 finding 2 the cache cells changed and every file was regenerated: lab full run `2026-11-04T00-31-47.791Z-eddf7694-1181-4e7d-b672-0bbce47cbb0f`, lab smoke run `2026-11-04T00-32-42.268Z-22bcd5cf-4198-4589-a1aa-ebe418548fca`, host run `host-2026-11-04T00-35-50.347Z`, which also records `E3.directoryListing` after Codex E3 finding 4 (first round: host `host-2026-11-03T23-46-55.536Z`).

## Question

Once the extension may read `file://` (E1), does the read work the same in an extension page and in the offscreen document, which is where the folder watch polls? Does a repeated read see a file that changed between two polls, or does a cache hide the change? What does a directory URL return?

## Method

Each sample installs the build with `Extensions.loadUnpacked` (diagnostic, external client) on a fresh root, writes `e3-probe.txt` into the root from Node, opens `chrome-extension://<id>/diagnostics.html` with `Target.createTarget`, and evaluates `window.__poc.readFile(url, { via, cache?, api? })` there. With `via: "page"` the page calls `fetch` itself; with `via: "offscreen"` it sends `POC_READ_FILE` to the background, which creates the offscreen document if none exists (the mesh's `ensureOffscreen`) and relays the request, and the offscreen document calls `fetch` and answers `{ ok, status, text }` or `{ ok: false, error: { name, message } }`. The code exists only in the POC builds: `vp run test:extension-manifest` checks that the production `background.js` and every production script lack `POC_READ_FILE` and that the three POC builds' background, offscreen, and diagnostics scripts carry it.

The cache cells write the probe as version A and read it, then, one poll apart, overwrite it from Node with B, C, and D; after each write they read at once with the default cache mode and again one poll later. A cell passes only when every one of those reads returns the version just written: a first read that answers older bytes fails it, even if the next poll sees the change (`cacheRun` in `tests/experiments/e3-cache.ts`). When a first read is stale, the cell also reads with `cache: "no-store"` to note whether that would have helped. A to D have the same length, so a cache keyed on size and a coarse modification time would miss the change. PLAN.md §4 names no poll interval, so the cells use the folder watch's own, 1000 ms (`POLL_MS` of `src/offscreen/folder-watch.ts`, the "one poll" of P1.4), read from the extension's source, not copied.

Samples: 3 full, 1 smoke (lab); 3 on the host. The smoke run gave the same verdicts. Gestures: 0 everywhere.

| Hypothesis          | What it claims                                                                                                       | Label      | Lab         | Host        |
| ------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------- | ----------- | ----------- |
| E3.page.fetch       | `fetch(file://)` in the extension page reads the probe's exact bytes                                                 | diagnostic | pass        | pass        |

`E3.directoryListing` is `unavailable` by rule: "no dedicated experiment and validated parser (§6.3)". The lab still records what the URL returned, so the next phase can decide; the host twin records the same `unavailable` without reading a folder, so no path of this Mac lands in a verdict.

## Observation

- Read: every sample, page and offscreen, lab and host, read the probe with status 200 and the exact text. The offscreen document's `fetch` never failed, so the `XMLHttpRequest` alternative was never needed and is not measured.
- Cache: in every sample the first read after each of B, C, and D returned the new text, and so did the read one poll later, in both contexts and on both environments. No first read was stale, so `no-store` was never read (`noStoreNeeded: false` in all 12 full cache samples, lab and host, and in both smoke ones).
- Directory listing (lab): `fetch("file:///tmp/recnrun-e3-…/e3-listing/")` resolves, in the page and in the offscreen document alike, with **status 0** (not 200) and Chrome's HTML directory page: 9447 characters starting `<!DOCTYPE html>` … `<script>function addRow(name, url,`, which names both files of the folder (`a.json`, `b.txt`). So a listing is readable, but only by parsing Chrome's internal HTML, whose shape no API promises.
- Content scripts: no build declares a content script that matches `file:` or `*:` (`vp run test:extension-manifest`, production and the three POC builds), which is the §4 rule "no content script reads `file://`". It is a static check of the manifests, not a verdict.

## Negative controls

- Red before `readFile` existed (scratch worktree at `2d27b01` with only the spec): the four sampled hypotheses recorded `fail` with `window.__poc.readFile is not defined in diagnostics.html`, the listing test threw it, and "every hypothesis ran" failed.
- Stale once (`vp test --project=harness tests/experiments/e3-cache.test.ts`): an in-memory reader that answers the previous bytes on the first read after a change and the new ones a poll later passed the earlier rule, which let the next poll make up for it, and fails `cacheRun`, also when only the last of the three changes is stale.
- Stale offscreen, before the A→B→C→D cells (scratch worktree, the offscreen handler answering the first content it ever read for a URL): `E3.offscreen.cache` recorded `fail` "offscreen: the default cache mode saw the change after null polls (no-store: null)" after waiting out the TTL, while `E3.page.cache` passed. A first version of the cell rewrote A for the `no-store` step, and that control showed `no-store: 0` because the stale A matched; the cell now writes a third version, C.

## Prediction check

- [CHROMIUM.md group 7](../CHROMIUM.md#7-file-loading-from-extension-contexts) predicted that `fetch(file:)` works the same from any `chrome-extension://` initiator, the page and the offscreen document included, once access is allowed (and, per E1, the `file:` host permission is declared). Lab and host agree; no contradiction to record there.
- [CHROMIUM.md group 10](../CHROMIUM.md#10-file-responses-caching-status-and-directory-listings) inventories the file loader (`file_url_loader_factory.cc`) and predicted both measurements: no HTTP cache in the path (fresh read, 0 polls) and a directory page with no response headers (status 0, generated HTML). The adapter recommendation relies on no unverified assumption the code contradicts; the code adds that `file:` answers carry `Last-Modified` and no cache headers, and a same-size, same-mtime rewrite was not measured.

## What it means for the plan

- §14 question 1, "read back": the offscreen document, which hosts the folder watch, reads `file://` exactly as the page does, so the Downloads adapter of P3.1 can poll from there with plain `fetch`, no alternative API.
- Polling: in these runs, three same-length rewrites one 1000 ms poll apart were each seen on the first read with the default cache mode, so the adapter needs no `no-store` or cache-busting query for that cadence; this does not cover rewrites faster than one poll or a long session, and adding `cache: "no-store"` costs nothing and guards against a future cache.
- Discovery (P2): a directory listing works today only through Chrome's internal HTML (status 0, `addRow(...)` calls); using it needs its own experiment and a validated parser (§6.3), or the catalog file of P2.1 instead.
