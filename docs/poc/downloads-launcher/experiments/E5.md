## Question

§14 question 1, for the handshake and the mesh: "Downloads + `file://` substituem o FSA sem seletor/grant de escrita?" Once each profile writes its presence through `chrome.downloads` and the launcher catalogs it (P2), do the profiles of one OS user pair and keep the mesh of PR #19 by themselves, with no folder picker, no write grant, no pairing code, no page open, and no click, and do the files they exchange hold up against stale, repeated, damaged, and badly stamped copies and against profiles that quit or crash?

## Method

The extension (`poc-d0`) gains one trigger (`background/downloads-pairing.ts`): every presence a profile writes once Chrome told it its Downloads root starts the folder flow of PR #19, or starts it again, with no page open. The offscreen document then reads `registry.json` and each listed peer's presence and signal files through `file://` with `cache: "no-store"` every second (`POLL_MS`), and writes signals through the background's relay, in the layout P3.1 fixed (decision 11). Of each pair the lower `profileId` offers, with ICE gathered completely before it writes (`gatherTimeoutMs` 10 s); the other answers each offer once: not one whose `pairingId` it answered in this browser run (`session:folderActed`), in an earlier run (`local:answeredOffers`, pruned at expiry), or whose answer of its own is still on disk (it reads its own `answer-<peer>` file back on each poll). The offerer offers whenever it holds no unexpired offer for that peer (`PAIRING_TTL_MS`, 5 min), connects with the answer to the one it holds, and offers again once that offer has had no answer for `RETRY_MS` (30 s), or `RETRY_MS` after a connection whose link did not come up. Readers refuse a signal whose `sequence` is more than `CLOCK_SKEW_MS` (5 s) ahead of their clock or whose `expiresAt` is more than `PAIRING_TTL_MS` plus `CLOCK_SKEW_MS` ahead, and hear a presence that expires up to `PRESENCE_TTL_MS` plus `CLOCK_SKEW_MS` ahead, as `catalog.sh` does; a writer whose last sequence is more than `CLOCK_SKEW_MS` ahead of its clock stamps from its clock again. After a Forget the dashboard offers **Pair with other profiles** whenever the transport is available, and the Downloads builds show none of the File System Access controls. Nothing else changed in the pairing, the mesh, or the trust model.

The harness (`tests/browser/fixtures/downloads-profiles.ts`) starts every profile on a throwaway root of its own, gives Chrome its own download behaviour back (`Browser.setDownloadBehavior { behavior: "default" }`), and installs `poc-d0` with `Extensions.loadUnpacked`. All the profiles of a sample share one Downloads folder: in the lab Chrome's own default, the container user's `$HOME/Downloads` (nothing written in `Preferences`); on the host a stand-in folder written into each root's `Preferences` before its first launch. A stand-in launcher record names that one root, and the harness runs `catalog.sh` once after every profile's first presence is on disk, then every 2 s; E5 opens no bootstrap page, since the record already names the root (E4 measured discovery). The profiles are named `Default`, then `Worker 1` to `Worker 4` in launch order; E5 gives them no role (P3.4). A quit is SIGTERM and a crash SIGKILL, both to the PID the sample spawned; a relaunch starts Chrome on the same root and installs again, since a CDP install does not survive a relaunch (group 9). "Detached" means the extension's pages closed and Playwright's connection, which attaches to every service worker, closed (group 12); Chrome keeps its other tabs.

E5 reads files on disk and their mtime; each profile's storage through its own worker (`local:authorizedPeers`, `local:profileIdentity`, `local:peerPins`, `local:answeredOffers`, `session:pendingOffers`, `session:folderActed`); each profile's own download history, where each write is one item whose `data:` URL holds the bytes, to count writes and to date each answer; and `Target.getTargets` over a CDP client that attaches to nothing, to tell whether Chrome lists the worker. No observation carries a path.

Six cells need files no real profile writes. There the test plays a virtual peer (`tests/experiments/fixtures/e5-virtual.ts`): it writes a presence and signals in the extension's exact bytes, each replaced by a rename, with a complete SDP and the certificate fingerprint of a real `RTCPeerConnection` in a blank tab of the Default, so the Default judges them by its own rules and answers with a real answer. Its id is the lowest v4 id, so the Default answers it; in E5.a.duplicate a second one with the highest id receives the Default's offer; a third (`00000000-0000-4000-8000-000000000001`) carries the presences `catalog.sh` must refuse. Each mutation is one write into the throwaway folder, never a change to RECnRun. Every mutation sits between controls, fresh offers the Default must answer within 15 s; a mutation holds when no answer to it came within 6 s, and the sample also fails if the Default's history shows an answer to it later. Worker 1, beside them, must link with the Default.

Samples: 3 full and 1 smoke (lab), 3 (host); E5.a.closePages takes 2, since each of its samples waits two presence lifetimes. Gestures: 0 everywhere. Every sample starts fresh roots and a fresh Downloads folder and removes them afterwards.

## Answer to §14 question 1, for the handshake and the mesh

> Yes, on Google Chrome 157 in the Linux lab and 156 on the macOS host, for unpacked installs: profiles of one OS user that write through `chrome.downloads` into one Downloads root, and that a launcher catalogs, pair and form the mesh of PR #19 with no folder picker, no write grant, no pairing code, no page open, and no click (0 gestures). Each file is acted on within one 1 s poll; the Default plus one worker link within 1.9 s of the first catalog in the lab and 2.9 s on the host, and the Default plus four within 2.2 s in the lab and 2.8 s on the host, each pair from one offer. The layout of P3.1 refuses an earlier boot's signals, lower sequences, repeated offers and answers, expired, truncated, malformed, and self-contradicting files, presences stamped an hour off, and signals whose `sequence` or `expiresAt` is an hour ahead; a presence within `CLOCK_SKEW_MS` is heard at once, and a writer whose stamps ran ahead is heard again from its next signal. A restarted profile links again within 2.2 s of the quit, and a crashed one within 2.1 s of the kill, or after one 30 s retry period when it crashed after its answer was on disk, keeping its id and pins; an answerer answers each offer once across a crash and a relaunch. A pair whose pages are closed and whose clients are gone keeps its presences fresh and its link up, and links again after a crash with nothing attached. A fifth profile joins four such profiles in under 4.2 s. Disconnect, Reconnect, Forget, and pairing again after a Forget hold over Downloads. Different roots per profile were not measured; packed installs and Windows were not executed.

## Limits of this measurement

- Clock: neither environment can change its OS clock (the container shares the Docker machine's clock, and the host's is the owner's), so E5.a.clockChange moves the virtual peer's stamps instead. It shows what a profile does with files a clock an hour off would write, not what a profile does when its own clock steps; the writer's restart of its stamps after its clock stepped back is covered only by `rendezvous-transport.test.ts`.
- E5.a.quitDuringIce kills the answerer once it has read the offer, which in the lab always landed before its answer was on disk; E5.a.quitAfterAnswer chooses the other side, 108 to 122 ms after the answer landed and before the pair linked. A kill after the offerer connected and before the link came up (5 to 15 ms in E5.a.arrival) was not aimed at, since the harness sees the answer land but not the offerer connect.
- One shared Downloads root per sample; pairing across two roots (E4.b.differentRoots) was not measured.
- E5 never opens the bootstrap page. A profile adopts the launcher's token as its boot (P2.1), and the boot is asked on each write (`p2p/downloads-transport.ts`), so an offer written before the adoption carries a boot readers then drop. The offerer offers again once that offer has had no answer for `RETRY_MS` (30 s). Not measured.
- The dashboard of the Downloads builds was observed only in E5.b.disconnectForget; the absence of the File System Access controls there is checked by the component test, not by E5.
- The launcher is a Node stand-in that reruns `catalog.sh` every 2 s; P4 sets the real cadence.
- Installs are diagnostic (`Extensions.loadUnpacked` over CDP); the owner's `Load unpacked` gesture is M-P1.a. Packed installs and Windows: not executed.
- The unattended relaunch of E5.a.noPage installs over a raw CDP client opened after Playwright's connection closed. A worker that started while Playwright's connection was closing stalled for about 60 s, with no presence and no offscreen document, until a client attached and detached. This is a harness effect, not explained by the sources read, and the harness avoids it.
- Sleep: the Mac that runs Docker slept for 450 s during the first full run (`2026-11-04T07-02-25.262Z-152ab6df-cb7d-459f-9334-71b5a515f840`) and for 86 s during a smoke run (`2026-11-04T07-51-48.111Z-e9c185b6-16b4-4b7e-9353-511aba20a25a`).
