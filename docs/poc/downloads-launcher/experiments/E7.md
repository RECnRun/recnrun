## Question

How many Downloads writes and visible history items does a five-profile mesh produce with a 60 s presence TTL and 30 s alarm? Can a POC-only renewal policy bring steady-state writes below 100/hour while the ten DataChannels remain connected and a lost link brings presence renewal back within one TTL? Business traffic must use the DataChannel and produce no Downloads write.

## Method

`tests/experiments/E7-presence-cost.spec.ts` uses the same `downloads-profiles.ts` fixture as E5: Default and Worker 1 through Worker 4, each on a fresh root, sharing Chrome's default Downloads folder inside the container. The harness installs with `Extensions.loadUnpacked`, runs the stand-in launcher's `catalog.sh` after the first presences and every 2 s, and waits for all ten verified connected DataChannels. There is no bootstrap page, folder picker, or user gesture. Every sample disposes its own processes, roots, and Downloads files.

After the mesh forms, each profile's **own** service worker sets `local:pocPresencePolicy` and wraps its own `chrome.downloads.download`, recording every attempted call before invoking Chrome. The observer records presence, signal, and other calls separately, and reads every retained history item with that same worker's `chrome.downloads.search({})` before and after the window. It never reads another profile's history. A lost counter is a harness error, not a zero measurement. The total hourly rate is the sum of `calls × 3,600,000 / actualWindowMs` for the five profiles. Bootstrap and pairing writes are outside that rate but remain in the reported history counts.

Full mode takes three samples per measured cell, each with a requested **185 s** steady-state window, enough for at least six 30 s renewals per profile. Smoke takes one sample with a **35 s** window, explicitly marked `smokeShortWindow`; it does not prove the six-renewal claim. Each profile's actual window is recorded, including sequential observer overhead. Before cleanup the harness opens that profile's own `chrome://downloads/` and checks its rendered item count against its API history. It then clears `poc-presence`, asks the real offscreen document to `folder-stop`, awaits the relay's signal deletion and history erase, and counts both lists again. Presence items are deliberately left untouched. These lists fit the first WebUI chunk.

`E7.baseline` uses the existing half-TTL alarm. `E7.variant.linkedSilence` sets the POC-only `local:pocPresencePolicy` to `linked-silence`: the alarm still checks every 30 s, but skips the write when the Downloads root is known, at least one authorized peer exists, and **every** authorized peer has a verified connected link. Missing, unverified, disconnected, or unreadable link state keeps renewal on. A missing or invalid switch retains baseline behavior; invalid state is logged. Explicit bootstrap publication always writes. The skipped write still lets pairing restore the offscreen watcher after a worker restart. Production does not start this Downloads path.

The linked-silence cell also runs a separate fresh five-profile recovery probe, excluded from its steady-state rate and completion counts: after the mesh forms and the switch is set, Worker 4 quits by SIGTERM. The four survivors must rewrite their presence within 60 s and retain all six links among themselves. This measures a real dropped DataChannel, without changing production messages or adding a heartbeat.

Owner-approved scope: heartbeat liveness and launcher-published presence are implemented and measured **only if linked silence leaves more than 100 items/hour with five profiles**. Otherwise their verdicts are `unavailable`, with the observed rates and this reason; they are neither implemented nor credited as successful experiments.

## Recommendation for P9's §11.3 metric

Recommend linked silence for P9's extended measurement. Adoption requires unattended lifetime and late-discovery validation. P9.1 should report attempted API writes/hour, completed writes/hour, retained history growth/hour, visible `chrome://downloads` items before and after cleanup, and bytes/disk growth separately. Split bootstrap, steady-state, and recovery traffic, with per-profile counts as well as totals. A single overwritten file is not a single history item. Compare the one-hour five-profile D0 and D2 cells without extension pages or a CDP client, alongside CPU, memory, read rate, cold starts, and reconnections already required by P9.1.

The silence rate applies only while all known peers are linked; a missing known peer deliberately restores recurring writes until it links again or is forgotten. Linked silence lets presences expire while channels remain up. It does not establish discovery of a late newcomer after every existing presence has expired; that requires a separate recovery/discovery design and test before adopting the policy. This experiment tests an already formed mesh and one departure, not a returning or newly arriving profile after silence. It adds no DataChannel heartbeat protocol and makes no claim for a real launcher's presence publisher.
