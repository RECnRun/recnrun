Lab only: Google Chrome 157.0.8103.38 on Linux (Ubuntu noble) in Docker on Xvfb (image `sha256:cc994da3…`), full run `2026-11-04T16-15-49.204Z-be08a3f3-9ae2-4fe1-bd59-2fa04182e310`, smoke run `2026-11-04T17-14-32.976Z-833699af-8991-49e4-a957-cafcc1702c17`, both on the tree of the commit that added the newcomer cells. Chromium predictions were read at tag 156.0.8078.80 before the probes: [group 4](../CHROMIUM.md#4-downloads-destination-filename-conflictaction-saveas), [group 12](../CHROMIUM.md#12-worker-idle-stop-and-the-presence-refresh), [group 14](../CHROMIUM.md#14-download-history-and-erase).

## Question

How many Downloads writes and history items does a mesh of five profiles cost with the current presence (60 s TTL, renewed every 30 s), and which of the three hypotheses of P3.6 cuts that cost while the ten DataChannels stay up and a profile that leaves or comes back is still handled: renewal only while a link is missing (`linkedSilence`), renewal only after a TTL with no DataChannel heartbeat (`heartbeat`), or a presence the launcher writes instead of the extension (`launcherPresence`)? A silent policy lets every presence expire while the mesh holds, so a second question is whether a profile that starts after that still links (the two newcomer cells). Business traffic must stay on the DataChannel and write nothing to Downloads.

## Method

`tests/experiments/E7-presence-cost.spec.ts` uses the fixture of E5 (`tests/browser/fixtures/downloads-profiles.ts`): Default and Worker 1 to Worker 4, each on a throwaway root, sharing Chrome's default Downloads folder in the container, installed with `Extensions.loadUnpacked`. A stand-in launcher record names that root, and the harness runs `catalog.sh` after the five first presences and every 2 s. No bootstrap page, folder picker, or gesture. Each sample waits for the ten verified connected DataChannels, then each profile's own service worker sets `local:pocPresencePolicy` and wraps its own `chrome.downloads.download`, counting every attempted call (presence, signal, other) before Chrome answers; it reads its own history with `chrome.downloads.search({})` before and after the window, and asks its offscreen document how many heartbeats its links sent (`POC_LIVENESS`). The hourly rate is the sum over the five profiles of `calls × 3,600,000 / window`. After the window the harness renders each profile's `chrome://downloads/` and checks its item count against the API, asks the catalog which profiles it lists with an unexpired presence, then clears the `poc-presence` alarm, sends the real `folder-stop`, and counts both lists again. Every sample removes its processes, roots, and Downloads files.

The policies (`apps/extension/src/background/presence-renewal.ts`, POC builds only; [ARCHITECTURE.md](../../../ARCHITECTURE.md)) decide at start and on each 30 s alarm whether the extension writes its presence. Until Chrome has told the profile its Downloads root (once per browser session) every policy writes; an explicit bootstrap publish always writes; a missing or invalid switch, or state it cannot read, keeps the baseline write and is logged.

- `baseline`: writes on every alarm.
- `linked-silence`: skips the write while every authorized peer has a verified connected link.
- `heartbeat`: skips the write while every authorized peer's DataChannel delivered something within one TTL. The offscreen document answers `POC_LIVENESS` with, per peer, when its link last heard anything (the 1 s heartbeat of `p2p/peer-link.ts` included) and the beats it sent. A peer never heard counts as missing.
- `launcher`: never renews; the launcher keeps the file fresh.

Both silent policies (`linked-silence`, `heartbeat`) renew once for a newcomer (Codex P3 finding 2): when a catalog look lists a profile that no peer record knows and the policy has not seen, the background notes it in `session:pocNewcomers` (per browser session, in `storage/poc-presence-repository.ts`), and the next alarm writes the presence once whatever the links say, then remembers that profile as served. Without it a fresh profile reads no survivor, since the catalog lists only unexpired presences. The rule is POC-only and writes nothing for business frames.

The launcher stand-in (`tests/experiments/fixtures/e7-launcher.ts`) is Node in the harness, never the extension. Every 30 s it reads each profile's own `RECnRun/poc/lab/peers/<profileId>/presence.json`, validates it against the keys of `RegistrationSchema`, and writes it back with `createdAt` now and `expiresAt` one TTL later, every other key unchanged. It takes the file aside by an atomic rename, compares what it took with its snapshot (bytes and mtime, so `boot`, `fingerprint`, and `identity.signedAt` included), and puts its own version back with a link that fails when the profile published meanwhile; a taken file that is newer goes back the same way. A profile's newer publication therefore always wins, and the launcher retries on its next tick (`e7-launcher.test.ts` injects a publication before the rename and before the link). It can make neither the identity statement nor the boot, so it replays both.

Full mode takes 3 samples per cell with a 185 s window (six renewal periods); smoke takes 1 with a 35 s window (`smokeShortWindow`). The two newcomer cells (`tests/experiments/e7-newcomer.ts`) have no steady window: four profiles link under the policy, the harness waits 70 s (one TTL plus 10 s), checks that the catalog lists none of them, starts a fifth profile (Worker 4) and waits up to 90 s for the ten links; it then counts the survivors' calls since the policy was set. They run the same in smoke. The three silent cells of the steady window add a recovery probe on a fresh group of five, outside the window's counts: Worker 4 quits (SIGTERM).

## Observation

Full run, three samples per cell; every figure is the range over the samples. In the four steady cells windows lasted 185.03 to 188.41 s. All ten links survived every window, no profile made a signal or other write in a window, no measured item was erased during one, and the API and `chrome://downloads` counts agreed in every profile before and after cleanup. - E7.baseline: exactly six renewals per profile in each window, 600/hour over a long run (five profiles × 120). Cleanup erased every signal item and left seven presence items per profile (one at start, six renewals): each overwrite of `presence.json` replaces the file and adds one history item.
- E7.variant.linkedSilence: no write while the mesh held; one presence item per profile remained. After the quit, the survivors wrote on the next alarm after their link to Worker 4 dropped. One sample counted 75,587 heartbeat frames/hour, 5% above the others: one profile sent 930 frames in its window where the others sent 740 to 748, which the verdict does not explain.
- E7.variant.heartbeat: no write while the mesh held. After the quit, the survivors wrote on the first alarm after a TTL with nothing heard from Worker 4, 84 to 87 s after the quit: about 60 s slower than linked silence, since the hypothesis waits a TTL of silence where linked silence acts on the dropped link.
- E7.variant.launcherPresence: the extensions wrote nothing; the stand-in wrote each profile's file 7 times in each window (680.9–681.0 file writes/hour for five profiles, 600/hour over a long run). Worker 4 itself wrote one presence on relaunch (a new boot, its root not yet known in that session), then the stand-in re-stamped it; the four survivors wrote no presence during the whole probe.

## Prediction check

1. Group 4: every presence write replaced its own path (`overwrite`), and no write raised a prompt (0 gestures).
2. Group 12: the 30 s alarm fired six times per profile in each 185 s baseline window. The harness keeps a CDP client attached, which keeps the workers alive; E5.a.closePages measured the alarm with no client.
3. Group 14: the API's history and `chrome://downloads` both count every retained presence overwrite (seven per profile in the baseline), and the relay's erase on `folder-stop` removed every signal item from both, leaving the presence items. Holds.

## Limits of this measurement

- Lab only: Docker on Linux, unpacked diagnostic installs with an external CDP client attached. The client keeps the workers alive (group 12), so the alarm's cadence here is not an unattended worker's.
- Windows of 185 s (35 s in smoke, shorter than six renewal periods); the newcomer cells wait one TTL plus 10 s and watch 90 s, one fifth profile at a time; the one-hour session with five participants is P9.1's.
- The launcher is a Node stand-in that re-stamps by a rename every 30 s; the real launcher, its cadence, and its access to each profile's Downloads root are P4's.
- Heartbeat cost is counted in frames by the sender; wire bytes and CPU are not measured.

## Conclusion and recommendation for P9's §11.3 metric

The current presence costs 600 downloads/hour with five profiles (582 in each 185 s window), and each one stays in the profile's history and Downloads list: seven presence items per profile in three minutes, about 120 per profile per hour, until something erases them. All three hypotheses bring the extension's steady-state cost to 0 downloads/hour, R7's budget holds (no business message writes a download), and the ten links survive. The newcomer cells add that the two silent policies are not a dead end for a fresh profile: it links with the four within 14 to 20 s because every survivor that notices it renews once, which costs one presence download per survivor per newcomer (4 for a fifth profile; the heartbeat cell saw 2 to 4 by the time the links stood). They differ in what happens off the steady state:

- `linkedSilence` writes again as soon as a link drops (25 to 27 s after a quit), but lets every presence expire while the mesh holds, so the catalog lists nobody.
- `heartbeat` costs no frame beyond the links' existing keep-alive, but resumes only after a TTL of silence (84 to 87 s) and also lets every presence expire. It gives nothing linked silence does not, and resumes about 60 s later.
- `launcherPresence` keeps every profile listed, writes no download, and lets a profile that was gone longer than a TTL link again within 3.3 s, with the survivors silent.

What decision 13 means for the launcher: the launcher cannot sign, since the statement covers the profile id and the certificate fingerprint and only the profile holds its identity key (`extractable: false`, in its IndexedDB). It can replay the statement it reads, as any program of the same user can (decision 13 already allows for this), and a verifier accepts that replay, because it checks the statement against the presence's fingerprint and the signature, not against the age of `signedAt`. A launcher presence is therefore possible without changing the trust model, and the replay grants nothing new: the statement still names the profile's own certificate, which the DTLS handshake proves. From each profile the launcher needs `profileId`, `displayName`, `fingerprint`, `identity`, `namespace`, and `boot`, all taken from the profile's own latest presence. It stamps only `createdAt` and `expiresAt`. The profile must therefore write its presence itself whenever any of those change: once per browser session (a new `boot`, which E7 measured as one write on relaunch), and after a certificate renewal (about every 29 days) or a discarded key (P5.3's clones), since only the profile can sign the new fingerprint. The `launcher` switch of E7 writes only while the root is unknown, that is once per session; a renewal within one session was not exercised.

What overlapping publication means for P4 (Codex P3 finding 3): a first version re-read the file and then renamed over it, and a profile that published between that read and the rename lost its new boot and certificate to the launcher's old snapshot, which later renewals then kept. No file API replaces a file conditionally, so a launcher that overwrites the profile's file always has a window. The stand-in closes it only by taking the file aside, judging what it took, and linking back, which leaves the path absent for a moment and is a lab device. P4 should not copy it: the profile owns its identity and boot (its presence file, written only by the extension, once per boot and when its statement changes), and the launcher owns freshness in a file of its own (for example one `renewed.json` per profile, or the catalog's own `expiresAt`), which the catalog and the readers join with the profile's file. Then no file has two writers and no interleaving can restore a stale boot. If P4 keeps one file with two writers, it needs a coordination the filesystem does not give, and the launcher must at least verify and repair after each write.

Recommendation: P4's launcher should publish the presence, the extension writing it once per boot and whenever its statement changes, with `linked-silence` as the extension's policy when no launcher keeps its file fresh; the newcomer cells make that fallback viable, at the cost of one presence download per survivor per newcomer. For P9's §11.3 metric (reads/downloads, bytes per hour, history and disk growth), report per profile and for the five, split into start-up, steady state, and recovery: extension `chrome.downloads` calls per hour; retained history items and `chrome://downloads` items before and after cleanup; launcher file writes per hour (not downloads); DataChannel heartbeat frames per hour; and the number of profiles the catalog lists over time, since a policy that writes nothing can also leave nobody discoverable. Measure it in the one-hour five-profile session with no extension page and no CDP client, D0 against D2.
