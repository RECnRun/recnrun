# E0: two lab install methods

Task E0 of [PLAN.md](../PLAN.md), decision 5. Environment: Google Chrome 156.0.8078.79 on Linux (Ubuntu noble) in Docker (the host Chrome is not involved). Verdict files: [full](verdicts/E0-lab-full.json), [smoke](verdicts/E0-lab-smoke.json), [versions](verdicts/E0-lab-versions.json).

## Question

Which way of installing the extension in the lab survives a full quit and a relaunch of the same profile root?

## Hypotheses

| Hypothesis       | Method                                                                                                              | Label      | External client | Samples (full / smoke) | Verdict |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- | ---------- | --------------- | ---------------------- | ------- |
| E0.loadUnpacked  | `Extensions.loadUnpacked` over CDP with `--enable-unsafe-extension-debugging`, then quit and relaunch the same root | diagnostic | yes (CDP)       | 3 / 1                  | pass    |
| E0.managedPolicy | Managed-policy force-install from a loopback update server, no CDP, SIGTERM quit and relaunch of the same root      | strict     | no              | 3 / 1                  | pass    |

Both verdicts are `pass` because the hypothesis was that the install works and that the harness records its persistence honestly; the persistence result itself is the observation below.

## Observation

- Unpacked, installed over CDP: after the relaunch of the same root, even with the debugging flag, the extension did not run. The prefs entry stayed at install location 4, no service worker started, and the dashboard did not open. All full samples agree.
- Managed policy: the extension survived the SIGTERM quit and the relaunch, at install location 7, on disk, with no debugging flag, and the dashboard opened. The update server saw the policy request and the crx download.

## Prediction check

[CHROMIUM.md group 9](../CHROMIUM.md#9-extensionsloadunpacked-and-the---load-extension-removal) predicted that an extension installed over CDP is purged at the next profile load (`CleanUpCdpInstalledExtensions`). The lab confirms the effect (the extension does not run after a relaunch) with one nuance: the prefs entry was still present at location 4, whereas the source says the entry is deleted when the profile loads. The entry may be read before the cleanup, or the cleanup may run later; the lab does not decide it, and the effect on the plan is the same.

## What it means for the plan

- V3's CL17 mechanism (`Extensions.loadUnpacked` as the base install, P6.2) is predicted to fail the persistence check ("still installed after a full quit and a relaunch without any debugging flag"). The host run of E10 still has to measure it on macOS before the cell is declared failed.
- Policy force-install is the persistent lab method: strict cells install that way, and diagnostic cells may use the CDP install only within one process lifetime.
- `--load-extension` stays unavailable on branded Chrome; this report does not retest it.
