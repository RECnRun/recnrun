# E10: install.sh installs the extension in a clean base, and the base keeps it

Task P6.2 of [PLAN.md](../PLAN.md) (CL17), build variant `poc-d0`, installed unpacked over the DevTools pipe (`diagnostic`; external client true during the install, none afterwards), no debugger, namespace `lab`. Lab: Google Chrome 157.0.8103.38 on Linux in Docker on Xvfb, **smoke mode** (one chain), run `2026-11-05T15-00-12.272Z-ec478911-658e-4ade-89d6-1b2f9e1926c3`, after `base.sh template` gained `--no-first-run --no-default-browser-check` (see [What the measurement changed](#what-the-measurement-changed)). Host: pending the owner's run. Verdict files: [lab](verdicts/E10-lab.json), [lab versions](verdicts/E10-lab-versions.json). The source read before measuring is [CHROMIUM.md group 18](../CHROMIUM.md#18-the-devtools-pipe-the-policy-force-list-and-a-first-run), with groups [9](../CHROMIUM.md#9-extensionsloadunpacked-and-the---load-extension-removal) and [16](../CHROMIUM.md#16-developer-mode-gates-unpacked-extensions-and-is-a-tracked-preference-on-windows-and-macos).

## Question

Can the launcher install the extension in a clean base with no gesture, so that every later launch of the base, with no debugging flag and no client, still runs it and acks its template token, and can `base.sh freeze` then record it as an unpacked build?

## Method

`scripts/poc-cross-profile/install.sh install-base <bases-dir> <name> <namespace> <build-dir>` (POSIX `sh`) refuses with 65 a missing, partial, or frozen root, a bad name or namespace, a root whose `Default/Preferences` does not pin its Downloads root inside it, and a build that is not a plain absolute directory with `manifest.json`; with 75 while a process names the root. It starts Chrome with separate words `--user-data-dir=<root> --profile-directory=Default --no-first-run --no-default-browser-check --remote-debugging-pipe --enable-unsafe-extension-debugging`, the pipe on fds 3 and 4, and sends these NUL-terminated messages, each waited for up to `RECNRUN_OPEN_TIMEOUT_S`:

1. `{"id":1,"method":"Extensions.loadUnpacked","params":{"path":"<build>"}}`; `result.id` must equal `extension-id` (70 otherwise, after closing Chrome).
2. `{"id":2,"method":"Target.createTarget","params":{"url":"chrome://extensions/"}}`, then `{"id":3,"method":"Target.attachToTarget","params":{"targetId":"<id>","flatten":true}}`.
3. On that session, `Runtime.evaluate` with `awaitPromise` and `returnByValue`, each repeated until it gives `true`: `chrome.developerPrivate.updateProfileConfiguration({inDeveloperMode:true})` read back through `getProfileConfiguration`, `chrome.developerPrivate.reload('<id>',{failQuietly:true})`, and `getExtensionInfo('<id>')` with `state === 'ENABLED'`.
4. `{"id":7,"method":"Browser.close","params":{}}`; the pid is waited for, SIGINT (Chrome's normal shutdown, never SIGTERM: [TROUBLESHOOTING.md](../../../TROUBLESHOOTING.md#a-quit-chrome-leaves-its-singleton-files-and-an-unclean-exit-solved)) only after a full wait, then the helpers of the root; stderr names what ended Chrome.

It prints `extensionId=` and `installS=`; no reply gives 69 and leaves Chrome for `lifecycle.sh stop`, and an install whose settings entry is missing after the close gives 70. `install.checks.mjs` holds the refusals, the argv, the seven messages, another id, no reply, no entry, and a Chrome that lingers after `Browser.close`, against a pipe stub, in `sh` and `dash`.

`tests/browser/E10-base-install.spec.ts` writes a base root as `base.sh create-base` leaves it (only the Downloads pin, no extension), runs `install.sh`, reads the settings entry, then runs `base.sh template` (ack) and `base.sh quit` twice with the image's Chrome first on `PATH`, and finally `base.sh freeze`. After each quit and after the install's close, no `SingletonLock`, `SingletonSocket`, or `SingletonCookie` may stay in the root (`noSingletonAfterQuit`, `noSingletonAfterClose`), so `freeze` never copies them into a clone. `tests/host/E10-base-install.spec.ts` is the same chain on this Mac below `RECNRUN_HOST_BASES`.

## Observation

- E10.pipe.load: `install.sh` exited 0 in 7 s with `extensionId=omllgeochjfpkjbkpcgjmnnbncdpiedd`; the entry in `Default/Preferences` had `location` 4, the build path, `creation_flags` 38 (no `1 << 15`), and `extensions.ui.developer_mode: true`; no process named the root after the close.
- E10.pipe.persistFirstRelaunch: `base.sh template` acked in about 1 s under `<root>/downloads`; the entry was unchanged after `quit`.
- E10.pipe.persistSecondRelaunch: the second template acked in about 1 s; `freeze` wrote `install=unpacked` and `unpackedPath=` the build folder.
- E10.policy.forcelist: unavailable. The force list needs a CRX behind an update manifest and a mandatory policy, which needs a root-owned folder on Linux or an MDM profile on macOS (CHROMIUM.md group 18); the POC builds no CRX server (decision 4).

### What the measurement changed

The first green run (`2026-11-05T14-32-44.875Z-1fc015ce-16dd-45ef-8baf-6b94e36ffcd3`) passed `E10.pipe.load` and failed both relaunches with `base.sh: no template ack ... within 60 s`, although the entry kept `creation_flags` 38 and Developer mode. A screenshot of the display during the wait (run `2026-11-05T14-37-28.678Z-1cd3a363-cf65-4ce6-8acf-95d38eebdce7`) showed Chrome's modal "Google Chrome and ChromeOS Additional Terms of Service" dialog: `base.sh template` starts Chrome without `--no-first-run`, while every earlier launch of the root passed it, and Chrome writes its `First Run` sentinel only on a first run (CHROMIUM.md group 18). `base.sh template` now passes `--no-first-run --no-default-browser-check`, as `create-base`, `open.sh`, and `clone-open.sh` already did (the same fix landed with P5.5 run B, `base.checks.mjs` holding the argv), and both relaunches acked (a scratch run first, `2026-11-05T14-40-41.329Z-f412f26d-8418-41af-af8b-230403a9b437`, then the run above).

## Limits of this measurement

- Smoke mode: one chain in the lab; the spec's default is three.
- The lab's Linux Chrome; the host twin is what proves CL17 on macOS, where Developer mode is a tracked preference (group 16).
- The build stays where it was loaded from; `base.sh` refuses the base with 66 once that folder is gone (P5.6).

## Conclusion

In the lab, one `install.sh install-base` over the DevTools pipe installed poc-d0 in a clean base with no gesture, and two later launches with no debugging flag and no client ran it and acked their template tokens. A policy force list is unavailable for an unpacked build. CL17 is recorded when the host twin passes.
