# POC RECnRun — Downloads, launcher, headless e clonagem de base limpa

Data: 3 de novembro de 2026. Documento de implementação e experimentação para Claude Code ou Codex.

## 1. Objetivo e condição de aprovação

Partir da implementação do PR [RECnRun/recnrun#19](https://github.com/RECnRun/recnrun/pull/19), que já implementa pareamento por File System Access API e uma malha WebRTC entre instalações da extensão. Substituir experimentalmente a seleção de uma pasta por escrita em Downloads e leitura por `file://`, acrescentar um launcher feito com ferramentas nativas e testar perfis visíveis, sem janela inicial e headless, com e sem `chrome.debugger`.

Resultado desejado: depois da preparação da máquina, a extensão descobre os demais participantes, o launcher abre os perfis fechados quando necessário e o pareamento/repareamento ocorre automaticamente, sem dashboard obrigatório, seletor de pasta, cópia de códigos ou aprovação de escrita. Acrescentar à variante original de instalação por perfil uma variante de **base limpa, instalação única e clonagem**, iniciada pelo onboarding da RECnRun no Default pessoal.

Tratar como três níveis de aprovação independentes:

| Variante                                  | Preparação permitida                                                                                                                                 | Condição específica de aprovação                                                                                                                                                                     |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V1 — instalação por perfil                | RECnRun instalada no Default master; instalar manualmente também em cada perfil worker participante                                                  | Workers se vinculam ao Default sem gesto adicional de configuração ou pareamento.                                                                                                                    |
| V2 — instalação única na base limpa       | RECnRun instalada no Default master; preparar uma base limpa de workers, instalar/configurar uma vez nela, fechar e congelar; gerar clones completos | A, B e C são workers do Default e funcionam sem reinstalação, autorização ou provisionamento manual por clone. As ações únicas na base são contabilizadas.                                           |
| V3 — instalação manual somente no Default | RECnRun já instalada no Default pessoal; usuário executa uma vez o script fornecido no onboarding                                                    | Preparar e instalar persistentemente a RECnRun na base limpa de forma automática; clonar e provisionar sem segunda instalação manual. Exige aprovação de V2 e do provisionamento automático da base. |

V2 não prova V3. Uma segunda instalação manual na base é permitida para isolar o experimento V2 e reprova a promessa específica de V3. Não clonar o Default pessoal para contornar essa diferença. A instalação única vale pela base e ambiente validados, no mesmo computador e usuário do sistema; não implica distribuição de uma base entre máquinas, contas ou sistemas operacionais.

Essa frase é uma hipótese a testar, não um resultado herdado do PR. Registrar separadamente:

| Critério                             | Aprovação                                                                                                                                 |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Preparação por perfil existente — V1 | Somente a instalação manual da extensão; zero gestos adicionais de configuração ou pareamento.                                            |
| Preparação por clone — V2/V3         | Nenhuma instalação, autorização ou atribuição manual de identidade; todas as intervenções iniciais na base são registradas separadamente. |
| Preparação por máquina               | Entregar e executar o launcher uma vez; inicialização automática é uma opção explícita e mensurável do pacote.                            |
| Operação após a preparação           | Abrir os participantes e estabelecer/reestabelecer os links automaticamente.                                                              |
| Operação invisível                   | Nenhuma janela visível dos executores; aprovação separada de apenas iniciar os perfis automaticamente.                                    |
| Distribuição                         | Resultado separado para unpacked e instalação empacotada normal.                                                                          |

Em V1, ativar manualmente “Allow access to file URLs” prova no máximo a comunicação e **reprova o critério de instalação como única intervenção**. Em V2, essa configuração pode ser feita uma vez na base: aprovar ausência de intervenção por clone somente se a capacidade efetiva acompanhar A, B e C sem novo gesto. Em V3, qualquer nova intervenção manual na base também precisa ser eliminada ou registrada como exigência adicional. Se só funcionar com diretórios de dados separados, aprovar apenas essa topologia; isso não prova headless de perfis existentes dentro da raiz usada pelo Chrome normal.

“Somente instalar a extensão”, no sentido literal de nenhuma preparação na máquina, não inclui um launcher já executando. A extensão não instala nem inicia silenciosamente um shell script arbitrário. O relatório deve manter essa diferença visível, sem tratar a preparação do launcher como se não existisse.

### 1.1 Regra comum a todas as variantes: Default master e demais perfis workers

**Em V1, V2 e V3, a RECnRun deve estar instalada e habilitada no perfil pessoal Default. Essa instalação é sempre o master/head, o controlador principal. Todas as outras instalações operacionais são workers executores subordinados a esse Default.** As variantes alteram apenas como preparar e instalar os workers; não alteram essa hierarquia nem tornam o Default opcional.

| Instância                                    | Papel fixo              | Responsabilidade                                                                                                                       |
| -------------------------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Default pessoal, na raiz habitual do usuário | Master/head/controlador | Onboarding, dashboard principal, cadastro dos workers, solicitação de abertura ao launcher, distribuição e acompanhamento do trabalho. |
| Outros perfis existentes — V1                | Worker                  | Executar no próprio contexto as operações solicitadas pelo Default e devolver status/resultados.                                       |
| Clones A/B/C — V2/V3                         | Worker                  | Mesmo contrato dos workers existentes, em raízes independentes provisionadas a partir da base limpa.                                   |
| Base congelada ou cópia de manutenção        | Template administrativo | Preparar futuros workers; não é master nem worker de trabalho anunciado.                                                               |
| Launcher nativo                              | Auxiliar do Default     | Criar/abrir/acompanhar instâncias e encaminhar os acks de preparação; não substitui o controlador da extensão.                         |

“Default” nesta regra significa **a instalação do perfil pessoal controlador**, identificada pela raiz de dados, identidade e certificado registrados. Um clone aberto com `--profile-directory=Default` continua sendo worker: seu subdiretório `Default/` não o transforma no Default pessoal master. Não deduzir o papel apenas do nome do diretório, nome exibido, ID do pacote ou de um campo `role` recebido sem validação.

O pacote da extensão pode ser o mesmo em todas as instâncias. Persistir a atribuição de papel e a vinculação de cada worker à identidade/certificado do Default master no registro e no bootstrap. A base de workers nunca herda o papel de controlador, e um clone não pode ser promovido automaticamente a master por ser o primeiro processo iniciado ou por o Default ficar indisponível.

O Default coordena; o worker executa localmente, inclusive `chrome.debugger` na própria aba quando solicitado. O worker não distribui trabalho nem controla o Default ou outros workers. Mensagens de resposta, status, heartbeat e sinalização continuam bidirecionais. Links/relays da malha do PR podem ser reaproveitados como transporte, mas não concedem autoridade de controlador a todos os peers. Não é necessário reescrever o transporte como estrela para comprovar a hierarquia; a autorização de comandos deve obedecê-la em qualquer topologia.

O dashboard principal e o onboarding pertencem ao Default. Workers podem oferecer diagnóstico técnico e ter interface gráfica nas rodadas correspondentes, sem se tornarem controladores. O modo headless deste POC se aplica aos **workers**; o Default permanece o master no Chrome normal. Fechar o dashboard do Default não remove seu papel. Uma rodada que suprima o Default ou eleja outro perfil como controlador não aprova nenhuma variante deste plano.

Registrar o comportamento quando o Default fecha: workers não assumem o comando nem aceitam novo trabalho de outro peer. Trabalho já em andamento segue a política explícita do executor, com estado preservado; ao reabrir, o mesmo Default recupera o vínculo, status e resultados sem reexecução indevida. Testar essa recuperação separadamente de reiniciar um worker.

## 3. Regras de implementação

Ler `AGENTS.md`, as regras aplicáveis em `.claude/rules/`, `docs/ARCHITECTURE.md` e os documentos do POC na base escolhida. Manter código, comentários, diagnósticos e documentos incluídos no repositório em inglês. Este plano em português é a especificação do trabalho.

Preservar os gates existentes, o teste red/green e a separação entre builds experimentais e produção. Antes de depender de uma hipótese sobre Chrome, ler a função correspondente no Chromium da versão testada e só então executar o experimento. Nunca marcar um teste como validado apenas porque sua implementação parece correta.

O usuário final usa o **Google Chrome instalado**, sempre com a RECnRun no Default pessoal master. Além dessa instalação obrigatória, V1 instala a extensão em cada worker; V2 instala uma vez na base limpa de workers; V3 automatiza essa base e mantém como única instalação manual a já existente no Default. Não substituir por Electron, Chrome for Testing, Chromium empacotado ou `chrome-headless-shell` para declarar o objetivo atingido. Os testes de regressão existentes podem continuar usando seu Chromium isolado; seus resultados devem ser identificados como tal.

O runtime entregue não pode exigir Node.js, Python, Bun, Deno, Puppeteer, Playwright, `jq`, servidor HTTP, WebSocket local, Native Messaging ou backend de sinalização. Dependências do monorepo e ferramentas de laboratório continuam permitidas para desenvolvimento e verificação, sem entrar no pacote de execução do usuário.

Não editar seletivamente `Preferences`, `Secure Preferences` ou bancos do perfil para fingir instalação/permissão. A cópia completa de uma base fechada é a hipótese explícita de V2/V3, não uma edição dessas preferências. Uma pasta previamente autorizada na base pode ser testada como herança em V2, mas não prova acesso sem preparação em V1. Não usar concessões artificiais por CDP ou opções de teste para mascarar essa distinção.

Em V3, permitir uma investigação de instalação por mecanismos compatíveis com o Chrome real, inclusive CDP quando disponível, sem conceder artificialmente permissões para aprovar a célula. Exigir persistência da instalação após encerramento completo, reabertura e execução sem o cliente de provisionamento. Uma instalação que só existe durante a sessão de automação não aprova V3. O caminho vencedor continua sujeito ao runtime sem dependências extras e não pode depender de flags de carregamento removidas ou indisponíveis no Chrome testado.

Não compartilhar uma raiz de dados simultaneamente entre processos que o Chrome não permite. Não remover locks de instâncias ativas. Somente no clone recém-copiado, ainda fechado, é permitido remover marcadores raiz `SingletonLock`, `SingletonCookie` e `SingletonSocket` comprovadamente herdados de uma base totalmente fechada. Não remover `LOCK` recursivamente de SQLite/LevelDB nem usar essa limpeza para forçar abertura de um diretório ocupado.

## 6. Fase 1 — Downloads e leitura local, isoladamente

Começar por Default master + um worker visível, ambos com a extensão instalada e sem `chrome.debugger`, sem scripts de abertura automática e sem reaproveitar grants FSA. Só depois combinar os eixos. Testar o transporte entre dois workers pode ser um controle técnico, mas não substitui a validação do fluxo Default → worker → Default.

### 6.1 Instalação limpa e permissões

Usar perfis de teste novos, sem decisões prévias de permissões, e duas formas de distribuição:

- Unpacked: instalação manual pelo fluxo normal do Chrome; observar o estado inicial de acesso a arquivos, sem ativar a opção por automação.
- Empacotada normal: instalação por um canal aceito pelo Chrome/OS, como uma publicação de teste na Web Store já disponível. Um CRX criado localmente não prova instalação normal em Windows/macOS. Se esse canal não estiver disponível, marcar a célula não executada e não extrapolar unpacked.

Registrar permissões declaradas, prompts de instalação, `isAllowedFileSchemeAccess()` e qualquer gesto após a instalação. Testar revogar o acesso e atualizar a extensão. A instalação de uma nova versão com permissões novas pode exigir reaprovação; isso é evidência de distribuição, não deve ser escondido.

### 6.2 Escrita e identificação da pasta real

Publicar um pequeno arquivo de probe com `chrome.downloads.download`, destino relativo em `RECnRun/poc/<namespace>/`, `saveAs: false` e `conflictAction: 'overwrite'`. Esperar o estado `complete`, recuperar o `DownloadItem.filename` e ler de volta o arquivo pelo caminho absoluto convertido corretamente em URL `file://`.

Testar:

- Download inicial e substituição do mesmo destino 100 vezes, sem virar nomes `(1)`, `(2)`.
- Conteúdo vazio, espaços, Unicode e nomes/caminhos com caracteres que exigem encoding de URL.
- Falha/cancelamento/reinício durante a publicação, arquivo temporário e `.crdownload`.
- Configuração “perguntar onde salvar cada arquivo”, permissões de pasta do OS, proteção do sistema e política corporativa quando presente.
- Downloads em local personalizado e Downloads redirecionado. Não deduzir o destino por `$HOME/Downloads` ou `%USERPROFILE%\Downloads`.
- Consequências visíveis: shelf/bubble, notificações, histórico, alertas e eventuais interrupções. “Sem seletor” não significa “nenhum vestígio visual”.

Não assumir atomicidade idêntica a `createWritable()`. Verificar o comportamento real em cada OS. O leitor deve tolerar ausência, JSON incompleto, versão antiga, arquivo em substituição e erros temporários; a última publicação válida continua valendo até expirar.

### 6.3 Leitura e descoberta são testes distintos

Ler um arquivo cujo caminho já é conhecido não demonstra enumeração de diretório nem descoberta dos outros perfis.

Primeiro provar leitura em uma página da extensão e no offscreen. Avaliar `fetch` e, se houver diferença de suporte, uma alternativa web do contexto offscreen, documentando qual funciona na versão testada. Não executar a leitura a partir de content script de um site e atribuir ao site privilégios da extensão.

Depois testar uma estratégia real de descoberta sem picker. Prioridade:

1. Uma raiz comum de Downloads, com manifesto de participantes atualizado por **um único escritor**, o launcher.
2. A extensão envia seu registro usando nome/payload restrito; o launcher enumera arquivos nativamente e publica o catálogo.
3. As extensões leem esse catálogo em um caminho de rendezvous que elas consigam determinar automaticamente.

Existe um problema de bootstrap a resolver: como cada extensão encontra o primeiro catálogo e como o launcher descobre a pasta real do primeiro registro? Implementar e provar uma solução concreta, não um arquivo `registry.json` cujo caminho só o desenvolvedor conhece.

Para Downloads comuns, o probe fornece a raiz local. Para Downloads diferentes, investigar a publicação automática de localizadores pelo launcher durante uma abertura com token de bootstrap, ou descoberta de caminhos/configuração por leitura validada na extensão. Registrar limites para raízes personalizadas e perfis fechados. A configuração manual de caminhos pode ser um controle diagnóstico, mas reprova o objetivo de nenhuma configuração adicional.

Não fazer múltiplos perfis reescreverem simultaneamente um índice compartilhado. Não usar `chrome.downloads.search` em A como se ele enxergasse o histórico de B. Não depender de HTML de listagem de `file://` sem um experimento específico e um parser validado para isso.

Na variante de clonagem, o launcher já conhece os diretórios que criou e seus identificadores: reutilizar esse registro para descobrir clones, sem exigir um `profiles.json` preenchido pelo usuário. Isso facilita o bootstrap, mas não dispensa provar a localização real de Downloads e o acesso aos arquivos em cada clone.

## 7. Fase 2 — substituir o transporte e preservar o protocolo

Executar o mesmo handshake e as verificações de transporte do PR usando o adaptador Downloads. Começar por Default master + um worker e repetir com Default + quatro workers. Manter as regressões da malha, mas acrescentar a autorização hierárquica do protocolo de trabalho.

Layout proposto, ajustável após os testes de descoberta:

```text
RECnRun/poc/<namespace>/registry.json
RECnRun/poc/<namespace>/peers/<profileId>/presence.json
RECnRun/poc/<namespace>/peers/<profileId>/offer-<recipientId>.json
RECnRun/poc/<namespace>/peers/<profileId>/answer-<recipientId>.json
RECnRun/poc/<namespace>/launcher/requests/<requestId>.request
RECnRun/poc/<namespace>/launcher/acks/<requestId>.ack
```

Os caminhos acima descrevem arquivos, não uma API de acesso livre ao disco. Cada extensão só publica destinos relativos ao seu Downloads; o catálogo pode precisar mapear as raízes reais de vários escritores.

Preservar `profileId`, certificado persistente, códigos/validade, validação de remetente/destinatário, fingerprint fixado, eleição do ofertante, deduplicação, limite de payload, isolamento por destinatário e pausa de Disconnect/Forget. Acrescentar geração de processo/boot e sequência quando necessárias para distinguir presença e sinais de uma execução anterior.

A eleição do ofertante ICE/SDP decide apenas quem inicia o handshake; nunca elege o master. O Default continua controlador mesmo se o UUID do worker for menor e ele criar a oferta. Cada worker valida a identidade/certificado do Default como origem dos comandos; o Default valida de qual worker vêm os resultados. Um worker com link verificado não ganha autoridade para comandar outro worker ou o master. Relays de sinalização não transformam o relay em autor de comandos de trabalho.

Manter os fingerprints já fixados. Não aceitar alteração de certificado só porque um catálogo ou presença novo aparece no disco. O PR considerava escolher a pasta como consentimento; aqui isso muda para participar de um namespace automaticamente. Documentar que é um grupo de extensões instaladas pelo mesmo usuário do OS, com confiança inicial pelo canal local. Um certificado anunciado num arquivo modificável não autentica sozinho o primeiro encontro. Qualquer necessidade de aprovação manual de peers deve aparecer no resultado de usabilidade, e não ser omitida da contagem de gestos.

O DataChannel deve transportar os dados após o handshake; Downloads fica para presença, descoberta, inicialização e recuperação. Não gerar um download por mensagem de negócio. Medir o custo da presença: com TTL atual, cinco perfis renovando a cada 30 segundos produzem aproximadamente 600 publicações/hora, antes dos handshakes. Avaliar reduzir escritas usando presença do launcher e do canal, mantendo descoberta de novos participantes.

Ensaios obrigatórios: chegada simultânea, oferta/resposta duplicada, arquivo vencido/corrompido, relógio alterado, peer encerrado durante ICE, reinício de ambos, cache de leitura, reconexão sem dashboard e chegada do quinto perfil quando os quatro primeiros não têm página da extensão aberta.

## 8. Fase 3 — launcher nativo por sistema

### 8.1 Pacote e responsabilidades

| OS      | Runtime permitido no pacote                                                   | Serviços de inicialização a avaliar                                                     |
| ------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Windows | Windows PowerShell disponível no sistema; `.cmd` opcional apenas para entrada | Task Scheduler do usuário                                                               |
| macOS   | `/bin/sh` e utilitários entregues com o sistema; `plutil` quando necessário   | LaunchAgent do usuário                                                                  |
| Linux   | `/bin/sh` e utilitários básicos do sistema suportado                          | `systemd --user` quando disponível; execução em background documentada como alternativa |

“Sem linguagem adicional” significa sem instalar um runtime extra: o próprio shell/PowerShell interpreta o script. Não depender do Python histórico do macOS, PowerShell 7, `jq` ou ferramentas de desenvolvimento. Definir versões mínimas de OS e testar os utilitários presentes nelas. O shell POSIX não deve tentar interpretar JSON arbitrário por regex.

O launcher:

- Localiza o binário do Google Chrome e raízes de dados existentes, inicialmente pelas localizações padrão do OS.
- Descobre candidatos e identifica aqueles com a extensão instalada. Automatizar o vínculo entre `profileId` da extensão e o par `(userDataDir, profileDirectory)`. Não assumir que o nome exibido no dashboard é `Profile 2`.
- Pode usar a extensão, que já tem JavaScript, para interpretar configuração JSON lida com permissão; isso não acrescenta runtime externo. Se usar um bootstrap da extensão com token, validar o token e comprovar que ele chegou ao perfil solicitado.
- Mantém o catálogo e observa pedidos de abertura. Para o shell POSIX, preferir um formato de controle simples, fixo e validado, ou nomes de arquivos restritos, evitando a necessidade de um parser JSON de terceiros.
- Abre somente perfis existentes e registrados; nunca cria acidentalmente um perfil por erro de nome.
- Trata a mesma raiz usada por múltiplos perfis separadamente de raízes distintas.
- Aguarda um ack da extensão contendo token da tentativa, identidade e boot atual. PID, código de saída zero ou existência de uma janela não provam que o perfil certo inicializou.
- É idempotente: duas execuções não abrem uma tempestade de janelas; pedidos duplicados não iniciam várias cópias.
- Controla timeout, backoff, trava do launcher, reinício e encerramento voluntário. Não relança um executor explicitamente pausado sem uma política definida.
- Tem comandos/ações documentados para iniciar, consultar status, parar e remover sua inicialização automática, sem exigir edição manual de arquivos de configuração para o caminho padrão.

Pedidos de abertura contêm somente identificadores registrados e opções enumeradas, dentro de operações iniciadas/autorizadas pelo Default master. Workers enviam seus acks e estado; não assumem a coordenação do launcher. Nunca executar `eval`, comandos de shell, URLs arbitrárias ou argumentos livres recebidos de arquivos. Não executar como administrador para contornar limitações do perfil.

### 8.2 Descoberta automática é um entregável

Testar máquinas com Chrome fechado, somente perfil Default aberto, um perfil secundário aberto e múltiplas raízes. Distinguir nomes de diretório, nomes visíveis e UUIDs. Testar extension ID fixo, extensões unpacked em caminhos diferentes, atualização e remoção da extensão.

Se não for possível identificar perfis e caminhos automaticamente com a estratégia escolhida, entregar a evidência e a limitação. Um `profiles.json` preenchido pelo usuário não satisfaz o objetivo, embora possa ajudar a isolar um teste.

O launcher não tem de retransmitir SDP: as extensões podem continuar trocando os arquivos diretamente. Ele pode publicar um catálogo e atuar como escritor único de metadados de máquina, sem virar um servidor.

### 8.3 Preparação versus uso diário

Entregar um pacote por OS, com uma entrada de execução e sem build na máquina do colega. O bundle da extensão é preparado pelo desenvolvedor. V1 exige instalação manual em cada perfil; V2 prepara uma base uma vez; V3 começa pela instalação já existente no Default e precisa automatizar a base. Documentar exatamente o primeiro comando/clique de execução do launcher e eventuais prompts do OS. Após isso, demonstrar o fluxo diário sem comandos adicionais, quando habilitada a inicialização automática.

Não aprovar o critério literal “apenas extensão instalada” se o script precisa ser baixado/executado separadamente. A formulação de V1 é “launcher preparado uma vez na máquina; por perfil, somente instalar a extensão”. A de V2 é “base limpa preparada uma vez; clones provisionados automaticamente”. A de V3 é “RECnRun instalada manualmente somente no Default; usuário executa uma vez o launcher e o restante da preparação é automático”.

### 8.4 Variante de base limpa e clonagem — macOS primeiro

Esta variante incorpora a especificação fornecida pelo usuário, **POC RECnRun — perfil limpo, instalação única e clonagem da base**, de 3 de novembro de 2026. É um plano de execução sem resultados medidos. A cópia da instalação é uma hipótese experimental, não uma API oficial de provisionamento. A rodada inicial usa o mesmo computador, usuário do OS e Chrome instalado; não exige portabilidade entre máquinas, contas ou sistemas.

Pré-condição de V2 e V3: a RECnRun já está instalada no Default pessoal e ele é o master. A instalação única desta seção refere-se à **base dos workers**, além da instalação obrigatória do controlador. Clonar a base gera workers do mesmo Default, nunca novos masters.

#### Onboarding e sequência de preparação

| Etapa                    | Responsável                             | Evidência necessária                                                                                               |
| ------------------------ | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Iniciar configuração     | RECnRun já instalada no Default pessoal | Apresentar a base limpa e quantidade desejada de clones; registrar `operationId`.                                  |
| Preparar execução local  | Usuário                                 | Baixar e executar uma vez o script nativo; download sozinho não conta como execução.                               |
| Criar diretório vazio    | Launcher                                | Raiz exclusiva, sem informação importada do perfil pessoal.                                                        |
| Instalar RECnRun na base | Preparação da base                      | V2 admite instalação manual nesta etapa; V3 exige instalação automática persistente, sem novo carregamento manual. |
| Configurar e congelar    | RECnRun da base + launcher              | Configuração reutilizável, modo template e encerramento completo da instância.                                     |
| Criar e provisionar A/B  | Launcher + RECnRun                      | Cópias completas independentes, identidades distintas e bootstrap concluído antes do anúncio.                      |
| Concluir onboarding      | RECnRun no Default                      | Ack de cada clone, extensão ativa e comunicação verificada. A presença da base não prova que clones estão prontos. |

O onboarding acompanha sucesso, erro e ações pendentes, com conclusão por confirmação real correlacionada ao `operationId`, nunca por temporizador. A base pode emitir um ack administrativo de preparação, separado da descoberta normal. Na primeira rodada técnica, ações manuais para isolar cópia e identidade são controles permitidos; registrar o resultado como parcial.

V3 acrescenta a investigação do provisionamento automático da base na versão real do Chrome. Se avaliar CDP, testar instalação persistente após encerramento completo e reabertura sem cliente de automação. Uma instalação transitória não aprova CL17. Não presumir que instalar uma extensão via CDP tem o mesmo comportamento em todas as versões nem que esse caminho dispensa a execução do script pelo usuário.

#### Diretórios, base e código da extensão

Raiz inicial sugerida no Mac: `~/Documents/RECnRun/profile-clone-poc`.

| Caminho relativo         | Finalidade                                                                      |
| ------------------------ | ------------------------------------------------------------------------------- |
| `base-v1/`               | Raiz de dados limpa, preparada e fechada, incluindo `Local State` e `Default/`. |
| `clones/A/`, `clones/B/` | Raízes completas e exclusivas para os primeiros executores.                     |
| `clones/C/`              | Clone posterior da base original para repetibilidade.                           |
| `extension/recnrun-vX/`  | Build unpacked identificado, em caminho estável e versionado, quando aplicável. |
| `reports/`               | Evidências e resultados sanitizados.                                            |

Criar a raiz da base somente se não existir; abrir o executável real do Chrome com `--user-data-dir` dessa raiz e `--profile-directory=Default`. Confirmar o caminho em `chrome://version`. Não importar o Default pessoal, cookies, senhas ou sessões, nem ativar sincronização Google. Instalar somente a RECnRun como extensão do usuário; componentes internos do Chrome não invalidam a base limpa.

Para unpacked, registrar ID, versão e caminho externo do código. Copiar a raiz de dados não torna independente esse código externo. A/B podem compartilhar o mesmo build imutável na primeira rodada. Testar remoção temporária do caminho e recuperação após restaurá-lo; verificar novamente o ID se mover/duplicar o código. Não modificar o build compartilhado durante uma rodada. Instalação via Web Store é outra modalidade e precisa de resultado próprio.

Configurar somente capacidades realmente usadas: acesso a `file://`, Downloads e/ou grants FSA, cada um com verificação efetiva e gestos registrados na base. Salvar marcador inofensivo como `pocSetting = 'base-v1'`. Não deixar gravações, ações pendentes ou sinais de pareamento de trabalho. A base entra em modo template e o launcher recusa abri-la como executor normal.

#### Cópia completa e publicação do clone

Fechar totalmente a instância da base antes de copiar; fechar a janela não prova encerramento de processos. O Chrome pessoal pode continuar aberto em outra raiz se a identificação das instâncias for segura. Sem detector confiável, exigir o fechamento como pré-condição do ensaio diagnóstico e registrar a limitação; não aprovar preparação totalmente automática por essa rodada.

Copiar **toda a raiz da base**, incluindo `Local State` e `Default`, sem transplante seletivo da extensão ou edição de preferências protegidas. Usar ferramentas nativas, inicialmente `ditto` no macOS. Criar em destino temporário novo, verificar o sucesso e só então publicar o clone pronto. Recusar destinos existentes, sem sobrescrever. Não abrir cópias interrompidas.

Não usar symlinks/hard links que compartilhem dados mutáveis. Cópia física ou copy-on-write é aceitável se as escritas seguintes forem independentes. Remover marcadores Singleton apenas no clone novo e fechado conforme a seção 3; nunca apagar `LOCK` de bancos ou forçar raiz ocupada. O script não encerra todo o Chrome por padrão: só instâncias que consiga identificar como suas.

#### Template, bootstrap e identidades

A clonagem não é uma nova instalação garantida: não depender de `runtime.onInstalled` para regenerar identidade. Também não gerar uma identidade persistente nova a cada boot. Não presumir que a extensão consegue obter seu caminho absoluto de perfil por uma API padrão.

1. A base mantém `templateMode = true`. Esse estado bloqueia descoberta, anúncio e comandos de trabalho desde o início do service worker, até o clone ser provisionado. Provar o bloqueio já na primeira ativação da extensão na base, inclusive `onInstalled`: não basta entrar em template depois de ela anunciar. Se o papel ainda não estiver atribuído, o fluxo de preparação precisa manter o anúncio bloqueado até a decisão, sem impedir o onboarding administrativo no Default.
2. O launcher mantém fora da base um registro estável entre diretório e `profileInstanceId`, namespace, versão da base, papel `worker` e identidade/fingerprint do Default master, com ID gerado por recurso nativo do OS. O template nunca recebe o papel de master.
3. Na primeira abertura, fornecer ID, vínculo ao master e token da operação a uma página da extensão, por exemplo `bootstrap.html` com fragmento de URL. Implementar e testar essa página; ela não é presumida na base atual. Os parâmetros são não secretos e estritamente validados. Validar a atribuição contra o registro da operação; um campo `role=master` forjado não muda o papel de um clone.
4. O bootstrap inicializa identidade e certificado de trabalho do clone antes de liberar a descoberta. Como o PR persiste certificado DTLS, evitar também duplicar a chave privada/fingerprint da base entre clones: IDs diferentes sozinhos não resolvem a identidade criptográfica. Preferir template sem certificado de trabalho ou gerar um certificado próprio na primeira provisão, preservando-o nas reaberturas seguintes.
5. Limpar somente estado transitório/peer herdado que não deve existir no template: pending offers, sessões, caches de links e pins de trabalho. Preservar configuração reutilizável; não apagar um IndexedDB inteiro para limpar um registro. Não alterar pins válidos de um clone já provisionado.
6. Persistir a provisão de forma recuperável, sair de template e emitir ack correlacionado ao `operationId`. Só então anunciar. Repetir o mesmo bootstrap é idempotente; outra identidade conflitante falha com diagnóstico, sem substituição silenciosa.

O `extensionId` pode ser igual entre clones; identidade persistente de peer e `profileInstanceId` precisam ser próprios; `bootId` muda por execução. Adaptar os nomes ao `profileId` existente, sem criar identidades concorrentes sem mapeamento. Não usar `storage.sync` como identidade exclusiva. Atribuição manual de A/B por diagnóstico isola o experimento de cópia, mas não aprova V2/V3 sem intervenção por clone.

## 9. Fase 4 — modos de execução e topologias

**Modo silencioso e headless não são equivalentes.** Testar o Chrome normal com `--no-startup-window` como variante própria. Headless nativo usa o headless unificado do Chrome instalado (`--headless`, ou a grafia suportada pela versão testada), nunca apenas uma janela minimizada/Xvfb.

| T1  | Uma raiz, Default master + um a quatro workers visíveis                                                | O launcher carrega o worker certo e o conecta ao Default já aberto?                                           |
| T2  | Uma raiz, Default master no Chrome normal e workers com `--no-startup-window`                          | Workers inicializam a extensão e mantêm o offscreen sem janela própria?                                       |

Em T4/T5, o lock é por raiz de dados, não por `profileDirectory`. Não copiar um perfil em uso para uma nova raiz e chamar isso de execução do mesmo perfil: identidade criptografada, caminhos e estado do Chrome podem mudar. Não encerrar o Chrome pessoal do usuário para fazer um teste passar. Conflitos esperados devem ser reportados, com alternativa T2 ou T6 avaliada separadamente.

Na série V1, usar perfis de teste previamente criados e extensão instalada **manualmente**, depois iniciar pelo launcher. Na série V2/V3, usar clones da base preparada conforme a seção 8.4, sem reinstalar a extensão nos clones. As flags `--load-extension`/`--disable-extensions-except` das fixtures Chromium atuais não são evidência de distribuição ou headless no Google Chrome instalado.

Ajustar o POC para o worker inicializar sem `showDirectoryPicker`, `requestPermission`, abertura automática de dashboard, chamada de PiP ou ativação de usuário. Gerar nome padrão sem “Save name”. Atribuir papel worker e vínculo ao Default sem novo clique por perfil. O Default mantém o dashboard principal e pode abri-lo quando solicitado; workers não recebem essa função de controle.

Usar uma página estática de teste ou fixture empacotada para comprovar navegação e operações no contexto certo. Headless não pode ser aprovado só por uma presença em disco. Confirmar extensão ativa, offscreen, link DTLS validado, mensagens bidirecionais, abas remotas, navegação e uma resposta que inclua o marcador exclusivo daquele executor.

Foco de janela e PiP visível são não aplicáveis ao executor headless. Separar esses comportamentos das operações de abas que devem funcionar. Não transformar “PiP indisponível no executor” em falha de handshake nem chamar isso de sucesso do PiP.

## 10. Fase 5 — com e sem chrome.debugger

Executar os modos/topologias viáveis nos três estados abaixo. O eixo é independente do transporte Downloads, do headless e da origem do executor: instalado individualmente em V1 ou clonado em V2/V3.

| Variante | Manifest / execução                                                                                       | Finalidade                                                   |
| -------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| D0       | Sem permissão `debugger`, zero attaches e nenhum CDP externo                                              | Provar comunicação e ciclo de vida autônomos.                |
| D1       | Permissão `debugger` declarada, nenhum attach                                                             | Separar o efeito da permissão do efeito de uma sessão ativa. |
| D2       | Permissão declarada, `chrome.debugger.attach` executado pela extensão numa aba de teste do próprio perfil | Provar funcionamento com debugger e operações CDP reais.     |

Construir as variantes a partir do mesmo código. Nos testes comparativos, preservar o ID da extensão quando necessário e evitar que estado herdado entre variantes invalide a comparação. Primeira instalação limpa e atualização são séries separadas.

Para V2/V3, preparar versões de base identificadas para D0/D1/D2 e verificar a herança efetiva das permissões em cada clone. Não contar como sucesso “sem intervenção por clone” uma troca de build que abre novo prompt em todos os clones. CDP externo usado somente para provisionar a base em CL17 é um eixo de preparação separado; a execução final D0/D1 deve continuar sem ele após reabertura completa.

Em D2, o Default solicita a operação; a extensão no worker faz o attach na própria aba e envia `Runtime.enable`, `Page.enable` e um `Runtime.evaluate` simples que devolva um marcador da página de teste, dentro dos domínios permitidos. O worker devolve o resultado ao Default. Registrar attach, resposta, detach e erro, sem payloads de aplicações reais. O debugger não participa do pareamento nem concede acesso a arquivos; o master não se anexa diretamente à aba de outro processo/perfil.

Testar detach deliberado, aba fechada, navegação e tentativa de attach já ocupado/restrito. A malha deve sobreviver à falha do debugger. Testar attach no executor antes da conexão e após estabelecer o DataChannel, e manter conexão após detach por pelo menos dez minutos.

Não confundir `chrome.debugger` com `--remote-debugging-port`, WebDriver ou CDP aberto por Playwright. No ensaio final D0/D1 não deixar DevTools ou cliente externo conectado ao worker. Uma sessão de debugger pode prolongar sua vida; a comparação deve revelar esse efeito, não utilizá-lo para esconder ausência de inicialização/recuperação.

A instrumentação final consiste em diagnósticos limitados produzidos pela própria extensão e observação do processo/arquivos pelo launcher. Quando uma inspeção externa for necessária para diagnosticar falha, repetir a célula sem ela para declarar aprovação.

## 11. Matriz de aceitação e ensaios

Executar primeiro Default master + um worker em V1. Na clonagem, manter o Default master presente e criar workers A/B, depois C para provar repetibilidade. Expandir a série de comunicação para Default + quatro workers e longas durações após os testes elementares. Não gerar um produto cartesiano desnecessário: registrar combinação inválida com sua causa e exercitar as fronteiras relevantes. Contar separadamente o master, os workers e a base template.

### 11.3 Métricas e repetição

Metas iniciais, não números já obtidos:

- 20 inicializações frias para a melhor variante de cada OS; zero clique extra por participante e zero perfil incorreto. Em V2/V3, preservar também identidade/certificado do clone.
- 50 reconexões de um executor; zero duplicação de identidade, comando ou peer.
- Link após ack de boot: P95 até 15 segundos; abertura até ack: P95 até 30 segundos. Se a máquina exceder, registrar os tempos e a causa, sem maquiar timeout como sucesso.
- Sessão de uma hora com cinco participantes e páginas da extensão fechadas; zero queda não recuperada. Comparar D0 com D2.
- Queda detectada no canal em até dez segundos e presença abandonada expirada conforme TTL do transporte.
- Medir CPU, memória do Chrome/launcher, quantidade de leituras/downloads, bytes/hora e crescimento do histórico/disco.
- Medir janelas surgidas/focadas e prompts separadamente do número de cliques.
- Em clonagem, medir três rodadas novas de CL03–CL12, tempo de cópia, espaço e latências de provisionamento; contabilizar gestos no Default, na base e em cada clone em colunas distintas.

Reduzir polling quando ocioso e serializar leituras/publicações. Usar heartbeat do canal para liveness dos links; não criar downloads só para acordar o worker. O launcher não deve rodar em busy loop. Sleep do OS não conta como garantia de execução contínua.

## 12. Observabilidade e método red/green

Para cada execução, guardar `runId`, SHA, versão do build, ID da extensão, OS/Chrome, instalação unpacked/empacotada, estado de acesso `file://`, topologia, modo, estado D0/D1/D2 e qualquer cliente de diagnóstico conectado. Acrescentar V1/V2/V3, versão da base, clone/diretório, `operationId`, estado template/bootstrap e intervenções manuais por etapa. Registrar identidade/certificado do Default master, papel e master vinculado de cada worker, origem dos comandos e destino dos resultados. Não confundir teste de clonagem com uma instalação limpa independente.

Registrar timestamps para: processo solicitado, perfil reconhecido, worker iniciado, offscreen pronto, probe publicado/lido, catálogo encontrado, presença observada, oferta/resposta concluída, ICE/DTLS/DataChannel prontos, link verificado e primeiro comando respondido. Identificar transição de worker sem exigir anexar DevTools. Logs não precisam conter SDP completo, cookies ou dados de páginas do usuário.

Cada hipótese nova precisa de um controle negativo que falhe pela causa prevista. Exemplos: acesso a arquivos desligado, caminho errado, resposta vencida, ID de destinatário forjado, launcher ausente ou raiz ocupada. Após a mudança, repetir o mesmo caso com a causa resolvida. Manter controles negativos fora do código final quando forem mutações temporárias.

Na clonagem, acrescentar negativos para identidade/certificado herdados, template que anuncia antes de provisionar, bootstrap repetido/conflitante, cópia interrompida, base ainda ativa e instalação CDP que não persiste. Verificar que a base congelada não foi modificada pela criação/abertura dos clones. Um UUID diferente no diagnóstico sem teste de comunicação e certificado não comprova isolamento completo.

Para a hierarquia, provar rejeição de comandos worker→worker e worker→Default, inclusive quando o canal/peer é válido, e preservar respostas/relays legítimos. Testar boot de worker antes do master, ausência temporária do Default e clone com subdiretório `Default/`; nenhum caso promove outro controlador. Os testes de regressão da antiga malha simétrica não bastam para aprovar essa autorização.

Preservar os gates atuais. A regra existente de E2E headed em Docker continua para a suíte de regressão. Acrescentar um runner experimental separado para headless real; não mudar toda a suíte para `headless: true` e apagar o controle que já funcionava. Quando os resultados demonstrarem que a regra contém uma limitação ultrapassada, atualizar sua justificativa e escopo com a evidência, mantendo os testes de UI que exigem janelas.

Executar `vp run verify` no encerramento de uma implementação. Ensaios no Chrome de marca e nos outros OS complementam esse gate; não são substituídos por ele. Ferramentas de automação do laboratório não integram o runtime distribuído.

## 14. Decisão final obrigatória

O relatório deve responder individualmente:

1. Downloads + `file://` substituem o FSA sem seletor/grant de escrita?
2. Isso funciona imediatamente após instalação unpacked? E após instalação empacotada normal?
3. Como as raízes reais de Downloads e os perfis são descobertos sem configuração manual?
4. O launcher abre perfis existentes da raiz normal com Chrome já aberto?
5. O modo sem janela inicial funciona para esses perfis, mesmo sem nenhum dashboard?
6. O headless nativo funciona na mesma raiz? Em raízes separadas? Qual limitação concreta impede uma célula?
7. O fluxo funciona em D0, D1 e D2, e após detach?
8. Quais gestos são exigidos por perfil, por máquina e após reinício?
9. Quais OS/versões foram efetivamente testados?
10. Qual variante atende integralmente ao objetivo e quais são apenas sucessos parciais?
11. A instalação única na base limpa sobrevive à cópia completa, inclusive permissões e dependência do código unpacked?
12. A/B/C têm dados, identidade e certificado próprios e persistentes, com template impedido de anunciar antes do provisionamento?
13. O onboarding prepara a base tendo como única instalação manual a do Default? CL17 persiste após reabertura sem o cliente de provisionamento?
14. Quais ações são únicas no Default/na máquina, quais ocorrem uma vez por base e quais ainda são exigidas por clone? Atualizar a base mantém os clones antigos independentes?
15. A RECnRun estava instalada e habilitada no Default pessoal em todas as variantes, sempre como único master? Todos os demais perfis operacionais foram workers, inclusive clones cujo subdiretório se chama `Default/`?
16. O Default distribuiu os comandos e recebeu os resultados, com rejeição de controle por workers e recuperação após reinício do master sem promoção ou duplicação de trabalho?

Classificar cada variante como **aprovada**, **aprovada com exigência adicional**, **reprovada** ou **não executada**, com evidência. Se só unpacked satisfizer a ausência de clique em `file://`, dizer “instalação manual unpacked”, e não “qualquer instalação”. Se headless só passar com raízes dedicadas, não apresentar isso como headless transparente dos perfis existentes da raiz normal.

Aplicar ainda os critérios próprios de clonagem:

| Resultado                                           | Condições                                                                                                                                                                                                   |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Regra de arquitetura obrigatória — V1/V2/V3         | RECnRun no Default pessoal como único master/head; demais instâncias operacionais como workers vinculados; base como template; launcher como auxiliar. Falhar nessa regra impede aprovar qualquer variante. |
| Clonagem funcional aprovada                         | Instalação única na base; A/B/C habilitados sem reinstalação; dados independentes; identidades/certificados distintos e persistentes; base reutilizável.                                                    |
| V2: provisionamento transparente por clone aprovado | Clonagem funcional, bootstrap automático antes do anúncio, permissões efetivas sem novo gesto, comunicação e reconexão sem páginas de configuração manuais por clone.                                       |
| V3: instalação manual somente no Default aprovada   | V2 aprovada e CL16/CL17 aprovados: preparação automática persistente da base, com execução única do script explicitamente contabilizada.                                                                    |

Se houver autorização manual por clone, registrar **“clonagem aprovada; provisionamento transparente não aprovado”** e qual autorização falta. Se a base ainda exigir instalação manual, V3 não está aprovada, mesmo que V2 funcione. Se o Chrome desabilitar a extensão ou exigir reinstalação no clone, a clonagem funcional não está aprovada naquele ambiente; não editar preferências protegidas para mascarar isso. Headless, debugger e portabilidade continuam com resultados separados.

Um resultado parcial não encerra o trabalho de investigação: corrigir falhas da ferramenta dentro do escopo e usar o cenário que revelou o problema como primeiro teste red/green. Limitações efetivas do Chrome devem ser documentadas com fonte e experimento; não contornadas mudando silenciosamente o objetivo.
