## Hypotheses and verdicts

The hypothesis of P1.4: `Fetch.enable` on the tab session (and on the worker session) intercepts the service worker's main script on first registration, on update, and its `importScripts`/`import` requests; `Fetch.fulfillRequest` with a wrapped body keeps the script working; the wrapper never embeds the session; byte comparison still detects updates; an offline start from the persisted script runs the wrapper. A `first` sample passes only when the main script was paused and fulfilled wrapped, the worker was released, its first request to the fixture's API carries `__rec=<marker>`, and IndexedDB and Cache Storage hold its stores only as `__rec:<marker>:<name>`. `pausedMs` is the time from `Fetch.requestPaused` to the reply of `Fetch.fulfillRequest`.

## How it runs

The isolator owns every `chrome.debugger` call. `apps/isolator/src/background/route-b/` exposes `recnrunRouteB` on its service worker (`arm`, `journal`, `disarm`, `update`, `stopWorker`), with Valibot-validated requests. `arm({ tabId, marker })` attaches to the tab, sends `Fetch.enable` with the pattern `*/sw-*.js*` at the response stage (or `*` for one diagnostic), and `Target.setAutoAttach({ autoAttach: true, waitForDebuggerOnStart: true, flatten: true })`. On each `Target.attachedToTarget` for a worker it sends `Fetch.enable` with the same patterns on the worker's session (and `Network.enable` for the diagnostics that read network events), then `Runtime.runIfWaitingForDebugger`. On `Fetch.requestPaused` at the response stage for a JavaScript response, a main script (the `Service-Worker: script` request header) gets `Fetch.getResponseBody`, the wrapper, and `Fetch.fulfillRequest` with the original status and headers minus `Content-Length` and `Content-Encoding`; imported scripts are continued unless the arm request asks to transform them; everything else gets `Fetch.continueRequest`. The journal records every pause (session, URL, `resourceType`, stage, action, sizes, `declared: "transformed"` for each fulfilled script, the wait, Chrome's exact error), every worker (waiting, `Fetch.enable` result, release), and, when asked, the worker's `Network.requestWillBeSent`, `Network.loadingFailed`, and `Network.requestWillBeSentExtraInfo` fields.

The wrapper never names a session. A classic script, and the `module` variant (a module without a static import), gets `withMarker(marker)` from `@recnrun/worker-bootstrap` prepended to the original body. A module with a static import (`static`, `dynamic`) gets `import "chrome-extension://<id>/route-b/bootstrap.js?marker=<marker>";` as its first statement, since imports are evaluated before the importing module's body. `route-b/bootstrap.js` is a web-accessible resource the isolator's build writes from the bootstrap source (a WXT `build:publicAssets` hook in `apps/isolator/wxt.config.ts`); it reads the marker from its own `import.meta.url`, so one file serves every marker and the wrapped script is byte-stable for a given marker and body (`apps/isolator/tests/route-b-wrap.test.ts`).

The spec only drives pages and reads results. Each load opens a new tab, arms it with a marker unique to the load, opens `sw.html?sw=<variant>`, waits for the page's report and its `first-paint` ledger entry, disarms the tab (which returns the journal), lists the app origin's IndexedDB databases and caches through the tab's own CDP session, reads the ledger since its checkpoint, clears the origin's service workers and storage through Route A's `clearOrigin`, closes the tab, and closes every service-worker target left through `stopWorker` until `getTargets()` lists none. The paths:

- `first`: 20 first registrations of each of the five variants.
- `imports`: the same loads of `imports` and `static`, read for where `/sw-main.js` and `/sw-imported.js` paused.
- `update`: after a first load the tab is armed again with the same marker or a new one and the isolator evaluates `navigator.serviceWorker.getRegistration().then(r => r.update())` in the page; the outcome is whether `updatefound` fired and a version was installing, and the requests the classic worker made afterwards.
- `offline`: after a first load the tab closes, the isolator closes the worker target (`Target.closeTarget`), the spec waits until `getTargets()` lists no running worker, cuts the fixture with `POST /__network?mode=offline`, opens a new tab armed with a new marker, navigates to `/index.html` under the scope, reads the ledger and the stores, and restores the network in `finally`.
- The diagnostics: `imports-transform` (5 loads each of `imports` and `static` with imported scripts fulfilled too), `tab-session-main-script` (every `first` journal plus 5 classic loads armed with the pattern `*`), and `fulfilled-worker-address-space` (5 classic loads fulfilled and 5 where Route B leaves the worker's script alone, both with `Network.enable` on the worker session).

The fixture's workers open a request, a database, and a cache as their first statements (PLAN.md P0.6), so the ledger and the physical store names show whether the wrapper came first. The ledger's effects are the requests Chrome made to the fixture's API; the harness's own control calls carry no `Sec-Fetch-Dest` and are left out. The pure evaluation lives in `tests/experiments/e5-samples.ts` and `tests/experiments/e5-paths.ts`, tested by `tests/e5-samples.test.ts` and `tests/e5-paths.test.ts`; `samples.json` keeps every sample, its outcome, the page report, and the journal.

## Observations

- **Chrome never pauses a service-worker script on the tab session.** `Fetch.enable` on the tab answered `ok` in every load, yet across 105 loads no main script paused there, also with the pattern `*`: the tab saw only the page's own requests (`sw-page.js` as `Script`; with `*` also `sw.html` as `Document`, `page.js` as `Script`, and `/__marker?name=sw:start` as `XHR`). Every main script paused on the worker's session, which auto-attach delivered with `waitingForDebugger: true` before the script was fetched and where `Fetch.enable` answered `ok`: the main script as `Other`, `importScripts` requests as `Script`, static imports as `Other`, and the worker's own `fetch()` calls as `XHR`. E1 did not probe `Fetch` on a worker session.
- **The fulfilled script runs, and its wrapper runs first.** `Fetch.fulfillRequest` answered without error for 100 of 100 main scripts: `sw-main.js` grew from 2,526 to 19,354 to 19,359 bytes (classic and module, the size varying with the marker's length), `sw-imports.js` from 117 to 16,948 to 16,950, `sw-static.js` from 92 to 203 to 205, and `sw-dynamic.js` from 367 to 479 to 480. Chrome registered every wrapped script with the kept headers (`Content-Type`, the fixture's `Cache-Control: no-cache`), resolved `importScripts("/sw-main.js", "/sw-imported.js")` and the static `import "./sw-main.js"` against the script's original URL, and accepted the cross-origin static import from `chrome-extension://` in a module service worker. Every first registration left only `__rec:<marker>:fixture-sw` in IndexedDB and only `__rec:<marker>:fixture-sw` and `__rec:<marker>:fixture-shell-v1` in Cache Storage.
- **Route B marks Cache Storage**, which Route A could not reach in E2. Inferred: the wrapper is part of the script, so it runs after Chrome completes the worker's global (E2 found `caches` undefined at the start pause), and before the script's own first statement.
- **A fulfilled worker cannot reach a loopback API: the first effect never reaches the ledger.** In every `first` sample the page reported `TypeError: Failed to fetch` for the worker and no request reached the fixture's API, so the oracle's `noEffect` fails all 100. The address diagnostic shows why: every request of a fulfilled worker left with `initiatorIPAddressSpace: "Unknown"` and `requestPolicy: "BlockFromInsecureToMorePrivate"`; its requests to `api.localhost:4601` (`/me?from=…&__rec=<marker>` and the sync `/__marker`) failed with `net::ERR_FAILED` and `corsError: "InsecureLocalNetwork"`, while same-origin requests passed (`index.html`, `page.js`, `/__marker?name=sw:first-paint&__rec=<marker>`). With the script left alone, the same worker's requests left as `Loopback` under `PermissionBlock` and `/me` reached the API. So the first request carried the marker in 5 of 5 (the blocked URL shows `__rec=<marker>`), but Local Network Access blocked it. Inferred from Chromium's source: `CalculateIPAddressSpace` derives a worker's address space from its main script response's remote endpoint, which a response fulfilled through DevTools does not have, so the worker gets `kUnknown`; any fulfilled worker that calls a loopback or private API (the developer's `localhost` backend) hits this, whatever the fixture.
- **`importScripts` and static imports pause on the worker session only, and can be transformed.** All 60 imports in `imports` paused there, none on the tab. In `first` they were continued; `imports-transform` fulfilled all 15 too (`sw-imported.js` 183 to 17,016 bytes). Prepending the bootstrap again is redundant once the main script ran it, but possible.
- **`update()` escapes Route B and installs the unwrapped original.** After a first load, `registration.update()` paused nothing on the tab or on the running worker's session (attached with `waitingForDebugger: false`, `Fetch.enable` `ok`), in 20 of 20. Chrome reported `updatefound` with an installing version in 20 of 20, including the 10 with the same marker; the new version attached waiting, `Fetch.enable` on its session answered `ok`, it was released, and its script never paused there either: its `/me?from=%2Fsw-main.js%3Fvariant%3Dclassic` reached the fixture without the marker. Inferred: the update check fetches the script outside any session with `Fetch` enabled and compares the original bytes with the stored wrapped bytes, which always differ. The task's proxy (a changed wrapper standing in for a changed app script, since the fixture is frozen) is therefore not valid: the same wrapper already installs a new version, so byte comparison cannot tell a changed app from an unchanged one, and every update, including Chrome's own soft updates, replaces the wrapper with the unwrapped script.
- **An offline restart runs the persisted wrapper, with the marker of the first registration.** `Target.closeTarget` from the isolator answered `{ success: true }` and `getTargets()` listed no running worker afterwards in 10 of 10. With the fixture offline, the new tab showed `Fixture offline` (the worker's cached shell) in 10 of 10; the ledger recorded the dropped `/sw-main.js?variant=classic` requests (destination `serviceworker`; inferred to be Chrome's update checks) and `/index.html` as `network:dropped`; IndexedDB and Cache Storage held only the first load's prefixed names. No request reached the fixture: the restarted worker's `/me` failed with `net::ERR_FAILED` and `LocalNetworkAccessPermissionDenied` (run A: 2 failures with the URL, both carrying the first load's marker rather than the restart tab's, 7 without a URL, 1 sample with no failure event; run B: 10 without a URL); navigation preload failed with `net::ERR_EMPTY_RESPONSE` in 5. The stored script therefore bakes the marker of its registration; P1.5 tests selecting the namespace without baking it.
- **The restart's waiting target closes before release.** In 10 of 10 restarts a waiting target attached, and both `Network.enable` and the release on it failed with `{"code":-32000,"message":"Inspected target navigated or closed"}`; the worker then attached running (`waitingForDebugger: false`) twice under one target id. It also happened in an exploration run (`2026-11-03T07-52-11.021Z-79783525`) whose first load Route B left alone (`Inspected target navigated or closed`), and in its fulfilled samples as `{"code":-32001,"message":"Session with given id not found."}`, so it is not caused by the wrapper. Route B does not need the pause for an installed version, since the wrapper is in the stored script.
- **The fixture's push subscription is refused** (`NotAllowedError: Registration failed - permission denied`) in every load, as in E2; Background Sync registers.

## Not covered

`Service-Worker-Allowed` and `Content-Security-Policy` on the script response (the frozen fixture sends neither, so the kept headers are untested), a real change of the app's script bytes on update (the fixture is frozen, and the update path fails before that matters), any Local Network Access grant or other mitigation (an owner decision), dedicated and shared workers (P1.6), the namespace selection without baking it, MV3 background suspension, and Chrome restarts (P1.5), and Chrome on a desktop or outside Linux.
