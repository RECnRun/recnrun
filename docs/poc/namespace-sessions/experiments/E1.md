# E1: what chrome.debugger allows from inside the extension

Task P0.4 of [PLAN.md](../PLAN.md#p0-audit-harness-and-capability-map-source-14-deliverable-1). Spec: `tests/experiments/E1-debugger-capabilities.spec.ts`, run by `vp run test:experiments`. Result: Google Chrome 156.0.8078.79 on Linux in Docker, 2026-11-02, three samples per probe, every sample identical. The table of record is [CAPABILITIES.md](../CAPABILITIES.md), generated from [capabilities.json](../capabilities.json). Nothing here is validated on macOS or Windows yet.

## Why it is an experiment

The route of P1 to P6 depends on which Chrome DevTools Protocol commands an extension may send through `chrome.debugger`, on which targets, and with what errors. Chrome restricts extension clients ("untrusted clients") more than a DevTools frontend, and the documentation does not list the restrictions per command, so each one is a probe with a verdict.

## How the probes run

The isolator owns every `chrome.debugger` call. `apps/isolator/src/background/probes/` defines 29 probes and exposes them on the service worker's global `recnrunProbes` (`ids`, `descriptions`, `run(urls)`, `holdTab`, `releaseTab`, `tabHeight`). The spec only drives pages and reads results: it opens the fixture's `sw.html?sw=classic` (registers the classic service worker) and `workers.html?type=classic` (starts a dedicated and a shared worker), waits until the fixture ledger shows the first authenticated request of each worker script, and calls `recnrunProbes.run()` through the fixture's `Runtime.evaluate` on the extension worker. It sends no other CDP command, except `Target.getTargets` on the browser session for the infobar check, and never evaluates in the fixture's pages (the P0.7 allowlist forbids both).

The isolator manifest asks for `storage`, `management`, and `debugger`, with no host permissions; every probe below ran with that set. A probe is `allowed` when the call answered or the hypothesis held, `rejected` with Chrome's exact error otherwise, and `unavailable` when a precondition (a target, a session) was missing. Cookie values are never recorded, only counts.

## Outcomes

| Group                  | Allowed                                                                                                                                                                                                                                                                  | Rejected, with the exact error                                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getTargets()`         | lists the service worker and the shared worker as `worker`, the dedicated worker as `other`                                                                                                                                                                              |                                                                                                                                                                                                                      |
| `attach({ targetId })` | service worker, shared worker, dedicated worker                                                                                                                                                                                                                          |                                                                                                                                                                                                                      |
| Auto-attach on a tab   | `attach({ tabId })`; `Target.setAutoAttach({ autoAttach, waitForDebuggerOnStart, flatten })` reports the dedicated worker (`worker`), the running service worker (`service_worker`), and a cross-site iframe (`iframe`); `Runtime.runIfWaitingForDebugger` releases them | the shared worker: no `Target.attachedToTarget` in any sample                                                                                                                                                        |
| Tab session            | `Fetch.enable` with worker-script patterns, `Storage.getCookies`, `Network.setCookie`, `Network.enable`, `Page.addScriptToEvaluateOnNewDocument`                                                                                                                         | `Target.getTargets` and `Target.attachToTarget`: `{"code":-32000,"message":"Not allowed"}`; `ServiceWorker.enable`: `{"code":-32601,"message":"'ServiceWorker.enable' wasn't found"}`                                |
| Worker sessions        | service worker: `Runtime.evaluate`, `Fetch.enable`, `Debugger.pause` (the `Debugger.paused` event arrives), `Target.closeTarget` (the worker leaves `getTargets`)                                                                                                        | `ServiceWorker.enable` on the service worker: the same `-32601`; `Runtime.terminateExecution` on the dedicated worker: `{"code":-32000,"message":"Runtime.terminateExecution is not allowed for untrusted clients"}` |
| Infobar                | no change of the tab's height and no new `chrome://` target while the tab is attached                                                                                                                                                                                    |                                                                                                                                                                                                                      |

Observations that shape P1 and later phases:

- **Type strings differ by API.** `chrome.debugger.getTargets()` reports both the service worker and the shared worker as `worker` and the dedicated worker as `other`; `Target.attachedToTarget` reports `service_worker`, `worker`, and `iframe`. Code must match by URL and by the API it asked.
- **Auto-attach covers what a tab owns, not shared workers.** The dedicated worker attaches both when it already runs (`waitingForDebugger: false`) and after a reload (`waitingForDebugger: true`). The iframe attaches waiting, with an empty URL until released, so it is matched by type. The service worker attaches only once, already running and not waiting; a shared worker needs `attach({ targetId })` from `getTargets()`.
- **A tab session cannot reach other targets.** `Target.getTargets` and `Target.attachToTarget` are refused there; browser-wide discovery is `chrome.debugger.getTargets()` only.
- **There is no ServiceWorker domain for extensions.** `ServiceWorker.enable` is unknown (`-32601`) on both the tab and the service worker session, so registration, update, and stop events must come from elsewhere (auto-attach, `Fetch`, the page).
- **`Fetch.enable` works on the tab and on the service worker session.** P1.1 can test interception of the worker's main script from either.
- **Stopping a worker means closing its target.** `Runtime.terminateExecution` is refused for untrusted clients; `Target.closeTarget` on the service worker's own session succeeds and the worker leaves `getTargets()` until the next navigation starts it again.
- **`chrome.debugger.onDetach` stays silent on explicit detach and `closeTarget`.** Cleanup detached three sessions with `ok` and saw no `onDetach` event, so a detach the extension did not request is the only one it hears.
- **The infobar stays hidden with `--silent-debugger-extension-api`.** The isolator reads the tab's height with `chrome.tabs.get` (no `tabs` permission needed) before any attach and while it holds the tab: 1333 px both times, and no new `chrome://` target (only the always-present omnibox popup). A control run in a scratch copy without the flag (`tests/browser/fixtures/chrome.ts`) gave `rejected` in 3 of 3 samples with `tab height 1333 -> 1277`, so the check sees a 56 px infobar. The baseline is taken once, because a shown infobar outlives the detach that follows. What a person sees on a desktop is [MANUAL_VALIDATION.md](../MANUAL_VALIDATION.md) M-P0.a.
