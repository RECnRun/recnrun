# E7: Route C reaches pages and frames, and refuses workers

Task P1.6 of [PLAN.md](../PLAN.md#p1-minimal-service-worker-proof-source-5-14-deliverable-2). Spec: `tests/experiments/E7-route-c-pages-workers.spec.ts`, run by `vp run test:experiments`. Result: Google Chrome 156.0.8078.79 on Linux in Docker, load method `cdp-load-unpacked`, 2026-11-03, two runs: A `2026-11-03T07-52-10.527Z-35435d5b` (E7 alone, 4.4 min) and B `2026-11-03T07-59-15.543Z-d4158286` (the whole experiments layer, E7 in 4.5 min). Both ran 40 page loads, 60 worker loads, 20 IdP loads, and 9 two-tab pairs, and every count below is the same in both; run A predates two renamed reason texts (`noReport` was `notStarted`, "did not start: …", and `storeMissing` named the slot instead of "the load's marker"). The plan asks for a generated report; this one is written by hand from those runs' `verdicts.json` and `samples.json`. Nothing here is validated on macOS or Windows yet.

## Hypotheses and verdicts

The hypothesis of P1.6: a `chrome.scripting.registerContentScripts` registration at `document_start` in the MAIN world runs before the first script of every window it matches, frames included, and the wrapped `Worker` and `SharedWorker` constructors either start the worker with the bootstrap first while its `self.location`, `baseURI`, relative imports, and `name` stay correct, or throw (fail closed). A sample passes only when the realm's start marker (each fixture page's first statement, `/__marker?name=<page>:start`) carries the load's marker, every later request of the realm carries it, IndexedDB and Cache Storage hold the realm's store only as `__rec:<marker>:<name>`, and, for a worker, `self.location` is its own script. A refused worker counts as `failClosed`, apart from `unpatched` (a worker that ran without the marker), so a realm that fails closed is told apart from one that leaks.

Every variant of both worker realms fails on its own reason alone: `fail-closed/*` only `failClosed`, `blob/*` only `locationChanged`, and `data/*` only `noReport` plus `storeMissing` for both stores. `firstEffectBeforeMarker`, `unmarkedEffect`, `staleMarker`, `noEffect`, `workerError`, `unprefixedIndexedDB`, `unprefixedCacheStorage`, `storeUnreadable`, and `openerMessageMissing` are 0 in every realm and both runs. The plan accepts a worker realm "recorded `fail-closed` with the thrown error"; the default strategy does exactly that in 20 of 20 loads per realm, and the two opt-in wrappers show why it is the default.

`capabilities.json` gets `routeC`: the registration as `chrome.scripting.getRegisteredContentScripts()` returns it (`{"allFrames":true,"id":"recnrun-route-c","js":["ns/slot-0.js","route-c.js"],"matchOriginAsFallback":true,"matches":["http://app.localhost:4600/*","http://app.localhost:4603/*"],"persistAcrossSessions":false,"runAt":"document_start","world":"MAIN"}`), `firstScript` (`before` 40 of `samples` 40), every realm's verdict, and each wrapper variant's verdict.

## How it runs

The isolator owns every `chrome.scripting` call. `apps/isolator/src/background/route-c/` exposes `recnrunRouteC` on its service worker (`install`, `setMarker`, `uninstall`, `registered`). `install({ marker, matches, workers })` registers one content script (above) whose files are a slot file (`public/ns/slot-<k>.js`, one line that sets `globalThis.__recnrunMarker = "slot-<k>"`), the worker strategy file when the strategy is `blob` or `data` (`public/ns/workers-<strategy>.js`), and `route-c.js`. The page bootstrap (`apps/isolator/src/content/route-c/start.ts`) installs the marker with `installMarker` from `packages/isolation-core`, so the window's `fetch`, IndexedDB, and Cache Storage carry it, and replaces `Worker` and `SharedWorker`. `fail-closed` throws `SecurityError` from the constructor; `blob` and `data` build a wrapper (`importScripts(<slot>, <strategy>, route-c.js)` then `importScripts(<original>)` for a classic worker, the same as static `import`s for a module) and pass the original options, `name` included, to the native constructor. Chrome reads a registration's files when a frame starts, so a marker per load is a slot: `setMarker()` calls `updateContentScripts` to name the next of ten prebuilt slot files.

The spec only drives pages and reads results. Each load takes a new slot, opens a new tab, loads its page, and waits for the page's report and its `first-paint` ledger entry; it then lists the app origin's IndexedDB databases, caches, and Web Storage keys through the tab's CDP session, reads the ledger since its checkpoint, has Route A's `clearOrigin` reset the origin, closes the tab, and waits until `Target.getTargets` lists no shared worker of the app (native, `blob:`, or `data:`). Pages are `/` and `/storage.html` (20 loads each, `fail-closed`). Worker loads open `workers.html?type=<classic|module>` 10 times per strategy and type; each fixture worker sends its `location.pathname + search` as `from`, so an API request belongs to the realm whose script its `from` contains (a native location, or a `data:` wrapper's source), and requests whose `from` names no fixture script (a `blob:` location) go in construction order to the realms that were not refused. The IdP loads open `/`, then click the silent-renew button (a cross-site iframe on `idp.localhost:4602`) or the login popup (filled and submitted), 5 times per registration: `app-only` expects the IdP realm unmarked, `with-idp` marked. An identity pair opens `workers.html?type=classic` in two tabs at once under one slot and counts the shared-worker targets. The pure evaluation lives in `tests/experiments/e7-samples.ts` and `tests/experiments/e7-summary.ts`, tested by `tests/e7-samples.test.ts` and `tests/e7-summary.test.ts`; `tests/experiments/page-loads.ts` holds the load helpers E2 and E7 share. `samples.json` keeps every sample, its outcome, the page's report, and each identity pair's worker URLs.

## Observations

- **Route C runs before the first script of every window it matches.** In 40 of 40 page loads the start marker, the first statement of `index.js` and `storage.js`, carried the slot's `__rec=slot-<k>`, as did every later request; `/storage.html` opened `fixture-page` only as `__rec:slot-<k>:fixture-page` in IndexedDB and Cache Storage. Unlike Route A in E2, the bootstrap therefore found `caches` to wrap; inferred: a MAIN-world `document_start` script runs once the window's global is complete.
- **A slot switch takes effect on the next navigation.** `staleMarker` was 0 over the 120 sampled loads: after each `updateContentScripts` resolved, the next document ran the new slot file, with no other wait before the navigation.
- **Frames and popups follow the registration's `matches`, not the top-level page.** The IdP's silent-renew iframe is cross-site (out of process under Chrome's default site isolation, not checked per frame); registered for the app only, its start and `/renew` request were plain in 5 of 5, and registered with `http://idp.localhost:4602/*` both carried the marker in 5 of 5. The login popup did the same, including its second document after the cross-origin redirect through the API (`idp-popup-done:start` marked 5 of 5 with the IdP registered). The app page got the frame's `fixture-renew` and the popup's `fixture-login` messages in 20 of 20, so the bootstrap did not break `postMessage` to the parent or through `window.opener`. Route C therefore marks any origin a session reaches only if the registration names it in advance.
- **Failing closed is observable and leaves nothing behind.** Every `fail-closed` constructor threw `SecurityError` with the message above; the page reported it, the realm made no request, and no store was created (`unpatched` 0 of 40).
- **A `blob:` wrapper bootstraps first but moves the worker.** All 40 `blob` workers marked every request and opened only prefixed stores, and all 40 reported `self.location` as a `blob:http://app.localhost:4600/<uuid>` URL (the fixture's `from` is `http://app.localhost:4600/<uuid>`). The fixture uses absolute URLs, so nothing broke here, but a worker that resolves a relative URL against its location would. Inferred: in Node, `new URL("./helper.js", "blob:http://app.localhost:4600/0b6f")` and the same against a `data:` base throw `TypeError: Invalid URL`, so a classic worker's relative `importScripts` and `fetch` fail under either wrapper; a module's own static imports resolve against the module's URL and stay correct. `baseURI` was not measured apart from `self.location`. `name` reaches the native constructor unchanged (`apps/isolator/tests/route-c-page.test.ts`), not measured in Chrome.
- **A `blob:` wrapper splits a shared worker.** Two tabs of one session constructing `/shared-worker.js?type=classic` ran one instance with native constructors (3 of 3 pairs) and two under `blob` (3 of 3, two distinct `blob:http://app.localhost:4600/<uuid>` URLs): each page mints its own wrapper URL, and a shared worker's identity is its constructor URL plus `name`. A page-side cache of wrapper URLs cannot cross tabs, so same-session tabs stop sharing state.
- **A `data:` wrapper runs the worker in an opaque origin.** All 40 `data` workers ran the bootstrap first (their `/me` request carried `__rec=slot-<k>`, so the `chrome-extension://` imports loaded), and every `data` request in the saved ledger had `Origin: null`; `self.location` is the wrapper's `data:` URL, extension id included. No `fixture-dedicated` or `fixture-shared` store appeared on the app origin. The page got an `error` event from each dedicated worker ("worker failed to start") and no report from any shared worker within 10 s. Inferred, not verified: a store opened from the opaque origin threw, and a shared worker's runtime error does not reach the page. The `data:` URL is the same for every tab of a slot, and the shared-worker pairs ran one instance (3 of 3), but in an origin that has no app storage.
- **Web Storage carries no prefix in P1, by design.** `localStorage` held `fixture:user` in 39 of 40 page loads and every worker load, and `sessionStorage` in the 20 `/storage.html` loads. `/storage.html` writes both; `clearOrigin` clears `service_workers,indexeddb,cache_storage` only, so the `localStorage` key outlives the load. These are notes, not failures; P2.2 namespaces Web Storage.
- **The physical database name leaks,** as in E2: a `blob` worker reports `IDBDatabase.name` as `__rec:slot-<k>:fixture-dedicated`.
- **The wrapper exposes the extension.** The `data:` location names `chrome-extension://<id>/ns/slot-<k>.js` and `route-c.js`, and the manifest makes `route-c.js` and `ns/*.js` web-accessible to the app origins so the wrappers can import them; a page can therefore tell the isolator is installed and which slot it runs under (inferred from the manifest and the observed `data:` URL, not probed from a page).

## Not covered

Same-origin iframes, `about:blank` and `srcdoc` children (and so `matchOriginAsFallback`, registered but never exercised), and sandboxed frames: the frozen fixture has none, and the plan forbids editing it. Nested workers, a worker that uses relative URLs, `baseURI` and `name` in Chrome, a page that navigates while a slot switch is in flight, service workers (Route C cannot reach them; E2 and E5 cover Routes A and B), and Chrome on a desktop or outside Linux.
