# E0: load the unpacked extension into Google Chrome Stable

Task P0.3 of [PLAN.md](../PLAN.md#p0-audit-harness-and-capability-map-source-14-deliverable-1). Spec: `tests/experiments/E0-load-extension.spec.ts`, run by `vp run test:experiments`. Result: Google Chrome 156.0.8078.79 on Linux (arm64) in Docker, 2026-11-02. Nothing here is validated on macOS or Windows yet; that is [MANUAL_VALIDATION.md](../MANUAL_VALIDATION.md) M-P0.a and M-P0.b.

## Why it is an experiment

Chrome 137 removed `--load-extension` from branded builds, and Playwright's documentation sends extension tests to Chromium. The POC must run on Google Chrome Stable (decision 3) without flags beyond decision 5, so loading the isolator is itself a hypothesis with a verdict.

## Hypotheses and outcomes

Each hypothesis loads `apps/isolator/.output/chrome-mv3-test` and passes only when the extension's own service worker answers: `chrome.management.getSelf().id` equals the expected id and the `chrome.storage.session` marker the isolator writes on install reads `{ loaded: true, id }`. Both are evaluated in the worker found with `Target.getTargets` (type `service_worker`, URL `chrome-extension://<id>/`).

| Hypothesis  | Variant                                                                                             | Verdict            | Exact outcome                                                   |
| ----------- | --------------------------------------------------------------------------------------------------- | ------------------ | --------------------------------------------------------------- |
| (a)         | `--enable-unsafe-extension-debugging`, `Extensions.loadUnpacked` on the `--remote-debugging-port`   | pass               | returns `{ id }`; `installType: "development"`                  |
| (a)         | the same over `--remote-debugging-pipe`, launched with `--remote-debugging-port=0` too              | pass               | the pipe answers; `DevToolsActivePort` is still written         |
| (a) control | `Extensions.loadUnpacked` on the port **without** `--enable-unsafe-extension-debugging`             | pass (`control`)   | Chrome 156 does not require the flag on this transport          |
| (b)         | `ExtensionSettings` `force_installed`, loopback `update_url`, harness-packed CRX3, default policies | fail               | installs and runs, but `Target.attachToTarget: Not allowed`     |
| (b)         | the same plus `DeveloperToolsAvailability: 1`                                                       | pass               | `installType: "admin"`; worker listed about 100 ms after launch |
| (c)         | Playwright's bundled browser with `--load-extension`                                                | pass, `diagnostic` | `Google Chrome for Testing 156.0.8078.4`, not Chrome Stable     |

Ten repetitions (`vp run test:experiments -- --repeat-each=10`, run before the control was added) gave the same verdict for every variant of (a), (b), and (c), 10 of 10. The control ran in single samples (the spec and two standalone probes), all passing.

Observations that shaped the harness:

- **Chrome's documentation says `Extensions.loadUnpacked` needs `--remote-debugging-pipe`.** On Chrome 156 it is accepted over the port, with or without `--enable-unsafe-extension-debugging`. The loader still passes the flag, since Chrome documents it as the requirement and may enforce it again; dropping it would remove one flag from decision 5's list and is the owner's call.
- **Pipe and port coexist.** Launching with both `--remote-debugging-pipe` and `--remote-debugging-port=0` serves CDP on both, so Playwright can still `connectOverCDP` after a pipe-only command. `launchChrome({ pipe: true })` implements that (stdio fds 3 and 4, NUL-terminated JSON).
- **A worker can be attached before its `chrome` bindings exist.** In the first full run, the port variant of (a) and the `DeveloperToolsAvailability: 1` variant of (b) failed with `ReferenceError: chrome is not defined` when evaluated right after the worker target appeared; the loader now retries the first `getSelf` until the worker answers (15 s budget), and stops at once on an attach refusal.
- **Policy-installed extensions refuse DevTools by default.** `DeveloperToolsAvailability` defaults to "disallow on force-installed extensions", which also blocks CDP attachment to their worker. Chrome accepted an `http://127.0.0.1` update URL and an off-store CRX3 on Linux with no other policy. The update check carried `installsource=notfromwebstore&installedby=policy`.
- **Unavailable cases.** Method (b) writes `/etc/opt/chrome/policies/managed/recnrun.json`, so it needs Linux and root; elsewhere it records `unavailable` with the reason (not exercised: every run so far was in Docker as root).

## How the loader works

`tests/browser/fixtures/extension.ts` exports the `extension` fixture and `loadExtension()`. It tries, in order:

1. `cdp-load-unpacked`: `launchChrome({ args: ["--enable-unsafe-extension-debugging"] })`, then `Extensions.loadUnpacked({ path })` on the browser CDP session. This is what every run uses today.
2. `managed-policy`: packs a CRX3 with a fresh RSA key (`tests/browser/fixtures/crx3.ts`: hand-written protobuf header, stored ZIP, id from the key's SHA-256), serves `updates.xml` and the CRX from a loopback server, writes the policy file with `DeveloperToolsAvailability: 1`, launches Chrome, and removes the policy file when the extension closes.
3. `chromium-load-extension`: Playwright's browser with `--load-extension`, labelled `diagnostic`.

A method counts only when the worker answers `management.getSelf()` with the expected id. When none does, the fixture fails with "Google Chrome <version> accepted no extension-loading method; see docs/poc/namespace-sessions/experiments/E0.md and MANUAL_VALIDATION.md M-P0.a", followed by each method's error. `tests/browser/extension.spec.ts` covers both paths.

## Evidence

Each run writes `.artifacts/evidence/<run>/verdicts.json` (one entry per hypothesis, with its variants) and merges `capabilities.json`, which now holds `{ "chrome": { "version": "Google Chrome 156.0.8078.79" }, "extensionLoad": { "method": "cdp-load-unpacked" } }`. Docker runs export both to `.artifacts/docker/<run-id>/evidence/<run-id>/`.
