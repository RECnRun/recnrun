# E2: Route A bootstraps workers before their first statement

Task P1.1 of [PLAN.md](../PLAN.md#p1-minimal-service-worker-proof-source-5-14-deliverable-2). Spec: `tests/experiments/E2-route-a-register.spec.ts`, run by `vp run test:experiments`. Result: Google Chrome 156.0.8078.79 on Linux in Docker, load method `cdp-load-unpacked`, 2026-11-02, three runs of the same code, 140 armed page loads each: A `2026-11-02T21-07-38.129Z-3ec346fc` (E2 alone, 14.9 s), B `2026-11-02T21-12-16.403Z-3cda1144` (the whole experiments layer), and C `2026-11-02T21-14-21.179Z-11a25df3` (E2 alone, 20.7 s). The plan asks for a generated report; this one is written by hand from those runs' `verdicts.json` and `samples.json`. Nothing here is validated on macOS or Windows yet.

## Hypotheses and verdicts

The hypothesis of P1.1: with `attach({ tabId })` and `Target.setAutoAttach({ autoAttach, waitForDebuggerOnStart, flatten })` installed before the page calls `register()`, each worker target attaches paused, `Runtime.evaluate` of the bootstrap runs, and `Runtime.runIfWaitingForDebugger` releases it, so the worker's first statement already carries the marker. A sample passes only when the worker attached waiting, the bootstrap answered with this load's marker, the worker was released, every request it made carries `__rec=<marker>`, and IndexedDB and Cache Storage hold its store only as `__rec:<marker>:<name>`.

## How it runs

The isolator owns every `chrome.debugger` call. `apps/isolator/src/background/route-a/` exposes `recnrunRouteA` on its service worker (`setMarker`, `arm`, `journal`, `disarm`, `attachTarget`, `clearOrigin`, `tabs`). On each `Target.attachedToTarget` from the armed tab it sends `Runtime.evaluate` of `withMarker(marker)` (`packages/worker-bootstrap`), `Target.setAutoAttach` on the worker's own session, and `Runtime.runIfWaitingForDebugger`, in that order, and awaits the bootstrap's reply last; the journal records the target, whether it waited, the time from the event to the reply (`bootstrapMs`), what the bootstrap answered, and Chrome's exact errors.

The spec only drives pages and reads results. Each load opens a new tab, gives the isolator a marker unique to the load, arms the tab, opens `sw.html?sw=<variant>` or `workers.html?type=<classic|module>`, and waits for the page's report and its `first-paint` ledger entry. It then disarms the tab (which returns the journal), lists the app origin's IndexedDB databases and caches through the tab's own CDP session, reads the ledger since its checkpoint, has the isolator clear the origin's service workers and storage (`Storage.clearDataForOrigin`), closes the tab, and waits until `Target.getTargets` lists no shared worker on the app origin. The fixture's workers open a request, a database, and a cache as their first statements (PLAN.md P0.6), so the ledger and the physical store names show whether the bootstrap came first; a log line from the worker is not evidence. The service-worker requests are every API request of the load; a worker's are the requests whose `from` is its script. The pure evaluation lives in `tests/experiments/e2-samples.ts`, tested by `tests/e2-samples.test.ts`; `samples.json` in the run's evidence keeps every sample, its outcome, the page report, and the journal's unattached targets.

## Observations

- **The service worker attaches paused when the tab is armed before `register()`.** All 300 service workers, in every variant, attached as `service_worker` with `waitingForDebugger: true`, answered the bootstrap with the load's marker, and were released. E1 saw the service worker only when it already ran, not waiting.
- **Requests and IndexedDB usually carry the marker from the first statement.** In 296 of 300 service-worker samples every request was marked (the first `/me?from=<script>`, the `importScripts` worker's `/me?from=sw-imported`, and the Background Sync marker) and the only database was `__rec:<marker>:fixture-sw`. All 30 dedicated workers did the same (`__rec:<marker>:fixture-dedicated`).
- **Cache Storage does not.** Every dedicated worker left `fixture-dedicated` without the prefix, and every service worker but one left `fixture-sw`. In a scratch run that evaluated `typeof` probes next to the bootstrap, `caches` and `CacheStorage` were `"undefined"` at the pause in both service and dedicated workers while `fetch`, `indexedDB`, and `navigator.storage` existed, so `patchCaches` found nothing to wrap and skipped without a word; the bootstrap's answer does not say which patches it installed. Inferred from Chromium's source: `WorkerOrWorkletScriptController::PrepareForEvaluation()` installs a worker's conditional features (`isolate_->InstallConditionalFeatures`), and for workers it is called from `WorkerGlobalScope::Initialize()`, after the release; `caches` is declared `[SecureContext]` (`third_party/blink/renderer/modules/cache_storage/window_or_worker_global_scope_cache_storage.idl`), so it appears only then. Evaluating at the pause on start therefore cannot reach `caches`. A later pause, after the global is complete and before the first script runs (for example `Debugger.setInstrumentationBreakpoint` with `beforeScriptExecution` on the worker's session), is a different hypothesis that E2 did not test.
- **A paused service worker runs the bootstrap only once released, and not in a fixed order with its script.** In the scratch run a dedicated worker answered the bootstrap within 1 to 2 ms while paused; a service worker answered only after the reply to `Runtime.runIfWaitingForDebugger`. Where the queued evaluation then lands varies: in 295 of 300 samples before `caches` existed; in 1 (run B, `dynamic`) after `caches` existed and before the first statement, so every store carried the prefix and the sample passed; and in 4 (runs B and C, `imports` twice and `classic` twice) after the top-level script, so the first request and `fixture-sw` were plain while the Background Sync marker and the install handler's `fixture-shell-v1` cache carried the marker. Dedicated workers, which take the evaluation while paused, never lost the order (30 of 30). The first full run, with the engine awaiting the reply before the release, stalled every service worker 5 s and journaled `bootstrap failed: Runtime.evaluate: no reply within 5000 ms` although the bootstrap then ran (all 100 marked their requests and database); the engine now releases without waiting for the reply ("Release a paused worker without waiting for its bootstrap reply"), so a service worker's `bootstrapMs` includes the release. Whether the stall changed the odds of a late bootstrap is untested.
- **Auto-attach never reports the shared worker,** as in E1: 30 of 30 had no `Target.attachedToTarget`, made their first request without the marker, and opened `fixture-shared` and its cache under the plain name. `chrome.debugger.getTargets()` lists it (the journal's `unattached`); P1.2 and P1.6 test the direct attach.
- **Reused pages skew the samples.** The first full run navigated one tab to `about:blank` between loads. The shared workers of the first classic and module loads stayed alive through every later load, so 8 of 10 shared samples made no request and opened no store, and 8 of 10 dedicated workers attached with `waitingForDebugger: false` (their requests and databases were still marked). With a new tab per load, closed afterwards, and the wait for shared workers to end, every dedicated worker attached waiting and every shared worker started anew. Inferred, not verified: the back/forward cache kept the earlier page and its shared-worker connection, and the reused renderer started the dedicated worker before the pause applied.
- **Stale service-worker targets stay listed.** `chrome.debugger.getTargets()` keeps the targets of earlier service-worker versions after `Storage.clearDataForOrigin` and after their tab closes, so `unattached` grows with every load (2,000 `sw-main.js` rows over the 100 service-worker samples of run A); in a scratch run `Target.getTargets` still listed a service worker 15 s after its tab closed. A listed service-worker target is not evidence of a running worker.
- **The physical database name leaks.** The fixture reports `IDBDatabase.name` as `__rec:<marker>:fixture-sw`: P1 marks names without namespacing them, and P2.3 must return the logical name.
- **`import()` fails in a service worker.** The `dynamic` variant reports `TypeError` (`/__marker?name=sw:dynamic-import:TypeError`, 20 of 20 per run), as Chrome forbids `import()` there; its first-statement request is still the first effect the oracle checks.

## Not covered

Nested workers (the fixture has none; the engine's auto-attach on each worker session is covered only by `apps/isolator/tests/route-a.test.ts`), update, cold start, offline, and wake paths (P1.2, P6.2), any later pause point for Cache Storage, more runs to bound the rate of late service-worker bootstraps (P1.2's stress run measures the race), and Chrome on a desktop or outside Linux.
