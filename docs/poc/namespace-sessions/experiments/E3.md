# E3: Route A reaches workers cold, racing, and already running

Task P1.2 of [PLAN.md](../PLAN.md#p1-minimal-service-worker-proof-source-5-14-deliverable-2). Spec: `tests/experiments/E3-route-a-cold.spec.ts`, every test tagged `@order-critical`, run by `vp run test:experiments` and `vp run test:stress`. Result: Google Chrome 156.0.8078.79 on Linux in Docker, load method `cdp-load-unpacked`, 2026-11-03, three runs of the same code: A `2026-11-03T08-49-28.160Z-0808245f` (E3 alone, 2.9 min), B `2026-11-03T08-52-46.961Z-d14ad428` (the whole experiments layer, 3.9 min), and C `2026-11-03T08-57-01.623Z-2c552650` (E3 alone, 2.7 min); plus stress runs of 3 and 7 iterations. ## How it runs

The isolator owns every `chrome.debugger` call; `recnrunRouteA` (`apps/isolator/src/background/route-a/`) gained three calls for E3:

- `arm({ tabId, pauseBeforeScript: true })`: on each worker the tab's auto-attach reports waiting, it sends `Debugger.enable` and `Debugger.setInstrumentationBreakpoint({ instrumentation: "beforeScriptExecution" })`, releases the worker with `Runtime.runIfWaitingForDebugger`, and at the first `Debugger.paused` evaluates the bootstrap, removes the breakpoint, and resumes. The journal records each step's result, `typeof caches` at the pause, and later pauses.
- `watch({ origin, marker })` and `unwatch()`: polls `getTargets()` every 10 ms and attaches each new worker target of the origin by id (`attach({ targetId })`), then evaluates the bootstrap; a direct attach never pauses the worker. Targets listed when the watch starts form a baseline it never attaches (`staleSkipped`), because Chrome keeps the targets of earlier workers listed.
- `closeTarget({ targetId })`: attaches the target by id and sends `Target.closeTarget` on its own session.

The spec only drives pages and reads results:

- `before-script-execution` and `direct-attach-race` load each service-worker variant (`sw.html?sw=classic|module|imports|static|dynamic`) 20 times and `workers.html?type=classic|module` 10 times, each in a new tab with a marker unique to the load, as E2 does; the first arms the tab with `pauseBeforeScript`, the second watches the origin.
- `cold-start-navigation` registers each variant once without Route A, then 20 times per mode stops the origin's service workers through `closeTarget`, waits until `getTargets()` no longer lists them, and loads the page again in a new tab, armed (`pause`) or watched (`watch`): the navigation restarts the worker.
- `pre-existing-running` registers a variant without Route A and, while its page keeps the worker running, either arms the tab (`armed`) or attaches the worker by id (`direct`). The isolator is loaded when Chrome starts, so "running before the extension was enabled" is approximated as "running before Route A attached".
- `wake-without-tab` registers the classic worker (its page asks for Background Sync `fixture-sync`), closes the tab, stops the worker, watches the origin, then cuts and restores the fixture's network (`/__network?mode=offline`, then `online`) and waits 10 s for a request from the worker.

Each sample keeps the ledger since the load's checkpoint, the journal, and the origin's IndexedDB and Cache Storage names read through the tab's own CDP session. A service worker's effects are the API origin's requests minus another worker's top-level request and the harness's own `/__network` and `/__expire` control calls; a dedicated worker's are the requests whose `from` names its script. The pure evaluation lives in `tests/experiments/e3-samples.ts`, tested by `tests/e3-samples.test.ts`; `tests/experiments/route-a-harness.ts` holds what E2 and E3 share. `samples.json` per hypothesis keeps every sample, its outcome, and what the load saw.

Every verdict carries `condition` (`RECNRUN_STRESS_CONDITION`, `baseline` outside a stress run) and `lateAttaches`. Under `vp run test:stress` (`RECNRUN_STRESS_ITERATION` set) one iteration loads each variant once: 7 fresh samples per hypothesis, 10 cold, 2 running, and 1 wake, 25 to 49 s per iteration in the final stress run, so 100 iterations take about 60 to 80 minutes. The conditions act as follows: `net-delay` makes a 300 ms API request before each load (it slows the preparation only, not the worker's script or its requests: the frozen fixture offers no delayed script or API route, so no condition slows those), `cpu-load` runs busy threads, `cold` stops the origin's service workers before each load, `warm` keeps the origin between fresh loads, and `switch-late` sets the load's marker after arming instead of before.

## Observations

- **A breakpoint before the script reaches every new worker.** All 360 samples of runs A to C attached waiting, set the instrumentation breakpoint (`ok` 120 times per run), paused once (`laterPauses` 0), saw `typeof caches` as `"object"` at the pause, and left every request, database, and cache marked; the same held in every stress iteration of the final run, `warm` and `switch-late` included. This answers E2's Cache Storage failure: at `beforeScriptExecution` the worker's global is complete, so `patchCaches` installs, while at the pause on start it is not. The cost is one pause of 15 to 18 ms (p50) per worker. In one preliminary run (before the final code), one `sw-classic` worker set the breakpoint with `ok` and never paused, so it ran unmarked; the pause flow has no fallback for that. It did not recur in the 360 final samples or the stress iterations.
- **Attaching by id after `getTargets()` lists a worker loses.** For service workers the bootstrap usually landed before the first statement (requests and IndexedDB marked in 99 of 100 per run) but before `caches` existed (`caches` patch `skipped` in 98 to 102 of 120 samples), so Cache Storage stayed plain; 1 of 300 passed and 1 per run lost the first request too. Dedicated workers made their first request and opened their database before the bootstrap in 17, 17, and 20 of 20; the others had the `caches` patch skipped. Inferred, not verified: the service workers were held at start by Playwright's own session (see below), and the isolator's evaluation, queued during that hold, ran at release before `WorkerGlobalScope::Initialize()` added `caches`, as E2 saw at the pause on start. Without Playwright attached, nothing would hold the worker, so the race would be no better.
- **A navigation-restarted worker is not held by the tab.** After `closeTarget`, the armed tab's auto-attach reported the restarted worker in 300 of 300 `pause` samples, always with `waitingForDebugger: false`, so neither the breakpoint nor the bootstrap came before the script. Watching the origin did better but not enough: 17, 11, and 12 of 100 passed; the first request was plain in 63, 49, and 84; the `caches` patch skipped in 20, 40, and 4. `sw-main.js?variant=classic` and `sw-imports.js` never passed; `sw-dynamic` passed most (10, 5, and 7 of 20), and in run C the classic, module, and imports variants lost the first request in 60 of 60. A cold start is the common case for a service worker, so Route A cannot rely on it.
- **`Target.closeTarget` stops a service worker reliably.** 209 of 209 closes in run C answered `ok` and the worker left `getTargets()` within 6.7 ms (p50), 40.8 ms at most; E1 had seen the same on 3 samples. Recorded as `debugger.worker-close-target-cold-start` in the run's `capabilities.json`, next to `debugger.worker-instrumentation-breakpoint` (`allowed`, 120 `ok`); `docs/poc/namespace-sessions/capabilities.json` is not yet regenerated from them.
- **A worker already running is reached late, by construction.** The armed tab reported it running (`waitingForDebugger: false`) and the direct attach found it running; its first request, its Background Sync marker, and its stores were plain in 10 of 10, and the bootstrap ran 75 to 92 ms (p50) into the worker's life. Route A has no way to mark what a worker did before the attach.
- **No wake without a tab could be produced.** The fixture's page registers `fixture-sync` while online, so the sync fires during registration (5 of 5) and nothing stays pending; the harness may not take Chrome offline, and `/__network?mode=offline` only makes the fixture drop its connections while Chrome stays online. Push needs a granted notification permission, which the harness may not grant. P6.2 and P6.3 need either a fixture page that registers sync while Chrome is offline or a permission the harness can grant.
- **An instrumented service worker marks the requests it forwards for its clients.** In the `warm` iteration of the second stress run, the service worker of an earlier load still controlled `workers.html`; its `cacheFirst` handler calls `fetch(request)`, which the bootstrap had patched, so the dedicated worker's script was fetched as `/worker.js?type=classic&__rec=<the service worker's marker>`. The worker's `location.search` then carried that marker, so its `/me?from=` named the marked URL and the evaluation, which compared `from` with the plain script, missed it. The evaluation now drops `__rec` from `from`. The URL change itself is visible to the page and its worker: P2 must keep a forwarded request's URL, or the response's `url`, as the client asked for it.
- **Playwright's own CDP session changes what Chrome does.** `connectOverCDP` sends a browser-level `Target.setAutoAttach` with `waitForDebuggerOnStart: true` (seen with `DEBUG=pw:protocol`), so every worker in these runs had a second DevTools client. Chromium's `ServiceWorkerVersion::Doom()` does not stop a doomed worker while DevTools is attached (it sets `stop_when_devtools_detached_`), so after `Storage.clearDataForOrigin` and closing its tab a service worker kept running and listed for 45 s and more; this explains E2's stale targets. E3 therefore stops workers itself with `closeTarget` instead of waiting. Separately, with trace snapshots on, Playwright's HAR tracer calls `Network.getResponseBody` for every response; on a service worker's navigation preload response (`requestId` `preload-<n>`) Chrome's connection closed and the run failed with the browser closed, in 3 runs. The spec turns snapshots off (`trace: { mode: "retain-on-failure", snapshots: false }`), after which no such call was made and every run passed. Route B (P1.4) reads response bodies through `Fetch`; whether a body request on a preload response hurts it is for E5 to check.
- **`import()` still fails in a service worker** (`/__marker?name=sw:dynamic-import:TypeError`), as in E2.

## Not covered

Shared workers (P1.6 tests the direct attach), nested workers, an extension enabled after the worker started (approximated above), a wake by Background Sync or push (unavailable here), the update path (`install`, `waiting`, `activate` with changed bytes, P6.2), any run without Playwright's CDP session attached, the 100-iteration stress run (gate P1), and Chrome on a desktop or outside Linux.
