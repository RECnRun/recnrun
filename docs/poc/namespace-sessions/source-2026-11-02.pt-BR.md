# POC RECnRun — sessões por namespace com service workers e aplicação intacta

Plano de implementação para Claude Code ou Codex · 2 de novembro de 2026

Revisão 2 — arquitetura obrigatoriamente 100% extensão Chrome MV3.

## 1. Missão e resultado esperado

Construir e executar um POC para responder com evidências: conseguimos trocar de usuário rapidamente, no mesmo perfil do Chrome e nas mesmas URLs, preservando autenticação e dados locais em namespaces permanentes, mantendo service workers funcionais e sem modificar a aplicação?

Implementar toda a solução de isolamento em uma única extensão Chrome MV3, incluindo coordenação, instrumentação, persistência, rede, descoberta e interface. CDP é permitido exclusivamente pelo transporte chrome.debugger da própria extensão e dentro das capacidades que ele realmente expõe. Não existe fallback para companion, native messaging host, servidor/processo local, cliente CDP externo, proxy ou navegador modificado. Se uma hipótese falhar, investigar outra técnica dentro da extensão. Se os requisitos não puderem ser satisfeitos, entregar a limitação reproduzível sem mudar a arquitetura nem prometer sucesso.

O objetivo é A → B → A → C → A, com uma única identidade executando por ambiente a cada instante. A sessão original, existente antes de ativar o RECnRun, é uma sessão gerenciada com namespace vazio. Suspender significa parar sua execução, não fazer logout nem apagar seus dados. Retomar recria os contextos e lê os mesmos dados persistentes; não restaura a memória JavaScript ou uma fotografia da tela. O retorno deve permitir consultar dados atualizados do servidor.

## 2. Requisitos inegociáveis

1. Não editar código-fonte, build, configuração, backend, autenticação ou service worker da aplicação alvo. Não exigir SDK, import, endpoint, header ou alteração de CSP por parte da aplicação.
2. Injeção de instrumentação no browser é permitida. Como rota experimental separada, pode-se transformar em trânsito a resposta de um script exclusivamente por mecanismos implementados e executados pela extensão, se disponíveis, sem alterar o artefato no servidor; declarar esse fato e medir seus efeitos. Essa rota não pode ser descrita como execução de bytes idênticos.
3. Sem dump/restore, staging, cópia ou migração de IndexedDB, Web Storage e Cache Storage a cada switch. Os dados permanecem em seus namespaces. Jars de cookies são armazenamento permanente, não staging.
4. Não desabilitar ou fazer bypass do service worker como solução final. Demonstrar fetch interception e funcionamento offline reais.
5. Não exigir lista manual de API, SSO ou domínios relacionados. O usuário escolhe o ambiente/aba e a identidade; a ferramenta descobre as dependências observáveis.
6. A sessão original não pode continuar ativa em outra aba enquanto B está ativo no mesmo ambiente. Abranger iframes, popups, PWAs e workers relacionados, inclusive clientes ocultos.
7. Uma nova execução/documento por troca. Não tentar mudar o namespace de handles vivos de IndexedDB, Cache ou memória da aplicação.
8. Não aceitar resposta tardia de A como resultado de B. Não repetir automaticamente POSTs ou operações com efeitos colaterais.
9. Não adotar perfis/BrowserContexts/subdomínios por usuário como solução deste POC: isso muda a estratégia avaliada. Podem servir como controle experimental, nunca como aprovação do requisito.
10. Chrome instalado e de marca é alvo de validação. Chromium e Chrome for Testing podem ajudar no diagnóstico, mas não bastam como evidência final.
11. Todo o runtime do produto fica na extensão: sem executável auxiliar, native messaging host, serviço HTTP/WebSocket local, remote debugging externo, proxy, CA instalada ou fork de navegador. O usuário instala a extensão e usa sua interface; não inicia um daemon ou CLI para o isolamento funcionar.
12. Ferramentas de build, servidores da aplicação-fixture e test runner externo são permitidos apenas no desenvolvimento/teste. Não podem executar nenhuma parte da instrumentação, coordenação, bloqueio ou recuperação exigida do produto. Confirmar o funcionamento manual após desligar o runner.

Nenhuma implementação poderá alegar isolamento contra código hostil ou isolamento nativo do navegador. O alvo é compatibilidade funcional para dev/tester; quotas, permissões e várias capacidades do perfil continuam compartilhadas.

## 4. Modelo de dados e invariantes

Separar ambiente lógico, origin de armazenamento e domínio de cookie. Origin inclui esquema, hostname e porta. Cookies não são separados por porta; Domain/path/SameSite/partição também importam.

```ts
type SessionId = string;
type Epoch = number;
type Phase = "inactive" | "quiescing" | "prepared" | "active" | "failed";

interface EnvironmentState {
  id: string;
  entryOrigin: string;
  activeSessionId: SessionId | null;
  epoch: Epoch;
  phase: Phase;
  discoveredOrigins: string[];
  conflictingEnvironments: string[];
}

interface ExecutionOwner {
  environmentId: string;
  sessionId: SessionId;
  epoch: Epoch;
  targetId?: string;
  documentId?: string;
  workerVersionId?: string;
}
```

O vínculo de cada contexto e requisição é imutável durante aquela execução. A sessão ativa é a autorização para iniciar trabalho novo; não é uma variável que decide retroativamente a quem pertence uma resposta.

Invariantes verificáveis:

- Nenhum código da aplicação executa num contexto gerenciado antes do bootstrap de isolamento.
- Apenas a geração ativa pode iniciar operações; gerações revogadas não escrevem nem enviam trabalho novo.
- Toda requisição identificável conserva seu dono até conclusão, erro ou cancelamento, inclusive redirects.
- Nenhum contexto da sessão original escapa ao controle após a ativação concluída.
- Nenhum clear/list/match/delete de uma sessão atravessa namespaces.
- Uma falha de instrumentação interrompe a ativação; não libera silenciosamente o contexto sem patches.
- Registro persistente de service worker e execução do worker são entidades diferentes. Parar execução não prova que ela não pode voltar.

Exemplo de mapeamento: app-db → app-db na sessão original; app-db → __rec:<env>:<session>:app-db em sessões novas. Usar IDs opacos, codificação sem colisões e prefixo reservado. Não incluir epoch no nome persistente: isso criaria bancos novos a cada retomada. Epoch pertence à execução.

## 5. Primeira prioridade: experimento mínimo de worker

Antes de construir dashboard ou abstrações amplas, demonstrar ou refutar a captura antes da primeira instrução do worker.

Criar uma aplicação-fixture independente, sem qualquer integração RECnRun. Ela usa APIs nativas normalmente e já na avaliação inicial do worker abre IndexedDB, Cache Storage e inicia uma requisição autenticada. O servidor registra o usuário efetivamente recebido. O fixture também registra marcadores de ordem para o teste, sem cooperar na seleção de sessão. Congelar e registrar hashes dos artefatos antes de ligar o isolador.

Testar worker clássico e módulo, importScripts, imports estáticos e dinâmicos, versões instaladas antes da extensão, install/activate/fetch, execução quente, parada natural, retomada e atualização. Um prefixo textual em módulo pode executar depois dos imports estáticos; não assumir que prepend resolve a ordem.

Evidências exigidas: trace CDP, ordem do bootstrap versus primeiro efeito observável da aplicação, banco/cache fisicamente aberto, cookie recebido pelo servidor e ausência de escrita no namespace original quando B deveria executar. Um console.log de “patch instalado” após o carregamento não serve.

### Rota A — somente extensão

Investigar chrome.debugger, Target.setAutoAttach, sessões filhas/flatten, Runtime/Debugger e captura de contextos. Verificar na versão real quais comandos e targets são permitidos. A lista pública de domínios de chrome.debugger não inclui ServiceWorker; não assumir acesso ao CDP completo ou ao browser target.

Experimentos separados: anexar à aba; anexar diretamente ao target do worker; autoattach antes de register; retomada do worker sem aba; worker existente ao ativar a extensão. Pausar antes do início quando suportado, instalar bootstrap, validar e só então liberar com o comando adequado. Tratar targets filhos recursivamente quando necessário.

Se houver corrida entre targetCreated e execução, medi-la e produzir caso mínimo. Polling ou attach tardio não satisfazem o contrato. Não concluir que uma execução bem-sucedida prova todos os caminhos de ativação.

### Rota B — instrumentação de scripts inteiramente pela extensão

Se A não cobrir o ciclo completo, investigar interceptação de respostas via Fetch através de chrome.debugger, redirecionamento permitido e wrappers/bootstrap administrados pela própria extensão. Confirmar experimentalmente quais carregamentos e targets são acessíveis. Não assumir que DNR reescreve bodies, que uma URL chrome-extension/blob pode substituir o script de um service worker ou que Fetch intercepta toda instalação/update.

Nenhuma alteração do servidor ou repositório da aplicação. Nenhum proxy, companion ou transporte CDP externo. O código de instrumentação deve ser empacotado com a extensão e obedecer às restrições aplicáveis de execução.

Verificar: carregamento inicial e updates, scripts já instalados, execução offline a partir do script persistido, módulos/imports, URL/baseURL, MIME, CSP, integridade, source maps, escopo permitido e comparação de bytes para atualização. A ferramenta não pode quebrar o algoritmo de update nem manter namespace antigo embutido no script persistido. Não relaxar CSP como atalho para declarar compatibilidade.

Se um bootstrap persistido for necessário, selecionar o namespace por protocolo seguro antes do código da aplicação, não gravar “usuário A” no script. Provar funcionamento offline, suspensão/retomada do background MV3 e reinício do navegador. Não depender de um serviço fora da extensão para obter a identidade. Se a extensão não puder garantir a atribuição, falhar fechado quando tecnicamente possível e registrar a lacuna quando não houver mecanismo de bloqueio.

### Rota C — composição de capacidades e prova dos limites da extensão

Combinar apenas capacidades disponíveis à extensão: content scripts registrados em document_start/MAIN, chrome.scripting, chrome.debugger, DNR, webRequest, mensagens e persistência. Avaliar documentos offscreen somente quando seu uso e APIs forem permitidos; não tratá-los como forma de obter APIs privilegiadas indisponíveis ou como processo imortal.

Separar o service worker da extensão dos service workers das aplicações. Investigar coordenação persistente e retomada após suspensão do background MV3. Priorizar uma sequência determinística de bootstrap, barreiras e controle de clientes; não substituir a prova de ordem por polling ou espera arbitrária.

Inspecionar o código do Chromium para explicar restrições e descobrir combinações válidas de APIs. Essa inspeção é pesquisa: não autoriza alterar o navegador ou introduzir componente externo. Para cada falha, entregar o menor reproducer, comandos/eventos e versões. Esgotar hipóteses concretas dentro da extensão; se nenhuma satisfizer o contrato, registrar NO-GO ou resultado parcial para os requisitos testados, sem migrar a arquitetura.

## 6. Adaptadores de APIs

Implementar núcleo de namespaces sem dependência de window, com entradas distintas para Window e WorkerGlobalScope. Capturar nativos antes do app, aplicar uma vez por realm e fornecer handshake versionado de integridade. Não expor ao app um seletor mutável de sessão confiável.

| API                         | Cobertura e verificações                                                                                                                             |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| localStorage/sessionStorage | Métodos, acesso por propriedades, length, key, enumeração, clear, eventos e frames.                                                                  |
| IndexedDB                   | open/deleteDatabase/databases/name; preservar transações, upgrades, blocked e versionchange; objetos vivos morrem com a execução antiga.             |
| Cache Storage               | open/has/delete/keys/match, Cache.match/put/add/addAll; caches privados por padrão, inclusive assets no primeiro POC.                                |
| Cookies                     | document.cookie e Cookie Store; HttpOnly invisível ao JS; atributos completos; eventos/subscrições precisam de teste específico.                     |
| Dedicated/Shared workers    | Bootstrap antes do código; identidade dos SharedWorkers/nome/URL e clientes; encerrar conexões ao suspender.                                         |
| BroadcastChannel/Web Locks  | Namespaces, enumeração quando disponível, locks pendentes e limpeza de handles.                                                                      |
| WebSocket/EventSource       | Identificar conexão e autenticação; encerramento na troca; bloquear reconexão de geração antiga.                                                     |
| OPFS                        | Adapter de raiz virtual por sessão, incluindo worker e access handles; namespace original filtrado. Se não implementado, declarar fora de cobertura. |
| Storage Buckets/outros      | Inventariar, testar detecção e declarar cobertura; não alegar isolamento de “todas as APIs”.                                                         |

sessionStorage permanece ligado à vida da aba. Testar se o mecanismo de navegação/estacionamento mantém os namespaces na mesma aba. Se precisar fechar a aba e perder sessionStorage, isso é limitação, não dado preservado. Não substituir silenciosamente sessionStorage por storage durável com semântica diferente.

Compartilhamento de quotas/evicção persiste. Medir comportamento sob pressão de armazenamento; não prometer proteção física dos dados inativos contra eviction.

## 7. Cookies e rede sem staging

Sessão original usa os cookies nativos como fonte; sessões novas usam jars virtuais. Enquanto B estiver ativa, seus requests não podem enviar cookies originais nem seus Set-Cookie alterar o jar nativo. Cookie Store dentro do worker exige adapter; só substituir headers não cobre leituras locais.

Reaproveitar parsing/semântica do SplitSession, validando Secure, HttpOnly, SameSite, hostOnly/Domain, path, expiração, remoção, prefixos, CHIPS e múltiplos cookies homônimos. Preservar credentials: omit/same-origin/include e regras de CORS; nunca inserir cookies em requests que deveriam ser sem credenciais.

Para abas gerenciadas, instalar isolamento abrangente antes da primeira navegação, inclusive para destinos ainda desconhecidos. Popups devem receber dono antes do primeiro request. onBeforeRequest observacional seguido de atualização assíncrona de DNR não garante interceptar o primeiro request.

Para requests sem tabId, atribuir pelo target/worker/origin e registro de execução comprovado. Não usar “domínio de destino = sessão ativa” como regra universal: ambientes diferentes podem chamar a mesma API. Quando não houver atribuição inequívoca, serializar os contextos conflitantes ou bloquear ativação com diagnóstico, nunca adivinhar.

Comparar dois mecanismos com os mesmos testes: DNR + webRequest e CDP Fetch via chrome.debugger da extensão no target correto, quando permitido. Não instalar duas camadas concorrentes de reescrita. Medir atualização de cookie entre login e redirect/fetch imediato. Não reutilizar regras antigas quando o namespace já mudou.

Registrar requestId com identidade adequada ao transporte/target e dono capturado na partida. Resposta atrasada de A atualiza, no máximo, o jar de A conforme política; jamais B. Bloquear novas operações não desfaz mutações já recebidas pelo servidor. Em resultado incerto de uma operação não idempotente, registrar a incerteza e não repetir automaticamente.

## 8. Descoberta automática de dependências

Construir grafo de evidências: aba/documento/frame/opener → request/redirect → origin → registro/versão de worker → recursos compartilhados. Usar initiator, requestId, documentId e target quando disponíveis. O grafo aprende destinos; não precisa classificar perfeitamente “isto é SSO” para isolar cookies da cadeia gerenciada.

Cobrir redirects HTTP/JS, OAuth via popup, iframes de silent renew, API cross-origin, chamadas iniciadas por workers, subdomínios e diferentes portas localhost. Permissões de host continuam sendo necessárias: evitar configuração de domínios não significa dispensar consentimento do navegador.

Não tomar posse de todas as abas de uma CDN ou provedor só por observar um request. Diferenciar dependência de rede, participação em autenticação e recurso de execução realmente compartilhado. Conservar evidências e razão de cada associação.

Se dois ambientes dividirem um recurso que não pode ser isolado, ampliar automaticamente a exclusividade e estacionar os contextos conflitantes antes de ativar a nova sessão. Mostrar o efeito ao usuário, sem formulário de configuração. Se isso envolver contas/abas alheias ao ambiente de teste e não puder ser feito dentro do escopo controlado, bloquear com explicação; não encerrar silenciosamente uso pessoal.

Para uma dependência desconhecida encontrada pela primeira vez num worker, demonstrar proteção antes do request ou registrar o caso como não coberto. Não “aprender após vazar”.

## 9. Ativação inicial e sessão original

Inventariar abas, frames, PWAs, registrations e workers relacionados antes do primeiro switch. Marcar o estado inicial como sessão original, sem renomear/copiar seus dados. Instalar proteção e recriar os contextos de forma controlada. Workers existentes podem já ter nativos capturados e handles abertos; attach tardio não os torna seguros retroativamente.

Não apagar IndexedDB/cache/cookies originais. Aplicar filtros à sessão original para impedir que clear/list/delete atravessem namespaces novos. Validar colisões com o prefixo reservado.

Se o usuário já estiver autenticado em dependências descobertas depois, incorporar os cookies nativos dessas dependências na visão lógica original sem copiar os bancos. A ferramenta não pode recuperar histórico que não observou; deve registrar o instante a partir do qual a cobertura está estabelecida.

## 10. Transação de switch

Estados: ACTIVE(A,e) → QUIESCING → PREPARED(B,e+1) → ACTIVE(B,e+1), com caminho explícito para FAILED.

1. Adquirir mutex do ambiente e recursos compartilhados. Rejeitar switches concorrentes ou enfileirar um pedido explícito.
2. Fechar a admissão de novas operações da geração antiga em páginas, workers e rede. Uma barreira DNR sozinha não impede execução local ou resposta por cache.
3. Drenar transações/requests quando possível; impor timeout explícito. Cancelar apenas quando seguro e registrar resultados incertos. Nunca abortar silenciosamente operações críticas apenas para bater meta de velocidade.
4. Estacionar/descarregar clientes antigos preservando a aba quando necessário para sessionStorage. Impedir retomada via BFCache, history, prerender, popup ou reconexão automática.
5. Parar/resetar workers e confirmar a ausência de execução antiga. Não presumir acesso a comandos ServiceWorker do CDP indisponíveis em chrome.debugger. O mecanismo de parada escolhido deve ser acessível à extensão e provado. Parar não impede reinício; o coordenador da extensão precisa controlar as futuras ativações. unregister não é equivalente a parada imediata e é último recurso, com impacto em subscriptions/update documentado.
6. Persistir intenção/epoch e preparar cookies/regras/bootstrap de B. Não mexer nos bancos/cache de A.
7. Recriar workers sob B; confirmar patch antes da aplicação; navegar/recarregar clientes. Não reaplicar patches parcialmente sobre um worker quente de A.
8. Publicar ACTIVE somente após confirmação de cobertura. Liberar novas operações.
9. Em falha, manter estado bloqueado ou reconstruir A por novo protocolo. Não restaurar cegamente o marcador antigo com operações de B já iniciadas.

Reset de uma sessão exclui apenas seu namespace e jar, após suspensão; não é parte de switch. Não oferecer reset destrutivo da sessão original no primeiro POC.

## 11. Background, offline e falhas

Provar a execução do SW via fetch e Cache Storage sem rede externa e sem processo auxiliar. Testar background MV3 ativo, suspenso e retomado, além do reinício dos workers da aplicação. Separar o debugger da extensão, quando parte do produto, de DevTools/test runner usados para observação: a observação externa não pode manter o sistema vivo artificialmente ou instalar a proteção que falta ao produto.

Push/Background Sync são uma dificuldade separada: evento criado para A não pode ser executado automaticamente como B. Testar subscriptions, tags, periodic sync quando disponível, cookiechange e notificationclick. Tags podem receber namespace, mas dados nativos de registration/subscription nem sempre oferecem namespace equivalente.

Definir dono persistente quando observável. Adiar o trabalho de A só conta como suporte se o evento puder ser preservado e entregue com semântica adequada; descartar evento e dizer “suspenso” é falha. Evento sem dono não deve ser reinterpretado como sessão ativa. Se não for possível preservar esses serviços, registrar suporte parcial, mesmo que fetch/offline funcione.

Testar suspensão e falha do background MV3, detach pelo usuário/DevTools, update/desativação da extensão, crash/restart do Chrome e recuperação após journal incompleto. Não prometer fail-closed quando a própria extensão está desativada: medir quais efeitos e regras ainda persistem, quais deixam de existir e como recuperar na reativação. Não adicionar supervisor externo para encobrir uma lacuna da arquitetura; classificá-la explicitamente.

Além do fixture, testar ao menos uma PWA não adaptada com worker de framework e uma aplicação representativa Angular/Dexie/Keycloak quando disponível. Não depender de acesso não fornecido: montar laboratório equivalente e manter validação real como pendência explícita.

## 13. Harness e observabilidade

Criar test runner independente, executável sem IA. Playwright pode orquestrar UI/testes, mas não deixar seus contextos isolados ou mocks substituir o isolamento que o RECnRun deve prover. Nunca interceptar rede somente no teste para fazer o produto aparentar funcionar. O runner apenas dirige ações e coleta evidências; não injeta patches, pausa workers para o produto, instala regras de isolamento ou fornece identidade. Repetir o fluxo central manualmente sem runner nem conexão CDP externa (T23).

Rodar headed Chrome em Linux/Docker+xvfb e no Chrome instalado em macOS; registrar plataformas realmente executadas. Se Windows não for testado, marcar não validado. Não assumir que --load-extension funciona em toda versão/distribuição; documentar instalação real suportada e eventual passo inicial.

Servidores de laboratório com múltiplas origins, portas e domínios de teste; HTTPS quando necessário; SSO simples com redirects/popups e API que registra usuário, operação e sequência. Testes de efeitos no servidor verificam o usuário real, não apenas o badge da extensão.

Logs estruturados: environment/session/epoch, target/document/worker/version, request, timestamps, transição, patch handshake, decisão de atribuição e erro. Redigir tokens e cookies, guardar hashes/identificadores sintéticos. Produzir traces de rede e eventos, inventário de DB/cache e contadores de cópia. Observador de diagnóstico pode usar CDP para inspecionar dados físicos, mas deve ser removido no T23 e não pode fornecer capacidades ao runtime do produto. Registrar se a observação mudou o ciclo de vida dos workers.

Métricas: p50/p95 de suspensão, instrumentação e switch completo, tempo de reload, overhead de fetch e operações de storage, CPU/memória e número de regras. Comparar volumes pequenos e grandes (por exemplo 1/100/500 MB conforme quota). Tempo pode depender de operações pendentes, mas não de uma cópia integral do volume armazenado.

## 14. Entregas em ordem

1. **Auditoria e mapa de capacidades:** commit da base, versão do Chrome, APIs permitidas, decisão de licença, contratos e fixture congelado.
2. **Prova mínima do SW:** experimentos A e B, ambos inteiramente na extensão, antes de UI; composição/diagnóstico C se necessário. Relatório de execução antes da primeira instrução, parada e wake sem aba.
3. **Núcleo de namespaces:** páginas + workers, sessão original e testes de APIs, sem rede real complexa ainda.
4. **Cookies/rede:** jar original/virtual, requests sem tabId, primeiro request, redirects e respostas tardias.
5. **Switch transacional:** clientes concorrentes, sessionStorage/BFCache, crash e recuperação.
6. **Descoberta automática:** API/SSO, popups/iframes, conflito de recursos e exclusividade ampliada.
7. **Compatibilidade:** offline, updates de SW, eventos em background, framework real e APIs adicionais.
8. **Empacotamento:** pacote da extensão, instalação, permissões, diagnóstico/exportação na interface e desinstalação limpa, sem apagar dados de sessão automaticamente. Scripts de build/test pertencem somente ao desenvolvimento. Nenhum CLI/serviço precisa ser iniciado pelo usuário para usar o produto.
9. **Relatório final:** decisão por técnica interna à extensão e por capacidade, testes reproduzíveis, limites e próxima etapa dentro da mesma arquitetura.

Estrutura sugerida: packages/extension, packages/isolation-core, packages/worker-bootstrap, packages/coordinator, fixtures, tests/e2e, experiments e reports. Os módulos de runtime são empacotados na única extensão; coordinator não é serviço externo. Separar explicitamente dependências de desenvolvimento e dependências executadas pela extensão.

Scripts-alvo de desenvolvimento, a implementar: build da extensão, execução das suítes workers/full e geração de relatório. Não constituem CLI de uso do produto. Diagnóstico, ativação, suspensão e exportação de relatório do usuário ficam na interface da extensão.

UI mínima: ambiente detectado, sessão original/A/B/C, criar/ativar/suspender, estado da troca, capacidades verificadas e diagnóstico. Sem editor de domínios obrigatório. Mostrar quais contextos foram suspensos e se alguma API está fora de cobertura.

## 15. Critérios de decisão

**GO somente extensão:** uma técnica ou combinação A/B/C satisfaz os testes centrais de inicialização, wake, switch, cookies, preservação, descoberta e T23, sem modificar a aplicação e sem qualquer componente externo de runtime. Descrever eventuais transformações de scripts realizadas pela extensão e as permissões necessárias.

**GO parcial:** fetch/offline e isolamento de dados funcionam, mas push/sync, startup, worker específico ou API permanecem sem cobertura. Listar cenários permitidos e bloqueados. Isso não é aprovação do requisito amplo de todos os serviços globais.

**NO-GO para a arquitetura testada:** não conseguimos impedir execução anterior ao patch, atribuir requests, impedir tarefa de A sob B ou manter SW funcional. Entregar reproducer e limites; continuar na próxima hipótese dentro da extensão enquanto houver experimento concreto. Não criar fallback externo.

Nenhum GO se: houve vazamento, cópia oculta de dados, alteração da aplicação, bypass do SW, worker desabilitado, isolamento nativo por perfil substituindo namespaces, teste maquiado por mocks ou dependência externa de runtime (mesmo se chamada de auxiliar opcional). Deixar a aplicação offline sem worker não conta como suporte offline ao SW.

## 16. Instruções para o agente implementador

Não parar na primeira limitação documental, mas também não converter experimentos em garantias. Para cada hipótese, escrever o teste falsificável, executar, registrar resultado e seguir para a próxima hipótese dentro da extensão quando necessário. O limite arquitetural é obrigatório: não implementar companion, proxy, native host, serviço local ou conexão CDP externa para superar uma limitação.

Ao encontrar erro na ferramenta, criar primeiro um caso de regressão a partir da situação problemática, corrigir o produto e repetir esse teste e a suíte pertinente. Não editar a aplicação-fixture para colaborar com o isolador ou eliminar o caso difícil. Novas fixtures podem ampliar a matriz, mantendo as anteriores.

Conservar distinção entre observado, inferido e não testado. Relatar parâmetros CDP recusados, sequência exata e versão. Um comando disponível no protocolo tip-of-tree não prova suporte no Chrome instalado nem em chrome.debugger.

O relatório final deve responder: “Funciona sem modificar a aplicação? Tudo funciona somente com a extensão instalada e o runner desligado? Qual técnica interna foi utilizada? Para quais workers e eventos? Funciona em Chrome já aberto? Que acontece se o background MV3 for suspenso ou o debugger da extensão for desconectado? Há zero configuração de domínio? Quais dados nunca foram copiados? Quais requisitos ainda falham?”
