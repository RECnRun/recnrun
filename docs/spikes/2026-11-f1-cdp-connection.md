## 2. Connection procedure

The order the adapter follows; [ARCHITECTURE.md](../ARCHITECTURE.md#adapter) describes each module.

1. **Discovery** (`discover`, F1.1). Read `<userDataDir>/DevToolsActivePort`: line 1 the port, line 2 `/devtools/browser/<id>`. Answer `ws://127.0.0.1:<port><path>`, or `missing-file`, `malformed-file`, or `stale-file` (no TCP answer on 127.0.0.1 within 500 ms) with a remedy naming `chrome://inspect/#remote-debugging`. Without `userDataDir`, the channel picks the per-OS default folder.
2. **Preflight on a raw browser socket** (`connect`, F1.2). Before Playwright attaches anything, send `Target.getTargets` on a browser-level WebSocket of our own. A page already marked `attached` is held by another debugger: emit `control.contested` (`signal: "attached-before-connect"`) and never detach it.
3. **Playwright `connectOverCDP`** on the same endpoint, then a browser CDP session.
4. **Handshake.** `Browser.getVersion`, then probe each domain of `CDP_PROBE_DOMAINS` with a side-effect-free command (`Target` on the browser session, the others on a page session of ours, detached afterwards). A domain is `unavailable` only when Chrome answers that the method was not found.
5. **Instrumentation on its own socket** (`instrument`, F1.4 and F1.5). A second browser-level socket in flatten mode sends `Target.setAutoAttach` with `autoAttach`, `flatten`, and `waitForDebuggerOnStart`: every existing target is attached, every new one is held before its first script. Per attached target, commands go out in one burst, in this order:

| Target type                   | Commands before resume                                                                                                                                                                                                         | Resume                                           |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| `page`, `iframe` (OOPIF)      | nested `Target.setAutoAttach`, `Page.enable`, `Page.addScriptToEvaluateOnNewDocument` (hook, `runImmediately`), `Runtime.enable`, `Runtime.addBinding` (`__recnrunObserver`); with capture also `Network.enable`, `Log.enable` | `Runtime.runIfWaitingForDebugger` only when held |
| `worker` (dedicated)          | nested `Target.setAutoAttach`, `Runtime.enable`, `Runtime.addBinding`                                                                                                                                                          | same                                             |
| `service_worker`              | `Runtime.enable`, `Runtime.addBinding`                                                                                                                                                                                         | same                                             |
| any other type                | none (`ignored`)                                                                                                                                                                                                               | same                                             |
| any target running at connect | the same install, marked `late`; the hook runs in the current document through `runImmediately`                                                                                                                                | never sent                                       |

6. **Messages.** Every binding payload is validated with `ObserverMessageSchema` (64 KiB cap) and dropped and counted when invalid (`droppedInvalid`) or when it comes from an execution context the session never announced or claims another target (`droppedUnknownFrame`). Captured events get the §11 envelope: one producer per CDP session (`cdp:<sessionId>`) plus `cdp:browser`, a `seq` per producer, and `targetId`, `frameId`, `documentId`. Persistence appends them to `events.jsonl` (`openJournal`).

## 6. Open decisions

1. **Extension targets.** Chrome's own extension service workers are attached and instrumented as `late`, like any running target (CHECKLIST F1.4 `note:`). Decide whether to skip `chrome-extension://` targets, which RECnRun never needs to observe and which add sessions to every report.
2. **The `@/` alias across workspaces.** Apps import their own `src` through `@/` (each `tsconfig.json`, repeated in `tsconfig.deps.json` for dependency-cruiser, and enforced by the lint override on `apps/*`), while packages import with relative paths (`../src/index.ts` in their tests). When an app bundles a package, a package-level `@/` would resolve to the app's `src`, so packages cannot adopt the same alias as is. This is the collision noted during F0.2; no document in the repository records it yet, so the reasoning here is not backed by a test. Settle a package alias (or keep relative paths) before F2 adds `apps/service` code that imports packages heavily.
3. **`if` branch names.** The DSL names the branches `steps` and `otherwise`, not the source plan's `then`/`else` (§9.3), because an object with `then` is a thenable ([ARCHITECTURE.md](../ARCHITECTURE.md#protocol); CHECKLIST F0.3 `commit:`). The owner should confirm the names before F4A.4 and F4A.6 put them in front of users.
4. **Two document identities.** The hook's `documentId` (main world) and CDP's `loaderId` (references) both name a document; the locator trace of F4A.1 needs one join rule.
5. **Contested control after connect.** Accept `partial` as final, or look for another signal before F5.4 relies on control (M-F1.d decides).

- **F2 is L, not XL**: every browser-facing piece it needs exists as a spike module with a browser test; the new work is mostly ordinary service, file, and UI code. The risk sits in `first-flow.spec.ts`, the first test that runs service, UI, and Chrome together in Docker.
- **F3 is L**: capture already produces envelopes; what remains is many surfaces, each with its own browser test, plus flow control (buffers, ACK, gaps) and a benchmark that has no baseline yet.
- **F4 is L**: mostly UI and persistence; M-F1.c is the one result that could force a change to bindings.
- **F4A is XL**: the widest scope of the plan (registry, two runtimes, macros, a UI editor) and only the page runtime was proved.
- **F5 is L**: thin adapters over F2's service, but configuration formats of two external agents and handoff semantics are untested here.
- **F6 is M**: the targets are already reachable; each surface is bounded and the pilot does not wait for it.
- **F7 is M**: packaging was not started in F1 (the source plan allows starting it early), so its risks are still open, but the Docker image already installs Chrome cleanly.

The phases depend on each other in plan order; F6 can run beside F5 once F3's buffers exist, since both build on capture.
