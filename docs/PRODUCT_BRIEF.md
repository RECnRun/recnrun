# Product brief

RECnRun records a browser tour once and lets the developer inspect and re-run it: logging in, filling a long form, reproducing a bug. The browser extension owns the user's data. The website at [recnrun.com](https://recnrun.com) detects the extension and shows that data.

The first user is an AI agent (Claude Code through Claude in Chrome, Codex) that tests an application in the developer's browser. Without RECnRun, that tour is lost when the conversation ends; with it, the developer sees every step in a dashboard and can ask for it again.

## Concepts

| Concept       | Meaning                                                                                                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Workflow**  | One recorded scenario: an autogenerated id, a required title, an optional description, tags, a status (`recording` or `stopped`), and when it was created and last changed. Steps are added while it is recording. |
| **Tag**       | `tag`, `tag:subtag`, `tag:subtag:subsubtag`, …: segments of letters, digits, `_`, and `-` joined by `:`. Case is kept. Conventions: `env:local`, `env:ACC`, `feature:login`, `bug:123`, `rerun-of:<workflow id>`.  |
| **Step**      | One thing that happened in a recorded tab: when, in which tab and URL, who caused it, a command (`navigate`, `click`, `fill`, `clear`, `select`, `press`), a selector, and a value. Passwords are stored as `***`. |
| **Recording** | The binding between one tab group and the workflow it records. Every tab in the group is recorded; tabs outside it are not. One recording per group; several groups may record at once.                            |

A step's author is `user` for a trusted DOM event, `page` for an event dispatched by the page's own scripts, and `browser` for what the extension observes itself (navigation). Browser tools that drive pages through DevTools produce trusted events, so an agent's steps also read `user`.

## Who records, and how

Recording is explicit: nobody records until a workflow is started, and nothing is monitored by URL.

- **An AI agent** calls the extension's public API from a page on recnrun.com (or the local dev website) inside its own tab group, with the browser tool it already has. The `recording-a-workflow` skill teaches the flow: start with a title and tags, pass the app URL so it opens in the group, perform the test, stop, report the link to the steps.
- **A human** uses the toolbar popup: a title, an optional description, and tags, then **Start recording**. The extension puts the active tab in a tab group named "RECnRun" so later tabs join the recording. The popup also stops and resumes, and offers the stopped workflows to resume.

Both paths share one implementation in the extension, so they behave the same.

### Site access

The extension installs with access to no site. The first time a recording reaches an origin the user has not allowed, the dashboard and the popup show **Allow access to <origin>**; one click shows Chrome's prompt and, once accepted, that origin records silently from then on. An agent cannot grant access (Chrome needs a human click), so its start call answers `permission-required` and the skill tells it to ask. `localhost` is allowed on every port at once.

## The website and the extension

1. A visitor opens recnrun.com (or the local dev website).
2. The website asks whether the extension is installed.
   - **Missing:** it shows a banner explaining what the extension does, with a link to the install guide.
   - **Installed:** it lists the workflows, newest first, with status, tags, and when they last changed, and filters them by title or tag. Opening one shows its steps in order and keeps appending the ones the extension records.
   - **Installed but empty:** it says there are no workflows yet, rather than asking to install.
   - **Installed but unreadable** (for example, stored data from an incompatible version): it shows the reason.
3. While the visitor's own tab group records, the website shows which workflow, and the **Allow access** button when a tab in the group needs it.
4. Stopped workflows can be deleted from the list.

The website never stores the user's data and never sends it anywhere: it reads it from the extension in the visitor's own browser.

## Limits

- A tab that navigates to an origin the user has not allowed records nothing until they click **Allow**; the steps before the click are lost. This is Chrome's permission model, not a bug to fix.
- Steps are what the recorder can observe in the page: no screenshots, no network, no DOM snapshots.
- Clicks on the dashboard itself are not recorded, so an agent's API calls leave no steps.

## Next

Product direction, not commitments; each step gets its own milestone in [MILESTONES.md](MILESTONES.md).

- **Re-run.** Run a workflow's steps against the live application, from the start or from a chosen step, and report what differs.
- **Organize.** Reorder, edit, and export steps; merge workflows.
- **Replay.** Play a recording back as the user saw it (rrweb remains the candidate).

## Platforms

Chromium-based browsers with Manifest V3 (Chrome, Edge, Brave). Firefox and Safari are not planned yet.
